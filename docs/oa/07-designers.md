## 🔎 表单设计器：三大区 = 一个 schema 的编辑器

任何表单设计器（SmartOA、form-create、宜搭）都是这个结构：

```
┌──────────┬───────────────────────┬──────────────┐
│ 控件区    │       画布(Canvas)      │   属性区      │
│ 输入框    │   [申请人  ____]        │ 字段名: days  │
│ 下拉      │   [请假类型 ▼]          │ 标签: 天数    │
│ 日期      │   [天数    ___]  ←选中  │ 必填: ☑       │
│ 子表单... │                        │ 最小值: 0.5   │
└──────────┴───────────────────────┴──────────────┘
        拖 →         放置/排序           编辑选中控件
```

**三个区操作的是同一个对象——`schema.fields` 数组**：

- **控件区拖到画布** = `fields.push({field:'field_x', type:'number', label:'新字段'})`
- **画布拖动排序** = 数组元素 reorder
- **属性区改设置** = 改选中那个 field 对象的属性
- **画布本身** = 用第01章的 `DynamicForm.vue` 实时渲染当前 `fields`（这就是所见即所得！）

> 💡 **关键复用**：设计器的画布预览，用的就是第01章那个动态渲染器。你早做的运行时渲染器，在这里第二次发挥作用——这就是"运行时优先"的回报：设计器几乎是免费搭出来的。

```ts
// 拖放落点：本质就是往 fields 数组插一条
function onDrop(controlType: string, index: number) {
  schema.fields.splice(index, 0, {
    field: `field_${genId()}`,   // 自动生成唯一 field
    type: controlType,
    label: defaultLabel(controlType),
  })
}
// 属性区双向绑定到 schema.fields[selectedIndex]，改属性即改 schema
```

## 🔎 流程设计器：图 = 节点 + 连线

流程设计器是画流程图——节点是框、审批线是箭头。它产出的就是第02章的 `{nodes, edges}`：

- **拖一个审批节点到画布** = `nodes.push({id, type:'approval', ...})`
- **从 A 拉线到 B** = `edges.push({from:'A', to:'B'})`
- **点节点配审批人/字段权限/会签** = 编辑该 node 的 `assignee`/`fieldPerms`/`multi`
- **在线上配条件** = 编辑该 edge 的 `condition`

**画流程图这件事不要从零写**——用成熟的图编辑库：

| 库 | 特点 |
|---|---|
| **LogicFlow**（推荐） | 滴滴开源，专为流程/审批图设计，节点自定义方便 |
| **bpmn-js** | BPMN 标准，功能全但偏重，适合走 BPMN 路线 |
| **AntV X6 / G6** | 通用图编辑，灵活但要更多封装 |

它们负责"画图 + 给你图的数据结构"，你负责把这个数据结构**序列化成你的 flow schema**（节点/边的字段映射），以及在节点/边上挂你的属性面板。

## 🔎 表单设计器：从零写 vs 用轮子

**强烈建议直接用 `form-create` / `variant-form`**，而不是从零造：

- 它们已经实现了拖拽、排序、属性面板、嵌套布局、20+ 控件、schema 导入导出。
- 你要做的是**把它的 schema 格式适配成你的 FormDef 格式**（或直接采用它的格式），以及补业务控件（如"选审批人""关联 ERP 物料"）。
- 从零写一个像样的表单设计器是数月工作量，且坑极多（拖拽吸附、栅格、撤销重做、复制粘贴…）。

**何时才考虑自研设计器？** 当你的控件高度业务化、或要和 CP6 深度集成（直接拖出"绑定 WMS 库位"的控件）、或要做差异化商业卖点时。即便如此，也建议在开源库基础上扩展，而非从零。

## 💡 资深视角

**为什么说设计器"最不核心"？**
因为它产出的 JSON，你在阶段0~3 已经能手写并跑通了。设计器宕机，你手改 JSON 系统照常跑；但渲染器/引擎宕机，再漂亮的设计器也没用。**核心是解释器，设计器是糖**。这也是为什么本书把它放最后——很多失败的低代码项目恰恰先砸钱做炫酷设计器，结果运行时撑不住。

**设计器和运行时必须用同一份 schema 定义**
最常见的撕裂：设计器产出的 schema 字段名/结构，和运行时渲染器期待的对不上。**必须用同一份 schema 规范（最好有 JSON Schema 校验）**，设计器存之前校验、运行时读之前也校验。

**版本与发布**
设计器改了表单/流程，不能直接覆盖线上——在途单子还在用旧版。设计器要有"草稿/发布"概念：编辑产生草稿，发布生成新 `Version`，旧实例继续用旧版（呼应第01/02章的版本化）。

## ⚠️ 踩坑记录

1. **从零写表单设计器**：低估工作量，三个月还在调拖拽吸附。先用 form-create。
2. **设计器 schema ≠ 运行时 schema**：两套格式各自演进，最后对不上。统一规范 + JSON Schema 校验。
3. **直接覆盖发布**：改了流程，在途单子全乱。必须草稿/发布 + 版本化。
4. **field 名让用户随便填**：重名、特殊字符导致数据 key 冲突。自动生成 + 校验唯一。
5. **流程图能画出非法结构**：没有 start、有孤立节点、有环、出边条件不互斥。发布前要做流程图合法性校验。
