# 05 · 规则引擎：显隐 / 计算 / 联动 / 条件分支

> 第01章打桩的"天数>3 显示附件"、第02章打桩的 `EvalCondition`，本质是同一件事：**把一段"规则配置"在运行时解释执行**。本章把表单联动和流程条件统一讲清。

## 📍 学习目标

1. 表单里的字段联动（显隐/计算/必填变化）是怎么配、怎么跑的？
2. 流程的条件分支和表单的字段联动，底层是不是一回事？
3. 表达式怎么从字符串变成结果？自研 vs 表达式引擎 vs 规则 DSL 怎么选？
4. 规则在前端跑还是后端跑？
5. 怎么防止规则写出死循环 / 性能黑洞？

---

## 🔎 两类规则，一个内核

低代码里"规则"出现在两个地方，但内核都是 **`条件 → 动作`**：

| 出现位置 | 例子 | 触发时机 |
|---|---|---|
| **表单字段联动** | `days>3` 时显示附件、`单价×数量` 自动算总价 | 用户改字段时，前端实时跑 |
| **流程条件分支** | `days>3` 走 HR 节点 | 流转时，后端跑 |

两者都是"判断一个条件、执行一个动作"。区别只在**动作类型**：表单动作是"显示/隐藏/赋值/改必填"，流程动作是"走哪条边"。**理解了这一点，你就知道规则引擎是可以统一设计的。**

### 表单规则 schema（挂在 FormDef 里）

```json
"rules": [
  { "when": "days > 3",            "action": "show",    "target": "attachment" },
  { "when": "leaveType=='sick'",   "action": "required","target": "attachment" },
  { "when": "true",                "action": "compute", "target": "total",
    "expr": "price * qty" }
]
```

### 流程条件（挂在 FlowDef 的 edge 上，第02章已见）

```json
{ "from": "n1", "to": "n2", "when": "approve", "condition": "days > 3" }
```

`days > 3` 这串东西，两边长得一样——**因为它们用的是同一个表达式求值器**。

## 🔎 核心：表达式怎么求值

把 `"days > 3"`（字符串）+ `{days: 5}`（变量）变成 `true`。三条路：

| 方案 | 怎么做 | 适用 |
|---|---|---|
| **自研极简** | 约定只支持 `字段 op 值`，split 自己比 | 阶段1 跑通，不推荐长期用 |
| **表达式引擎** ✅ | `DynamicExpresso` / `NCalc`（.NET） | 后端流程条件，推荐 |
| **JSON 规则 DSL** | `{field,op,value}` 结构化表示 | 设计器友好，可视化配置 |

```csharp
// 后端：用 DynamicExpresso 求流程条件（推荐）
using DynamicExpresso;
bool Eval(string expr, Dictionary<string, object> vars)
{
    if (string.IsNullOrWhiteSpace(expr)) return true;
    var interp = new Interpreter();
    foreach (var kv in vars) interp.SetVariable(kv.Key, kv.Value);
    return interp.Eval<bool>(expr);
}
```

```ts
// 前端：表单联动实时求值（可用极简解析或轻量库）
// 监听字段变化 → 重算所有规则 → 改 UI 状态
watch(formData, () => {
  for (const r of schema.rules) {
    const hit = evalExpr(r.when, formData)        // 条件成立？
    applyAction(r, hit, formData, fieldState)      // 显隐/赋值/必填
  }
}, { deep: true })
```

> 💡 **DSL 方案的价值**：`{field:"days", op:">", value:3}` 这种结构化规则，拖拽设计器能直接生成、也能反向回显成可视化条件块（你在 SmartOA 配的"条件分支"就是这种）。代价是要自己写一个 DSL → bool 的执行器。生产级低代码平台多走这条，因为**可视化配置必须能双向转换**。

## 🔎 前端跑还是后端跑？两边都要

| | 前端 | 后端 |
|---|---|---|
| **表单联动**（显隐/计算） | ✅ 必须（实时体验） | 提交时复核计算字段（防篡改） |
| **流程条件**（走哪条边） | ❌ | ✅ 必须（流转决策不能信前端） |

原则同校验：**前端做体验、后端做权威**。计算字段（如总价）尤其危险——前端算的 total 不能直接信，后端要按 expr 重算一遍再落库。

## 💡 资深视角

**为什么要把"条件"做成数据、而不是 if-else 写死？**
这是低代码的命根子。`days>3 走HR` 如果写死在 C#，业务想改成 `days>5` 就得改代码发版。做成 edge 上的 `condition` 字段，业务在设计器改个数字即可。**所有"业务会变的判断"都应该外置成可配置规则**——这是低代码 vs 传统开发的本质区别。

**统一规则引擎 vs 分开做？**
理论上表单联动和流程条件可共用一个求值内核（都是表达式→结果），建议**求值器复用，动作执行分开**（表单动作和流程动作语义不同）。新手常各写各的，导致两套表达式语法不一致，用户困惑"为什么表单里能写的条件流程里报错"。统一语法是好产品的细节。

**规则的可测试性**
规则是数据，意味着可以脱离 UI 单元测试：喂 `(expr, vars)` 断言结果。把求值器做成纯函数，是规则引擎可维护的关键。

## ⚠️ 踩坑记录

1. **联动死循环**：规则 A 改 B、规则 B 又改 A，`watch` 无限触发。要做"本轮已变更集合"去重或限制迭代轮数。
2. **eval 注入风险**：直接 `eval()` 用户字符串 = 任意代码执行。**用沙箱表达式库（DynamicExpresso/NCalc）或自研 DSL，绝不用裸 eval**。
3. **计算字段信前端**：total 前端算完直接入库，被改包就能改金额。后端按 expr 重算。
4. **字段引用了不存在的字段**：表单删了字段但规则还引用它，运行时报错。保存 schema 时校验规则引用的字段都存在。
5. **前后端表达式语法不一致**：前端 JS 语法、后端 C# 语法，`==` vs `=` 之类差异让同一条件两边结果不同。统一成一种 DSL 或约定子集。
