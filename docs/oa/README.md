# CP6 OA 低代码引擎 · 完整学习与实现丛书

> **定位**：你是 SmartOA 这类低代码 OA 的**使用者**（会拖控件配微表单、配审批流），但没做过框架实现。这套丛书的目标是带你**从"会用"跨到"能造"**——把"拖拽 → 微表单 → 审批流"背后的引擎，在 CP6 里从零亲手实现一遍，同时理解一个完整 OA 项目的全貌。

## 一、先记住这一句话（整套书的题眼）

> **拖拽产生的不是代码，而是一段 JSON 配置（schema）。系统里有"解释器/渲染器"，运行时读这段 JSON，把页面画出来、把逻辑跑起来、把流程转起来。**

SmartOA、宜搭、简道云、明道云、泛微 e-cology —— 全是这一个套路，**没有魔法**。你拖一个输入框，它往表单 JSON 加一条字段；你连一根审批线，它往流程 JSON 加一个节点。所以"做一个 OA" = **做两个解释器**：一个解释表单 JSON，一个解释流程 JSON。

**拖拽设计器是最后做的，不是最先做的。** 这是本书最重要的方法论：从运行时倒推，先手写 JSON 跑通引擎，最后才做生成 JSON 的可视化工具。很多人反着来（先做设计器）所以失败。

## 二、一个完整 OA = 5 个引擎

| 引擎 | 干什么 | 设计器产出 | 运行时干什么 | 本书章节 |
|---|---|---|---|---|
| **表单引擎** | 动态表单 | form schema | 读 schema 动态渲染页面 | [01](./01-form-engine.md) |
| **规则引擎** | 字段联动 | rules | 表单运行时执行显隐/计算/联动 | [05](./05-rule-engine.md) |
| **流程引擎** | 审批流转 | flow schema | 状态机：当前节点+动作→下一节点 | [02](./02-flow-engine.md) · [06](./06-advanced-flow.md) |
| **数据引擎** | 表单数据怎么存 | — | 存/查动态表单提交的数据 | [08](./08-data-storage.md) |
| **组织引擎** | 审批人怎么算 | — | 部门树/上下级/角色 → 解析具体审批人 | [04](./04-org-engine.md) |

你在 SmartOA 里"配微表单 + 配审批流"，本质就是在喂前 3 个引擎的 schema。

## 四、分阶段动手路线（关键：反着做，运行时优先）

| 阶段 | 目标 | 做什么 | 不做什么 | 完成标志 |
|---|---|---|---|---|
| **阶段 0** | 理解微表单 | 手写 form JSON，Vue 写一个动态渲染器把它画成页面 | 不做设计器 | 改 JSON 就能改页面 |
| **阶段 1** | 理解审批流 | 流程引擎运行时：提交/同意/驳回/流转/记历史，**只串行+简单条件** | 不碰会签 | 一张单子能从头审到尾 |
| **阶段 2** | 合体 | 表单×流程绑定（节点字段权限）+ 待办中心 + 我的申请 + 审批痕迹 | 不做设计器 | 一个**手工配 JSON 的可用 OA** 跑起来 |
| **阶段 3** | 复杂流程 | 会签 / 或签 / 加签 / 退回到指定节点 / 超时升级 / 委派 | — | 接住真实审批场景 |
| **阶段 4** | 可视化 | 表单设计器 + 流程设计器（拖拽生成阶段0/1的 JSON） | — | 业务人员不写 JSON 也能配 |

**每个阶段都是一个能演示的里程碑**，不要跳。阶段 2 结束时你已经拥有一个"难看但能用"的 OA——那一刻你就真正理解 SmartOA 了。

## 五、最小数据模型（贯穿全书）

先建立全局的表结构直觉，细节在各章展开：

```
■ 组织引擎（阶段0/1 前置——审批人靠它算）
  OrgUnit        部门树（Id, ParentId, Name, Path）
  Position       职务/职级
  StaffOrg       员工-部门-上级（绑定现有 Sys_User / M_Staff）

■ 表单引擎
  FormDef        表单定义（FormKey, Name, SchemaJson, Version）
  FormData       表单提交的数据（FormKey, BizId, DataJson）  ← JSON 列存

■ 流程引擎
  FlowDef        流程定义（FlowKey, Name, SchemaJson, Version, 关联 FormKey）
  FlowInstance   流程实例（运行中的一张单：当前节点、状态、变量、发起人）
  FlowTask       待办任务（实例×节点×审批人，状态=待办/已办）
  FlowHistory    审批痕迹（谁、在哪个节点、什么动作、意见、时间）
```

> 注意 `FormDef.SchemaJson` 和 `FlowDef.SchemaJson` —— **设计器的产出全进这两个字段**。整个低代码平台就是围着这两段 JSON 转。

## 六、它怎么嵌进 CP6（你已有的便宜可占）

| OA 需要的能力 | CP6 现成的东西 | 怎么用 |
|---|---|---|
| 表单数据存储 | SQL Server 原生 JSON 支持 | `DataJson` 直接存 JSON 列，不用纠结 EAV |
| 流程异步驱动/补偿 | `IntegrationEvent` + 重试/死信（Phase 6） | 流转事件复用这套，天然幂等可补偿 |
| 审批通过后回写各模块 | `IErpBridgeHook` / `IMesBridgeHook` / `IWmsBridgeHook` | 批准 → 走原有 Hook 落地执行 |
| 外部 OA 对接（可选） | `IPowerEggWorkflowService`（已有桩） | 升级为正式 `IExternalOaConnector` |
| 实时待办提醒 | SignalR Hub（已有） | 新审批任务实时推到待办中心 |
| 登录/角色/菜单 | `Sys_User` / `Sys_Role` / `Sys_Menu` | 复用，但要补组织（见下） |

**唯一硬缺口：组织架构。** CP6 现在只有薄薄的 `Sys_User`（无邮箱、无部门、无上级）和 `M_Staff`（担当者+据点）。审批人"找直属上级/部门长"算不出来，所以 [04. 组织引擎](./04-org-engine.md) 是阶段 1 之前的硬前置。

## 七、强烈建议先读的开源项目（你是使用者，看实现学最快）

| 你想理解 | 去读 | 学什么 |
|---|---|---|
| 表单设计器 + 动态渲染 | **form-create**、**variant-form / vue-form-making** | 拖拽如何产出 form schema、运行时如何渲染 |
| 流程引擎（.NET，匹配 CP6） | **Elsa Workflows**、**Workflow Core** | 节点定义、实例持久化、状态机驱动 |
| 流程图设计器 | **LogicFlow**、**bpmn-js** | 拖拽如何产出 flow schema |
| 完整低代码 OA 参考 | **JeecgBoot（online 表单 + flowable）** | 一个国产 low-code OA 的整体拼装方式 |

读它们的目的不是抄，而是**确认"原来就这么回事"**——你会发现它们的核心和本书讲的 5 个引擎一一对应。

## 八、里程碑自检（学到没学到，问自己）

- [ ] 阶段0：我能不写一行页面代码，只改一段 JSON，就让表单多一个字段吗？
- [ ] 阶段1：我能说清"一张单子从提交到结束，引擎每一步在算什么"吗？
- [ ] 阶段2：节点字段权限（这个节点能改、那个节点只读）我能讲清它存在哪、怎么生效吗？
- [ ] 阶段3：会签和或签在数据上的区别是什么？退回到指定节点要清理哪些状态？
- [ ] 阶段4：我的设计器产出的 JSON，和阶段0手写的 JSON 是同一种结构吗？（应该是）

全部能答 → 你不再是 SmartOA 的使用者，而是能造一个 SmartOA 的人。
