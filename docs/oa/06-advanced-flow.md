## 🔎 会签 / 或签 / 依次签：一个节点，多个任务

第02章一个节点开一个 FlowTask。多人审批的关键转变：**一个节点开多个 FlowTask，靠"计数策略"决定何时算这个节点通过**。

| 类型 | 含义 | 通过条件 | 否决条件 |
|---|---|---|---|
| **会签(and)** | 都要同意 | 全部 approve | 任一 reject |
| **或签(or)** | 一人同意即可 | 任一 approve | 全部 reject |
| **依次签(seq)** | 按顺序逐个 | 最后一个 approve | 任一 reject |
| **比例签** | 超过 N% 同意 | approve 占比≥阈值 | — |

节点定义加上策略：

```json
{ "id": "n1", "type": "approval", "name": "三总监会签",
  "assignee": { "type": "role", "value": "Director" },
  "multi": "and",        // and=会签 / or=或签 / seq=依次
  "rejectMode": "anyReject" }
```

引擎流转逻辑升级（替换第02章 AdvanceAsync 里"办完直接走边"）：

```csharp
// 办完一个待办后，先判断"这个节点整体定了没"
async Task<bool> IsNodeSettled(FlowInstance inst, NodeDef node, string lastAction)
{
    var tasks = await _db.FlowTasks.Where(t => t.InstanceId==inst.Id && t.NodeId==node.Id).ToListAsync();
    var done  = tasks.Where(t => t.State=="done").ToList();

    if (lastAction == "reject" && node.RejectMode == "anyReject") return true; // 一票否决，节点定了

    return node.Multi switch
    {
        "or"  => done.Any(t => t.Action=="approve"),       // 或签：一人同意即定
        "and" => done.Count == tasks.Count,                 // 会签：全部办完才定
        "seq" => done.Count == tasks.Count,                 // 依次：本质也是全办完
        _     => true                                        // 单人节点：办完即定
    };
}
// 节点定了 → 按整体结果(通过/否决)走边；没定 → 什么都不做，等其他人办
```

**会签的本质**：把"节点通过"从"一个人点同意"变成"一组任务达到计数条件"。**所有多人审批，都是这个计数游戏的变体。**

## 🔎 加签：运行时往节点里塞人

审批到一半，李经理觉得"这事得让王总也看看"——**加签 = 给当前节点动态新增一个 FlowTask**：

- **前加签**：新人先审，审完回到李经理 →（实现上是插一个临时前置任务）
- **后加签**：李经理先审，再交给新人 →（追加一个后置任务）

数据上就是 `FlowTasks.Add(新任务)` + 调整本节点的计数预期。难点是**会签计数要把新加的算进去**（`tasks.Count` 变了）。所以加签后要重算 `IsNodeSettled`。

---

## 🔎 退回：看似简单，实则最坑

"退回到发起人"或"退回到第N个节点重审"。难点不在"跳回去"，在**清理**：

```
退回 n3 → n1 时要做：
  1. 把 n3（及中间 n2）的 pending 待办全部作废
  2. CurrentNode 改回 n1，给 n1 重新开待办
  3. ★决定：重审后是"逐节点重走"还是"直接回到 n3"？（两种产品策略）
  4. 流程变量/表单数据是否保留？（通常保留，但要记一笔历史）
  5. 历史记录要体现"被退回"，不能假装没发生过
```

第3点是产品决策：**退回再提交，是从 n1 重新逐级审，还是直接回到退回点 n3？** 两种都有产品这么做，引擎要支持配置。新手常只做"跳回去"忘了"清理中间态"，导致单子出现多个活动节点。

## 🔎 超时 / 自动处理：谁来触发？

"3天没审自动升级给上级"——关键问题：**没有用户动作，谁来推动？** 答案是**后台定时扫描**。CP6 已有 BackgroundService 机制（Phase 6 的重试 Worker 就是），照搬：

```csharp
// 后台 Worker 周期扫描超时待办
var overdue = await _db.FlowTasks
    .Where(t => t.State=="pending" && t.DueTime < now)   // DueTime 在开任务时按节点 SLA 算
    .ToListAsync();
foreach (var t in overdue)
{
    // 按节点配置：升级给上级 / 自动通过 / 自动驳回 / 仅提醒
    await HandleTimeout(t);
}
```

节点定义加 `"timeout": { "hours": 72, "action": "escalate" }`。**超时是 OA 从"能用"到"好用"的关键体验**，但务必幂等（扫描可能重入），复用 CP6 的事件/重试基建最稳。

## 🔎 委派 / 代理 vs 加签

容易混。区别：

- **委派/代理**：李经理出差，把"我的待办"全权交给张三办（改 `FlowTask.AssigneeId` 或配代理规则期间自动转派）。**人不变多，办的人换了。**
- **加签**：审批人数变多了，新拉一个人进来一起审。**节点计数变了。**

代理常做成"时间段规则"（出差期间 A 的所有待办自动给 B），不是单张单子操作。

## 💡 资深视角

**为什么阶段1 要刻意跳过这些？**
因为它们全是"单人节点状态机"的扩展。先把骨架（一进一出）吃透，会签只是"节点上多任务+计数"、退回只是"跳转+清理"、超时只是"后台扫描+动作"。骨架不稳就上这些，你会被并发计数、状态清理搞到崩溃。**复杂度要分层引入。**

**会签的并发问题**
三个人同时点同意，三个请求并发判断 `IsNodeSettled` 都觉得"还差一个"或都觉得"齐了"，可能重复流转。要对实例加乐观锁（版本号）或行锁，保证"节点结算"串行。这是会签真正的工程难点，不是计数本身。

**什么时候该停止自研、上 BPMN 引擎？**
当你需要并行网关、子流程、跨流程消息、定时边界事件这些，自研维护成本会超过收益。届时评估 Elsa（.NET 原生、可嵌入）。但**会签/或签/退回/超时这些，自研完全够且更可控**，不必为它们上重引擎。

## ⚠️ 踩坑记录

1. **会签计数并发错乱**：多人同时审导致重复流转或漏流转。实例加乐观锁，结算逻辑串行化。
2. **退回不清中间待办**：出现多个活动节点，单子"分裂"。退回必须作废跳过区间的所有 pending 待办。
3. **加签后没重算计数**：会签 `tasks.Count` 变了但结算逻辑用了旧值，节点永远定不了或提前定了。
4. **超时扫描不幂等**：Worker 重入把一张单升级两次。处理前置 `state=pending` 条件 + 乐观锁。
5. **代理把权限也带过去**：张三代李经理审，却看到了李经理的其他权限。代理只转"待办处理权"，不转角色权限。
