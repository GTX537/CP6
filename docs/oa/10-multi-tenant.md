# 10 · 多租户与商业化

> 前 9 章你已经能造出一个能用的 OA。本章解决最后一步：怎么把它从"我们自己用的 OA"变成"能卖给 N 个客户、各用各的、互不干扰"的**产品**。这也是你做这一切的初衷——商用。

## 🔎 多租户的三种隔离模式

| 模式 | 怎么隔离 | 隔离强度 | 成本 | 适用 |
|---|---|---|---|---|
| **共享库 + TenantId 列** ✅ | 每张表加 `TenantId`，查询自动带租户过滤 | 中（靠代码纪律） | 低 | SaaS 起步、中小客户多 |
| **独立 Schema** | 每租户一套 schema | 较高 | 中 | 中型客户、合规要求 |
| **独立数据库** | 每租户一个库 | 最高 | 高 | 大客户、强合规、私有化 |

**OA/CP6 商业化建议：共享库 + TenantId 起步，预留"大客户独立库"能力。** 大多数 SaaS 这么做。关键是**从第一天起每张表就带 `TenantId`**——后补极痛苦。

```csharp
// 所有 OA 表的基类带 TenantId，EF 全局查询过滤器自动加 WHERE TenantId=当前租户
public abstract class TenantEntity : BaseEntity { public Guid TenantId { get; set; } }

// CP6Context.OnModelCreating 里
modelBuilder.Entity<FlowInstance>().HasQueryFilter(e => e.TenantId == _tenant.Current);
// → 业务代码再也不用手写 WHERE TenantId，框架自动隔离，杜绝"忘了过滤"的越权 bug
```

> ⚠️ 全局查询过滤器是多租户安全的命脉。一旦某个查询绕过它（如裸 SQL/Dapper），就可能跨租户泄露数据。Dapper 查询要手动带 TenantId，并加测试覆盖"租户A查不到租户B数据"。

## 🔎 隔离 vs 可配置：分清两件事

商业化要区分"每个客户各一份"和"每个客户能自己调"：

| 要**按租户隔离**的（各存各的） | 要做成**租户可配置**的（客户能自己设） |
|---|---|
| 组织架构、用户、表单/流程模板实例 | 流程模板（在标准模板上改） |
| 表单数据、审批实例、待办 | 审批规则（审批人、条件、会签策略） |
| 文件/附件 | 字段、表单布局 |
| 角色权限配置 | 主题/Logo/品牌（白标） |
| | 通知方式（站内/钉钉/邮件） |

**低代码的天然优势**：表单和流程本就是 schema 配置（前 9 章的成果），所以"客户自定义"几乎是免费的——客户用设计器改自己的 schema 即可，不用改代码。**这正是低代码 OA 适合商业化的根本原因。**

## 🔎 标准模板 + 客户自定义

商业产品要开箱即用，又要可改：

- **预置行业模板库**：请假、报销、采购、用印、合同审批…作为"标准模板"内置。
- **客户复制改造**：客户开通后，把标准模板**复制**成自己租户下的实例，再用设计器改（改了不影响标准模板，也不影响别的租户）。
- **模板版本/升级**：你升级标准模板时，客户可选择是否合并更新（类似 fork + merge）。

数据上：`FormDef`/`FlowDef` 带 `TenantId` + `IsTemplate` + `SourceTemplateId`，标准模板 `TenantId=null/系统租户`，客户实例指向其来源。

## 🔎 商业化要补的非功能能力

功能做完，离"能卖"还差这些：

| 能力 | 说明 |
|---|---|
| **租户开通/管理** | 注册、初始化（建组织、复制模板、建管理员）、停用 |
| **计费/套餐** | 按租户/用户数/流程数/存储计量；功能按套餐开关（Feature Flag） |
| **开放 API + AppKey** | 让客户的其他系统对接你的 OA（发起审批、查状态），Token 鉴权 |
| **白标/品牌定制** | Logo、主色、域名、登录页——按租户配置（呼应第07章主题） |
| **数据导出/迁移** | 客户要能导出自己的数据（合规 + 信任） |
| **审计/合规** | 操作审计（复用 CP6 OperLog）、数据留存策略、权限分级 |
| **SLA/可观测性** | 复用 CP6 的 Prometheus 指标，按租户看用量和健康 |

## 💡 资深视角

**怎么避免一开始过度设计多租户？**
矛盾：多租户后补很痛，但一上来全做又拖慢一期。**折中：数据层从第一天带 `TenantId` + 全局过滤器（这是最难补的，必须早做），但计费、开放 API、白标这些上层能力按需后加。** 即"隔离机制早做，商业化外围晚做"。这样既不过度设计，又不会在隔离上踩不可逆的坑。

**单租户私有化 vs SaaS 多租户**
很多 ToB OA 客户要私有化部署（数据不出厂）。好在"共享库+TenantId"的代码，部署成单租户私有化只是"只有一个租户"的特例，**同一套代码两种交付**。CP6 已有 Docker/K8s（见 `docs/learning/12-devops.md`），私有化交付现成。

**多租户下的性能**
共享库租户多了，热点表（待办、实例）数据量大。`TenantId` 要进复合索引前缀，大租户考虑分区或迁独立库。早期不用管，但 schema 设计时把 TenantId 放索引第一列。

## ⚠️ 踩坑记录

1. **TenantId 后补**：上线后再加，要改全部表+全部查询+迁数据，几乎是重做。**第一天就加。**
2. **Dapper/裸 SQL 绕过全局过滤器**：EF 有全局过滤器，但 Dapper 查询不会自动带 TenantId，成跨租户泄露口子。所有裸查询手动带 + 加越权测试。
3. **客户改了标准模板影响别人**：模板没复制成租户实例，客户改的是共享模板。必须"复制后改"。
4. **Feature Flag 散落各处**：套餐功能开关写得到处都是。集中到一个租户能力配置，按套餐统一控制。
5. **缓存不带租户键**：Redis 缓存 key 没带 TenantId，租户A读到租户B的缓存。所有缓存 key 前缀带租户。
