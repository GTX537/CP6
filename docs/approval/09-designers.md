# 09 · 自研设计器：表单设计器 + 流程设计器

> **阶段 4 · 最后做的一章。** 前面八章，所有 schema 都是**手写**的。本章做最后一块：把"手写 JSON"升级为"拖拽生成 JSON"——表单设计器拖控件产出 form schema、流程设计器画节点连线产出 flow schema。关键约束：**设计器产出的 JSON，必须和你前面手写的同一种结构**。运行时一行不改，只是换了生产 JSON 的方式。本章结束时，业务人员不写 JSON 也能配表单和流程。
>
> 上游：[02 表单](./02-form-runtime.md)、[03 流程](./03-flow-runtime.md)（设计器产出喂给它们的运行时）。决策：[总纲](./README.md)定的**全自研**（不集成开源），但仍**最后做**。

---

## 一、题眼：设计器只是 JSON 的生产工具

整套书最重要的方法论，到这里收口：

> **拖拽设计器是最后做的，不是最先做的。设计器的产出 = 前面手写的同一种 schema JSON。运行时（02/03 的渲染器、状态机）完全不变，设计器只是把"手敲 JSON"换成"拖拽生成 JSON"。**

为什么必须最后做、为什么很多团队反着来就失败：

- **反着来**（先做设计器）：你还没验证运行时能不能跑，就陷进画布交互、拖拽对齐、属性面板的泥潭，半年出不来一个能用的表单。
- **正着来**（本书顺序）：02~08 已经用手写 schema 把表单/流程/规则/高级动作全跑通、全验证。设计器现在只需做一件事——**生成那段已被验证的 JSON 结构**。风险被前面消化干净了。

> 检验标准：设计器导出的 JSON，**直接喂给 02/03 的运行时能跑**，且和你手写的那段长得一样。能，就对了；不一样，就是设计器跑偏了。

## 二、表单设计器：三栏布局

经典的三栏结构，自研也是这个骨架：

```
┌──────────┬─────────────────────┬──────────────┐
│ 控件库     │      画布(预览)        │   属性面板     │
│ 输入框     │  ┌───────────────┐  │  字段key: days │
│ 下拉      │  │ 请假类型 [▼]   │  │  label: 天数   │
│ 日期      │  │ 开始日期 [📅]  │  │  type: number │
│ 数字      │  │ 天数    [  ]   │  │  required: ☑  │
│ 选人      │  └───────────────┘  │  ...          │
└──────────┴─────────────────────┴──────────────┘
   拖 ───────────▶ 放                  选中→编辑
```

三个动作对应三种 schema 操作：

| 设计器操作 | 对 form schema 的改动 |
|---|---|
| 从控件库拖一个控件到画布 | 往 `fields` 数组 **push 一条** `{key, label, type, …}` |
| 选中画布上某控件 | 加载它到属性面板 |
| 在属性面板改属性 | 改 `fields[i]` 对应的属性 |
| 拖动排序 | 调整 `fields` 数组顺序 |

```ts
// 拖一个控件进画布，本质就是这一句
function onDropControl(type: string) {
  schema.fields.push(defaultFieldOf(type))   // 如 { key: genKey(), type, label: '新字段', required: false }
}
```

**画布即预览**：画布直接复用 [02 章的 `DynamicForm`](./02-form-runtime.md) 渲染当前 `schema`——所见即所得，且**预览用的就是运行时渲染器**，不会"设计时一个样、运行时另一个样"。这是"同构"的直接红利。

## 三、流程设计器：画节点连线

流程设计器是个**有向图编辑器**：拖节点、连线、配节点属性，产出 [03 章](./03-flow-runtime.md)的 `nodes` + `edges`。

```
[开始] →→ [直属上级] →→ [部门长] →→ [结束]
              │                ↑
              └── days≤3 ───────┘  (条件连线)
```

| 设计器操作 | 对 flow schema 的改动 |
|---|---|
| 拖一个审批节点到画布 | 往 `nodes` push `{id, type:"approval", …}` |
| 从 A 拉一条线到 B | 往 `edges` push `{from:"A", to:"B"}` |
| 在连线上配条件 | 给该 edge 加 `condition: "days <= 3"` |
| 选中节点配属性 | 编辑该节点的 `approver` / `countersign` / `fieldPerms` / `timeout` |

节点属性面板要能配齐前面各章的能力：审批人规则（[01](./01-org-model.md)）、会签规则（[03](./03-flow-runtime.md)）、字段权限（[04](./04-form-flow-binding.md)）、超时策略（[07](./07-advanced-flow.md)）——**设计器属性面板 = 前面所有 schema 字段的可视化录入口**。

**自研画布用什么？** 一个轻量有向图层：可以基于 `<svg>`/`<canvas>` 自己画节点和连线，或用一个无业务侵入的画图内核（仅负责节点拖拽/连线/缩放，业务属性自己管）。**核心是：图编辑器只管"图的拓扑与坐标"，节点的业务语义（审批人等）由属性面板写进 schema**——图和语义分离。

## 四、全自研的取舍（总纲决策）

总纲定了**全自研**（不集成 form-create/LogicFlow）。这意味着：

- **收益**：控件库、画布交互、属性面板、整体视觉完全可控，与 CP6 其余界面统一，不被第三方库的风格/限制绑架。
- **代价**：拖拽、对齐、连线吸附、撤销重做这些交互要自己实现，工作量大。
- **风控**：正因为代价大，更要守住"**最后做**"——前面把运行时和 schema 结构全定死了，自研设计器只是"生成已固定的 JSON"，不用边做设计器边改 schema，否则成本翻倍。

> 自研 ≠ 最先做。这两件事不冲突：你可以全自研，但必须等运行时跑通、schema 稳定之后。本书的顺序正是为这个决策铺好的路。

## 五、产出落库即用

设计器存的就是 [02](./02-form-runtime.md)/[03](./03-flow-runtime.md) 的实体字段：

```
表单设计器 →保存→ FormDef.SchemaJson（+ Version+1 留旧版）
流程设计器 →保存→ FlowDef.SchemaJson（+ Version+1）
```

存完，运行时立刻按新 schema 渲染/流转——**没有"生成代码""编译部署"步骤**，这正是低代码的意义：配置即生效。改版用 `Version+1`，进行中的旧实例/历史单据仍按旧版跑（[02](./02-form-runtime.md)/[03](./03-flow-runtime.md)的版本化在此收益）。

**设计时校验**：保存前用运行时同款校验跑一遍——必填项漏配、流程有断头节点（连不到 end）、审批人规则不完整等，设计器当场提示，别让坏 schema 进库。

## 六、资深视角

**同构是怎么保证的？** 不要让设计器有"自己的中间格式"再转成运行时 schema——那等于维护两套结构、迟早漂移。**设计器直接读写运行时 schema**，画布预览直接用运行时渲染器。一套 JSON，从手写、设计器生成、到运行，自始至终是它。

**撤销/重做怎么做？** schema 是个普通 JS 对象，每次操作前快照一份，撤销=回到上一快照。别为撤销设计复杂的命令模式，对 schema 这种小对象，快照栈最省事。

**为什么属性面板比画布更重要？** 画布的拖拽是"面子"，属性面板才是"里子"——审批人、会签、字段权限、超时全在属性面板配。一个朴素画布 + 完整属性面板，比一个炫酷画布 + 配不全属性的设计器有用得多。**先把属性配全，再打磨画布交互**。

## 七、与业界对照

| 想理解 | 去看 | 学什么 |
|---|---|---|
| 表单设计器 | **form-create designer / variant-form** | 控件库→画布→属性面板三栏、拖拽产出 schema |
| 流程设计器 | **LogicFlow / bpmn-js** | 节点连线编辑、产出流程 JSON |
| 同构验证 | **任意 low-code "导出 JSON"功能** | 设计器导出能否直接喂运行时 |

> 读它们不是为抄，是**确认"设计器产出就是一段 schema JSON"**——和本书一致。自研时借鉴它们的交互范式，但 schema 结构用你自己的（前八章定的那套）。
