# C04A 首写前恢复协调

从 Core `fa0b58b405b230037563a646d98c022227391175`、CRM `3dab2c45de7212a23d6116f580e683e2c97e2bd0` 各自最新 main 建立同一任务的独立分支。保留已通过的 C01/C02/C03 与未受影响组件结果，整体目标仍为 60%（3/5）。

## 约束与最终行为

- 目标库不一定独占，因此不得通过整库 READ_ONLY 停止其他 Schema 的业务。
- 目标必须先为 Closed 且没有首写，再在同一组织事务中安装 CRM Control 的永久写入拒绝触发器并保存规范回执。现有业务表保护及 Control/Audit 行保持；终止扩展使旧版 Enable 的绑定检查失败，直接修改 Control 也被 SQL 拒绝。
- 回执绑定组织、原 TargetBinding、SQL 实际身份、源冻结请求摘要集合、操作批准引用及精确保护快照。最多16份来源，排序、唯一，避免把原生与 Docker 同名库合并成一份来源。
- 源恢复直接连接目标读取并验证回执、永久保护、元数据及 Closed/无首写，持有目标读取锁直到源事务提交。只拿状态 JSON 文件或普通 Closed 快照不能恢复来源。
- 源在同一事务中验证原冻结回执、精确身份/状态/摘要，撤销自有20表保护并写入恢复记录。相同恢复请求可重放；恢复后的真实旧写入不破坏相邻重放，元数据漂移仍拒绝。首写后的目标不得生成终止回执。
- 协议在两仓逐字节镜像，使用相同 C# DTO、SQL保护定义和摘要算法；跨仓集成通过独立发布 Core CLI 调用，避免把两套服务装进同一进程。

## 实施与验证

1. 新增协议与 CRM 目标终止 API/本机 CLI，验证永久关闭、错误来源/目标/请求拒绝、事务失败无半成品、其他 Schema 仍能写。
2. 接通 Core 实际 reopen/recovery-status CLI，保留原 rehearsal 边界；增加源/目标锁定、恢复记录和重放检查。
3. 独立跨仓 SQL 套件验证发布 CLI 的完整冻结→目标终止→来源恢复，以及目标已首写、回执漂移、并发/失败拒绝。合成夹具只作开发验证，不替代实际迁移验收。
4. 一次集中审查，修复仅定向复验；同步四份状态与必要 CRM02 边界记录，正常 PR 合并并核验双方远端 main。每次远端写入前重新确认不会触发 Actions。

当前不冻结实际来源、不停止既有服务、不替换预览。后续仍需实际原生/Docker 启动路径隔离、路由停启/恢复包、0.2实际采用签收和 CRM11/观察期；上述组件与恢复验证完成后再请求具体实际执行批准。
