# C02：组织、权限与撤销事件

状态：用户于 2026-09-10 明确确认“确定按设计继续实施”。实现以 C01 真实身份验收完成为前置。

## 业务结果

在 CP6 停用租户或用户、调整部门或角色权限、撤销登录会话后，CRM 更新本地授权状态。重复消息不会重复执行，旧消息不会恢复已经收回的权限。对账发现缺失或漂移时，受影响的管理请求拒绝访问；已发布的公开内容继续服务。

沿用 [CRM V1 可执行规格](../../crm/CRM-V1-EXECUTABLE-SPEC.md) 第 9、10 节的五类事件、CloudEvents、15 分钟对账和撤销生效目标。C03 ERP 业务、CRM03 完整动作/数据范围/PII 矩阵、C04 迁移与生产部署分别交付。

## 方案选择

采用“CP6 保存业务变更和版本化快照时同时写 Outbox，CRM 以 Inbox 消费完整快照”。角色授权按角色形成快照，用户快照携带主角色和附加角色引用；CRM 按现有规则聚合角色权限。这样一次角色变更只发布该角色的完整权限，不需要在 CP6 的管理事务中逐个重算全部成员。

另一种方案是每次角色修改都发布所有受影响用户的有效授权。它使消费简单，但大角色需要大量事务内重算和消息，撤销时容易排队。仅依赖定期轮询虽然改动少，却不能满足撤销传播和可重放事件的要求，因此不采用。

消息基础设施复用已固定版本的 Platform CloudEvents 校验、Outbox、Inbox、租约、去重、重试和死信能力。Core/CRM 各自拥有业务 Schema、投影和迁移；原有审计 Kafka、工作流通知 Outbox 不改变用途。

## 事件与版本

Topic 固定为 `cp6.platform.events.v1`，消息值就是结构化 CloudEvent。`source` 固定为生产者身份 `urn:cp6:platform`；租户从已授权的业务实体或命令上下文取得。分区键为 `{tenantid}:{aggregateid}`，每条消息保留 correlation/causation。

聚合 ID 带类型前缀，防止用户与权限等事件使用同一 ID 时被 Inbox 的版本检查互相覆盖。版本在 SQL 事务内分配，以 `(TenantId, AggregateId)` 唯一，并发冲突回滚整个命令；不以时间戳或进程内计数代替版本。

| 事件 | 快照内容 | 聚合 |
| --- | --- | --- |
| `tenant.changed.v1` | tenantId、enabled、version，以及可选的 UTC 到期时间 | `tenant:{id}` |
| `user.changed.v1` | userId、deptId、enabled、version、角色引用和必要的身份有效期约束 | `user:{id}` |
| `department.changed.v1` | deptId、parentId、path、enabled、version；删除保留禁用墓碑 | `department:{id}` |
| `permission.changed.v1` | subjectId、version、enabled 与完整 grants；每个 grant 包含 resource、action、scope | `permission:role:{roleId}` 或 `permission:user:{id}` |
| `token.revoked.v1` | issuer、jti、subjectId、expiresAtUtc | `token:{issuerDigest}:{jti}` |

表中 Type 均以前缀 `com.gtx537.platform.` 发布。`grants: []` 明确表示清空该主体授权；单条事件原子替换整个主体快照。角色 ID 保留 CP6 现有租户内整数身份，subjectId 使用 `role:{roleId}`，避免与用户 Guid 混淆。用户主角色与附加角色去重，禁用或缺失角色不授予权限。数据范围与自定义部门按当前 Core 聚合规则计算，不另造新的权限名称。

Schema 在 Core 的 `contracts/events/platform/<event-type>/v1/schema.json` 版本化，使用 Draft 2020-12。生产者与消费者均验证完整 Envelope/Data、类型、标识、UTC 时间、长度和版本；未知可选扩展保持兼容，已知 PII/Secret 字段明确拒绝。事件只传标识与授权事实，不传姓名、邮箱、电话、密码、Cookie、令牌或私钥。显示名称继续由获授权的目录查询提供。

每种事件保留 valid、missing-required、unknown-optional、wrong-type、PII-negative 样例。Platform 只登记对应合同索引及校验入口；消费端绑定源版本和摘要，禁止按运行时提供的 URL 下载任意 Schema。

## CP6 的事务边界

在 `CP6Context` 的同步和异步保存路径中捕获受影响的身份聚合，参与现有业务与字段审计事务。根据事务中的最终状态生成快照、更新版本并校验/写入 Outbox，全部成功后才提交。没有身份变更的保存不增加快照查询。快照、版本或 Outbox 失败时，业务变更也回滚。

必须覆盖的入口如下：

- TenantAdmin 的创建、停用、恢复和有效期修改。
- UserController、DeptService.SetUserOrg、UserRoleService、SSO 创建用户，以及密码/2FA/锁定等使既有身份失效的路径。
- 部门创建、更新、移动整棵子树、删除和负责人变化。
- 角色启停、删除、菜单动作、数据范围、字段授权及影响 CRM 权限键的菜单修改。
- GDPR 匿名化和清除的直接 SQL 路径：在同一事务保存必要的禁用墓碑和撤销事件，不能依赖 ChangeTracker 自动发现直接 SQL。

角色权限快照从实际角色授权表生成，用户角色快照从主角色与附加角色的最终集合生成。删除关联前收集受影响的主体，避免保存后失去定位信息。初始种子和重跑不会人为增加无变化的版本。

撤销使用实际消费令牌的身份。当前 CRM access token 的 `jti` 等于 `CrmOidcGrant.Id`，与 CP6 原始登录令牌的 `SourceJti` 不同。`SqlCrmOidcGrantStore.RevokeSourceFamilyAsync` 必须在现有会话族锁与 SQL 事务中，枚举并撤销相关 CRM grant，同时写各 grant 的撤销事件。独立 grant 撤销也遵守同一规则。密码、2FA 和用户禁用等会话失效路径同样覆盖已签发 grant。

服务令牌撤销按 issuer/jti/绑定租户处理，不能把服务客户端冒充自然人。新增必要的签发记录，保留到令牌过期；记录不保存令牌原文或客户端秘密。`POST /connect/service-revocations` 复用已注册服务客户端的严格 Basic 认证，接收 jti，只能撤销相同 client_id、绑定租户的签发记录；未知或已撤销 jti 返回同样的成功响应。客户端不能撤销其他客户端或浏览器令牌。签发记录未能持久化时不返回令牌，撤销记录与事件必须同事务提交。

## 发布、消费与授权

身份消息使用独立的调度预算；停用与撤销使用优先 Outbox 队列，普通组织/权限快照使用普通队列。两者仍发布同一业务 Topic，使用相同固定 Platform 消息组件和原子数据库事务，防止大批普通变更饿死撤销。发送失败保留消息并有界退避，达到上限进入死信；确认发布失败后不得标记成功。

CRM 先校验来源、事件 Schema、租户和分区键，再通过 Platform Inbox 在事务内更新投影。相同 ID/相同摘要是重复；相同 ID/不同摘要拒绝并留冲突证据。落后的聚合版本记为已处理但不回退状态。较新完整快照可以直接替换旧状态；版本跳跃触发对账标记，权限在完成核对前关闭。

Tenant/User/Department/Permission 投影和 RevokedToken 使用明确的租户键；令牌撤销键为 `(Issuer, Jti)`。`expiresAtUtc` 保存原始令牌到期时间，墓碑清理不早于该时间加已配置的最大验证时钟偏差，避免消费者在偏差窗口内重新接受已撤销令牌。管理请求在 materialize 业务数据之前检查租户、用户、令牌撤销及投影健康；初版每次读取这些投影，不缓存跨请求的允许结果。

持久会话增加租户、主体、issuer/jti 的非秘密索引元数据，令牌仍只保存在原有保护的内容中。消费停用/撤销后删除对应会话记录，并沿用已有前端重新验证/清除草稿行为。首次启用时旧格式会话要求重新登录；不通过解密扫描所有会话来查找受影响用户。

首次启用需要完整初始快照和版本基线。缺少任何必需投影、依赖部门或角色，或投影存储不可用时，不使用宽松默认值授权。保留现有登录的会话族、issuer、租户、有效期验证；本地投影不得扩大原有权限。C02 建立实际浏览器管理请求的投影接入，CRM03 再完成完整的 22 动作交叉矩阵与剩余数据范围/PII 功能。

## 初始化和对账

Core 提供 `CP6.Services` 保护的只读 `GET /internal/crm/identity/versions` 和 `GET /internal/crm/identity/snapshots/{aggregateId}`。版本清单每页最多 200 条，游标绑定租户、排序位置和快照边界；服务客户端除通用服务 scope 外还必须被显式配置为 CRM 投影读取客户端。客户端严格绑定一个租户，请求不能通过参数切换到其他租户。摘要包括类型化聚合 ID、版本、内容摘要和墓碑，快照来自与 Outbox 同事务持久化的权威版本状态。

CRM 首次启动先导入快照基线，再追平其后的消息；每 15 分钟比较版本/摘要。发现漂移时先标记受影响用户不可授权并告警，再从 Core 读取对应完整快照修复。更新投影与解除漂移标记在同一 SQL 事务完成；并发到来的更新不能被旧对账快照覆盖。租户漂移影响全租户，部门或角色漂移只影响依赖它们的用户。

对账自身失败也保留失败状态和重试记录。已过期的基线不能无限期授予管理权限；只读公开内容不经过该授权分支。

## 实施顺序与完成证据

1. Core：五种合同、版本/快照与 Outbox 迁移、真实业务写入口、会话/服务撤销、只读快照 API。
2. CRM：Inbox 与投影迁移、版本处理、管理请求接入、初始化及对账。
3. 跨仓：实际 Dapr/Kafka 传输、优先调度、故障恢复与撤销传播验证。

局部开发只运行对应新增行为的测试。一次真实 SQL 集成覆盖业务/版本/Outbox 回滚、并发、删除与直接 SQL 路径；一次跨仓场景覆盖重复/乱序/冲突、双租户隔离、投影故障、对账修复、真实用户和服务令牌撤销。普通单元测试可控制时钟；30 秒传播与完整传输验收必须使用真实时钟、SQL 和 Dapr/Kafka。

撤销验收分别记录用户停用、租户停用和令牌撤销的每次触发/实际拒绝时间、样本数、p99 和失败数；要求至少 99% 在 30 秒内生效。所有必需用例零跳过，缺真实传输输入就保留未完成状态。测试凭证和原始令牌只存放在隔离的私有输入中，公开结果仅包含源 SHA、固定包/合同摘要、计数和安全的时延记录。

每个任务分支仅提交其实现、必要测试和四份状态记录；审查一次完整 diff，完成所需 CI、正常合并并核对远端 main。文档不重跑业务测试，未变更的历史包证据复用。不会通过合成传输、缩短真实令牌寿命或删除失败用例关闭 C02。
