状态：`core_semantics_consolidated`。当前 Order/Demand 功能文本组合已获有限认可；物理接口、真实 Owner 实例、旧数据迁移及运行验证分别保留。本册覆盖 Planning 接收端，Sales 的完整商业流程和共同 140 字段字典见 [ERP-ORD-01](D:/CP6/docs/CP6_开发设计文档_20261010/modules/ERP-ORD-01.md)。[P:66] [P:690]

## 1. 目的、角色与Owner

Planning 接收 Sales 已正式释放的准确责任份额，建立可追溯的 Demand 和版本；在有权变更、取消、工程影响及真实发运发生后，维护当前有效需求、源控制和补给责任。商业 Confirm、ATP 查询、保存草稿均不是需求接收；不能扫描所有订单代替 H10 正式输入，也不能因标题叫“独立需求”而补造预测、服务里程碑、安全库存来源合同。[R1:50] [R3:436]

Sales 拥有来源订单、行、交期份额、SalesRelease、SourceVersion 和商业决定；Planning 拥有 Demand、DemandVersion、计划控制、Pegging、Run 和接收结果；MES、Procurement、WMS、Quality、PLM 各持其原事实。PlanningReader 只读；PlanningReceiver/受控服务身份接收准确源请求；PlanningPlanner 提源字段纠正或重评；PlanningController 评估、应用本域控制及有权变化。协调角色仅跟踪真实处置，不能替原 Owner 宣布取消成功。[R2:1464] [R2:1589] [R2:1630] [R2:1716]

业务要分开回答：是否收到请求、是否真正建立需求、当前哪个版本有效、哪些原因阻止后续动作、目前覆盖多少、实际发了多少。这些结果不能压成一个“成功”状态。

## 3. 数据、身份与状态

### 3.1 稳定身份与版本

| 对象/字段 | 设计约束 |
|---|---|
| OrderId / OrderLineId / ScheduleId | Sales 的稳定对象和份额身份；行号、SKU、日期不是去重身份，同 SKU 不同来源/价格不能合并。[R1:93] |
| SalesReleaseLineId / ReleaseLineageId | 一次释放明细与持续供给责任谱系不同；修改目标保留谱系。[R2:2232] |
| SourceVersion / ExpectedAcceptedSourceVersion | 新来源版与最后真实接受版；前驱不是数值减一。v1 已接受、v2 明确拒绝、v3 可持 v2 终态沿 v1；v2 UNKNOWN 则普通 v3 不得越过。[R2:213] [R3:349] |
| DemandId / DemandVersion | 由 Planning 真实生成并返回；源请求失败不预造 ID。已存在 Demand 全取消可产生同一对象目标 0 的后继；初次取消先到只建源控制。[R2:1704] [R3:333] |
| CommercialVersion / TechnicalScope | 与需求/源版分开。技术包含 Item、Revision、Baseline、配置/生效范围；冻结技术引用不表示暂停需求，更不自动取得制造许可。[R2:1548] [R3:623] |

| CurrentSourceEffectivity | 当前接受前驱、有效/替代/取消范围、控制、后继；与历史成功分栏。[R3:325] |

### 3.2 复合输入必须有成员，不能用调用方布尔值替代

接收载荷至少关联原请求类别、Order/Line/Schedule、ReleaseLineage、SourceVersion、真正已接受前驱、目标量/事务及标准 UOM、转换依据、技术、Site、需求日期和日期节点、Purpose/适用证据、原键及内容证明。CommercialSupplyScopeMap 仅证明纯改价等商业后继的供给字段等同性，不复制旧商业批准。[R2:1466] [R2:1470] [R3:323]

FactWatermark 要说明 Owner、范围、版本/截止点、完整性、查询时间及未知原因。CoverageAndFinality 还需说明原键和入口的覆盖，以及是否另有控制能排除未来执行；一个时间戳或空查询不能证明“未发生且永不发生”。[R2:295] [R3:327]

Condition 分别保存必要性 `REQUIRED / JUSTIFIED_NOT_APPLICABLE / UNDETERMINED` 和证据 `SATISFIED / NOT_SATISFIED / UNKNOWN / STALE`。缺真实实例不能变成 N/A；已知 FAIL 不能因当前不可读而变 PASS。ActivityAssessmentRequest 使用真实活动、产品、技术、Purpose、数量、Site、时间节点和现货/新制造/返工背景。[R2:176] [R3:631]

### 3.3 数量口径

同一范围、UOM 和完整当前事实下，令 Q 为当前商业量、R 为当前真实接受的释放目标、S 为有效发运：确定未释放 U=Q−R，已释放待补给=R−S，商业未发=Q−S。R 已含已发部分，不能再加 S；UNKNOWN 不计作确定未释放；超发负差保留例外，不能静默裁成零。[R2:112] [R2:118]

| 示例 | 结果 |
|---|---|
| 同谱系目标30改40 | 当前40，增量10；不累加成70。[R4:139] |
| Q100/R60/S20，取消确定未释放30 | Q70/R60/U10；Demand不减30，已释放待补给40，商业未发50。[R4:135] |
| 同上，取消50=未释放40+已接受10 | Q50/R50/S20/U0；待补给30，取消只扣一次。[R4:137] |
| 合法来源100、可覆盖60或0 | 接收目标100，另列覆盖及不足；Planning不能把源目标直接编辑成60或0。[R4:143] |
| 原100、已发40、取消未发60 | 新目标40、取消60；保留历史发运和共享WO/PO后果。[R2:1714] |
| 目标100、发100、签80 | 普通重复补给责任结束，Sales仍追签收20；不自动造20新需求。[R2:1838] |

## 4. 接收、变化、控制与覆盖流程

1. 先验证可信身份与对象权，再按原键查权威结果。同内容已成功只返回原结果及当前效力；未应用新请求继续核当前源控制和真实接受前驱。[R3:331]
2. 区分 `INITIAL_RELEASE`、`REVISE_TARGET`、`CANCEL_EXISTING`、`CONTROL_SOURCE` 的功能语义。初次释放正目标且无同源已成立需求；后继目标是总量；取消依据准确取消分配；源控制无须虚构零量需求。这些名称不擅自宣布为已部署 wire 枚举。[R3:333]
3. 核源合法性、量纲/精度、Site/日期节点、技术/用途和最晚必需条件。合法单份额整体接收；短缺独立登记，不能暗做部分接收。独立 S1=40 可成功、S2=60 可拒绝；不可拆组转准备/共同启用合同。[R2:1521] [R3:334]
4. 在 Planning 本地业务提交同时持久 Demand 版、来源映射、必要控制和业务回执；Sales 以真实回执更新投影。拒绝或待补固定该输入、原因与负责 Owner，不删旧有效需求；实质补正另建来源版。[R2:1493] [R3:335]
5. 变更/取消先评准确 ImpactItem 和执行水位，保存必要控制；再次确认当前前驱、批准及发运后应用新目标。共享 WO/PO 只处理本需求份额，实际已执行不可抹掉；依赖原 Owner 逐项回执。[R2:1630] [R2:1687]
6. 控制是原因集合。Planning 只能解除有权本原因；质量 Hold、PLM 控制、Sales 停止各自保留。终结取消不能使用普通 Resume 复活。控制必须作用到真实计划/转换入口，不只改页面状态。[R2:1673]
7. 以当前有效 Demand/控制、水位请求 Planning 重评。Run 成功发布后才展示新覆盖；失败或旧 Run 晚到保留历史/陈旧，不把旧输入100当新需求120已覆盖。[R2:1800] [R3:439]
8. 有效发运/有权变化决定普通补给责任；覆盖、实物预留、实际发运、交付分别显示。关闭后原 Owner 更正误记，保留原 Closure 和新差异复核，不自动生产差额或复活旧操作键。[R2:1827] [R4:111]

## 6. 事务、并发与恢复

本地原子边界是 Demand版本、来源映射、源控制及业务回执的一致提交；跨 Owner 的后果、原对象状态、外部成功各有独立边界。不能声称 Sales 和 Planning 必定同库，也不能仅因使用 Outbox 宣称不可拆组原子切换已被实现。[R3:335] [R3:693]

同谱系普通后继不能跨过未明前驱；紧急更高版本控制可以独立存在，但保留未明操作的真实后果。评估到提交之间发运40→50时，原取消60不得直接提交；从目标/范围/水位变化重新评估受影响批准。控制比较实际业务发生时点与应生效点，不能用消息晚到时间抹掉旧发运或断言必然违规。[R3:349] [R3:389] [R3:402]

恢复分三类：查询原权威结果；已成功只修显示/投影；未定且现行控制准许才按原键同内容重放。旧成功回执留历史但不恢复取消范围；旧未执行命令受新控制阻止；新到实际发运/投产事实由原 Owner 合同收录。换键复制同一意图、扫描订单重建需求、万能强制成功均违背此设计。[R3:336] [R3:338] [R4:81]

后果承接必须由后继责任 Owner 明确接受对象、量/金额/单位、风险和仍需完成义务。会使原操作再次发生的 UNKNOWN 不能移到一个普通待办后从关闭条件删除；协调结束不等专业对象结束。[R3:379] [R3:391]

## 7. 权限、租户与专业证据

可信 Tenant/Actor、Site/对象/字段/附件权限先于存在性结果。Planning 的只读 Sales 源数量、日期、地点、技术不能因原字段字典写“提交前可选”就变为接收页可编辑；源纠正走 ACT-038 并等待 Sales 有权新版本。需要暂停时另走控制，不把纠正申请当已控制。[R2:1589] [R4:71]

专业动作逐活动判断：现货发运、新制造、同物返工、试制、外购不通用；已质检合格的试制品不自动成为量产供给。原料/工程准入和真实采用条件由专业 Owner 裁定，Planning管理员不能改其许可或质量 Hold。工程通知期间新释放/投产/发运改变范围时追加影响，不拿旧水位宣称全覆盖。[R3:639]

14 类策略需真实实例：角色委托/职责隔离、数量与换算精度、日期日历时区、技术产品活动、控制与在途核清、查询导入导出、物理启用能力等。null不是0、无限或N/A；缺条件只阻塞依赖动作，并显示具体 Owner、缺项及恢复出口。[R4:121] [R4:180]

## 9. 开发拆分与旧代码边界

实施顺序建议：先冻结双方准确源身份/版本/业务结果映射及当前控制，落实 Demand 本地提交；再接读模型与逐键恢复；接工程影响及多原因控制；接 MRP 当前有效输入/发布和真实 WMS 发运/预留；最后实现不可拆组准备/启用及完整运行恢复。依赖未被证明时保留相关能力门，不拿页面存在或历史成功代替门禁。

这是整理得到的实施建议，不增加新业务政策。R02 字段是逻辑字典，不是140数据库列；H10/H32是原交接标识，不足以指定路由、事件schema、锁协议或迁移规则。现存代码和生产数据没有在本册逐项评估；不得把候选SQL、旧状态或示例载荷直接当部署依据。[R4:182] [R3:709]
