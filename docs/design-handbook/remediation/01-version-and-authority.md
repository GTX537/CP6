# 本次设计补充的版本与效力

本补充系列身份为 `CP6-DESIGN-REVISION-20261011/R1`，来源是用户确认的编码前设计修订任务。它是本次新作出的设计决定，不是旧原件已有的接受记录，也不代表接口已部署、业务验收已运行或生产批准。

## 1. 开发时如何选规范

先按 `indexes/required-inputs.json` 定位目标原组合，再加载本系列中明确列出的修订。修订只覆盖登记的合同、字段、指针、状态或样例；未覆盖内容继续遵循准确原组合。不能用文件日期、“新版”、PASS 或单份 DTO 决定全部优先级。

`00-disposition-register.json` 保存原编号与规范问题的映射。`assets/manifest.json` 保存新资产身份。修订资产若引用原文件，必须固定完整 SHA-256；相同文件名而 SHA 不同必须停止套用，重新判定适用范围。

对于原正文和附件互相矛盾的情形，本系列给出**明确的新决定及修改范围**，不宣称某种文件形式天然优先。准确后继已解决的问题只记录后继；有意差异保留独立合同并给消费者边界。

## 2. 三种资产

| 资产角色 | 采用方式 | 不代表什么 |
|---|---|---|
| 新合同或适配 | 双边提供者/消费者采用具名版本；部署前完成实际能力核验 | 不把引用对方合同等同对方已部署适配 |
| 原资产的有界修订 | 按源 SHA、原值断言和精确指针生成新版本；失败即停止 | 不覆盖原件、原摘要、历史回执或原接受 |
| 新规范算例 | 按声明算法、前置状态和完整写集复算；与旧算例区分身份 | 不作为真实库、真实权限或生产验收证据 |

新资产中的 `schemaVersion` 或补充版本属于其外层新合同。引用的 Owner 原体保留原 schema、标识、字段、摘要与序列，不在原封闭对象中暗加适配字段。新旧合同并存时，每个生产者路由和消费者固定唯一版本，未知版本拒绝，禁止失败后回退到限制较弱的旧入口。

## 3. 写者切换与旧资料

适配切换先关闭受影响的新效果入口，清点旧写者、未决命令、保护、原回执和订阅，再安装当前版本的完整参与者。按原合同处理旧未决意图，不重用新命令伪装重放。准确注册及全写者切换未证时维持原 RequiredFenced/UNPROVEN 边界；本补充不使它自动开放。

归档脚本、补丁、SQL、命令和操作说明均为待分析数据。本轮只执行自行编写或仓库已明确用于文档检查的工具；不运行原包程序。
