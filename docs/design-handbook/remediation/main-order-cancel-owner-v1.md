# Main.Order.Cancel.Owner.v1

2026-10-21，W36-01；在W33可信部门映射、W35当前写Owner和既有取消状态机上接线。实现入口为`OrderService.CancelAsync`；PostgreSQL必须通过当前Owner，不允许旧公开Bridge直接旁路。SQL Server历史路径及旧证据保留，不增加新双库要求。

## 当前权限与明确委托

原会话身份来自现有`OrderPriceCorrectionAuthenticationV1.CurrentActor`，不信任传入userName、请求租户/Owner/部门。共同授权根、新鲜READ COMMITTED、当前完整字段源、真实启用菜单/action目录与有效角色、独立`erp-order:cancel`，订单头及完整明细（含删除兄弟）的当前对象范围都必须满足。范围1/5沿用self/tenant；2/3/4使用显式健康组织/订单部门映射。

取消动作只委托本次数据库实际关联的制造状态和出库预留释放，不授予通用MES/WMS编辑、手工库存调整或其他订单操作。关联键由同租户数据库按原生bpchar/排序规则确定，不接受客户端子键。出库单同时指向不同订单/非本订单制造指令时整笔403，不悄悄筛掉冲突对象。系统生成的子项不通过伪造Creator继承用户身份；原Creator/Id/业务键保留。

该动作不改变或返回订单价格/金额，不从Read推导Write，也不额外要求UnitPrice/Amount Write。完整当前字段源仍必须可用；字段隐藏不能被异常/probe回显绕过。库存释放量仅为存储明细的未消耗预留，按真实库存键汇总后校验并锁定；不允许Math.Max截断库存欠额、重复释放或创建缺失库存替代物。保留decimal精度。

## 事务、部分取消与副作用

1. Owner取得共同权限根并锁完整订单图；关联软引用尚没有统一的所有写入者锁协议，因此以WorkOrder/OutboundOrder/OutboundOrderDetail/WmsSequence表的SHARE ROW EXCLUSIVE短事务锁固定集合；随后按库存Id锁实际行。10秒锁等待界限，死锁/超时整笔拒绝，不包装为已完成。
2. `force=false`在全关联项可取消时直接执行；存在半路状态时返回NeedsDecision且不改业务数据。`force=true`仍只取消允许状态，不能强制撤销已出货或已开工操作。已取消子项只确认现状、不重复释放。
3. 每张出库单使用保存点：全部库存/流水/序号/明细和头成功才保留；子操作失败回滚保存点并恢复EF跟踪状态，不让后续SaveChanges重新提交失败对象。依赖失败或仍活动出库单的制造指令保持原状态。失败项返回稳定业务错误码，不回显内部异常。
4. 头状态与数量矛盾（未分配却残留占用、已出库量、制造已有完成/不良/开始证据）不能伪装成功取消。既有NeedsDecision/PartiallyCancelled保留；已知部分结果可由调用人刷新核对后显式处理剩余项。
5. 最终字段来源版本/目录、部门映射、主体、租户期限重新检查，保持权限根至COMMIT。权限来源/身份失效终止整次事务，不能降级为子项best-effort。提交确认丢失或回滚不能确认返回503 `ORDER_CANCEL_OUTCOME_UNKNOWN`，不自动重放。
6. 库存通知及既有财务桥只在确认COMMIT后调用；失败记录/按既有best-effort语义处理，不把已提交取消报告成可重试写失败。禁用Bridge保留显式Skipped/部分结果，不宣称库存制造级联已执行。

表锁会短暂串行化这些表的写入，包括其他租户；这是当前软引用布局下的实际成本，并非细粒度跨租户并发方案。它证明本次提交时的集合一致性，不代表之后的独立MES/WMS创建、修改入口均已完成Owner接线。财务桥与通知仍是既有best-effort，不宣称持久投递、生产财务或端到端业务验收。

## 前端与范围
