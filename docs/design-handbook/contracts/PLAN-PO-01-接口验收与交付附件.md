## 2. 数据身份与来源资格

每个事实以 E/T 加 Owner/Id/Version/digest 精确定位。body 经严格闭合解析后 JCS→UTF-8→SHA-256；版本是 opaque string。catalog body、事实 admission、实际 producer pin、当前 head 及完整 manifest 必须相互吻合。AuthenticatedProducer/Role 从真实适配器认证和独立采用记录取得，不能从 body.producerStatus、前端 refs 或应用初始化脚本生成。事实版本不可变，同版本异 body 冲突，重放旧事实不倒退 current head。[CP18_SOURCE_GRAPH_ALGORITHM.md](D:/CP6-archives/consolidation-20261010/root-planning-cache/plan-po-cp22/members/CP18_SOURCE_GRAPH_ALGORITHM.md:7)。

## 4. 本地事务、幂等与未知提交

Planning capture 和应用写集在同一 SERIALIZABLE outer UoW 内持锁。Owner HTTP 在全部本地锁释放并确认 commit 后进行；返回后另开 fresh capture/CAS，因此不是跨 Owner 的分布式事务。first send 的实际 ClaimDispatch 必须将 outbox、原 OwnerCommand、当前 checkpoint 和 writer lease 一起锁定并将状态变为 MAY_HAVE_BEEN_SENT；后续未知状态只能查询原 key。结果集须全部读取、精确 typed root 核验、确认外层 commit 后才发响应；commit 确认缺失保持 UNKNOWN 并给原命令查询入口。[PLAN_PO_R3_CP18_RECOVERY_BOUNDARY_DESIGN.md](D:/CP6-archives/consolidation-20261010/root-planning-cache/plan-po-cp22/members/PLAN_PO_R3_CP18_RECOVERY_BOUNDARY_DESIGN.md:15)。
