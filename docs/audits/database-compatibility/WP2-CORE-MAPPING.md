### Targeted provider implementation review (not a repeated whole-task review)

Read-only review identified two material gaps outside the shared model metadata tests. The initial type mapper gave all string keys an OrdinalIgnoreCase comparer, including explicit BIN2/C keys; this could merge distinct case-sensitive database identities during EF tracking or relationship fixup. The initial `bpcharsend→bytea→convert_from` query rewrite also lost the input column's collation before concatenation/string-operation results were cast back to bpchar. A text fixture comparing only the same-case operation result could miss the latter. A third boundary finding concerned the range function's empty-string result: SQL NOT LIKE accepts an empty string, so the managed range predicate must return true before iterating scalars. Existing fixed-length hash/currency checks reject empty values independently; the finding did not demonstrate that those whole constraints accepted a bad value.

Root corrected the mapper by overriding property-based mapping lookup and cloning the custom mapping with a collation-specific key comparer, while retaining exact normal value comparison so case-only edits are saved. EF8 has no public `SetKeyValueComparer` mutator; no temporary key annotation was added. Raw-text query output restores column collation, and the range function returns true for an empty string. Final PG **46/46** includes that assertion; unchanged four consumer hashes permit reuse. Historical fresh33/33 and later actual application first/repeat retention are separate evidence, with sources in [implementation](WP2-IMPLEMENTATION.md). Expression collation derives from collatable inputs, so bytea conversion requires deliberate restoration. [PostgreSQL collation derivation](https://www.postgresql.org/docs/18/collation.html#COLLATION-CONCEPTS).

Frozen dictionaries prevent consumers from mutating this classification. No suffix or type-wide assumption establishes membership.

The supported fixed fields are ASCII hashes, tokens and currency codes under the current writer contracts below. `SpaceModel.LastMaterializedHash` and `SpaceModelVersion.ContentHash` can initially be empty; optional hashes can be NULL. The added ASCII storage check therefore must permit existing blanks and NULLs rather than impose a new universal 64-hex validation rule. Adapter integration must reject unknown fixed fields, any `nchar` field and a capacity mismatch. SQL Server mappings remain intact. This manifest provides static input-domain evidence; it does not independently prove migrated database behavior or every future caller's validation.

General Unicode fixed text remains outside this declaration. PostgreSQL `character(n)` pads to a character count, whereas the source SQL `char(n)` capacity uses CP936 bytes and `nchar(n)` uses UTF-16 units. A valid general SQL fixed-text value can therefore exceed the PG capacity check after PG adds spaces. A later general implementation needs storage without a character typmod and explicit padding in the source storage units; it cannot inherit this ASCII classification. [PostgreSQL character types](https://www.postgresql.org/docs/18/datatype-character.html).
