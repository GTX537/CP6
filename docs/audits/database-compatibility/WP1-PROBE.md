## Experiment boundaries

- Use only a task-owner-created, loopback `CP6Compat_...` database. Before DDL, `CP6_TEST_DATABASE_OWNER` must match SQL Server database properties `CP6CompatTask=DB-COMPAT-01-WP1` / `CP6CompatOwner`, or PostgreSQL's `DB-COMPAT-01-WP1:<owner>` database comment. Every run creates a unique marked schema; cleanup checks database and exact schema owner identity and removes explicit temporary objects without `CASCADE`. Root owns database cleanup. No business databases, roles, authentication configuration, services or deployed application are modified.
- Red control deliberately omits a stale token predicate and must fail with lost-update evidence; preserve that failure. Positive checks require actual database writes, affected-row checks, direct token readback and independent-connection observations. Application candidate gaps are expected rejection evidence, not synthetic success.
- Database token candidate: SQL Server native rowversion; PostgreSQL `bytea` 8 bytes populated on every insert/update by a managed trigger using a private sequence. Encoding remains `byte[]` / 12-character Base64. Generated bytes are opaque and are never converted to identity watermarks.
- Identity candidate: tenant-bound durable generation row changes in the same transaction as directory mutation. Stable numeric position plus generation and tenant bind each **fixture** cursor. A short page transaction sees rows and generation together; later changed generation explicitly rejects continuation. Persisted event-version tombstones reject duplicate/older grants. New processes verify stable continuation with exactly two rows ordered `3,4`, and revocation invalidation. The actual reader/API still uses string `Boundary`, opaque `NextCursor` and `LastAggregate`; WP3 must preserve their semantics and use a new protector purpose/version discriminator to reject legacy rowversion-boundary cursors. No actual reader/API migration or cursor compatibility pass is claimed here.
- Transactions: representative entity SaveChanges in two EF contexts plus Dapper; separately the actual CP6Context, SpaceContext, IdentityMessagingContext and ErpIntegrationContext use production provider configuration and shared DatabaseFacade connection/transaction to write only limited owned tables. These are not full migration or business-entity compatibility tests.
- Platform: actual 0.10.2 package through its public store/processor APIs and original model. Consumer PostgreSQL override and generated token triggers are experimental managed migration objects. Both suites cover all four entities, bulk claim, stale loaded row, newer lease, retry/dead-letter/requeue, duplicate/order/checkpoint races, handler rollback and retention. PostgreSQL forced real SQLSTATE 40001 and recorded actual package retry behavior.

## Remaining WP1 limits

The evidence supports SQL Server native rowversion plus PostgreSQL managed database-generated 8-byte bytea tokens and the separately transactional tenant-generation paging mechanism. The parent WP1 decision owns the final freeze and the complete writer/model/DDL installation inventory. Full four-context models/migrations, actual API/identity paging wiring, true event transport, tombstone purge policy, deployed seeds/maintenance tooling audit, and later two-database business acceptance remain outside this limited harness. These dual-database limited experiments alone do not authorize WP2 until the parent decision closes dependency/provider/design-time/schema decisions and all remaining WP1 requirements.
