## Strengths and correctness analysis

1. **The retry boundary owns the complete transaction protocol.** `SpaceValidationInfrastructure.cs:111-129` retries the extracted `RequestValidationAttemptAsync`; the attempt's `await using` at lines 137-141 completes before its faulted task reaches the outer catch. This avoids attempting recovery while the failed transaction still owns a lock or Serializable snapshot. The explicit `CurrentTransaction` check at lines 124-125 refuses unsafe recovery if disposal did not clear ownership.
2. **Recovery refreshes both database and tracked state.** `ChangeTracker.Clear()` precedes each subsequent attempt, including after an exhausted classified failure. The attempt repeats transaction creation, tenant/version resource-lock acquisition, tenant-filtered scope reads, site write authorization, current version-state validation, capability profile, full content snapshot/hash, and reusable-run lookup. It therefore does not reuse the failed transaction's version/run entities or snapshot-derived decisions.
3. **Retry classification is appropriately narrow.** Only `DatabaseFailureClassifier.Classify(exception).CanRetryTransaction` enters recovery. The inspected classifier walks nested exception wrappers and admits Deadlock/SerializationFailure; unique, foreign-key, check, optimistic-concurrency, cancellation and unknown failures remain outside default retry. This handles the actual Npgsql execution-strategy -> DbUpdateException -> native 40001 wrapper in the RED artifact. The preexisting Space lock adapter still maps SQL Server application-lock `-3` to its busy result; this change does not alter that contract.
4. **Attempts and cancellation are bounded.** The service allows exactly three total attempts, checks the supplied cancellation token before each attempt, passes it through database/profile/snapshot/save/commit/DTO work, and rethrows the last classified exception when exhausted. Unknown exceptions propagate without clearing/retrying. The cancellation control cancels at a classified failed save and verifies that no second attempt starts.
5. **Caller ownership is protected.** The relational guard at lines 95-108 rejects an existing EF transaction, ambient transaction, explicit enlisted transaction, or pending tracked change before beginning its own transaction. This prevents service saves or recovery clears from accepting/discarding preexisting unsaved caller writes. This follows the already-established `SpaceMappingSaveTransaction` ownership pattern. The controller directly invokes the service with the scoped SpaceContext; inspected publish-test helper callers also create clean request contexts. The audit filter writes through `SpaceAuditWriter`'s separate context factory, rather than placing pending writes on the service context.
6. **Public and access semantics remain intact.** `CreateSpaceValidationResponse` and controller HTTP 202 behavior are unchanged. A recovered waiter runs the existing reuse path and returns the winner's validation with `Reused=true`, while the successful creator returns `Reused=false`. Version/job/run writes remain in one owned transaction. The model/version/run queries retain tenant filters and composite tenant foreign keys; the lock identity includes tenant/version. Site write authorization is re-executed in each attempt before profile/snapshot/reuse work. No schema, dependency, authorization bypass, or external write protocol was added.
7. **The central regression establishes a real native conflict.** The first request is held in its profile provider after acquiring the production lock. The second request's `DbTransactionInterceptor` executes `SELECT pg_catalog.txid_current_snapshot()::text` within its real Serializable transaction before releasing the first. It does not replace production lock acquisition. The PostgreSQL assertion requires an observed native `40001`, both calls must return the same validation with exactly one reused result, and an independent context must observe exactly one run/job and a Validating version. Cleanup releases the gate, cancels its owned budget, and drains both requests before disposing their contexts.
8. **Control tests distinguish synthetic inputs from native evidence.** Added preservation tests verify pending caller state and a usable caller-owned transaction. Unknown/cancellation/exhaustion controls deliberately inject a typed retryable exception before writes and verify one/one/three attempts, transaction release, empty committed run/job tables, and unchanged Draft state. Their source comment explicitly distinguishes them from the actual PostgreSQL serialization regression. Existing pass/reuse/state/tenant/read and incomplete-rack tests remain present; helpers retain both selected native-provider and legacy SQL Server paths while adding interceptors.
