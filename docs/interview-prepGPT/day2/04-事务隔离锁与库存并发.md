# 04 · 事务、隔离、锁与库存并发

## 1. ACID 用失败场景解释

- Atomicity：库存扣减和流水要么都成，要么都不成。
- Consistency：提交前后业务不变量成立；数据库不自动理解所有业务一致性。
- Isolation：并发事务的中间状态互相如何可见。
- Durability：提交成功后，系统在承诺的故障模型下保留结果。

ACID 不是“开启事务就绝对安全”。隔离级别、约束、应用逻辑和外部副作用仍决定结果。

## 2. 典型并发现象

| 现象 | 描述 |
|---|---|
| Dirty read | 读到未提交数据 |
| Non-repeatable read | 同事务两次读同一行值不同 |
| Phantom | 同一范围两次查询行集合变化 |
| Lost update | 后写覆盖先写，更新丢失 |
| Write skew | 两事务各自检查后写不同记录，合起来破坏约束 |

面试不应只背前三个。库存和排班常见 lost update/write skew。

## 3. SQL Server 隔离级别

| 级别 | 读取行为概念 | 代价/边界 |
|---|---|---|
| Read Uncommitted | 可读未提交 | 脏读、重复/漏行等 |
| Read Committed | 默认常见；语句级已提交 | 同事务多语句仍可能变化 |
| Repeatable Read | 已读行保持 | 范围仍可能出现幻行，锁更久 |
| Serializable | 范围串行化 | 阻塞/死锁/吞吐代价高 |
| Snapshot | 事务级版本快照 | tempdb 版本存储、写冲突 |

SQL Server 还有 `READ_COMMITTED_SNAPSHOT`，让 Read Committed 使用行版本，和显式 Snapshot 事务语义不同。回答要说明数据库配置会改变行为。

## 4. 锁的基本维度

- Shared：读。
- Exclusive：写。
- Update：为读后写降低部分转换死锁。
- Intent：表/页层表示下层锁意图。
- Key-range：Serializable 范围保护。

锁粒度可为行/键、页、表；SQL Server 可能锁升级。NOLOCK 不是“无锁”，它主要等价读未提交，并可能读到不一致结果。

## 5. 死锁

死锁是循环等待，SQL Server 选 victim 回滚一个事务。

处理步骤：

1. 获取 deadlock graph，不凭感觉。
2. 找资源和持锁顺序。
3. 统一访问顺序。
4. 缩短事务，补合适索引减少锁范围。
5. 必要时用版本隔离。
6. 对可重试事务做有界、带抖动重试。

只“把超时调大”不解决死锁。

## 6. 库存扣减的错误写法

```text
SELECT AvailableQty
if enough:
  UPDATE AvailableQty = old - request
```

两个事务都读到 10，各扣 8，可能覆盖或变负。

## 7. 方案 A：条件原子 UPDATE

```sql
UPDATE Stock
SET PhysicalQty = PhysicalQty - @qty,
    AvailableQty = AvailableQty - @qty
WHERE TenantId = @tenantId
  AND Id = @id
  AND AvailableQty >= @qty;

IF @@ROWCOUNT = 0
    THROW 50001, 'INSUFFICIENT_OR_CONFLICT', 1;
```

优点：单语句、数据库原子判断。边界：需区分不存在与不足；还要写流水，放同事务；复杂分配规则会让 SQL 膨胀。

## 8. 方案 B：RowVersion 乐观并发

```sql
UPDATE Stock
SET AvailableQty = @newQty
WHERE Id = @id AND RowVersion = @oldVersion;
```

影响 0 行表示冲突。适合冲突不高、业务可重新计算。高热点 SKU 会造成大量失败和重试。

## 9. 方案 C：悲观锁

事务内使用更新锁/行锁提示读取库存，再修改。优点是冲突事务等待；缺点是阻塞、死锁和吞吐下降，锁提示还可能被优化器/粒度条件影响。

## 10. 方案 D：串行化热点

按 SKU/库位分区把变动写入单线程消费者。可显著降低数据库写冲突，但增加队列、分区、幂等、延迟和故障恢复复杂度。

## 11. CP6 当前写路径评估

`StockMovementService.ApplyAsync`：

- 事务包住 Stock 和 StockTransaction。
- 读取/创建库存行。
- 根据交易类型计算数量。
- 检查负库存策略。
- 保存并提交。

文档声明 RowVersion 乐观并发，面试前还要核对实体和迁移是否实际配置 `[Timestamp]`/`IsRowVersion()`。不要只凭注释断言。

### 并发新行

两事务都没查到库存行，都 INSERT。正确性依赖业务唯一索引；一个成功、一个唯一冲突，失败方再读取并重试。没有唯一约束时会产生双库存行。

## 12. 移库两腿问题

当前 `MoveAsync`：来源 `ApplyAsync(-qty)` 提交，再目标 `ApplyAsync(+qty)` 提交。目标失败时来源已扣，形成悬挂。

改进选项：

1. 一个方法、一个 DbContext 事务内同时锁定/更新两行并写两条流水。
2. 使用 MoveHeader 状态机，允许补偿和重放。
3. 事件驱动 Saga，适合跨库/跨服务，但复杂度更高。

单数据库同服务优先选一个本地事务。若两地属于不同系统才引入 Saga。

## 13. 外部副作用与 Outbox

数据库 commit 后再发消息：commit 成功、发布失败会丢事件。先发消息再 commit：消息成功、数据库回滚会产生幽灵事件。

Outbox：

```text
同一数据库事务：业务行 + OutboxEvent
commit
后台发布器读取未发布事件
发送消息
标记已发布
消费者幂等
```

Outbox 解决原子记录“应该发什么”，不自动解决消息重复；消费者仍要幂等。

## 14. 事务要短

不要在数据库事务中等待用户输入、调用慢 HTTP、做大文件处理。事务越长，锁和版本存储占用越大。

常见拆法：

- 事务前完成纯计算/输入校验。
- 事务内只做权威读取、校验、写入。
- 事务后做可重试副作用。

## 15. 重试安全

只有当操作幂等或能检测重复时才重试：

- 使用请求幂等键。
- 业务唯一约束。
- 流水号/事件 Id 去重。
- 不在重试体内重复发邮件/扣款。

EF 的 transient retry strategy 与手工事务组合时要按官方模式执行整个事务委托，避免部分重试。

## 高频陷阱

1. Read Committed 防止所有并发异常。
2. NOLOCK 只是更快且结果最终正确。
3. Serializable 没有代价。
4. 发生死锁把超时加大即可。
5. RowVersion 冲突永远安全自动重试。
6. Outbox 提供绝对恰好一次。
