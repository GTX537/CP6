# 10 · 库存查询全栈闭环

这是 Day 1 和 Day 2 的汇合实验。目标是把一个按钮点击讲到 SQL Server，再从 JSON 讲回界面。

## 1. 文件证据

前端：

- `cp6.web/src/views/wms/StockQueryView.vue`
- `cp6.web/src/api/wms/stock.ts`
- `cp6.web/src/api/http.ts`
- `cp6.web/src/components/templates/CpListPage.vue`
- `cp6.web/src/directives/permission.ts`

后端：

- `CP6.WebApi/Controllers/Wms/StockController.cs`
- `CP6.WebApi/Program.cs`
- `CP6.Core/EFDbContext/CP6Context.cs`
- `CP6.Entity/DomainModels/Wms/Stock.cs`

## 2. 用户动作到请求参数

页面的 `CpListPage` 收集分页和筛选，调用 `fetchList`：

```text
page + size + filters
→ 组装 q
→ 加 hasStockOnly
→ stockApi.search(q)
```

`fetchList` 把组件模板的通用协议转换为 WMS 库存 API 协议，再把响应转换回 `{ rows, total }`。它是一个适配层。

## 3. API 模块与 axios

API 模块提供业务命名方法，axios 实例提供横切能力：

- `baseURL=/api`。
- 10 秒超时。
- 携带 httpOnly Cookie。
- 写请求注入 CSRF。
- 401 refresh single-flight。
- 错误码 i18n。

库存查询是 GET，不注入 CSRF 头。认证 Cookie由浏览器自动携带。

## 4. Vite 代理与生产代理

开发时 `/api` 通常由 Vite 代理到后端；生产可能由同域反向代理转发。前端不硬编码后端完整域名，减少环境差异和 CORS 复杂度。

面试要说“具体代理配置以 vite.config/部署配置为准”，不要假设所有环境拓扑相同。

## 5. ASP.NET Core 管道

请求进入：metrics → authentication → tenant → localization → exception → CSRF/must-change-password → authorization → Controller。

库存 Controller 有 `[Authorize]`，查询至少需要登录。细粒度查询权限是否另有全局/资源机制，要以当前端点特性与权限体系核对，不能把写端点的 `[RequirePermission]` 自动推到 GET。

## 6. 参数绑定

Controller 从 query string 绑定：

```text
warehouseCd, locationCd, productCd, lotNo,
ownerType, ownerCd, hasStockOnly,
page=1, pageSize=50
```

建议边界：

- page 至少 1。
- pageSize 限定 1～上限。
- code 长度与格式校验。
- ownerType 白名单。

当前签名给默认值，但不代表所有边界已验证。

## 7. EF 查询组合

```text
Stocks.AsNoTracking()
→ 软删条件
→ 按非空参数追加 Where
→ CountAsync
→ 复合排序
→ Skip/Take
→ ToListAsync
```

多租户过滤由 `CP6Context` 全局查询过滤器自动附加，不出现在 Controller 代码里。这是横切机制的价值，也意味着读代码时必须知道“隐式 SQL 条件”。

## 8. 可能的 SQL 形态

实际参数和 EF 版本会影响 SQL，概念形态：

```sql
SELECT COUNT(*)
FROM T_Stock s
WHERE s.TenantId = @tenant
  AND s.IsDeleted = 0
  AND s.WarehouseCd = @warehouse
  AND s.PhysicalQty <> 0;

SELECT ...
FROM T_Stock s
WHERE ...
ORDER BY s.WarehouseCd, s.LocationCd, s.ProductCd, s.LotNo
OFFSET @skip ROWS FETCH NEXT @take ROWS ONLY;
```

使用 `ToQueryString()`/EF 日志核对，不把推测 SQL 当逐字符事实。

## 9. 两次查询的一致性

total 和 items 分两次 SQL。并发写入时可能出现：total=100，但列表读取时已经 101/99。多数列表允许这种最终一致视图；若要求严格快照，可在 snapshot 事务中执行，但会增加成本。

这类取舍是很好的深挖点。

## 10. 排序与分页

当前排序四个业务列，但若组合键在当前租户内确实唯一，排序稳定；若没有唯一约束或存在重复，还应加 Id tiebreaker。

索引候选应从真实过滤组合和排序频率设计，不为每种可选条件建一个索引。可考虑以 TenantId、WarehouseCd 开头的高频查询索引，再用 Query Store验证。

## 11. JSON 返回

返回结构：

```json
{
  "code": 0,
  "message": "OK",
  "data": {
    "total": 123,
    "page": 1,
    "pageSize": 50,
    "items": []
  }
}
```

axios 响应拦截器已经返回 `response.data`，所以页面拿到的是业务 envelope，不是 AxiosResponse。类型定义必须反映这一层，否则容易出现 `.data.data` 混乱。

## 12. 回到 Vue 渲染

`fetchList` 返回 `{ rows, total }` 给 `CpListPage`。列表模板更新响应式状态，Vue 重新渲染：

- 普通列通过 columns 配置。
- AvailableQty 通过 slot，负数加样式。
- QC 用 tag。
- action slot 放历史与设置按钮。

formatQty 限定数量显示精度；显示精度不应反向改变数据库精度。

## 13. 历史查询支线

点击历史：

```text
row.id
→ GET /stock/{id}/history?days=365
→ 先查库存身份
→ 按组合键查交易
→ 弹窗显示
```

风险：库存组合键若后来变更，按当前键查历史可能漏掉旧键；更稳的流水通常保存稳定 StockId 或变更链路。是否需要取决于领域设计。

## 14. QC 写支线

QC 按钮有 `v-permission`；后端写端点应有对应权限。前端提交时：loading、防空、错误、成功后更新本地对象并 reload。

同时本地更新和 reload 有一点重复，但能即时反馈并以服务器结果校准。网络慢时要避免双击。

## 15. 故障定位演练

### 症状 A：列表一直空

按层检查：

1. 浏览器 Network 是否发请求，query 是否正确。
2. 401/403/200，响应 envelope 是否匹配。
3. 动态路由/页面是否真正加载。
4. Controller 参数绑定。
5. 当前 TenantId 是否正确。
6. 全局过滤 + IsDeleted + hasStockOnly 是否共同过滤。
7. 直接执行等价 SQL。

### 症状 B：总数正确，翻页重复/漏行

检查排序是否唯一、并发数据变化、前端页码是否重置、后端 skip 计算、数据库隔离语义。

### 症状 C：查询很慢

检查：请求时间分段、EF SQL、实际计划、IO、索引、`Contains('%x%')`、深分页、返回列大小和前端渲染。

## 16. 三分钟参考口述

> 用户在库存页输入仓库或产品条件后，通用 `CpListPage` 把分页和筛选交给页面的 `fetchList`。页面把它适配成库存 API 参数，通过统一 axios 实例发 GET `/api/wms/stock`。当前认证令牌由 httpOnly Cookie 携带，所以浏览器自动带凭证；这是读请求，不需要 CSRF 头。
>
> 后端先经过指标、认证、租户、本地化和授权管道，再进入 `StockController.Search`。Controller 从 query string 绑定条件，基于 `Stocks.AsNoTracking()` 创建 IQueryable。多租户条件由 DbContext 的全局过滤器隐式附加，Controller 再按非空参数追加 Where。直到 `CountAsync` 执行总数 SQL，排序、Skip、Take、ToListAsync 执行分页 SQL，所以过滤和分页在 SQL Server，而不是内存。
>
> JSON 返回后，axios 拦截器已经解包到业务 envelope，页面转换成 `{rows,total}` 给列表模板。常规列用配置渲染，数量、QC 和操作列用 slot。这个链路的边界有三点：total 和 items 是两次查询，不是严格快照；产品 Contains 可能不易走普通索引；分页排序必须稳定。我会用 EF SQL 日志、Query Store/实际计划和浏览器 Network 分层定位问题。
