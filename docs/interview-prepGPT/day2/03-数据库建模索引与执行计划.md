# 03 · 数据库建模、索引与执行计划

## 1. 从业务不变量开始建模

不要先画表。先列：

- 一个对象的身份是什么？
- 哪些字段必填？
- 哪些组合必须唯一？
- 生命周期和状态如何变化？
- 谁引用它？删除时怎么办？
- 是否按租户隔离？
- 哪些历史必须保留？

例如库存组合业务键：租户、仓库、库位、产品、批次。数据库应有相应唯一约束，否则并发可创建两条“同一库存”。

## 2. 主键与业务键

代理主键 Guid 便于跨系统生成和关联，但不替代业务唯一约束。

```text
PK: Id
UK: (TenantId, WarehouseCd, LocationCd, ProductCd, LotNo)
```

随机 GUID 作为聚集键可能导致页分裂和碎片；可选择顺序 Guid、非聚集 PK + 其他聚集键，或保持现状并用实际写入/碎片数据评估。

## 3. 范式

- 1NF：列值原子，按业务查询需求解释“原子”。
- 2NF：非键列依赖整个候选键。
- 3NF：非键列不传递依赖其他非键列。

范式减少重复和更新异常；反范式用额外一致性成本换读性能或历史快照。

CP6 `AvailableQty = PhysicalQty - AllocatedQty` 被物化，是反范式。好处是读取直接；风险是每个写入口必须同步三列。集中库存服务、约束/测试和对账可降低风险。

## 4. 数据类型

| 数据 | 建议考虑 | 风险 |
|---|---|---|
| 金额/数量 | decimal(p,s) | 精度、溢出、舍入 |
| 时间点 | datetime2 / UTC 约定 | 时区、精度 |
| 日期 | date | 不要混入时间 |
| 状态 | smallint/varchar + 约束 | 魔法值、演进 |
| 文本 | nvarchar(n) | 过宽、索引限制 |
| 布尔 | bit | 三态需求不要硬塞 bool |

列宽不是越大越安全。它影响行大小、索引、内存授予和业务验证。

## 5. 约束是最后防线

| 约束 | 防什么 |
|---|---|
| NOT NULL | 缺失值 |
| CHECK | 无效范围/状态组合的一部分 |
| UNIQUE | 并发重复 |
| FOREIGN KEY | 孤儿引用 |
| DEFAULT | 缺省插入值；不是业务验证 |

应用检查提升错误体验，数据库约束覆盖所有写入口。两者不是替代关系。

## 6. 索引是什么

SQL Server 行存索引可用 B+ 树理解。索引键按序排列，叶层保存行定位或聚集键/数据本身。

- 聚集索引叶层就是数据行，表只能有一个聚集顺序。
- 非聚集索引叶层保存索引键、include 列和行定位信息。

索引不是“复制一列”，它有页、层级、统计和维护成本。

## 7. 复合索引列顺序

设计来自查询：

```sql
WHERE TenantId = @tenant
  AND WarehouseCd = @warehouse
  AND ProductCd = @product
ORDER BY TxnDateTime DESC, Id DESC
```

候选：

```text
(TenantId, WarehouseCd, ProductCd, TxnDateTime DESC, Id DESC)
INCLUDE (Qty, LotNo, LocationCd)
```

经验：等值过滤列通常在前，范围/排序列后。但列选择性、其他查询复用、统计和写成本都会改变选择。不要把“最左前缀”背成唯一算法。

## 8. 覆盖索引与 Key Lookup

非聚集索引找到键后，若缺少 SELECT 列，可能回聚集索引做 Key Lookup。少量行 lookup 很好；大量行随机 lookup 可能昂贵。

用 INCLUDE 覆盖可减少 lookup，但索引会变宽、写放大和缓存占用增加。先看实际执行次数和逻辑读。

## 9. SARGability

可搜索谓词让优化器利用索引范围。

不利：

```sql
WHERE CAST(TxnDateTime AS date) = @day
WHERE ProductCd LIKE '%ABC%'
WHERE ISNULL(OwnerCd, '') = @owner
```

改写：

```sql
WHERE TxnDateTime >= @day AND TxnDateTime < DATEADD(day,1,@day)
WHERE OwnerCd = @owner OR (@owner = '' AND OwnerCd IS NULL)
```

包含匹配可能需要全文索引、搜索引擎或专用反向/片段方案，普通索引无法神奇解决。

## 10. 统计信息与基数估计

优化器根据统计估算各算子行数。估算错误会选错 join 类型、内存授予和访问路径。

排查重点：

- Estimated Rows 与 Actual Rows 差异。
- 统计是否过期。
- 数据倾斜和参数敏感。
- 表变量/临时表统计差异。
- 多列相关性。

## 11. 执行计划常见算子

| 算子 | 含义 | 看到时问什么 |
|---|---|---|
| Index Seek | 按范围定位 | seek 后实际读取多少行？残余谓词？ |
| Index/Table Scan | 扫描 | 表小是否合理？过滤选择性？ |
| Key Lookup | 回表 | 执行次数 × 单次成本？ |
| Sort | 排序 | 是否溢写 tempdb？索引能否支持？ |
| Nested Loops | 外侧每行查内侧 | 外侧实际行是否很少？ |
| Hash Match | 构建哈希处理大集合 | 内存授予、溢写？ |
| Merge Join | 两侧有序合并 | 排序来源与重复键？ |

不要把 Scan 一律当坏。读取表大部分行时 scan 可能最优；小表 scan 成本也低。

## 12. 读执行计划的顺序

1. 先确认实际返回行数和耗时。
2. 找最高成本仅作线索，不当真相。
3. 比较估算与实际行数。
4. 看数据从哪里大量膨胀。
5. 看警告：spill、隐式转换、缺统计。
6. 配合 `SET STATISTICS IO, TIME ON`。
7. 修改后在代表性参数下复测。

## 13. 参数嗅探/参数敏感

同一 SQL 的最佳计划可能随参数差异巨大。首次/缓存计划适合小客户，却不适合大客户。

方案包括更新统计、重写查询、`OPTION(RECOMPILE)`、`OPTIMIZE FOR`、动态分支、SQL Server 参数敏感计划功能。每种都需证据，不能先贴“参数嗅探”标签。

## 14. 多租户索引

共享表常以 TenantId 为过滤前缀，但如果平台管理员跨租户报表是关键查询，可能需要另一套索引。一个索引无法完美服务所有访问模式。

唯一索引尤为关键：租户内唯一通常 `UNIQUE(TenantId, Code)`。过滤唯一索引要考虑 NULL 语义。

## 15. 索引写成本

每个 INSERT/UPDATE/DELETE 都可能维护多个索引。过多索引带来：

- 写延迟。
- 日志量。
- 锁和页分裂。
- 缓存占用。
- 维护时间。

索引治理要用使用统计和真实工作负载，不只依赖“缺失索引建议”。

## LAB：执行计划对比

选择本地大于 1 万行的表：

1. 运行一个按租户+业务码过滤的查询。
2. 记录实际计划、logical reads、elapsed time。
3. 新建候选索引。
4. 重跑并比较。
5. 记录写成本与索引大小。
6. 在实验环境删除候选索引。

验收不是“从 scan 变 seek”，而是解释为什么读页、行数估计和总耗时变化。

## 高频陷阱

1. 每张表只能有一个索引。
2. Seek 一定比 Scan 快。
3. 高选择性列永远放复合索引第一位。
4. INCLUDE 没有写成本。
5. 缺失索引建议可以直接全建。
6. 实际计划中的 cost 百分比等于真实耗时。
