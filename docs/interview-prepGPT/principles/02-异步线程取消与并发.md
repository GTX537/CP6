# 02 · 异步、线程、取消与并发

异步最容易被学成语法替换：方法加 `async`，调用加 `await`。真正需要掌握的是等待期间线程发生什么、多个任务何时并发、取消怎样传播、异常在哪里重新抛出，以及共享资源能不能承受并发。

## 1. 先分清三件事

```text
异步：等待结果时不必占住当前执行流
并发：多个工作在时间上重叠推进
并行：多个工作同时在多个核心执行
```

一个网络请求可异步但不并行占 CPU；四个 CPU 计算用 Parallel 可并行但未必涉及 async。

## 2. I/O 异步为什么能提高 Web 吞吐

同步数据库调用等待网络/磁盘时，线程阻塞。Web 服务器要处理更多请求就需要更多线程，带来栈内存、上下文切换和线程池压力。

异步 I/O：

```text
线程发起数据库命令
→ OS/驱动登记完成通知
→ await 返回未完成 Task，当前线程回线程池
→ I/O 完成，continuation 排队
→ 某线程继续执行 await 后代码
```

不是“await 新开线程帮你等”。

## 3. async 方法怎样执行

调用 async 方法时，代码同步运行到第一个尚未完成的 await。编译器把局部状态和继续位置转换为状态机。

概念伪代码：

```text
state = -1
MoveNext:
  try
    if state == -1:
      task = OperationAsync()
      if not completed:
        state = 0
        register continuation MoveNext
        return
    if state == 0:
      get result (may throw)
    complete Task
  catch ex:
    fault Task with ex
```

这解释：

- await 前异常可能同步发生，但 async Task 方法通常把异常放进返回 Task。
- await 恢复时 `GetResult` 重新抛出异常。
- 局部变量跨 await 需要保存在状态机。

## 4. Task 不是 Thread

Task 表示一个最终完成/失败/取消的工作，不保证有专用线程。多个 Task 可共享线程池；I/O Task 等待时不占线程；`Task.FromResult` 完全不需要线程。

线程是执行资源，Task 是工作/结果抽象。

## 5. CPU-bound 与 I/O-bound

I/O：直接调用真正异步 API：

```csharp
await db.Stocks.ToListAsync(ct);
await httpClient.SendAsync(request, ct);
```

CPU：Web 请求里不要为了“异步”把普通小计算包 `Task.Run`。大型 CPU 工作可能移到后台队列/专用服务；桌面 UI 可 Task.Run 避免阻塞界面。

`Task.Run(() => syncDatabaseCall())` 只是换一个线程阻塞，不会获得可扩展 I/O。

## 6. await 是顺序，创建任务才可能并发

串行：

```csharp
var a = await LoadAAsync(ct);
var b = await LoadBAsync(ct);
```

若互不依赖：

```csharp
var taskA = LoadAAsync(ct);
var taskB = LoadBAsync(ct);
await Task.WhenAll(taskA, taskB);
```

但不能看到两个 await 就盲目 WhenAll：

- 是否共享同一个 DbContext？不能并发操作。
- 下游连接池/限流能承受吗？
- 结果是否有依赖？
- 部分失败怎样处理？
- 是否需要保持顺序？

## 7. DbContext 为什么不能并发

DbContext 包含 ChangeTracker、连接和内部状态，不是线程安全。以下会抛错或产生未定义状态：

```csharp
await Task.WhenAll(
    db.Stocks.CountAsync(ct),
    db.Orders.CountAsync(ct));
```

选择：

- 同一 context 串行。
- 每个并发任务创建独立 scope/context。
- 合并成一条 SQL/投影。

独立 context 也会增加连接和数据库并发，仍需限流。

## 8. `Task.WhenAll` 的异常

WhenAll 等所有任务结束。await WhenAll 会抛异常；聚合 Task 内可包含多个异常。调试时不要只记录第一条而丢失其他失败。

如果业务允许部分成功，应把每项结果建模：

```csharp
record ItemResult(string Id, bool Success, string? ErrorCode);
```

不要用一个大 try/catch 把失败项都变成“批处理成功”。

## 9. 取消是协作，不是强杀

CancellationToken 只是信号。调用链每一层都要：

- 接收 token。
- 传给下游 I/O。
- 长循环定期检查。
- 在不可中断临界区定义策略。

```csharp
public async Task<Result> SearchAsync(Query q, CancellationToken ct)
{
    return await db.Stocks
        .Where(...)
        .ToListAsync(ct);
}
```

ASP.NET Core action 参数 token 通常绑定 `RequestAborted`。浏览器断开后，数据库 provider若支持可收到取消。

## 10. 取消与业务提交边界

取消不是任何时刻都能安全停：

```text
提交前：通常可取消并回滚
Commit 进行中：结果可能未知
Commit 后：业务已成功，不能因通知取消说失败
```

事务提交后执行的通知可以使用独立短超时/后台 outbox，而不是继续盲目使用已经取消的 request token。

写请求要幂等，处理“客户端不知道 commit 是否成功”的重试。

## 11. 正确处理 OperationCanceledException

只把与预期 token 对应的取消当正常：

```csharp
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    throw;
}
```

不要把所有 `TaskCanceledException` 都当用户取消；HttpClient 超时也可能表现相似，需要结合自己的 timeout token/异常信息区分。

## 12. 超时与取消的组合

```csharp
using var timeout = new CancellationTokenSource(TimeSpan.FromSeconds(3));
using var linked = CancellationTokenSource.CreateLinkedTokenSource(
    requestToken, timeout.Token);

await CallAsync(linked.Token);
```

完成后根据哪个 token 被取消决定返回：用户断开不必写错误响应；服务超时可转 504/稳定错误。

## 13. 并发限流

对 10,000 项直接 WhenAll 会同时创建大量请求、连接和内存。使用 `SemaphoreSlim`：

```csharp
using var gate = new SemaphoreSlim(8);
var tasks = items.Select(async item =>
{
    await gate.WaitAsync(ct);
    try { return await ProcessAsync(item, ct); }
    finally { gate.Release(); }
});
await Task.WhenAll(tasks);
```

一定在 finally 释放。并发度不是越高越快，应依据下游容量、连接池和延迟测量。

`.NET` 的 `Parallel.ForEachAsync` 也可限制并发，仍要定义错误、取消和结果收集。

## 14. 竞态与原子性

```csharp
if (!cache.ContainsKey(key))
    cache[key] = Create();
```

即使 cache 是 ConcurrentDictionary，这个“先检查后写”复合动作也可能竞态。使用 `GetOrAdd`，但 value factory 可能执行多次，只有一个结果被采用；factory 若有副作用仍需处理。

数据库的“先查余额再更新”同样是复合竞态，需要 rowversion、条件 UPDATE 或锁。

## 15. `lock` 与 `SemaphoreSlim`

`lock` 保护进程内短同步临界区，不能在其内部 await。

异步互斥：

```csharp
await gate.WaitAsync(ct);
try { await CriticalAsync(ct); }
finally { gate.Release(); }
```

进程内锁不能保护多实例部署的共享数据库。跨实例用数据库约束/锁、分布式锁或幂等设计，并理解租约失效。

## 16. `async void` 的边界

事件处理器可能必须 async void；普通业务方法应返回 Task。async void 无法 await，异常不进入调用者 Task，测试和生命周期难控制。

```csharp
async void Button_Click(...)
{
    try { await SaveAsync(); }
    catch (Exception ex) { ShowError(ex); }
}
```

Web/service 代码不要 fire-and-forget 一个 Task 后丢引用。使用受宿主管理的后台队列。

## 17. SynchronizationContext 与死锁

传统 UI/ASP.NET 会捕获上下文，让 await 后回原线程。UI 线程同步 `.Result` 阻塞，同时 continuation 等待 UI 线程，形成死锁。

ASP.NET Core 默认没有经典请求 SynchronizationContext，但 `.Result/.Wait` 仍会阻塞线程、造成吞吐下降和线程池饥饿。结论不是“Core 里随便同步等”。

库代码的 `ConfigureAwait(false)` 可避免捕获上下文；应用层通常不必机械添加，先理解运行环境。

## 18. ValueTask 不要滥用

ValueTask 可减少高频同步完成路径的 Task 分配，但使用更复杂：通常只能 await 一次，不能随意缓存/多次组合。公开 API 默认 Task，只有性能测量证明分配是热点且同步完成常见时再用 ValueTask。

## 19. 异步流

`IAsyncEnumerable<T>` 让数据边到边处理：

```csharp
await foreach (var row in StreamRows(ct).WithCancellation(ct))
{
    await WriteAsync(row, ct);
}
```

适合大结果、流式导出；注意 DbContext/连接会在整个枚举期间保持，消费者太慢会占连接。异常可能在枚举中途发生，输出已部分发送。

## 20. 后台服务与 scope

BackgroundService 通常是 singleton，不能长期持有 scoped DbContext。用 `IServiceScopeFactory` 每次任务/消息创建 scope。

多租户任务还要先设 scoped tenant，再解析/使用 Context。取消时让 `OperationCanceledException` 上抛完成正常停止，其他租户异常按策略隔离并告警。

## 21. 诊断线程池饥饿

症状：CPU 不一定高，但请求延迟上升，线程数持续增加，队列长度高。常见原因：同步数据库/HTTP、`.Result`、长阻塞放线程池、锁争用。

证据工具：dotnet-counters、dotnet-trace、日志耗时、线程 dump。不要仅凭看到 async 关键字排除阻塞。

## 22. 必做实验

1. 比较 20 个 `Task.Delay` 串行、无限并发和限 4 并发耗时。
2. 同一 DbContext 并发两查询，记录异常；再用两个 scope 验证。
3. 取消 token 不传到最内层 Delay/SQL，观察取消失效。
4. 创建两个并发扣减，稳定复现 lost update。
5. 在 commit 后通知处取消，讨论应该返回成功还是失败。
6. 用 10,000 个任务观察无限并发的内存/连接压力。
