# 00 · 开发者学习法与证据记录

很多技术资料的问题不是“知识点太少”，而是把学习变成了浏览。浏览时每句话都觉得熟悉，关掉页面后却无法写代码、无法排错，也无法回答面试官的第二个“为什么”。开发者真正需要的是可检索的心智模型：看到症状能联想到原因，看到代码能预测行为，遇到异常能选择下一条证据。

本章先建立一套贯穿全书的练法。后面所有章节都按这套方法执行。

## 1. 掌握不是“我看懂了”

把掌握程度分成六级：

| 等级 | 表现 | 例子 |
|---|---|---|
| 0 · 见过 | 认得名词 | 知道 `AsNoTracking` 是 EF Core API |
| 1 · 能复述 | 能背定义 | 能说它不跟踪实体 |
| 2 · 能预测 | 给代码能猜结果 | 能判断修改查询结果后是否会被保存 |
| 3 · 能实现 | 不看答案能写 | 能在查询端点正确使用并投影 DTO |
| 4 · 能排错 | 失败时知道查什么 | 能区分跟踪冲突、并发异常和实体未附加 |
| 5 · 能取舍 | 能解释边界 | 知道只读查询该用，修改流程何时不能用 |

面试要求至少达到 3，项目深挖要求达到 4。上一版大多停在 1，所以读完没有抓手。

## 2. 一次学习循环必须留下四种证据

### 2.1 预测证据

运行前写下你认为会发生什么。不要只在心里想。

```text
实验：同一个 DbContext 并发执行两个查询
我的预测：两个 Task 都能完成，因为数据库可以并发
实际结果：InvalidOperationException
错因：把“数据库连接可并发”误当成“DbContext 实例线程安全”
新规则：一个 request scope 的 DbContext 不并发使用；并行任务各建 scope/context
```

预测错误不是失败，而是最有价值的记忆点。没有预测，实验结果只是又看了一遍答案。

### 2.2 运行证据

至少保留一种可复现输出：

- 单元测试名称与结果。
- HTTP 请求和响应状态。
- SQL 实际执行计划、logical reads 和耗时。
- 浏览器 Network 面板时间线。
- 日志中的 trace id 和异常类型。
- 断点处关键变量值。

“我试过，应该没问题”不算证据，因为别人无法复现，几天后的你也无法复现。

### 2.3 失败证据

正常路径通常最容易。开发者的价值主要体现在失败路径：

- 请求中途取消会不会继续占用数据库？
- 两个用户同时扣最后一件库存会怎样？
- Kafka 在处理完成、提交 offset 之前进程退出会怎样？
- refresh 请求同时收到十个 401 会怎样？
- 租户上下文缺失时系统是 fail-open 还是 fail-closed？

每个主题至少故意制造一次失败，并写下“系统看到什么、用户看到什么、数据留下什么”。

### 2.4 口述证据

用手机录音两分钟。回答必须包含：

```text
问题是什么
→ 当前怎么做
→ 为什么这么做
→ 代价和失败边界
→ CP6 证据
→ 如果继续演进会怎么改
```

如果回答只有定义，没有问题和代价，说明你还在背书。

## 3. 开发者读代码的五遍法

### 第一遍：只看入口和出口

先回答：谁调用它，返回给谁。不要马上钻进每个辅助函数。

以库存查询为例：

```text
页面搜索按钮
→ stockApi.search
→ GET /api/wms/stock
→ StockController.Search
→ SQL Server
→ PagedResult
→ CpListPage
```

第一遍的产物是一张不超过十个节点的图。

### 第二遍：标出状态和副作用

给每个步骤加标签：

- 只读还是写入？
- 本地状态还是共享状态？
- 是否访问网络、磁盘或数据库？
- 会不会抛异常？
- 有没有事务？
- 是否可能重试？

这一步能快速找到高风险位置。一个纯 DTO 映射错误通常只影响响应；一个事务外消息发送错误可能造成业务不一致。

### 第三遍：追边界数据

不要只看 happy path。拿一组具体数据走完整条链：

```text
tenant = T01
warehouseCd = W1
productCd = 空
page = 2
pageSize = 50
request 在 SQL 执行中取消
```

然后逐层问：空字符串在哪里被归一化？TenantId 从哪里来？页码是否可能为 0？取消令牌有没有传到底？

### 第四遍：找隐含契约

隐含契约没有写在方法签名里，却决定系统是否正确：

- 分页前排序必须稳定。
- 扣库存后不能为负。
- 租户数据不能跨边界出现。
- 业务成功但通知失败时不能回滚已提交事务。
- 重试不能重复产生财务单据。

把这些契约写成一句可测试的话，后面再找测试是否覆盖。

### 第五遍：反向设计测试

读完实现后不要问“作者测了什么”，先问“如果我要破坏它，会怎么做”。

库存查询可以从这些方向攻击：

- 空条件与超长条件。
- 同值排序导致跨页重复。
- 跨租户数据混入。
- 数据量扩大一千倍。
- 客户端快速连续查询产生乱序响应。
- 请求取消后数据库仍继续执行。

测试不是实现的附属品，而是你对隐含契约的可执行表达。

## 4. 每章 90 分钟标准训练

### 0～10 分钟：写问题，不看答案

例如本章研究异步：

```text
为什么 Web API 需要 async？
async 是否一定创建新线程？
取消发生后数据库查询会不会立刻停？
WhenAll 为什么可能把数据库打爆？
```

先写自己的答案并标置信心 0～100%。

### 10～30 分钟：读入口代码

只读真实入口、核心实现和一个测试。遇到名词先记录，不要每次都跳出去查，避免把调用链读碎。

### 30～50 分钟：补概念

回到 GPT 版 `principles/` 原理层查刚才阻塞理解的概念。只查当前问题需要的部分，并用自己的例子改写。

### 50～75 分钟：运行与故障注入

至少跑一条正常路径、一条失败路径。保存命令和输出，不要只截图结果不记输入。

### 75～85 分钟：闭卷重建

关掉材料，画调用链、写核心伪代码、回答最初的问题。

### 85～90 分钟：安排复习

只安排你答错的内容：当天晚上一次、第二天一次、三天后一次、七天后一次。已经稳定答对的内容不反复抄写。

## 6. 如何避免伪项目经验

代码库里存在某个设计，不代表你亲自设计、部署或处理过生产事故。证据分四级：

| 级别 | 可以怎么说 | 不可以怎么说 |
|---|---|---|
| 亲自完成 | “我实现并验证了……” | 省略团队协作，把全部功劳归自己 |
| 深度参与 | “我负责其中……并参与……” | “这个系统全是我做的” |
| 读码验证 | “我在当前代码里分析到……” | “我在线上处理过这个事故” |
| 方案推演 | “如果由我改，我会……” | “我们已经上线了这个方案” |

GPT 版会指出当前实现的优点和缺口，但不会替你编造履历。使用前必须把故事中的人物、数字和结果换成真实经历。

## 7. 记忆不是背句子，而是建立检索路径

一个知识点至少建立四个入口：

```text
从名词进入：什么是乐观并发？
从症状进入：为什么两个请求都看到库存 1？
从代码进入：RowVersion 如何参与 UPDATE？
从取舍进入：为什么不用 Serializable 包住所有库存操作？
```

面试官往往从症状或取舍进入，而普通教材只训练名词入口。这就是“明明看过，却答不出来”的主要原因。

## 8. 本章必须完成的动作

1. 选择一个你以为已经掌握的主题。
2. 不看材料写出调用链和三个失败边界。
3. 在仓库找三个证据。
4. 运行一个正常实验和一个失败实验。
5. 录两分钟回答。
6. 第二天只听录音，不看文字，列出三处含糊表达再重录。

完成以后再进入下一章。你会感觉进度比“快速看完”慢，但一周后能留下来的东西会多得多。
