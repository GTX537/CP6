# 01 · 库存查询请求链源码导读

这一章不从 `IQueryable` 的定义开始，而是从用户的一次点击开始。目标是亲手追踪 `StockQueryView.vue` 发出的请求，穿过 axios、中间件、Controller 和 EF Core，最后到 SQL Server，再把结果送回页面。学完后你应该能在任何 CRUD 系统中独立完成同样的代码考古。

## 1. 先把用户问题说清楚

仓库人员在库存查询页选择仓库、库位或产品，点击查询，希望得到满足条件的一页库存。用户并不关心 EF Core 或 Vue；他关心三件事：

1. 结果是不是当前租户、当前权限范围内的数据。
2. 翻到下一页时有没有重复、遗漏或顺序跳动。
3. 快速修改条件时，页面最终显示的是不是最后一次查询。

这三件事分别对应安全边界、数据库排序边界和前端竞态边界。只讲“页面调用 API，API 查数据库”远远不够。

## 3. 前端入口：状态不只是几个 ref

打开：

```text
cp6.web/src/views/wms/StockQueryView.vue
```

不要先逐行读模板。先把状态分成四类：

| 状态 | 例子 | 生命周期 | 风险 |
|---|---|---|---|
| 查询条件 | warehouse、location、product | 页面停留期间 | 空值归一化、旧条件残留 |
| 分页状态 | page、pageSize、total | 每次查询变化 | 条件变化后没有回第一页 |
| 请求状态 | loading、error | 单次请求 | 多请求竞争导致 loading 错乱 |
| 结果状态 | rows | 最近一次有效请求 | 旧响应覆盖新响应 |

开发者读页面时要寻找“谁能修改这些状态”。一个变量在五个 watcher、两个事件和一次路由恢复里被修改，比变量类型本身更重要。

### 3.1 查询条件变化为什么通常要重置页码

假设用户在仓库 W1 查到 20 页，当前停在第 18 页。然后把仓库改成 W2，而 W2 只有两页。如果代码继续请求 page=18，页面会显示空数据。用户会误以为 W2 没有库存。

正确契约是：

```text
筛选条件变化 → page 重置为 1 → 发起查询
页大小变化 → page 重置为 1 → 发起查询
仅翻页 → 保留筛选条件 → 发起查询
```

读 `StockQueryView.vue` 时，把触发查询的所有入口列出来，逐个核对是否满足契约。

### 3.2 为什么页面组件已经不是旧版描述的手写结构

当前页面使用 `CpPageShell` 与 `CpListPage`。这说明团队在把列表页的布局、loading、空状态和分页做成复用模板。面试时不能继续背旧教材里的“页面有几百行 el-table 手工结构”。更好的回答是：

> 目前库存页把壳层和列表状态交给通用模板，页面主要保留领域筛选和列定义。这样减少重复，但模板的 props、slots 和错误状态会变成新的公共契约，需要组件测试保护。

接着打开：

```text
cp6.web/src/components/templates/CpPageShell.vue
cp6.web/src/components/templates/CpListPage.vue
cp6.web/src/components/templates/__tests__/CpPageShell.spec.ts
cp6.web/src/components/templates/__tests__/CpListPage.spec.ts
```

先看测试，再看实现。测试能更快告诉你作者认为哪些行为必须稳定。

## 4. API 封装：参数如何变成 URL

打开：

```text
cp6.web/src/api/wms/stock.ts
```

阅读时回答：

- 空字符串会原样进入 query string，还是被省略？
- page/pageSize 的类型和默认值在哪里保证？
- 返回值是裸数组还是分页对象？
- API 层是否把后端 DTO 再映射成前端模型？

一个常见错误是把 `undefined`、`null` 和 `''` 当成同一种空值。它们进入 axios params 后可能产生不同 URL：

```text
productCd=          # 参数存在，值为空
                    # 参数完全不存在
productCd=null      # 字符串 null，取决于序列化配置
```

后端模型绑定后的结果也可能不同。实验时在 Network 面板直接看 Request URL，不要凭想象。

## 5. axios 实例：请求还没到 Controller 前发生了什么

打开：

```text
cp6.web/src/api/http.ts
```

当前实例的关键配置是：

```ts
axios.create({
  baseURL: '/api',
  timeout: 10000,
  withCredentials: true,
})
```

### 5.1 `withCredentials` 的工程含义

认证凭证放在 httpOnly Cookie 中时，JavaScript 读不到 token，这是防止 token 被普通脚本直接窃取的一层保护。浏览器仍可以随请求携带 Cookie，所以 axios 要配置凭证行为。

这不等于“已经防住 XSS”。同源恶意脚本虽然读不到 Cookie，仍可能调用 API。模板转义、CSP、依赖治理和服务端授权仍然需要。

### 5.2 为什么 GET 不注入 CSRF 头

CSRF 防护重点是改变服务器状态的请求。当前拦截器对非 GET/HEAD/OPTIONS 请求注入 CSRF 头。这里依赖一个前提：GET 必须保持安全语义，不能用 GET 做删除、审批或扣库存。

如果后端存在“方便起见”的 GET 写操作，前端规则本身无法补救。

### 5.3 十个请求同时 401 时为什么不能刷新十次

当前实现用共享 `refreshPromise` 做 single-flight：第一个 401 创建刷新任务，后续 401 等同一个 Promise。刷新成功后各自重放一次。

状态图：

```text
request A → 401 ─┐
request B → 401 ─┼→ one refreshPromise
request C → 401 ─┘         │
                            ├─ success → retry A/B/C once
                            └─ fail → clear state → login
```

需要继续问两个边界：

1. POST 已经在服务端成功，只是响应丢失，重放会不会重复写？
2. refresh 请求本身 401，会不会进入无限递归？

代码用 `_retried` 和登录/刷新路径特判限制循环，但非幂等业务仍应由服务端幂等键或唯一约束兜底。

## 6. 中间件管道：顺序就是语义

打开 `CP6.WebApi/Program.cs`，先搜索这些调用：

```text
UseCors
UseAuthentication
UseMiddleware<TenantMiddleware>
UseRequestLocalization
UseMiddleware<BizExceptionMiddleware>
UseMiddleware<CsrfProtectionMiddleware>
UseMiddleware<MustChangePasswordMiddleware>
UseAuthorization
MapControllers
```

不要把中间件背成列表。对每一个问：“它依赖前面提供了什么，又必须在谁之前执行？”

### 6.1 为什么租户中间件在认证之后

租户可能来自已认证用户的 claim 或平台 acting-as 上下文。如果认证还没解析身份，租户中间件拿不到可信身份信息。反过来，如果 Controller 已经执行后才确定租户，查询过滤器就失去意义。

### 6.2 为什么异常中间件的位置值得检查

异常中间件只能捕获它后面组件抛出的异常。放得太靠后，前面的租户解析、认证辅助或本地化异常可能绕过统一错误格式。放得太靠前，又要确保它自己不依赖尚未建立的上下文。

不要只说“异常中间件应该最前”。正确答案取决于它要捕获什么、错误响应需要哪些上下文。

### 6.3 画自己的依赖表

| 中间件 | 需要的前置状态 | 为后面提供什么 | 放错的症状 |
|---|---|---|---|
| Authentication | Cookie/请求头 | ClaimsPrincipal | 后续认为匿名 |
| TenantMiddleware | 已认证身份、租户头规则 | TenantContext | 跨租户或无数据 |
| Localization | culture 来源 | 当前文化 | 错误消息语言不对 |
| CSRF | Cookie、header、端点信息 | 写请求防护 | 403 或防护绕过 |
| Authorization | endpoint metadata、身份 | 访问决策 | 401/403 语义错 |

完成表格比背一个固定顺序更有用。

## 7. Controller：查询是在什么时候执行的

打开：

```text
CP6.WebApi/Controllers/Wms/StockController.cs
```

当前 `Search` 的思路是：

```csharp
var query = _context.Set<Stock>().AsNoTracking();

if (!string.IsNullOrWhiteSpace(warehouseCd))
    query = query.Where(x => x.WarehouseCd == warehouseCd);

if (!string.IsNullOrWhiteSpace(productCd))
    query = query.Where(x => x.ProductCd.Contains(productCd));

var total = await query.CountAsync(cancellationToken);

var items = await query
    .OrderBy(x => x.WarehouseCd)
    .ThenBy(x => x.LocationCd)
    .ThenBy(x => x.ProductCd)
    .ThenBy(x => x.LotNo)
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .ToListAsync(cancellationToken);
```

代码片段表达的是当前查询模式，字段名以源码为准。学习重点是执行边界。

### 7.1 `Where` 为什么没有立刻查数据库

`query` 是 `IQueryable<Stock>`。每次 `Where` 都在构建表达式树。真正执行发生在 `CountAsync` 和 `ToListAsync`。因此一个 HTTP 请求通常产生两条 SQL：总数查询和当前页查询。

用日志或 profiler 验证，不要只背“延迟执行”。

### 7.2 为什么 `AsNoTracking` 适合这里

结果只用于返回，不需要修改后保存。关闭跟踪可减少 change tracker 的内存和比较工作。

边界是：如果后面修改 `items[0].PhysicalQty` 再调用 `SaveChanges`，EF 不会自动把这个修改持久化。开发者要知道自己拿到的是“只读快照”，而不是魔法实体。

### 7.3 为什么分页排序要有稳定的最后一键

只按仓库排序时，大量记录同值，数据库可以任意排列同组数据。第一页和第二页在两次执行之间可能出现重复或遗漏。复合排序把库位、产品和批次也加入，稳定性更好。

但仍要检查最后组合是否真正唯一。如果同一组合允许多行，最好再加主键作为最终 tiebreaker：

```csharp
.ThenBy(x => x.Id)
```

这不是为了“看起来整齐”，而是为了分页契约。

### 7.4 `Contains` 会翻译成什么

字符串 `Contains` 通常翻译为 `LIKE` 模式。前导通配符会影响普通 B-tree 索引的 seek 能力。产品编码如果业务上要求前缀搜索，`StartsWith` 往往更容易利用索引；如果必须任意包含，可能需要全文索引或专门搜索方案。

不能脱离业务把 `Contains` 一律改成相等或前缀。先确认用户到底如何找产品。

## 8. 全局租户过滤器：代码没写 TenantId 为什么仍可能过滤

`CP6Context` 会针对租户实体配置全局查询过滤器。Controller 的 LINQ 没显式写 `x.TenantId == tenantId`，并不表示没有租户条件。

验证方式：

1. 找实体是否实现租户标记接口或继承租户基类。
2. 找 `CP6Context` 构建模型时如何生成过滤表达式。
3. 在开发测试里使用 `ToQueryString()` 查看 SQL。
4. 检查 `IgnoreQueryFilters()`、Dapper、原生 SQL 是否绕过。

全局过滤器减少遗漏，但也会让安全条件变得不显眼。越隐式的安全机制，越需要反射测试和跨租户测试。

## 9. 两条 SQL 带来的时间窗口

`CountAsync` 与分页 `ToListAsync` 是两次数据库往返。它们之间如果有新记录插入或记录删除，可能出现：

- total 说有 101 条，但当前页按新快照只返回不同数量。
- 最后一页突然为空。
- 页间数据移动。

多数后台查询页接受这种读已提交下的轻微漂移。如果业务要求审计报告式的一致快照，可以考虑快照隔离、一次查询返回窗口总数或固定查询时点，但都会增加复杂度或成本。

面试回答要先说业务要求，不能把所有分页都升级为串行化事务。

## 10. 响应回到页面：最后一次请求不一定最后返回

用户先查 A，马上改成 B：

```text
t0: request A 发出，预计 800ms
t1: request B 发出，预计 100ms
t2: B 返回，页面显示 B
t3: A 返回，页面被旧数据覆盖
```

这叫响应竞态。`loading` 也可能出错：A、B 同时进行，B 结束就把 loading=false，但 A 仍在执行。

常见解决：

- 请求序号：只接受最新 id。
- AbortController：发新请求前取消旧请求。
- 用每个请求独立计数，而不是一个布尔 loading。
- 对相同条件做请求合并。

第 6 章会完整实现。这里先在浏览器 DevTools 用网络限速复现。

## 11. 开发者调试路线

### 11.1 页面显示空，但接口是 200

按证据顺序排查：

1. Network 的 Request URL 是否含预期条件和页码。
2. Response 的 `items`、`total` 字段名是否与页面读取一致。
3. Vue Devtools 中 rows 是否更新。
4. `CpListPage` 的 props/slot 是否传错。
5. 后端日志中的租户是否正确。
6. SQL 是否包含全局租户条件和筛选条件。

不要一上来改 SQL，也不要一上来怀疑 Vue 响应性。

### 11.2 接口慢

把时间拆开：

```text
浏览器排队
+ 网络/代理
+ ASP.NET 中间件
+ COUNT SQL
+ page SQL
+ JSON 序列化
+ 前端渲染
```

先找到最大段。若 SQL 慢，再看 actual plan 与 logical reads；若接口快但页面卡，再看 DOM 数量和组件渲染。单看总耗时无法决定优化位置。

### 11.3 偶发 401 后又成功

检查 Network 是否发生：原请求 401 → refresh → 原请求重放 200。若同时多个请求，只应有一个 refresh。若有多个，检查实例是否重复创建或 `refreshPromise` 是否局部化了。

## 12. 必做实验 A：观察 IQueryable 的两次执行

目标：亲眼看到 COUNT 和分页 SELECT。

步骤：

1. 启动开发 API，并开启 EF Core command 日志。
2. 在库存页输入一个筛选条件。
3. 清空日志后只点击一次查询。
4. 找到两条 SQL，标出 WHERE、ORDER BY、OFFSET/FETCH。
5. 改变 pageSize，再比较 SQL 参数。

记录：

```text
COUNT logical reads：
PAGE logical reads：
是否使用目标索引：
排序是否发生在数据库：
租户条件是否出现：
```

如果没有本地数据库，可在测试中对 query 调用 `ToQueryString()`，但要注明这只验证翻译，不验证真实执行计划。

## 13. 必做实验 B：制造乱序响应

目标：证明“后发请求可能先返回”。

方法之一：在本地开发分支临时给条件 A 增加延迟，或在浏览器拦截工具中延迟一个请求。不要把延迟提交到正式代码。

执行：

1. 查询 A。
2. 100ms 内查询 B。
3. 记录请求开始、结束顺序和最终页面内容。
4. 用请求序号或取消机制修复。
5. 重复十次，确认最终始终是 B。

“重复十次”不是严格证明，但比只跑一次更容易暴露竞态。正式保障应写 deterministic test，用可控 Promise 或 fake timers 决定完成顺序。

## 14. 必做实验 C：验证分页稳定性

准备多条排序字段完全相同的数据，然后：

1. 请求第一页和第二页，记录主键。
2. 在两页之间插入一条排序靠前的数据。
3. 再请求第二页，观察 offset pagination 的移动。
4. 给排序补唯一主键，观察“同一快照内不确定顺序”问题消失。
5. 说明插入导致的位置漂移为何仍然存在。

最后比较 keyset pagination：用上一页最后一条的排序键继续查。它更稳定、更适合深翻页，但不方便任意跳到第 N 页。

## 15. 面试连续追问

### Q1：为什么查询用 `AsNoTracking`？

回答结构：这是只读列表端点，不需要 change tracker；关闭跟踪减少内存和比较开销。边界是返回实体修改后不会自动保存；若流程后续要更新，应重新加载跟踪实体或显式附加并控制并发。

### Q2：为什么不是一条 SQL？

分页响应需要 total 和当前页，所以当前实现用 COUNT 加 page query。代价是两次往返和轻微时间窗口。若业务需要一致快照或极致性能，可以评估窗口函数、估算总数、快照隔离或取消 total，但取决于数据量和 UX。

### Q3：全局查询过滤器是不是绝对安全？

不是。EF 查询默认受保护，但 `IgnoreQueryFilters`、Dapper、原生 SQL、错误的租户上下文以及后台任务都可能绕过。需要写入盖章、数据库约束、显式租户 scope 和跨租户测试共同防守。

### Q4：为什么不把所有查询都放 Repository？

Repository 能统一常见操作，但复杂读模型强行套泛型仓储容易泄漏 IQueryable 或制造大量特殊方法。当前库存读端点直接组合 EF 查询，写路径进领域服务，是一种轻量 CQRS 取向。代价是 Controller 可能变胖，需要用 query service 或 specification 控制增长。

### Q5：用户说查询慢，你第一步做什么？

先分段测量而不是先加索引。确认浏览器等待、API 总耗时、COUNT 与 page SQL、序列化和渲染各占多少；SQL 是主因后再看实际计划、logical reads、估算行数与真实行数差异。
