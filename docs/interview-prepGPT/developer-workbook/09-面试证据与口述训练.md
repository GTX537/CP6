# 09 · 面试证据与口述训练

面试不是把教材背给对方。面试官会从一句话追到源码、失败路径、取舍和个人贡献；背稿一旦被打断就会散。本章把前八个工作簿产生的代码、实验和错误变成可检索的证据网络。

## 1. 先建证据账本

每个可讲主题一行：

| 主题 | 我做了什么 | 代码证据 | 运行证据 | 失败边界 | 贡献级别 |
|---|---|---|---|---|---|
| 库存查询 | 追踪并分析 | StockQueryView/StockController | SQL 与 Network | COUNT 时间窗、响应竞态 | 读码验证 |
| 库存写入 | 测试/改进方案 | StockMovementService | 并发测试 | Move 两腿非原子 | 按真实情况填 |
| 多租户 | 负向测试 | CP6Context/TenantMiddleware | 跨租户测试 | Dapper/ExecuteUpdate | 按真实情况填 |

“贡献级别”只能填：亲自完成、主导、深度参与、读码验证、方案推演。不要把最后两种说成生产经历。

## 2. 三种长度不是三篇独立稿

先建立一棵信息树：

```text
CP6 是什么
├─ 业务：制造业全栈系统
├─ 技术：.NET 8 / SQL Server / Vue
├─ 主线：库存或工作流
│  ├─ 请求链
│  ├─ 一致性
│  └─ 安全
├─ 我的贡献
└─ 一个有证据的改进/故障
```

30 秒只说树干；90 秒展开一层；3 分钟展开一个主线。这样被打断后还能回到树，不会忘掉下一句逐字稿。

## 3. 30 秒项目介绍

结构：业务对象、技术栈、你负责的主线、一个差异化难点。

示例要按真实贡献改：

> CP6 是面向制造业的全栈业务系统，后端是 .NET 8、EF Core 与 SQL Server，前端是 Vue 3 和 Element Plus。我主要围绕库存和多租户请求链做开发/分析，从页面查询、库存事务到租户隔离和测试都有完整证据。这个项目最有区分度的地方不是 CRUD 数量，而是库存并发、审计绕过和后台消息至少一次语义这些失败边界。

不要在 30 秒塞控制器数、页面数和十个中间件。

## 4. 两分钟技术回答公式

```text
场景：用户/系统遇到什么
结论：当前采取什么
机制：关键数据怎样流动
边界：什么时候会失败
证据：文件、测试、输出
取舍：为什么没选另一种
改进：下一步具体怎么做
```

以 `MoveAsync` 为例：

> 库位移动需要源扣减和目标增加同时成立。当前实现复用了两次 `ApplyAsync`，每次各自提交事务，所以单腿内部余额与流水是一致的，但两腿整体不原子。源码在源 OUT commit 后才执行目标 IN，目标冻结、并发冲突、取消或进程退出都可能留下半移动。预检只能减少失败，不能消除窗口。单数据库下我会提取不自行提交的内部 apply，由 Move 开一个事务、按稳定顺序更新两行并写两条流水；再用 SQL Server barrier 测试证明并发和回滚。若未来跨服务，才改用带幂等和补偿的移动状态机。

答案里没有泛泛说“用了事务保证一致性”，而是明确事务保证到哪里。

## 5. 连续追问树

每个主题准备五类追问：

```text
Why：为什么这么设计？
How：底层怎样工作？
Failure：哪里会坏？
Alternative：为什么不用另一种？
Evidence：你怎么证明？
```

库存并发：

- 为什么乐观锁适合？
- RowVersion 怎样进入 UPDATE WHERE？
- 冲突后为什么不能无脑重试？
- 为什么不用 Serializable？
- 你的并发测试怎样确保真的重叠？

如果只能回答第一问，说明仍停在概念层。

## 6. STAR 不等于编故事

技术故事的 STAR：

```text
S：可观察症状、影响对象、时间约束
T：你负责的具体边界
A：假设 → 证据 → 排除 → 修复 → 验证
R：业务结果 + 防复发机制 + 未解决风险
```

差的 Action：“我查日志、看数据库，最后修好了。”

好的 Action：

> 我先用浏览器 Network 确认只有一次请求，排除了重复点击；再从两条 toast 的调用栈看到一次来自 axios 拦截器，一次来自页面 catch。根因是错误提示所有权没有协议。我让业务校验由页面接管、未知 5xx 由全局处理，取消不提示，并给 400/409/500/cancel 写了参数化组件测试。

这段能被验证，也展示了排查方法。

## 7. 真实性审计

每个故事问：

1. 我亲自做了哪一步？
2. 哪些是团队完成？
3. 哪些只是当前代码里读到？
4. 数字有日志/报告吗？
5. 功能已上线、测试完成还是只做方案？

安全说法：

```text
“我在当前代码里发现并复现……”
“我为这个缺口设计了……测试/方案”
“生产经历中我负责的是……，其他部分由团队……”
```

不要把仓库注释中的事故自动变成自己的线上事故。

## 8. 不会的问题怎么答

四步：

```text
承认边界
→ 说已有相关知识
→ 给验证路径
→ 不编结果
```

示例：

> 我没有在生产上调过 SQL Server 的 PSP 参数敏感计划功能，所以不想编配置细节。我遇到同参数化 SQL 因数据倾斜出现不同表现时，会先用 Query Store/实际计划确认是不是同 query hash 复用不合适计划，再比较 recompile、拆查询形状和索引方案；具体版本能力我会查当前兼容级别后再决定。

这比只说“不知道”更有能力，也比猜配置可靠。

## 9. 白板题先澄清契约

“设计库存扣减”先问：

- 是否允许负库存？
- 按仓库/库位/批次哪个粒度？
- 单数据库还是跨服务？
- 是否要求幂等？
- 并发冲突返回什么？
- 是否需要流水和审计？

再写不变量、数据模型、事务和测试。直接开始写 Controller 容易遗漏真正评分点。

## 10. 录音评分表

每项 0～2：

| 维度 | 0 | 1 | 2 |
|---|---|---|---|
| 场景 | 无业务问题 | 有背景但模糊 | 用户、数据和影响清楚 |
| 机制 | 只说名词 | 有调用链 | 能解释状态/事务/SQL |
| 边界 | 说“没问题” | 一个泛风险 | 具体失败时点与后果 |
| 证据 | 无 | 只报文件名 | 文件+测试/输出 |
| 取舍 | 无 | 说有优缺点 | 对比替代且贴业务 |
| 贡献 | 夸大/模糊 | 基本明确 | 精确区分个人/团队/推演 |
| 表达 | 背稿、绕 | 可听懂 | 结论先行、被打断可恢复 |

低于 10/14 不进入下一主题。不要靠继续读材料提高分数，回到缺失证据做实验。

## 11. 三轮模拟方法

### 第一轮：只问事实

技术栈、调用链、API、SQL、Vue 状态。目标是不说错当前实现。

### 第二轮：只追失败

并发、取消、重复消息、跨租户、401、慢查询。目标是能说数据留下什么。

### 第三轮：只问取舍与贡献

为什么这样做、为什么不换方案、谁完成、如何证明、重做会改什么。

同一主题分三轮比一次背完整答案更容易形成检索入口。

## 12. 七天训练计划

| 天 | 动作 |
|---|---|
| 1 | 画库存读写两条链，录 30 秒和 2 分钟 |
| 2 | 做并发/租户负向实验，补证据账本 |
| 3 | 做前端乱序与 401 测试，讲失败边界 |
| 4 | 做 SQL plan/IO 实验，讲优化取舍 |
| 5 | 完成制造业务建模工作坊 |
| 6 | 三轮模拟，所有追问只用证据回答 |
| 7 | 只重练评分低于 2 的维度，完成最终模拟 |

## 13. 最终交付

你需要有：

1. 一页证据账本。
2. 一张 CP6 全栈调用链图。
3. 三个真实贡献故事。
4. 两个读码发现/方案推演，明确不是生产经历。
5. 一次 SQL 输出、一次并发输出、一次前端竞态输出。
6. 30 秒、90 秒、3 分钟自我介绍录音。
7. 三轮模拟评分与改进记录。

这些材料比背 200 道孤立问答更能抵抗连续追问。

## 14. 闭卷验收

1. 不看稿讲清库存查询两分钟。
2. 不看稿讲清 Move 非原子及改造。
3. 回答五层租户安全和四条绕过。
4. 解释 Kafka 重复窗口与幂等。
5. 讲一个“假设—证据—排除—修复—验证”的调试故事。
6. 明确指出故事中个人、团队、读码和推演边界。
7. 被中途打断后从信息树另一节点继续，不回忆逐字稿。
