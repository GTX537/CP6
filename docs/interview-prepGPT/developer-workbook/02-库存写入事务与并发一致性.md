# 02 · 库存写入、事务与并发一致性

库存查询错了，用户通常还能刷新；库存写入错了，可能影响发料、生产、财务和追溯。本章不把“加一个事务”当作答案，而是拆清四个问题：库存有哪些必须永远成立的不变量，当前 `ApplyAsync` 的事务到底包住了什么，两个并发请求怎样竞争，以及库位移动为什么仍有两腿不原子的窗口。

## 1. 先写业务不变量，再读实现

打开代码前，先把“正确库存”写成可验证的句子。

### 1.1 数量不变量

当前 `Stock` 实体物化保存三类数量：

```text
PhysicalQty   实际物理数量
AllocatedQty  已分配但尚未出库的数量
AvailableQty  可用数量
```

核心关系：

```text
AvailableQty = PhysicalQty - AllocatedQty
```

这不是一个 UI 计算公式，而是写入服务必须维护的数据不变量。如果某条路径只修改 `PhysicalQty`，没有同步更新 `AvailableQty`，之后所有可用量判断都会漂移。

### 1.2 非负不变量

默认仓库不允许：

```text
PhysicalQty < 0
AvailableQty < 0
```

但当前业务允许仓库配置 `AllowNegative`，请求也可能使用 `AllowNegativeOverride`。因此准确说法不是“库存永远不能为负”，而是“在没有业务豁免时，物理量和可用量不能为负”。

### 1.3 账实与流水同生共死

一次库存变化至少有两份数据：

- `T_Stock` 的当前余额。
- `StockTransaction` 的历史流水。

只更新余额没有流水，无法追溯；只插流水没有余额，查询结果不变。所以它们必须在同一事务中提交或回滚。

### 1.4 业务唯一性

当前 `Stock` 注释定义业务唯一键：

```text
(WarehouseCd, LocationCd, ProductCd, LotNo)
```

在多租户环境下，数据库唯一约束还应包含 `TenantId`。应用层的 `FirstOrDefault` 只能帮助复用已有行，不能代替数据库唯一约束，因为两个并发请求可能都在同一时刻查到“没有”。

## 2. 当前写入链路

源码入口：

```text
CP6.Core/Services/Wms/StockMovementService.cs
CP6.Entity/DomainModels/Wms/Stock.cs
CP6.Entity/DomainModels/Wms/StockTransaction.cs
CP6.Entity/BaseBizEntity.cs
CP6.Tests/StockMovementServiceTests.cs
```

`ApplyAsync` 的主链：

```text
Validate request
→ 盘点冻结检查
→ BeginTransaction（非 InMemory）
→ 按业务键查 Stock
→ 没有则创建零余额行
→ ApplyDelta
→ 查询仓库 AllowNegative
→ 检查 Physical / Available
→ 生成流水号
→ INSERT StockTransaction
→ SaveChanges
→ Commit
→ 财务桥 best-effort
→ SignalR 通知 best-effort
```

这张图要分成三种颜色：事务前检查、事务内强一致、事务后副作用。颜色分错，后面所有一致性讨论都会混乱。

## 3. 请求校验为什么放在事务前

数量为 0、类型不合法、必填编码为空等纯内存校验不需要数据库。先校验可以避免无意义地占用连接和事务。

但“库存是否足够”不能只在事务前查一次，因为检查结果会随并发变化。任何依赖共享数据的校验，都要和写入并发策略一起设计。

判断标准：

| 校验 | 是否依赖共享数据 | 推荐位置 |
|---|---:|---|
| Qty 必须大于 0 | 否 | 事务前 |
| From 与 To 不能相同 | 否 | 事务前 |
| 仓库是否允许负库存 | 是 | 事务内读取或由约束兜底 |
| 当前余额是否足够 | 是 | 与 UPDATE 同一并发控制 |
| 目标库位是否被冻结 | 是 | 事务/并发设计的一部分 |

## 4. 盘点冻结不是一个普通 if

盘点开始后，系统会基于某一时点的账面数量进行计数和差异确认。如果计数过程中仍允许物理入出库，盘点差异就无法解释。

当前服务在物理变化类交易前调用 `IsLocationFrozenAsync`，对进行中的盘点覆盖位置拒绝操作；`RSV/UNRSV` 只改变分配量，不改变物理量，因此不在同一冻结集合；盘点批准自身产生的 `ADJ + RelatedType=STOCKTAKE` 被豁免，否则盘点永远无法用差异调整收敛。

这里的设计不是简单的“冻结时不让操作”，而是：

```text
保护盘点基线
  ├─ 禁止普通物理移动
  ├─ 允许不改变物理量的分配变化
  └─ 允许盘点自身的差异调整
```

### 4.1 TOCTOU 窗口

TOCTOU 指“检查时”和“使用时”之间状态发生变化。请求检查库位没有冻结，紧接着另一事务开始盘点，然后请求继续写库存，就可能越过冻结。

解决方向包括：

- 在同一数据库事务里用合适隔离级别重新检查。
- 对库位或盘点覆盖记录加锁。
- 盘点开始与库存移动使用同一并发版本/互斥资源。
- 允许窗口但设计后续收敛，并明确业务接受程度。

不能只说“已经提前检查，所以没有问题”。当前源码自己也承认移动目标预检仍有 TOCTOU 窗口。

## 5. 事务到底保证了什么

`BeginTransactionAsync` 到 `CommitAsync` 之间包含：

- 读取或创建库存行。
- 应用数量变化。
- 查询负库存策略。
- 插入交易流水。
- `SaveChangesAsync`。

因此在数据库支持事务时，余额和流水能够一起提交。若 `SaveChangesAsync` 抛异常，catch 会回滚。

### 5.1 `SaveChanges` 本身也有事务，为什么还显式开启

单次 `SaveChanges` 通常已经在事务中执行它生成的多条命令。显式事务的价值取决于事务范围内是否还有必须与保存保持同一快照/锁语义的读取，以及未来是否可能多次保存。

当前代码在一次 `SaveChanges` 前做了多次读取。显式事务把这些步骤放进同一事务边界，但默认隔离级别仍不自动消灭所有竞态。事务回答“哪些命令一起提交”，隔离级别和并发令牌回答“别人同时修改时看到什么、谁赢”。

### 5.2 InMemory 为什么跳过事务

EF Core InMemory provider 不提供真实关系数据库的事务、锁、rowversion 和 SQL 约束语义。当前服务检测 provider 后不创建事务，是为了让逻辑单测可运行。

这意味着 InMemory 测试通过只能证明：

- 分支计算大致正确。
- 数量校验按预期抛异常。
- 流水对象被加入上下文。

它不能证明：

- SQL Server rowversion 冲突能被捕获。
- 复合唯一索引能阻止重复库存行。
- 两条 SQL 在事务中符合预期隔离。
- 死锁、锁等待和回滚行为正确。

所以并发正确性必须补 SQL Server 或至少关系型 provider 的集成测试。SQLite 也不能完整模拟 SQL Server rowversion。

## 6. 乐观并发是怎样工作的

`Stock` 继承 `BaseBizEntity`，其中 `RowVersion` 标记 `[Timestamp]`。在 SQL Server 上，EF Core 更新一条已跟踪实体时会把原 rowversion 加到 WHERE：

```sql
UPDATE T_Stock
SET PhysicalQty = @p0,
    AllocatedQty = @p1,
    AvailableQty = @p2
WHERE Id = @id
  AND RowVersion = @originalRowVersion;
```

若另一事务已更新该行，rowversion 已变化，UPDATE 影响 0 行，EF 抛 `DbUpdateConcurrencyException`。

### 6.1 两个请求扣最后一件库存

初始：Physical=1，Available=1。

```text
Request A 读取 rowversion=10, Available=1
Request B 读取 rowversion=10, Available=1
A 计算 0，UPDATE WHERE rv=10 → 成功，rv 变 11
B 计算 0，UPDATE WHERE rv=10 → 0 行 → concurrency exception
```

没有 rowversion 时，A、B 都可能基于旧值写 0，系统产生两条出库流水，却只减少一件余额。这是 lost update。

### 6.2 冲突后能不能自动重试

不能无条件重放整个请求。重试要重新读取最新库存，再次校验业务条件。若最新余额已经不足，应返回库存不足或 409，而不是执意扣减。

建议流程：

```text
捕获 DbUpdateConcurrencyException
→ 清理/重建 DbContext 跟踪状态
→ 重新读取最新行
→ 重新执行业务校验
→ 最多有限次数重试
→ 仍冲突则返回 409 + 可识别错误码
```

还要确认流水号生成是否会因为失败重试产生空洞。序列有空洞通常可接受，但不能把“必须连续”暗中当作业务要求。

## 7. 新库存行的并发创建

rowversion 只保护已存在行。若库存行不存在：

```text
A 查询：null
B 查询：null
A INSERT key(W1,L1,P1,LOT1)
B INSERT key(W1,L1,P1,LOT1)
```

真正兜底的是数据库复合唯一约束。一个请求成功，另一个收到 unique violation。应用可以捕获后重新查询再按并发更新，但要小心事务和 DbContext 中失败实体状态。

这类问题说明：

```text
应用层查询避免常规重复
+ 数据库唯一约束阻止竞态重复
+ 冲突恢复逻辑改善用户体验
```

三层缺一不可。

## 8. `MoveAsync` 为什么不是原子移动

当前实现调用两次 `ApplyAsync`：

```text
腿 1：源库位 MOVE -Qty → 独立事务提交
腿 2：目标库位 MOVE +Qty → 独立事务提交
```

如果腿 1 成功、腿 2 因数据库故障、冻结、唯一冲突或取消失败，就会出现“源已扣、目标未加”。源码对此有明确注释，不能在面试中说当前移动是原子的。

### 8.1 预检查解决不了原子性

提前检查目标库位冻结能减少明显失败，但不能覆盖：

- 预检后才开始冻结。
- 腿 2 数据库连接失败。
- 目标行并发冲突。
- 请求在两腿之间取消。
- 进程在腿 1 commit 后崩溃。

预检是降低失败概率，不是原子保证。

### 8.2 三种改造方案

#### 方案 A：一个事务内执行两腿

提取一个“不自行开启/提交事务”的内部方法，让 `MoveAsync` 开一次事务，完成源扣减、目标增加和两条流水后一次 `SaveChanges/Commit`。

优点：单数据库内最直接的强一致。

代价：需要重构 `ApplyAsync` 的事务所有权；锁住两行时必须统一访问顺序，避免 A→B 与 B→A 形成死锁。

#### 方案 B：移动单状态机

先创建 `StockMove` 主单：Pending → SourceApplied → Completed/Compensating。每一步幂等，后台可恢复未完成移动。

优点：适合跨库、跨服务或长事务不可接受的场景。

代价：用户会看到中间状态，需要补偿、监控和运维界面，不再是瞬时强一致。

#### 方案 C：数据库存储过程/原子 SQL

由数据库在一个事务中锁定两行并更新。

优点：往返少，锁语义集中。

代价：业务规则分散到数据库，测试与版本管理要求更高；并不会自动解决通知和财务等外部副作用。

CP6 当前是单数据库写入，方案 A 通常是第一选择。若未来移动跨服务，再考虑状态机/Saga。

## 9. Commit 后的财务与 SignalR 为什么是 best-effort

数据库事务提交后，服务依次调用财务桥和通知器，并吞掉异常。设计意图是：财务桥或实时通知失败不能把已经成功的库存移动伪装成失败，否则客户端重试可能重复扣库存。

但吞异常也有代价：

- 财务过账可能永久丢失。
- 前端没有收到刷新通知。
- 没有日志/指标时运维不知道失败。

`best-effort` 只能说明主交易不回滚，不能等于“失败不用处理”。

### 9.1 Outbox 的改造思路

在库存事务内同时插入：

```text
StockTransaction
OutboxMessage(StockMoved, payload, Pending)
```

提交后后台发布 Outbox。发布成功标记完成；失败重试；消费者按事件 id 幂等。

这样能保证“只要库存提交，待发布消息就一定存在”。它不保证 exactly-once 送达，但把丢消息变成可重试、可观测的 at-least-once。

## 10. 取消发生在不同位置会怎样

| 取消点 | 预期行为 | 需要验证 |
|---|---|---|
| BeginTransaction 前 | 不开启事务 | 是否快速返回取消 |
| SELECT 中 | 数据库命令取消 | provider 是否响应 token |
| SaveChanges 前 | 回滚 | tracking 状态是否可复用 |
| Commit 过程中 | 结果可能不确定 | 客户端能否安全重试 |
| Commit 后、通知前 | 主交易已成功 | 不能告诉用户“库存失败” |

最难的是 commit 结果不确定：连接断开时客户端可能不知道数据库是否已经提交。解决不能只靠重试，写请求需要业务幂等键，服务器能查询相同请求是否已经完成。

## 11. 故障矩阵

| 故障 | 余额 | 流水 | 财务 | 通知 | 正确处理方向 |
|---|---|---|---|---|---|
| Validate 失败 | 不变 | 无 | 无 | 无 | 400/业务错误 |
| 冻结检查拒绝 | 不变 | 无 | 无 | 无 | 409/业务错误 |
| SaveChanges 失败 | 回滚 | 回滚 | 无 | 无 | 错误响应 |
| Commit 成功后财务失败 | 已变 | 已有 | 缺失 | 可继续 | Outbox/补偿告警 |
| 通知失败 | 已变 | 已有 | 视前一步 | 缺失 | 重试或客户端主动刷新 |
| Move 腿 2 失败 | 源已减 | 只有 OUT | 不确定 | 已通知腿 1 | 原子重构或补偿状态机 |

每个库存方案评审都应该先填这张表。

## 13. 必做实验 B：制造 Move 半成功

在测试 double 中让第二次 `ApplyAsync` 对应的目标写入失败，或在重构前用可控 provider 制造第二腿异常。记录：

```text
源库存：
目标库存：
流水数：
返回给客户端的错误：
重试整个 Move 后会发生什么：
```

如果现有结构不容易注入第二腿失败，这本身就是可测试性反馈：`MoveAsync` 同时负责流程编排和具体提交，缺少事务/端口边界。

## 14. 必做实验 C：真实并发

InMemory 不适合此实验。准备隔离的 SQL Server 开发库：

1. 创建一条可用量为 1 的库存。
2. 用两个独立 scope/DbContext 同时读取。
3. 两边都尝试 OUT 1。
4. 用 barrier 控制两边在读取后同时继续。
5. 断言只允许一边成功，另一边得到并发或库存冲突。
6. 验证最终余额、流水数和错误码。

测试结束后清理独立租户/测试数据，不要在共享开发数据上跑并发破坏实验。

## 15. 面试回答模板

> CP6 的单笔库存变化把余额更新和库存流水放在同一数据库事务中，库存实体带 rowversion 做乐观并发，默认还检查物理量和可用量不能为负。事务提交后财务桥和 SignalR 是 best-effort，避免外部失败把已提交库存伪装成失败，但当前需要 Outbox 才能把丢消息变成可恢复。另一个明确缺口是 `MoveAsync` 通过两次独立 `ApplyAsync` 提交源和目标，两腿不是原子；我会先提取无事务的内部 apply，在一个事务里锁定并更新两行、写两条流水，并统一锁顺序防死锁。如果未来跨服务，再用带幂等和补偿的移动状态机。

这段回答有当前事实、有边界、有改进，不会把设计目标说成已经实现。
