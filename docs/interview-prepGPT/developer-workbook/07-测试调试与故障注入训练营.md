# 07 · 测试、调试与故障注入训练营

测试不是为了让 CI 出现绿色，也不是“每个方法写三个 Assert”。开发者先写出系统必须维持的契约，再选择最低成本、最高可信度的测试层。故障注入则反过来问：数据库、网络、并发、权限或消息在最坏时间失败，系统会留下什么。

## 1. 从契约开始，不从覆盖率开始

库存模块的关键契约示例：

```text
同租户同业务键最多一条 Stock
Available = Physical - Allocated
不允许负库存时，OUT 不得让 Physical/Available 为负
余额与流水一起提交
并发扣减只能有一个请求赢
租户 A 看不到/改不到租户 B
Move 要么原子，要么有可观察的未完成状态和补偿
重复消息不产生重复业务效果
```

行覆盖率可能 100%，这些契约仍可能一个都没验证。先列契约，再映射测试。

## 2. CP6 当前测试层

### 后端

- xUnit：测试组织和断言。
- Moq/手写 fake：隔离依赖。
- EF InMemory：快速业务分支测试。
- SQLite：部分关系型行为。
- 反射守卫：租户、审计、权限等结构规则。
- Web/API 集成：中间件和端点组合行为。

### 前端

- Vitest：函数、store、组件逻辑。
- Vue Test Utils + jsdom：组件渲染与交互。
- Playwright：浏览器端 golden path、页面烟测和业务流。

选择依据不是“金字塔规定单测最多”，而是这个 bug 在哪一层才会真实出现。

## 3. 四种测试各负责什么

| 层 | 擅长 | 不擅长 |
|---|---|---|
| 纯单元 | 计算、分支、状态机，快且确定 | SQL、DI、序列化、浏览器行为 |
| 组件/服务集成 | EF 映射、中间件、HTTP envelope | 完整浏览器和真实基础设施 |
| 契约/架构守卫 | 防“新增实体忘租户/权限” | 具体运行时业务结果 |
| E2E | 用户主路径、路由、真实渲染 | 精确枚举所有边界，慢且定位难 |

一个并发 rowversion bug用 InMemory 单测验证不了；一个金额计算函数没必要启动 Playwright。

## 4. 好测试名称是业务句子

差：

```text
TestApply1
ShouldWork
SearchTest
```

好：

```text
ApplyAsync_OUT_WhenAvailableIsInsufficient_ShouldNotPersistStockOrTransaction
MoveAsync_WhenDestinationWriteFails_ShouldNotLeaveSourceCommitted
Search_WhenTwoRequestsFinishOutOfOrder_ShouldKeepLatestResult
TenantFilter_WhenCurrentTenantIsA_ShouldNeverReturnTenantBRows
```

名字包含动作、条件和结果。测试失败时不打开代码也知道哪个契约破了。

## 5. Arrange 不是随便造对象

测试数据要凸显边界：

```text
Physical=10, Allocated=8, Available=2
OUT 3
```

只看 Physical 足够，但 Available 不足，能抓住错误判断。若所有测试都用 Physical=100、Allocated=0，分配逻辑的 bug 很难暴露。

构造器/Builder 应让关键差异可见：

```csharp
var stock = AStock()
    .ForTenant(tenantA)
    .At("W1", "L1")
    .ForProduct("P1", lot: "LOT1")
    .WithQuantities(physical: 10m, allocated: 8m)
    .Build();
```

不要让 Builder 自动“修正”你故意制造的不一致，否则负向测试永远造不出坏数据。

## 6. InMemory 测试的正确定位

适合：

- `ApplyDelta` 数量分支。
- Validate 抛错。
- 普通 LINQ 行为的大致验证。
- 服务编排与 fake notifier。

不适合声称证明：

- transaction rollback。
- SQL Server rowversion。
- unique constraint。
- decimal 精度/列类型。
- case/collation。
- 并发锁和 deadlock。
- 查询计划。

在测试报告里明确 provider，避免把逻辑测试包装成数据库一致性证据。

## 7. 关系型集成测试如何隔离

优先选择可重建的独立数据库或容器。每个测试至少隔离 tenant，强一致并发测试最好隔离数据库或 schema，避免并行测试互相污染。

生命周期：

```text
创建/租用测试库
→ 应用迁移
→ 插入最小基线
→ 执行测试
→ 断言业务表 + 流水 + 审计
→ 清理确定的测试资源
```

不要连接共享开发库后用 `DELETE FROM` 全表清理。测试清理必须限定明确 tenant/id，并在删除前校验目标环境。

## 8. 并发测试必须可控交汇点

直接 `Task.WhenAll` 两个请求并不能保证它们在关键位置重叠。偶尔通过/失败的测试只制造噪声。

使用 barrier/hook：

```text
A 读取库存 ─┐
             ├─ 两边都到 barrier 后同时放行
B 读取库存 ─┘
→ 同时 SaveChanges
```

断言：

- 成功请求数。
- 失败异常/状态码。
- 最终库存。
- 流水数量。
- 重试后结果。

并发测试的目标是稳定复现交错，不是多跑几次碰概率。

## 9. 事务测试要断言失败后的数据库

只断言“抛异常”不够。事务测试必须在新的 DbContext 中查询最终状态，因为原 Context 的 ChangeTracker 可能仍保留内存修改。

例如 OUT 流水插入时故意违反约束：

```text
调用 ApplyAsync → 抛异常
dispose 原 scope
new scope/context
查询 Stock：数量未改变
查询 StockTransaction：没有新流水
查询 FieldAudit：没有孤立审计
```

这才证明回滚，不是证明方法进入 catch。

## 10. 多租户测试必须使用相同业务键

租户 A 放 P-A、租户 B 放 P-B，然后 A 只看到 P-A，不能强证明过滤生效；即使代码按 ProductCd 过滤也可能碰巧通过。

更强数据：两个租户都创建 `P001/W1/L1/LOT1`，数量不同。断言 A 只看到 A 的数量，B 同理；再验证唯一约束允许跨租户同码。

负向测试还要覆盖：

- `IgnoreQueryFilters` 只能在受控服务使用。
- Dapper SQL 漏 TenantId 的守卫。
- Added 显式带别租户 TenantId。
- 后台 scope 没设置租户。

## 11. 消息测试围绕交付点断开

对 Kafka consumer，在这些位置注入失败：

```text
反序列化前
反序列化后、写库前
写库成功后、SignalR 前
SignalR 成功后、offset commit 前
offset commit 抛错
```

每个点记录数据库行数、通知次数、offset 和下一次重试。这样才能验证 at-least-once 与幂等，而不是只 mock `Commit` 被调用。

## 12. Vue 异步测试不用真实 sleep

用可控 Promise：

```ts
function deferred<T>() {
  let resolve!: (value: T) => void
  const promise = new Promise<T>(r => { resolve = r })
  return { promise, resolve }
}
```

创建请求 A、B，先 resolve B 再 resolve A，断言页面保持 B。这比 `setTimeout(800)` 快且确定。

fake timers 适合 debounce、timeout；可控 Promise 适合网络完成顺序。不要为了看起来像真实网络而让单测真的等秒。

## 13. 组件测试观察用户可见结果

不要只断言内部 ref：

```text
点击保存
→ 按钮 disabled/loading
→ API resolve
→ 成功消息一次
→ 弹窗关闭
→ 列表 reload 一次
```

错误路径：

```text
API 409
→ 弹窗保留
→ 用户输入不丢
→ 显示冲突提示
→ 不重复 toast
```

内部实现可以重构，用户契约应稳定。

## 14. E2E 只保高价值路径

适合 Playwright：

- 登录/refresh/退出。
- 动态路由加载。
- 库存查询与 QC 权限。
- 核心制造业务 golden path。
- 多语言关键页面。

不适合把每个表单 required 都写成慢 E2E；这些可由组件/表单模型测试覆盖。

E2E 失败要保留 screenshot、trace、network、console。只有“第 42 行超时”无法排查。

## 15. 调试不是随机加日志

按假设推进：

```text
现象：QC 保存后弹两条错误
假设 1：请求发了两次
证据：Network 只有一次 → 排除
假设 2：拦截器和页面各提示一次
证据：两个 ElMessage 调用栈 → 命中
修复：明确错误所有权
验证：400/409/500/cancel 参数化测试
```

每一步写“证据如何区分两个可能原因”。这比加十个 Console.WriteLine 更快。

## 16. 故障注入目录

至少完成以下八类：

| 故障 | 注入方式 | 主要观察 |
|---|---|---|
| 网络慢 | deferred/代理延迟 | 竞态、loading |
| 请求取消 | AbortController | 无错误 toast、后端取消 |
| 数据库冲突 | 两 Context + barrier | 409、最终不变量 |
| 唯一冲突 | 并发创建同业务键 | 恢复策略 |
| 第二腿失败 | fake/数据库约束 | Move 半成功 |
| 消息重复 | 同 EventId 两次 | 幂等 |
| 通知失败 | notifier throw | 主交易与 outbox |
| 租户缺失 | 无 tenant scope | fail-closed/default 风险 |

## 17. 回归测试要放在最低可靠层

修 bug 后写测试，选择能真实复现原因的最低层：

- 纯函数 bug：单元。
- EF 翻译/约束：关系集成。
- 中间件顺序：API 集成。
- Vue 响应竞态：组件。
- 浏览器 Cookie/路由：E2E。

层级太低测不到真实原因，层级太高则慢且脆弱。

## 18. 本地验证命令

按改动范围选择，不要每次盲跑全部：

```powershell
dotnet test CP6.Tests

Set-Location cp6.web
npm run type-check
npm run test:unit
npm run build
npm run e2e
```

报告时写实际运行了什么、哪些没跑、为什么。不能说“测试通过”却省略只跑了一个 filter。

## 19. 必做训练

选择下面三个失败路径，各写一条先失败后通过的测试：

1. 历史弹窗 A→B 乱序。
2. 同库存并发 OUT。
3. Kafka 写库后、commit 前崩溃。

每条提交一份记录：契约、初始失败、根因、修复、回归层、未覆盖边界。

## 20. 面试回答模板

> 我不是按方法数量写测试，而是先列业务不变量和失败窗口。纯数量计算用单元测试；rowversion、唯一索引和事务回滚必须用 SQL Server 关系集成；租户漏标用反射守卫加跨租户负向测试；Vue 乱序响应用可控 Promise 决定完成顺序；Cookie 和动态路由放少量 Playwright。故障注入时我会在数据库提交、通知、offset commit 等边界逐点断开，断言最终数据而不只断言抛异常。这样测试保护的是系统契约，而不是当前实现细节。

## 21. 闭卷验收

1. 为库存模块写八条可测试契约。
2. 解释 InMemory 不能证明的六件事。
3. 设计可确定复现的并发 barrier。
4. 设计可确定复现的前端乱序 Promise。
5. 说明事务失败为什么要用新 Context 查结果。
6. 给一个 bug 选择最低可靠测试层并解释。
7. 输出一次测试命令、结果和未执行范围的诚实报告。
