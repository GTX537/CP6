# 04 · 异步、后台任务与消息一致性

“用了 async”“接了 Kafka”“手动提交 offset”都不是完成标志。后台任务真正难的是停止、重试、重复、毒消息、租户作用域和外部副作用。本章以 `KafkaOperLogConsumer` 为标本，追踪一条操作日志从 Kafka 到数据库再到 SignalR 的全过程，并推导当前至少一次语义下会发生的重复与泄漏风险。

## 1. 先画消息生命周期

当前主链：

```text
Kafka topic: cp6.operlog
→ consumer.Consume(stoppingToken)
→ JSON deserialize Sys_OperLog
→ create DI scope
→ CP6Context.SaveChangesAsync
→ SignalR Clients.All.SendAsync("NewOperLog")
→ consumer.Commit(cr)
```

注意 Commit 在数据库和 SignalR 都成功以后。这看起来谨慎，但会产生一个重要窗口：数据库已经写成功，SignalR 失败，于是 offset 不提交，下一次重新消费会再次插入数据库。

## 2. async 不等于所有调用都非阻塞

Confluent.Kafka 的 `Consume` 是阻塞调用。把它直接放在普通线程池任务里，长期占用一个线程池线程，负载高时可能加剧线程池饥饿。

当前 `ExecuteAsync` 使用：

```csharp
Task.Factory.StartNew(
    () => ConsumeLoop(...),
    stoppingToken,
    TaskCreationOptions.LongRunning,
    TaskScheduler.Default);
```

`LongRunning` 向调度器表达这是长时间阻塞工作，通常会使用独立线程。这里不是为了让 Kafka “更异步”，而是隔离阻塞循环。

### 2.1 `StartNew` + async 的返回类型陷阱

传入的 lambda 返回 `Task` 时，`StartNew` 常见结果是 `Task<Task>`，需要 `Unwrap`。当前 lambda 通过方法调用形式以及重载推断值得实际检查编译类型和宿主等待行为。开发者不能只看能编译就认为生命周期一定被正确跟踪。

更直白的替代是：

- 使用 Kafka 客户端推荐的专用消费线程模式。
- 明确创建线程并让 BackgroundService 返回可跟踪任务。
- 若用 `Task.Run`，理解它占线程池的代价。

关键验收是：宿主停止时是否等待消费循环真正退出，而不是某个外层任务提前完成。

## 3. BackgroundService 的取消契约

`stoppingToken` 表示宿主请求停止。当前代码把 token 传给 `consumer.Consume`，捕获 `OperationCanceledException`，最后 `consumer.Close()`。

理想停止序列：

```text
Host sends cancellation
→ blocking Consume throws OperationCanceledException
→ loop exits
→ Close leaves consumer group cleanly
→ scope/resources dispose
→ ExecuteAsync completes
```

检查点：

- `PersistAsync` 没有接收 stoppingToken，数据库保存和 SignalR 推送不能跟随宿主取消。
- 停止发生在处理消息中途时，是完成当前消息还是立刻终止，需要明确。
- 若数据库已提交但还未 commit offset，重启后会重复，这是至少一次语义的正常结果。

“支持取消”不是方法签名有 token，而是 token 一路传到真正会等待的 I/O。

## 4. 手动 Commit 带来 at-least-once

当前配置：

```csharp
EnableAutoCommit = false;
```

处理成功后才 `consumer.Commit(cr)`。这避免“消息还没落库 offset 已推进”导致永久丢失，但允许重复。

故障时间线：

```text
t0 消费 offset 42
t1 INSERT 操作日志成功
t2 进程崩溃
t3 offset 42 尚未提交
t4 重启，再次消费 42
t5 再 INSERT 一次
```

所以准确语义是：至少处理一次，不是恰好一次。

### 4.1 幂等需要稳定消息身份

消费者要去重，消息必须有跨重试稳定的 id，例如 `EventId`。数据库建立：

```sql
UNIQUE(TenantId, EventId)
```

处理时尝试插入；唯一冲突表示已经处理，可以安全推进 offset。仅使用 Kafka offset 也可做 inbox key，但要包含 topic、partition、offset，且考虑重新发布和 topic 迁移。

当前 `PersistAsync` 把反序列化实体 `Id` 清零，让数据库重新自增。数据库自增 Id 无法识别重复消息，因为每次重试都会得到新 Id。

## 5. 数据库成功、SignalR 失败的双写问题

当前顺序：

```text
SaveChanges
→ Clients.All.SendAsync
→ Commit offset
```

若 SignalR 失败，catch 位于外层，offset 不提交；数据库写入不会自动回滚，因为没有跨数据库与 SignalR 的事务。重试会再次插日志。

这里有三种语义选择：

### 5.1 日志落库是主结果，通知是 best-effort

数据库成功后即提交 offset；SignalR 失败只记录告警，不重试整条消息。

优点：不会因通知失败重复落库。

缺点：实时通知可能丢。客户端需主动刷新或通知另行重试。

### 5.2 Outbox

消费事务内写操作日志和 `SignalROutbox`。事务提交后 offset 可推进；另一个 worker 重试推送 outbox。

优点：日志和“待通知事实”同生共死，推送可恢复。

缺点：增加表、清理、重试和监控。

### 5.3 幂等日志 + 整体重试

保留当前顺序，但日志以 EventId 去重。重试时数据库发现已存在，继续尝试 SignalR，成功后 commit。

优点：改动较小。

缺点：需要把“已落库但未通知”状态表达清楚，否则去重后无法判断是否还应推送。

对于审计日志，数据库通常是主结果，建议至少做到日志幂等；若实时推送是业务要求，再加 outbox。

## 6. `Clients.All` 的租户边界

当前代码把新操作日志推给：

```csharp
_hubContext.Clients.All.SendAsync("NewOperLog", ...)
```

如果系统是多租户，这可能让所有已连接客户端收到别的租户的用户名、URL、控制器、状态码和耗时。即使前端最终不展示，数据已经越过网络边界。

更安全的模式：

```text
连接建立时根据可信 tenant claim 加入 group tenant:{TenantId}
→ 后台从消息中的可信 TenantId 选择同组
→ Clients.Group(group).SendAsync(...)
```

还需验证平台管理员跨租户监控是独立权限，不应把 `All` 当作省事的实现。

## 7. 消息里的 TenantId 能不能信

消费者没有 HttpContext。`PersistAsync` 新建普通 scope 后直接解析 `CP6Context`，没有使用 `TenantScopeRunner` 设置当前租户。反序列化的 `Sys_OperLog` 若自带 TenantId，`StampTenant` 只在空值时才补当前租户。

这产生两个问题：

1. 生产者是否有权决定 TenantId？
2. TenantId 空时会不会落入默认租户？

可靠设计要定义消息契约：

- TenantId 必填且格式有效。
- Producer 从认证后的服务端上下文写入，不接受浏览器任意值。
- Consumer 校验租户存在且启用。
- Consumer 为该 TenantId 建 scope，或显式写入并限制允许实体。
- 非法/未知租户进入 dead-letter，而不是默认租户。

## 8. 毒消息会怎样

若 JSON 永远无法反序列化，当前 catch 不 commit，循环可能反复收到同一消息并持续报错，阻塞 partition 后续消息。

毒消息策略通常包括：

```text
第 1～N 次：退避重试
超过 N 次：写 dead-letter topic / error table
记录 topic、partition、offset、异常、payload hash
提交原 offset，让分区继续
告警并提供人工重放工具
```

不能把原始敏感 payload 无限制写日志。操作日志可能包含 URL、用户信息或请求内容，需要脱敏和大小限制。

## 9. 重试为什么必须退避

数据库临时不可用时，立即 `continue` 会快速重新拉取/处理，形成日志风暴和下游压力。使用指数退避加抖动：

```text
1s, 2s, 4s, 8s ... 上限 1min
+ random jitter
```

但要区分：

- 可重试：连接超时、暂时网络故障、死锁。
- 不可重试：JSON schema 错、必填字段缺失、未知租户。
- 业务冲突：重复 EventId 可视为已处理。

所有异常都用同一 catch 无限重试，会把永久错误当临时错误。

## 10. Scope 为什么每条消息创建一次

`DbContext` 是 scoped 且非线程安全。后台 singleton 不能在构造函数直接注入并长期持有。当前每条消息创建 scope，处理后释放，能避免：

- ChangeTracker 无限增长。
- 跨消息实体状态污染。
- 失败事务影响后续消息。
- singleton 捕获 scoped dependency。

批量消费时可以每批一个 scope，但必须明确事务、失败重试和跟踪清理边界，不应仅为了少创建对象就长期共用 Context。

## 11. 顺序与吞吐的取舍

当前循环一次处理一条，天然保持单 partition 消费顺序，但吞吐受数据库和 SignalR 串行耗时限制。

并发处理前先问业务是否要求顺序：

- 操作日志通常可以并发，只要每条独立且最终按时间展示。
- 同一业务聚合的状态事件可能必须按 key 顺序。

并发方案可以按 key/partition 分区，每个分区内串行、分区间并行。还要保证 offset 提交不能越过尚未完成的较早消息。

`Task.WhenAll` 直接并发一批再提交最大 offset，在部分失败时很容易丢消息。

## 12. 可观测性不是打一个 Error 日志

至少需要指标：

```text
consumer lag
处理成功/失败计数
重试次数
dead-letter 数量
单消息处理延迟 p50/p95/p99
数据库写耗时
SignalR 推送失败
重复消息命中数
每租户失败分布
```

日志关联字段：topic、partition、offset、eventId、tenantId、trace/correlation id。不要只记录“处理失败”，否则无法定位哪条消息。

## 13. 必做实验 A：证明重复

1. 发送一条带稳定 EventId 的测试消息。
2. 在数据库保存成功后、commit offset 前故意抛异常。
3. 重启 consumer。
4. 查询数据库同 EventId 行数。
5. 在没有唯一约束时应看到重复；加唯一约束和幂等处理后应只有一条。

不要用生产 topic。使用本地 Kafka 或隔离 topic/group。

## 14. 必做实验 B：SignalR 失败窗口

使用 notifier/hub test double，让 `SendAsync` 第一次失败、第二次成功。验证当前实现是否：

- 第一次已经写库。
- offset 未提交。
- 第二次再次写库。
- 客户端最终收到几次。

然后分别实现“通知 best-effort”和“outbox”版本，比较测试断言。

## 15. 必做实验 C：毒消息

向隔离 topic 发三个消息：有效 A、非法 JSON、有效 B。观察 B 是否能被处理。实现有限重试 + dead-letter 后，验证：

- 非法消息进入 dead-letter。
- 原 partition offset 推进。
- B 最终处理。
- dead-letter 有足够定位信息但不泄露完整敏感数据。

## 16. 必做实验 D：租户 SignalR 隔离

创建租户 A、B 两个测试连接，分别加入对应 group。发送 A 的操作日志，断言只有 A 收到。再用无 tenant/伪造 tenant 的消息验证 consumer 拒绝或进入 dead-letter。

## 17. 面试回答模板

> 当前 Kafka 操作日志消费者关闭自动提交，数据库落库和 SignalR 推送成功后才手动提交 offset，所以语义是 at-least-once。它避免处理前提交造成丢消息，但数据库成功、推送或 commit 失败时会重复消费；当前实体 Id 每次清零自增，不能天然去重。我会给事件稳定 EventId，数据库做 TenantId+EventId 唯一约束，并把通知改成事务 outbox 或明确 best-effort。另一个多租户边界是当前 `Clients.All`，应按可信 tenant claim 建 SignalR group。永久坏消息还要有限重试和 dead-letter，否则会卡住 partition。
