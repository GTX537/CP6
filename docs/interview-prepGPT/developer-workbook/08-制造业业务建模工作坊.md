# 08 · 制造业业务建模工作坊

业务人员说“加一个扫码报工”，初级开发者会马上画页面和建表；成熟开发者先问谁在什么时点扫什么、系统必须阻止什么、失败后如何补录、数据将影响库存、工资、OEE 还是追溯。本章完整演练一次从车间原话到可实现、可测试设计的过程。

## 1. 原始需求

> 车间希望工人扫工单二维码就能报工，记录合格数和不良数，操作越简单越好。

这句话缺少几乎全部工程边界。不要问“页面要几个按钮”开场，先找参与者与结果。

## 2. 先观察现场

访谈对象不能只有提出需求的主管：

| 角色 | 关心什么 | 可能冲突 |
|---|---|---|
| 操作工 | 少输入、弱网也能用 | 不愿选很多代码 |
| 班组长 | 进度、异常、补录 | 需要修改权限 |
| 计划员 | 工单完成与齐套 | 不希望超报 |
| 仓库 | 领料、完工入库 | 报工是否自动动库存 |
| 品质 | 不良原因和隔离 | 合格/不良不能只记总数 |
| 财务 | 工时、成本归集 | 补录会影响已结期间 |
| IT/运维 | 设备、网络、追踪 | 扫码枪兼容与离线队列 |

至少现场观察一次真实报工，不只开会议。用户说的流程往往省略了他们已经习惯的纸面补救。

## 3. 用 5W1H 把动作说完整

```text
Who：谁能报？可替别人报吗？
What：报工单、工序还是设备任务？
When：开始、暂停、完工分别何时？能补昨天吗？
Where：工位、产线、设备是否必须匹配？
Why：数据用于进度、库存、计件、OEE、追溯中的哪些？
How：扫工单、员工、设备、批次的顺序？弱网怎么办？
```

把答案写成事实，不把猜测混进去。无法确认的字段标为待决策，并说明它影响哪部分设计。

## 4. 先建状态机，后建页面

工单/工序可能状态：

```text
Released
  → InProgress
  → Paused
  → InProgress
  → Completed
  → Closed

异常分支：Cancelled / OnHold
```

报工单据本身：

```text
Draft → Submitted → Approved → Posted
          └──────→ Rejected
Posted → Reversal（不能直接删除）
```

状态机要写每条转换的：发起角色、前置条件、产生副作用、是否可逆。

## 5. 写业务不变量

示例，最终以访谈决策为准：

1. 合格数和不良数不能为负。
2. 本次报工总数 = 合格 + 各不良数量。
3. 累计合格数不能无授权超过工单计划数。
4. 已关闭工单不能新增普通报工。
5. 每次提交有唯一客户端请求号，网络重试不重复报工。
6. Posted 记录不可直接编辑，只能冲销并重报。
7. 工序有先后约束时，后工序数量不能无依据超过前工序可转移数。
8. 批次追溯要求时，投入批次与产出批次必须关联。
9. 跨租户、跨工厂或无权限用户不能报工。
10. 若自动扣料/入库，业务单据与库存结果必须有可恢复的一致性方案。

这些句子以后直接变成测试名和验收条件。

## 6. 画领域数据，而不是一张万能表

可能实体：

```text
ProductionOrder
OperationTask
WorkReport
WorkReportDefect
WorkReportLabor
MaterialConsumption
OutputLot
EquipmentEvent
IntegrationOutbox
```

### 6.1 WorkReport 关键字段

```text
Id / TenantId
ReportNo
ClientRequestId       幂等键
ProductionOrderId
OperationTaskId
WorkCenterId / EquipmentId
ShiftDate / ShiftCode
StartedAt / EndedAt
GoodQty / DefectQty
Status
OperatorId / SubmittedBy
RowVersion
CreatedAt / PostedAt
```

不要把不良明细压成 JSON，除非查询、统计和约束都接受。若品质要按原因分析，不良原因应有结构化明细。

### 6.2 时间字段的含义

`ShiftDate` 不一定等于日历日期。夜班跨午夜，01:00 的报工可能属于前一天班次。存 UTC 时间用于技术排序，同时存业务班次归属；不要用 `CreatedAt.Date` 推断班次。

## 7. 命令与查询分开思考

命令：

```text
StartOperation
PauseOperation
SubmitWorkReport
ApproveWorkReport
PostWorkReport
ReverseWorkReport
```

查询：

```text
工人当前任务
班组进度看板
工单完成率
不良 Pareto
设备/人员工时
批次追溯链
待审批与失败过账
```

查询页面需要的宽 DTO 不等于写模型。强行让一个实体同时服务所有报表，后期会产生复杂导航、N+1 和越权字段。

## 8. API 设计从幂等开始

```http
POST /api/mes/work-reports
Idempotency-Key: terminal-17:20260722:000184
```

请求：

```json
{
  "operationTaskId": "...",
  "goodQty": 95,
  "defects": [
    { "reasonCode": "PRINT_SHIFT", "qty": 5 }
  ],
  "startedAt": "...",
  "endedAt": "..."
}
```

服务端以 `TenantId + IdempotencyKey` 唯一。同一 key 同一 payload 返回原结果；同一 key 不同 payload 返回冲突，不能悄悄覆盖。

弱网终端重试、用户双击和 401 refresh 重放都会因此安全很多。

## 9. 事务边界

一次提交可能要：

```text
INSERT WorkReport
UPDATE OperationTask progress/rowversion
INSERT Defect details
INSERT audit
INSERT outbox events
COMMIT
```

库存扣料、完工入库、工资和财务若都在远程服务，不能用一个本地数据库事务包住。选择：

- 同库强一致：同一事务写必要表。
- Outbox + 消费者幂等：异步传播。
- 状态机显示 Posting/Failed，允许重试和人工处理。
- 关键业务要求同步时，定义失败补偿，不假装分布式调用原子。

## 10. 并发场景

### 10.1 两台终端同时报最后 10 件

两边都读剩余 10，各报 10。若没有 rowversion/原子条件更新，累计会超计划。

方案：

```sql
UPDATE OperationTask
SET ReportedQty = ReportedQty + @qty
WHERE Id = @id
  AND RowVersion = @rowVersion
  AND ReportedQty + @qty <= PlannedQty;
```

或使用跟踪实体 rowversion，冲突后重新判断。业务允许超报时，也要显式权限和原因，而不是移除检查。

### 10.2 班组长补录与操作工同时报

补录不仅是权限问题，还涉及业务日期、已结算期间和追溯。可能需要独立 `BackfillWorkReport` 命令、原因、审批和审计。

## 11. 离线设计

车间网络不稳定时，前端本地队列记录：

```text
ClientRequestId
payload
createdAt
retryCount
lastError
status: pending/sending/sent/conflict/dead
```

安全问题：共享终端上的离线数据是否加密、退出是否清理、换班后谁能重发。同步时服务端仍是最终校验者，不能因为“离线时已经校验过”就跳过权限与状态检查。

冲突 UX 要能告诉用户：工单已关闭、数量超限、批次冻结，而不是统一“同步失败”。

## 12. 条码不是字符串输入框

需要定义：

- 条码类型与版本。
- 校验位/格式。
- 一个码表示工单、工序、批次还是组合载荷。
- 过期/作废码处理。
- 扫码枪回车、连扫、重复扫防抖。
- 手工输入的权限与审计。
- 解析失败的可操作提示。

扫码成功后界面要回显人能识别的信息，不能只显示一串 Id。

## 13. 追溯链

正向：原料批次 → 哪些报工/工单 → 产出批次 → 哪些客户发货。

反向：客诉产出批次 → 使用的原料批次、设备、班次、人员、质检记录。

追溯不是一个模糊“Remark”字段。关键关系需要结构化外键/关联表，并在冲销时保留历史。

## 14. OEE 不要只背公式

```text
Availability = RunTime / PlannedProductionTime
Performance = IdealCycleTime × TotalCount / RunTime
Quality = GoodCount / TotalCount
OEE = A × P × Q
```

系统难点不是乘法，而是时间分类：计划停机、换型、故障、待料、无订单分别算不算计划生产时间或停机。定义不统一，两个工厂的 OEE 不可比。

开发前必须得到损失代码字典和归类规则。

## 15. 验收条件写成 Given/When/Then

```text
Given 工序剩余可报 10，普通操作工已登录
When 在两台终端使用不同请求号同时各报合格 10
Then 只有一个提交成功
And 另一个收到可识别的数量冲突
And 最终累计不超过计划
And 只有一组库存/流水副作用
```

```text
Given 终端提交后响应丢失
When 使用同一 Idempotency-Key 重试相同 payload
Then 返回第一次生成的 ReportNo
And 不新增第二条 WorkReport
```

验收条件必须覆盖失败与恢复，不只是“点击保存成功”。

## 16. 上线与回滚

报工影响多模块，灰度顺序：

1. 先只记录不驱动库存/工资，与纸面并行核对。
2. 选一个班组/产品试点。
3. 对比数量、工时、班次和异常率。
4. 开启 outbox 消费但保留人工对账。
5. 扩大范围。

回滚不应删除已报数据。可关闭新入口、停止下游自动过账，保留记录供对账和后续恢复。

## 17. 必做工作坊

选择一个你熟悉的场景：领料、报工、盘点、质检或发货。交付：

1. 角色访谈表。
2. 状态机。
3. 十条不变量。
4. 核心实体与唯一键。
5. 命令/查询列表。
6. 两个并发场景。
7. 一个离线/重试场景。
8. 五条 Given/When/Then，其中至少三条失败路径。
9. 上线灰度和回滚方案。

## 18. 面试回答模板

> 用户说“扫码报工”时，我不会先画表单。我先去现场确认谁在什么时点扫什么，数据用于进度、库存、质量、工资还是 OEE；再画工序和报工状态机，写数量、关闭工单、冲销、批次追溯等不变量。提交接口带租户级幂等键，工序累计用 rowversion 或条件更新处理并发；同库的报工、明细、审计和 outbox 同一事务，库存/财务等下游由 outbox 幂等处理并暴露失败状态。弱网终端保留本地队列，但服务端重新校验。验收会覆盖双终端并发、响应丢失重试、已关闭工单、补录和下游失败，而不只测正常保存。

## 19. 闭卷验收

1. 把“扫码报工”追问成至少十五个问题。
2. 画工序和报工两个状态机。
3. 写十条业务不变量。
4. 解释为什么 Posted 记录要冲销而不是编辑。
5. 设计幂等键相同 payload/不同 payload 的行为。
6. 设计两终端并发报工测试。
7. 说明 OEE 真正难在数据定义而非公式。
8. 给出灰度上线和可恢复回滚方案。
