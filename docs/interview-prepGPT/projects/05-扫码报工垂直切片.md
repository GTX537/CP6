# 项目 5 · 从零设计扫码报工垂直切片

## 目标

从需求、数据模型、API、事务、Vue 页面到测试设计一个最小但能进试点的扫码报工功能。重点不是代码量，而是状态、不变量、幂等、弱网和下游一致性。

## 1. MVP 范围

包含：

- 扫工序任务码。
- 显示产品、工序、计划/已报数量。
- 输入合格数、不良数与原因。
- 提交报工。
- 同请求重试幂等。
- 班组长查看并冲销错误报工。
- 事务内写 WorkReport + detail + outbox。

不包含：完整 OEE、工资、复杂排产。它们只消费事件或后续迭代。

## 2. 决策清单

必须找业务确认：是否允许超报；PENDING 质量是否算合格；班次跨日；补录期限；前后工序数量约束；不良是否必须原因；报工是否自动入库/扣料；离线最长时间。

## 3. 状态机

```text
WorkReport: Draft → Submitted → Posted
                      └→ Rejected
Posted → Reversed（产生冲销单）

OperationTask: Released → InProgress → Completed → Closed
```

普通操作工不能修改 Posted。冲销引用原 ReportId，并生成相反下游事件。

## 4. 数据模型

```text
Mes_WorkReport
  Id, TenantId, ReportNo, ClientRequestId,
  OperationTaskId, GoodQty, DefectQty,
  ShiftDate, Status, OperatorId,
  RowVersion, CreatedAt, PostedAt, ReversalOfId?

Mes_WorkReportDefect
  WorkReportId, ReasonCode, Qty

IntegrationOutbox
  EventId, TenantId, Type, Payload, Status
```

约束：`UNIQUE(TenantId, ClientRequestId)`；defect sum=DefectQty 由服务验证；Good+Defect>0。

## 5. 命令 API

```http
POST /api/mes/work-reports
Idempotency-Key: terminal17-000184
```

服务流程：

```text
authenticate/tenant/permission/CSRF
→ validate shape
→ find existing idempotency result
→ load task tracking + rowversion
→ validate state/quantity/shift
→ create report/details
→ update task totals
→ insert outbox WorkReportPosted
→ SaveChanges transaction
→ return ReportNo
```

同 key 不同 payload 返回 409 `IDEMPOTENCY_KEY_REUSED`。

## 6. 查询 API

- GET task by scanned code：只返回当前租户、可报工字段。
- GET report history：分页、稳定排序。
- GET sync status by ClientRequestId：弱网终端查询结果。

不要让终端上传 TenantId/OperatorId 作为可信字段；来自服务端上下文。

## 7. Vue 页面状态

```text
idle
→ scanning
→ taskLoaded
→ editing
→ submitting
   ├→ success（显示 ReportNo，可继续下一单）
   ├→ conflict（保留输入，展示最新任务数量）
   └→ offlineQueued（显示本地待同步）
```

扫码连续输入要防重复；新任务加载使旧请求失效。提交按钮禁用只是 UX，幂等在后端。

## 8. 离线队列

本地保存 clientRequestId、payload、用户/租户绑定摘要、createdAt、retry。重新登录不同用户时不能自动发送前一用户队列。敏感数据考虑 IndexedDB 加密和终端管理。

同步结果分类：sent、retryable、conflict、rejected。冲突需要人工处理，不无限重试。

## 9. 下游事件

`WorkReportPosted` 包含稳定 EventId、ReportId、任务、数量、批次/时间。库存/成本消费者幂等。

若库存过账失败，报工显示 `PostedButIntegrationPending` 或在集成监控暴露，不删除报工伪装没发生。

## 10. 权限

- operator：创建自己的正常报工。
- supervisor：补录/冲销，要求原因。
- quality：维护不良处置，不一定能改数量。
- admin：配置，不默认拥有业务冲销。

前端隐藏按钮，后端每命令强校验。

## 11. 测试矩阵

- 正常合格+不良。
- defect sum 不等。
- 已关闭任务。
- 两终端并发超计划。
- 同幂等 key 同 payload。
- 同 key 不同 payload。
- 保存成功响应丢失重试。
- outbox consumer重复。
- 租户 A 扫 B 条码。
- 操作工尝试冲销。
- 离线队列换用户。
- Posted 冲销产生相反事件。

## 12. 试点指标

- 扫码到提交耗时。
- 重复/冲突率。
- 离线队列最老年龄。
- 报工与纸面差异。
- 下游 pending 数。
- 用户取消/手工改码频率。

## 13. 试点顺序

一个班组、单一产品/工序，先不自动财务；与纸面并行一周。每天对账后逐步打开库存/成本事件。保留功能开关和人工补偿工具。

## 14. 自我评审

- 状态转换和权限明确吗？
- 幂等是否含租户？
- 并发是否保护累计数量？
- Posted 是否不可直接编辑？
- 弱网/换用户安全吗？
- 下游失败是否可见可恢复？
- 验收是否包含失败路径？

## 15. 面试口述

按“现场问题—状态机/不变量—幂等与并发—事务+outbox—Vue 离线状态—权限/冲销—试点指标”回答，展示从需求到交付的完整开发思维。
