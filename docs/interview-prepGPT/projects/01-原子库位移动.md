# 项目 1 · 把库位移动改成单数据库原子操作

## 目标

当前 `MoveAsync` 分别调用两次 `ApplyAsync`。源库位 OUT 已提交后，目标库位 IN 失败会留下半移动。本练习在一个 SQL Server 事务中完成两腿，同时保留库存流水、冻结检查、负库存、租户、rowversion 和通知语义。

## 1. 不要马上改代码

先写验收：

```text
Given 源有 10、目标有 2，移动 3
When 请求成功
Then 源=7、目标=5
And 两条 MOVE 流水同一关联号

Given 目标写入失败
When 移动 3
Then 源、目标和流水都不变

Given A→B 与 B→A 并发
Then 不出现永久死锁；victim 可有限重试
And 最终总物理量守恒

Given commit 成功后通知失败
Then API 不把库存说成失败
And 有可重试通知记录/告警
```

核心不变量：

```text
source + destination 总量守恒
余额和两条流水同一事务
同租户
每腿数量关系正确
通知不属于数据库原子边界
```

## 2. 识别当前职责混合

`ApplyAsync` 同时：

- 校验请求。
- 检查冻结。
- 拥有事务。
- 读取/创建库存。
- 应用 delta。
- 检查负库存。
- 生成流水。
- Save/Commit。
- 调财务和通知。

为了复用两腿，不应在外层事务里调用一个自行提交的 public 方法。先拆：

```text
ApplyAsync               单腿公开用例，拥有事务
ApplyCoreAsync           在现有 Context/事务内改实体并创建流水，不提交
PublishAfterCommitAsync  commit 后副作用
```

## 3. 设计内部结果

```csharp
internal sealed record PendingMovement(
    Stock Stock,
    StockTransaction Transaction,
    StockChangedEvent Event);
```

`ApplyCoreAsync` 返回待发布数据，不在事务内调用 SignalR/财务。

内部方法参数要明确：

```csharp
private Task<PendingMovement> ApplyCoreAsync(
    StockMovementRequest request,
    CancellationToken ct);
```

不要暴露“skip validation”“skip transaction”多个 bool，让调用者组合出非法模式。事务所有权由只有两个清晰用例控制。

## 4. 单腿流程

伪代码：

```csharp
public async Task<string> ApplyAsync(StockMovementRequest request, CancellationToken ct)
{
    Validate(request);
    await using var tx = await db.Database.BeginTransactionAsync(ct);
    var pending = await ApplyCoreAsync(request, ct);
    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);

    await PublishAfterCommitAsync([pending], CancellationToken.None);
    return pending.Transaction.TxnNo;
}
```

为什么 commit 后不盲目继续 request token：客户端在 commit 时断开，库存仍可能已经成功。更成熟做法是事务内写 outbox，commit 后不依赖当前请求完成发布。

## 5. 两腿流程

```csharp
public async Task<MoveResult> MoveAsync(StockMoveRequest request, CancellationToken ct)
{
    ValidateMove(request);
    await using var tx = await db.Database.BeginTransactionAsync(ct);

    var legs = BuildLegsInStableOrder(request);
    var first = await ApplyCoreAsync(legs[0], ct);
    var second = await ApplyCoreAsync(legs[1], ct);

    await db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);

    await PublishAfterCommitAsync([first, second], CancellationToken.None);
    return MapResult(first, second, request);
}
```

返回结果不能因为稳定锁顺序打乱源/目标语义。给每腿带 `LegKind.Source/Destination`，最后按 kind 映射。

## 6. 稳定资源顺序

A→B 与 B→A 若各先锁自己的源，会死锁。用稳定键排序两个库存键：

```text
(TenantId, WarehouseCd, LocationCd, ProductCd, LotNo)
```

两个事务都先访问较小键，再访问较大键。EF 普通 SELECT 在 Read Committed 下是否取得预期更新锁需要实际 SQL/锁验证。可用明确原子 UPDATE、UPDLOCK 方案或存储过程，但不要只靠 C# 排序就声称彻底无死锁。

## 7. 新目标行并发创建

目标库存不存在时并发插入，需要数据库唯一约束：

```text
UNIQUE(TenantId, WarehouseCd, LocationCd, ProductCd, LotNo)
```

捕获唯一冲突后是否重试，要重新创建/清理 Context 状态。练习中先让事务失败并返回 409，再增加一次受控重试。

## 8. 流水关联

两条流水应共享稳定 MoveId/CorrelationId，而不只用第二条 `RelatedNo=outNo`。这样可查询未成对/重复，便于审计。

若不改 schema，至少保证：

- OUT 与 IN txnNo 不同。
- IN 的 RelatedNo 指 OUT。
- Remark 不作为机器关联。

## 9. 通知与财务

一次移动产生两腿，财务是否应收到两条库存移动还是一个移动事件要由归属规则决定。内部 `RelatedType=MOVE` 当前可能被财务桥过滤，练习要写测试确认，不凭注释猜。

推荐事务内写一个 `StockMoveCompleted` outbox，payload 包含两腿。SignalR 可按产品需要发送一个聚合事件，避免页面刷新两次。

## 10. 测试矩阵

| 场景 | Provider | 断言 |
|---|---|---|
| 正常移动 | SQL Server | 两余额、两流水、总量 |
| 源不足 | SQL Server/logic | 零修改 |
| 目标冻结 | SQL Server | 零修改 |
| 第二腿约束失败 | SQL Server | 第一腿回滚 |
| 并发同源扣减 | SQL Server | 一个成功/冲突 |
| A↔B | SQL Server | 可完成/有限 victim |
| 通知失败 | fake | DB 成功、outbox/告警 |
| 请求重复 | SQL Server | 幂等键不重复移动 |

## 11. 故障注入

在 `ApplyCoreAsync` 第二次调用后、Save 前抛异常；在 Save 后、Commit 前模拟；Commit 后 notifier 抛异常。每个点用新 Context 查询最终状态。

## 12. 自我评审

- 事务内是否有外部网络？
- 两腿是否共享同 Context/transaction？
- 访问顺序稳定吗？
- 新行唯一冲突怎样表现？
- 幂等键在哪里？
- 取消发生在 commit 后怎样报告？
- 测试是否真的用 SQL Server？
- 是否把计划中的 outbox 说成已实现？

## 13. 面试口述

用“当前缺口—不变量—拆事务所有权—稳定锁顺序—唯一/rowversion—outbox—集成测试”顺序讲两分钟。不要只说“把两个方法放一个事务里”。
