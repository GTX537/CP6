# 03 · 生产故障 STAR 与追问

旧版列出七个事故。本版不鼓励全背。先选三件你确实参与、能提供证据、能讲清个人动作的故事。若某件只是仓库文档里的案例而非亲历，不要使用第一人称“我处理了”。

## 1. 技术 STAR+

- S：时间、系统、用户影响。
- T：我的责任和恢复目标。
- A：证据链、假设、验证、修复。
- R：恢复和量化结果。
- +：根因、防复发、已知残余风险。

Action 是主体，至少占一半时间。

## 2. 故障叙事的证据链

优秀故事不是“发现 bug 然后修了”，而是：

```text
症状
→ 初始指标/日志
→ 两三个假设
→ 如何排除
→ 根因证据
→ 止血
→ 永久修复
→ 回归/生产验证
```

## 故事 A：磁盘满导致服务链故障

### 30 秒骨架

> 系统出现 API 和数据库同时不可用。我先按影响面止血，检查应用错误后发现数据库/容器异常，再向宿主磁盘追查，确认 WSL/容器存储无法增长。清理安全可回收空间并恢复服务后，我继续定位增长来源，补了容量阈值、日志保留和备份/恢复检查。这个事故让我把“服务健康”从进程存活扩展到宿主磁盘、数据库 ONLINE 和业务 smoke test。

## 故事 B：CSRF 豁免缺失导致外部回调 403

### 30 秒骨架

> 外部系统回调在生产被 CSRF 中间件拦成 403。根因不是认证失败，而是浏览器写请求的 CSRF 策略错误地覆盖了机器回调，外部系统无法提供双提交 token。我没有把整个路由段关闭，而是按精确端点形状豁免，并要求回调用 API key/签名等独立认证。随后补正向“合法回调通过”和反向“普通写接口仍被 CSRF 拦截”的测试，防止豁免过宽。

### 必须说清

- CSRF 面向 Cookie 浏览器威胁。
- 机器回调需要另一种真实性验证。
- 豁免要最小化。
- 测试必须双向，不能只测“通过”。

### 追问

- 攻击者伪造回调怎么办？
- 如何防重放？
- 签名内容和时间窗？
- 为什么 SameSite 不够？
- 如何在 staging 复现生产代理路径？

## 故事 C：跨租户写入风险

### 30 秒骨架

> 我们发现全局查询过滤器只自动保护读取，写接口若接受并信任请求体 TenantId，攻击者可能把数据写到别的租户。修复思路是边界 DTO 不接收 TenantId，服务端从认证上下文确定租户，并在 SaveChanges/写服务检查实体租户一致性。同时补负面测试：A 租户提交 B 的 TenantId、修改 B 实体、Dapper 漏条件和后台默认租户。核心经验是安全测试要验证“坏请求确实失败”，不能只测正常功能。

### 真实性提醒

当前 `StampTenant` 只在 Added 且 TenantId 为空时盖章。若要说“无条件覆盖/拒绝不一致”已实现，必须先核对最新代码。否则把它讲成发现的改进和测试计划。

## 故事 D：ExecuteUpdate 审计盲区

### 骨架

批量更新绕过 ChangeTracker 和 SaveChanges override，字段审计没有记录。先确认审计需求和影响数据，再选择：显式写审计、改为分批跟踪更新、引入数据库级变更捕获，或把该批量路径列为受控例外。修复后用“业务变更数 = 审计实体数/批次摘要”契约测试验证。

### 追问

- 大批量逐行审计容量怎么办？
- before/after 从哪里取？
- 事务如何保证？
- Dapper/DBA 修改怎么办？
- 审计是否可删除、谁能看？

## 故事 E：配置源顺序覆盖

### 骨架

本地 JSON 配置源如果在环境变量之后追加，会反向覆盖容器环境变量，导致连接错误。修复不是改一次连接串，而是把 Local 源插入 env source 之前，并为生产禁止/检查本地配置，启动时打印脱敏后的配置来源或做 ValidateOnStart。

### 追问

- 如何证明使用了哪个来源？
- 如何不泄漏 secret？
- Kubernetes Secret 如何映射？
- reloadOnChange 在生产的风险？
- 配置错误如何早失败？

## 故事 F：排序不稳定导致偶发测试

### 骨架

多个记录时间戳相同，只按 CreateDate 排序，测试偶发取错第一条。加 Id 只能提供确定性，不一定代表业务先后；更好的修复要定义权威顺序键，如流水号/版本。测试同时固定时间，构造并列值并验证稳定规则。

## 故事 G：测试装置本身有缺陷

### 骨架

测试失败不一定是产品 bug。隔离 fixture、时钟、共享数据库、并发和环境依赖，先证明测试可重复，再修改产品。最终修复测试装置并保留一个真正能拦产品回归的断言。

## 3. 故事选择矩阵

| 面试问题 | 首选 |
|---|---|
| 最严重生产事故 | 磁盘满 |
| 安全问题 | CSRF / 多租户 |
| 数据审计 | ExecuteUpdate |
| 最难定位 bug | 配置源 / 排序不稳 |
| 测试能力 | CSRF 双向测试 / 测试装置 |
| 如何防复发 | 任一故事的机制化收尾 |

## 4. 不要编的数字

影响用户数、停机时长、恢复时长、日志大小、测试数若无记录，就说：

> 具体数字我不想凭记忆报错。我能确认的是影响范围为 ___，从 ___ 到 ___ 恢复；准确时长我会从事故时间线核对。

## 5. 压力追问

### “这不是你造成的吗？”

> 根因归属和恢复责任要分开。无论最初变更是谁做的，我先负责恢复和证据保存。复盘时再用无责方式看为什么评审、测试、监控没有提前拦住。我个人负责的部分是 ___。

### “为什么测试没发现？”

不要说“测试环境和生产不一样”结束。分层回答：缺少哪种测试/环境契约/代理路径/负面断言，以及后来补了什么。

### “怎么证明修好了？”

至少三证：原复现步骤不再出现、自动化回归、生产/灰度指标恢复。安全修复再加反向测试，性能修复再加基线对比。
