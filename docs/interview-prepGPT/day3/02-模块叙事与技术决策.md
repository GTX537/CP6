# 02 · 模块叙事与技术决策

每张叙事卡遵循：业务问题 → 关键不变量 → 实现 → 个人决策 → 证据 → 限制 → 改进。

## 卡 1：库存/WMS

### 业务问题

仓库需要知道“什么货、在哪、多少、能否分配、来自哪个批次”，每次入出库还必须有流水可追溯。

### 不变量

- `AvailableQty = PhysicalQty - AllocatedQty`。
- 库存行和流水同事务。
- 不允许任意代码直接改库存。
- 租户、仓库、库位、产品、批次定义库存身份。
- QC/召回/盘点冻结影响是否可移动。

### 实现证据

- `Stock` 实体。
- `IStockMovementService`。
- `StockMovementService.ApplyAsync`。
- `StockController`。
- `StockQueryView.vue`。

### 决策与边界

> 我把单次库存变动集中在一个服务里，并让库存与流水同事务，防止只改数量不留痕。事务提交后再做财务桥和 SignalR 通知，避免通知故障回滚主库存。但这带来最终一致问题，当前空 catch 的可观测性也不足。另一个已知限制是 MoveAsync 两腿分两次提交，我会优先改为同一数据库事务内同时更新来源和目标。

### 追问

- 热点库存如何防超卖？
- 新库存行并发创建？
- FEFO/QC/召回怎样影响分配？
- outbox 如何补桥接可靠性？
- 盘点期间为什么冻结？

## 卡 2：多租户与权限

### 业务问题

一套 SaaS 服务多个企业，普通用户只能看本租户数据；平台运维有受控跨租户能力。

### 实现

- `BaseTenantEntity.TenantId`。
- 全局查询过滤器。
- SaveChanges 新增盖章。
- `TenantMiddleware` 从身份建立租户上下文。
- `TenantScopeRunner` 为后台任务逐租户 scope。
- `[RequirePermission]` 后端动作权限。
- `v-permission` 前端 UX。

### 决策与边界

> 自动过滤减少每条查询手写 TenantId 的漏口，但我不会把它说成绝对隔离。IgnoreQueryFilters、Dapper、特殊表、后台任务和写入非空错误 TenantId 都是绕过面。当前新增盖章只在 TenantId 为空时执行，更严格的普通租户写路径应拒绝或覆盖不一致租户值，并用负面测试验证。

### 方案取舍：单库 vs 每租户一库

单库共享表运维和资源利用更简单，跨租户平台能力更方便；代价是应用隔离和大租户噪声风险。独立库隔离/备份更强，但迁移、连接、成本和跨租户运营复杂。根据合规、客户规模、恢复要求和成本选择，也可分层混合。

## 卡 3：前端认证与权限

### 业务问题

浏览器登录要降低 token 被脚本直接窃取风险，同时处理 Cookie 自动携带导致的 CSRF，并让过期请求平滑刷新。

### 实现

- httpOnly 访问/刷新 Cookie。
- 非敏感 `cp6_authed` 只做前端信号。
- axios `withCredentials`。
- 双提交 CSRF。
- `refreshPromise` 合并并发 401。
- 每个请求最多重放一次。

### 边界

- httpOnly 不防同源 XSS 发操作。
- CSRF 不防 XSS。
- POST 重放要考虑幂等。
- 多标签页刷新竞争。
- v-permission 不是安全边界。

## 卡 4：EF Core + Dapper

### 决策

> 大部分实体写入和普通查询用 EF，利用映射、跟踪、迁移和统一 SaveChanges 横切；复杂报表或需要精确 SQL 的路径用 Dapper。代价是两套数据访问要统一租户、软删、超时、事务和审计规范，否则 Dapper 会绕过 EF 自动机制。

### 何时改选

- 纯 CRUD 不为“性能”盲目换 Dapper。
- 大型聚合先看 EF 生成 SQL；不可控再 Dapper。
- 批量导入可用 bulk 工具/原生 SQL，但显式补审计。

## 卡 5：Kafka + RabbitMQ

### 当前叙事

Kafka 用于可保留、可回放的操作日志流；RabbitMQ 用于业务通知/路由。不要绝对化为“Kafka 不可靠、RabbitMQ 可靠”。可靠性取决于配置和处理协议。

### 深挖

- 手动 offset commit 仍可能重复。
- 消费者幂等。
- DLQ、重试和 poison message。
- 顺序只在 Kafka 分区内。
- 多实例消费组的分区分配。

## 卡 6：页面模板标准化

### 问题

大量管理页面重复搜索、分页、表格和错误处理，复制粘贴造成不一致。

### 方案

`CpPageShell` + `CpListPage` + columns/searchFields 配置覆盖通用结构；slots 和原生 Dialog 是逃生舱。

### 取舍

标准化提高一致性和新页面速度，但抽象过度会形成难懂 DSL。评估指标：页面代码减少不是唯一目标，还看特殊需求表达、类型安全、回归半径和测试。

## 卡 7：强一致与最终一致

分界：

- 库存行 + 库存流水：同数据库本地事务，强一致。
- 提交后 SignalR：可丢的即时体验，客户端可重查。
- 库存 → 财务桥：若业务要求最终到达，应 outbox + 幂等，不应空 catch 后永久丢失。

面试亮点不是“用了事务”，而是说清事务能覆盖和不能覆盖的边界。

## 卡 8：测试策略

按风险分层：

- 纯函数：单元测试。
- EF 查询/约束：SQLite/SQL Server 集成测试。
- 权限/租户：负面契约和反射守卫。
- API：HTTP 集成。
- 前端：store/composable 单元、组件交互、少量 E2E。
- 生产关键链：部署后 smoke/canary。

不要只报总测试数。说明哪种风险由哪层测试拦。
