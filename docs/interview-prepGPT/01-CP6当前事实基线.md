# CP6 当前事实基线

本文只记录对面试准备有用、能从当前仓库核对的事实。它不是产品宣传页。日期基线为 **2026-07-22**。

| 层 | 当前事实 | 证据 |

## 2. 项目分层

```text
cp6.web
   │ HTTP / WebSocket
   ▼
CP6.WebApi
   │ 引用
   ▼
CP6.Core
   │ 引用
   ▼
CP6.Entity

CP6.Tests → 引用 WebApi / Core / Entity
```

各层职责：

- `CP6.Entity`：实体、DTO、标记接口、特性。
- `CP6.Core`：服务、EF 上下文、仓储、跨模块契约和工具。
- `CP6.WebApi`：Controller、DI 装配、中间件、过滤器、Hub、后台任务。
- `cp6.web`：页面、组件、API 封装、store、路由、国际化。
- `CP6.Tests`：单元测试、契约测试、反射守卫和部分集成测试。

“分层”不等于每个 Controller 都必须经过 Service。当前 `StockController.Search` 直接使用 `CP6Context` 组合只读查询，而库存写入通过 `IStockMovementService`。这是 CQRS 风格的一点影子：简单读路径可以直接查询，关键写路径集中业务不变量。

## 3. 一条库存读路径

```text
StockQueryView.vue
  → stockApi.search(...)
  → axios /api/wms/stock
  → ASP.NET Core 中间件管道
  → StockController.Search
  → IQueryable<Stock> 动态拼条件
  → SQL Server COUNT + 分页 SELECT
  → JSON
  → CpListPage 渲染
```

关键事实：

- 前端当前页面只有约 248 行，已使用 `CpPageShell` 和 `CpListPage` 模板，不是旧版教程里的大段手写表格结构。
- 后端读查询使用 `AsNoTracking()`。
- 条件在 `IQueryable` 上组合，直到 `CountAsync()` 和 `ToListAsync()` 才执行。
- 排序包含仓库、库位、产品、批次，再分页，结果比只按时间排序稳定。

## 4. 一条库存写路径

```text
POST /api/wms/stock/apply
  → [Authorize]
  → [RequirePermission("wms-stock", "adjust")]
  → StockController.Apply
  → IStockMovementService.ApplyAsync
  → 校验 + 盘点冻结检查
  → 事务
  → 更新/创建 Stock
  → 插入 StockTransaction
  → SaveChanges
  → Commit
  → 财务桥接与 SignalR 通知（best effort）
```

这里有三层一致性：

1. **事务内强一致**：库存行与库存流水一起提交。
2. **并发控制**：实体设计预期用 RowVersion 处理乐观并发。
3. **事务后副作用**：财务桥接和通知失败不回滚库存主交易。

必须诚实说明当前限制：`MoveAsync` 调用两次 `ApplyAsync`，来源 OUT 和目标 IN 不是同一个数据库事务。代码已有“双腿非原子”的注释和目标库位预检，但仍存在两腿之间失败的补偿问题。面试里可以把它讲成“识别到的改进项”，不能说已经实现原子移库。

## 5. 多租户隔离事实

多租户实体继承 `BaseTenantEntity`，获得 `TenantId`。`CP6Context` 在模型构建时反射扫描这类实体并注册查询过滤器：

```text
读：WHERE TenantId == CurrentTenantId
写：Added 且 TenantId 为空时，SaveChanges 前盖当前租户
```

这能减少漏写租户条件，但不是绝对安全证明。必须知道绕过面：

- `IgnoreQueryFilters()`。
- Dapper 或原生 SQL。
- 不是 `BaseTenantEntity` 的特殊表。
- 更新/附加一个已经带错误 TenantId 的实体；当前盖章逻辑只处理 `Guid.Empty`。
- 后台任务没有 HTTP/JWT，需要显式按租户创建 scope。

`TenantScopeRunner` 正是为后台任务提供逐租户 scope。

## 6. 请求管道当前顺序

当前 `Program.cs` 底部主要顺序：

```text
UseCors
UseHttpMetrics
UseAuthentication
TenantMiddleware
UseRequestLocalization
BizExceptionMiddleware
CsrfMiddleware
MustChangePasswordMiddleware
UseAuthorization
MapControllers / MapHub / MapMetrics
```

面试回答要解释依赖关系：

- 租户和语言读取用户 claim，所以在认证之后。
- 业务异常中间件包住后续业务，以便转换异常。
- CSRF 和强制改密要在授权及端点执行前拦截。
- `UseAuthentication` 负责建立身份，`UseAuthorization` 负责按规则决定是否允许。

## 7. 前端认证事实

当前前端不是“把 JWT 放 localStorage 再手动加 Authorization 头”的旧模式：

- 访问令牌/刷新令牌由 `httpOnly` Cookie 承载。
- axios 使用 `withCredentials: true`。
- 非安全 HTTP 方法从可读 CSRF Cookie 取值，写入 `X-CSRF-Token`。
- 并发 401 共享一个 refresh Promise，避免同时刷新多次。
- `localStorage` 的 `cp6_authed` 只是非敏感登录态信号，不是令牌。

因此回答 JWT 题时应区分“JWT 标准原理”和“CP6 当前浏览器承载方式”。

## 8. 前端权限事实

`v-permission` 会根据 Pinia 中的 action key 移除无权限元素。它只改善用户体验，安全边界仍在后端 `[RequirePermission]`。

一个值得讨论的边界：store 尚未加载时指令暂时保留元素，属于 UI 层 fail-open；后端必须 fail-closed。不要把 UI 的暂时可见说成权限漏洞，除非后端也缺少校验。

## 9. 异步与后台任务事实

`KafkaOperLogConsumer` 展示了三个重点：

- Kafka 的 `Consume` 是阻塞调用，因此使用 LongRunning 线程承载循环。
- `EnableAutoCommit=false`，成功落库后再提交位移，语义接近“至少一次”。
- `BackgroundService` 是单例宿主，使用 `IServiceScopeFactory` 创建 scope 解析 `CP6Context`。

“至少一次”意味着消费者可能重复处理。凡有外部副作用，应讨论幂等键或去重约束。
