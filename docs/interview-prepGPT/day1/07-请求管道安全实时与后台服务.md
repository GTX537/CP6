# 07 · 请求管道、安全、实时通信与后台服务

## 1. 中间件是嵌套调用，不是简单清单

请求按注册顺序进入，响应按相反顺序返回：

```text
Middleware A before
  Middleware B before
    Endpoint
  Middleware B after
Middleware A after
```

中间件可以：

- 在调用 next 前拒绝请求。
- 修改请求上下文。
- 捕获后续异常。
- 在 next 后修改响应或记录耗时。

## 2. CP6 当前管道

```text
CORS
→ HTTP Metrics
→ Authentication
→ TenantMiddleware
→ RequestLocalization
→ BizExceptionMiddleware
→ CsrfMiddleware
→ MustChangePasswordMiddleware
→ Authorization
→ Controller / Hub
```

逐层依赖：

- Metrics 要包住后续处理以观察耗时。
- Authentication 先解析 Cookie/JWT 建立 `User`。
- Tenant 和语言需要读取 claim。
- BizException 要包住会抛业务异常的下游。
- CSRF 和强制改密在业务端点前拒绝。
- Authorization 在身份和租户上下文已经就绪后检查权限。

### 顺序错误的可观测后果

| 错误 | 结果 |
|---|---|
| Tenant 在 Authentication 前 | 读不到 claim，可能落到默认租户 |
| Authorization 在 Authentication 前 | 已有凭证仍被当匿名或策略失效 |
| 异常处理中间件放在端点后 | 捕获不到端点异常 |
| 本地化在异常转换后 | 错误消息使用错误语言 |
| CSRF 在端点后 | 写请求已经执行，拦截失去意义 |

## 3. 中间件、过滤器和端点过滤器

| 机制 | 范围 | 能看到什么 | 适用 |
|---|---|---|---|
| 中间件 | 全应用 | HttpContext，MVC 之外也生效 | 异常、认证、租户、CSRF |
| MVC 过滤器 | Controller 管道 | Action、参数、结果 | 操作日志、MVC 授权/结果 |
| Action 内代码 | 单端点 | 完整业务上下文 | 端点特有分支 |

CP6 `OperLogFilter` 是 Action Filter；BizException/CSRF 是中间件。选择取决于需要的上下文和覆盖范围。

## 4. 认证与授权

- 认证：你是谁？
- 授权：这个身份能做什么？

`[Authorize]` 只要求已认证。细粒度动作权限由 `[RequirePermission("wms-stock", "adjust")]` 等特性检查。

前端 `v-permission` 移除按钮只是 UX。攻击者能直接调用 HTTP API，因此后端授权才是安全边界。

## 5. JWT 的准确回答

JWT 通常由三段 Base64Url 文本组成：Header、Payload、Signature。签名保证内容未被篡改，不提供加密；任何拿到 token 的人通常都能读取 payload。

验证至少包括：

- 签名。
- issuer。
- audience。
- 过期时间与时钟偏差。
- 必要时 jti 黑名单/撤销状态。

### CP6 当前浏览器承载

访问和刷新令牌放 httpOnly Cookie，JavaScript 不直接读取。优点是降低 XSS 直接窃取 token 的风险；代价是浏览器会自动带 Cookie，因此必须处理 CSRF。

不要回答成“JWT 放 localStorage，axios 自动加 Authorization”，那是旧模式或另一种选择，不符合当前 `http.ts`。

## 6. CSRF 双提交

当前前端对 POST/PUT/PATCH/DELETE 等非安全方法：

1. 浏览器自动携带认证 Cookie。
2. JS 读取非 httpOnly 的 CSRF Cookie。
3. 写入 `X-CSRF-Token` 请求头。
4. 后端比较 Cookie 与 Header，并结合端点豁免规则。

攻击站点能诱导浏览器带认证 Cookie，但通常不能读取同源 CSRF Cookie并构造正确自定义头。

边界：

- XSS 可以在同源上下文读取 CSRF 值并发请求，所以 CSP、输出编码仍重要。
- SameSite 是额外防线，不应代替完整威胁建模。
- webhook/外部回调通常不能提供浏览器 CSRF 头，需要精确豁免和另一种认证。

## 7. 401 与 403

- 401：身份不存在、无效或过期，通常引导重新认证。
- 403：身份有效，但权限不足。

把 403 自动当 401 刷新 token 没有意义，甚至造成循环。前端拦截器应分别处理。

## 8. 刷新令牌并发

CP6 `http.ts` 用模块级 `refreshPromise` 合并并发 401：第一个请求触发 refresh，其余等待同一 promise，再各自重放一次。

需要防：

- refresh 自身 401 再递归 refresh。
- 原请求无限重放，使用 `_retried` 标记。
- 非幂等请求重放是否安全。
- 多标签页之间 refresh 竞争。
- 刷新令牌轮换与旧 token 撤销。

## 9. CORS 不是认证

CORS 是浏览器对跨源读取的策略。它不能阻止 curl、后端服务或恶意客户端直接访问 API。即使 CORS 只允许某个站点，也必须认证授权。

带凭证的跨源请求不能随意用通配符 origin。生产 `AllowAll` 要谨慎评估，开发便利配置不应自动等同生产策略。

## 10. 全局异常响应

一个成熟错误响应应有：

- 稳定错误码。
- 用户可理解、可本地化的信息。
- HTTP 状态。
- trace/correlation ID。
- 服务端日志中的完整异常。

不把堆栈、SQL、连接字符串返回客户端。业务异常与未知异常分别处理。

## 11. SignalR

SignalR 抽象实时连接，优先使用 WebSocket，必要时回退其他传输。

CP6 Hub：Notify、MES、WMS、Space。库存提交后通过 `IWmsNotifier` 推送变动。

必须说明：实时通知不是数据库事实源。客户端断线、重连、消息丢失或重复时，应能重新查询权威状态。通知更像“有变化，请刷新/合并”，而不是唯一账本。

### 扩容边界

多实例部署时，客户端连接分散在不同实例。需要 backplane 或托管 SignalR 服务传播消息，并处理粘性会话/连接路由。

## 12. BackgroundService 生命周期

标准循环：

```csharp
protected override async Task ExecuteAsync(CancellationToken stoppingToken)
{
    while (!stoppingToken.IsCancellationRequested)
    {
        await RunOnceAsync(stoppingToken);
        await Task.Delay(interval, stoppingToken);
    }
}
```

生产要求：

- 启动时配置验证。
- 正确响应停止 token。
- 单轮异常不能静默杀死整个 worker。
- 重试有退避和上限。
- 多实例下有租约、分区或幂等。
- 记录最后成功时间、积压量和失败数。

## 13. 多租户 Worker

HTTP 请求从 JWT 取得租户；后台任务没有 JWT。若直接用默认租户上下文，只会处理默认租户。

`TenantScopeRunner` 的关键顺序：

```text
枚举租户
→ 每个租户创建新 scope
→ 先设置 ITenantContext.CurrentTenantId
→ 再解析/使用 CP6Context 和业务服务
```

为什么必须在同一 scope：DbContext 读取的租户上下文必须和刚设置的是同一个 scoped 实例。

## 14. 消息系统的角色

CP6 代码意图：Kafka 处理高吞吐 append-only 操作日志；RabbitMQ 处理业务通知/路由。

面试不要只说“Kafka 吞吐高、RabbitMQ 可靠”。更完整的比较：

| 维度 | Kafka | RabbitMQ |
|---|---|---|
| 核心模型 | 分区日志 | 消息代理与队列 |
| 重放 | 原生强项 | 通常不是核心消费模型 |
| 顺序 | 分区内 | 队列/消费者配置相关 |
| 路由 | topic/partition | exchange/routing key 丰富 |
| 消费状态 | offset | ack/队列状态 |

具体可靠性取决于副本、持久化、确认、重试和幂等配置，不由产品名自动保证。

## 高频陷阱

1. CORS 能阻止非浏览器攻击者。
2. JWT payload 是加密的。
3. 只要 httpOnly 就不需要 CSRF。
4. 前端隐藏按钮就是授权。
5. SignalR 消息可以替代数据库重新同步。
6. BackgroundService 可以直接持有 DbContext。
