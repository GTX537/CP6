# 04 · 异步、取消与并发

## 1. 先分清四个概念

| 概念 | 问题 | 例子 |
|---|---|---|
| 异步 | 等待期间不占着当前执行线程 | 等数据库、HTTP、文件 I/O |
| 并发 | 多个任务在时间上交错推进 | 同时请求三个独立服务 |
| 并行 | 多个计算在同一时刻使用多个核心 | 图像处理、批量 CPU 计算 |
| 多线程 | 使用多个 OS 线程 | 并行计算、阻塞库隔离 |

`async/await` 是异步控制流语法，不等于多线程，也不自动并发。

## 2. Web 服务器为什么需要异步 I/O

同步数据库调用等待 100ms 时，线程被占用却没有计算。异步调用把等待交给底层 I/O 机制，线程回线程池处理其他请求；完成事件到达后，再安排后续代码。

收益主要是**吞吐和资源利用率**，不是承诺单次请求更快。异步还有状态机、Task 和调度开销，小型纯 CPU 方法强行 async 可能更慢。

## 3. Task 是什么

`Task` 表示一个未来完成的操作，包含完成、失败或取消状态。它不是线程句柄。

```csharp
Task<Stock?> pending = db.Stocks.FirstOrDefaultAsync(..., ct);
Stock? stock = await pending;
```

一个 Task 可能：

- 立即同步完成。
- 以后由 I/O 完成通知推进。
- 在线程池运行 CPU 工作。
- 由另一个 Task 组合而来。

## 4. async 状态机

编译器把 async 方法改写成状态机。遇到未完成的 await：

1. 保存局部变量和当前位置。
2. 注册 continuation（后续动作）。
3. 把控制权返回调用者。
4. 等待对象完成后恢复状态机。

这解释了三个现象：

- async 方法在第一个未完成 await 前同步执行。
- await 不会阻塞当前线程。
- 异常存入 Task，在 await 时重新抛出。

## 5. `Task.Run` 的使用边界

| 工作 | ASP.NET Core 中通常做法 |
|---|---|
| 异步数据库/HTTP | 直接 await 异步 API |
| 短 CPU 计算 | 直接计算，避免无谓切线程 |
| 大 CPU 计算 | 后台队列/独立服务，或受控并行 |
| 只有阻塞 API 的调用 | 隔离到专用线程/Task.Run，评估容量 |

不要把同步 EF 查询包进 `Task.Run` 假装异步。它仍占线程，并让 DbContext 生命周期更难控制。

CP6 的 Kafka `Consume` 是阻塞式 API，`KafkaOperLogConsumer` 使用 LongRunning 线程承载循环。这是“隔离阻塞调用”，不是异步 I/O 示例。

## 6. 顺序 await 与并发启动

```csharp
var stockTask = LoadStockAsync(ct);
var priceTask = LoadPriceAsync(ct);
await Task.WhenAll(stockTask, priceTask);

var stock = await stockTask;
var price = await priceTask;
```

仅当两个操作相互独立时才并发。常见风险：

- 同一 `DbContext` 不支持并发操作。
- 下游服务有并发限制。
- 失败聚合与部分成功如何处理。
- 并发无上限导致连接池或内存耗尽。

## 7. 限流

```csharp
using var gate = new SemaphoreSlim(8);

async Task HandleAsync(Item item, CancellationToken ct)
{
    await gate.WaitAsync(ct);
    try
    {
        await ProcessAsync(item, ct);
    }
    finally
    {
        gate.Release();
    }
}
```

“并发越多越快”是错误命题。并发上限应根据数据库连接池、下游配额、CPU、内存和实际压测确定。

## 8. CancellationToken 是合作式取消

token 只发送信号，代码和底层 API 必须观察它。

传播规则：

```text
HTTP RequestAborted
  → Controller 参数 CancellationToken
  → Service
  → EF Core / HttpClient / Delay
```

不要无故在中间层换成 `CancellationToken.None`。也不要在事务已经完成后因为客户端断开而撤销必须完成的可靠发布；要先定义“取消边界”。

### 正常处理取消

```csharp
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    throw;
}
```

取消通常不应按系统故障记录 Error。后台服务停止时尤其如此。

## 9. 超时不是取消的同义词

超时是策略，取消是信号。可以用链接 token：

```csharp
using var timeoutCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
timeoutCts.CancelAfter(TimeSpan.FromSeconds(2));
await client.SendAsync(request, timeoutCts.Token);
```

还要区分：调用方等待超时后，底层操作是否真的停止；如果底层不支持取消，它可能继续消耗资源。

## 10. `.Result` / `.Wait()` 的风险

- 在带 SynchronizationContext 的 UI/旧 ASP.NET 环境可能死锁。
- 在 ASP.NET Core 即使不典型死锁，也会阻塞线程，造成线程池饥饿。
- 异常包装与代码可组合性变差。

原则是 async all the way。同步入口必须调用异步代码时，需要非常明确的边界设计，而不是随处 `.Result`。

## 11. `async void`

除 UI 事件处理器外，业务异步方法应返回 `Task`/`Task<T>`：

- 调用方能等待。
- 异常能进入 Task。
- 测试能观察完成。
- 取消和组合更清晰。

## 12. Fire-and-forget

在请求内直接：

```csharp
_ = SendEmailAsync();
```

可能丢异常、使用已释放 scoped 服务，并在进程重启时丢任务。更可靠的模式：

- 内存 `Channel` + `BackgroundService`，适合可丢或短期任务。
- 数据库 outbox/作业表，适合必须最终完成。
- 消息队列，适合跨服务可靠传递。

## 13. BackgroundService 与 scope

Hosted Service 通常是 singleton，DbContext 是 scoped。正确做法：

```csharp
using var scope = scopeFactory.CreateScope();
var db = scope.ServiceProvider.GetRequiredService<CP6Context>();
await db.SaveChangesAsync(ct);
```

多租户后台任务还要设置正确租户。CP6 的 `TenantScopeRunner` 先取租户清单，再逐租户创建新 scope 并设置 `ITenantContext`。

## 14. Kafka 消费语义分析

CP6 `KafkaOperLogConsumer`：

```text
Consume
  → 反序列化
  → 创建 scope
  → 写数据库
  → SignalR 推送
  → Commit offset
```

如果数据库成功、SignalR 成功，但 offset 提交前进程崩溃，消息会再次消费。因此“处理成功才提交”提供至少一次倾向，不提供恰好一次。数据库写入最好有幂等键；通知也要允许重复。

## 15. ValueTask

`ValueTask<T>` 可能减少“经常同步完成”热路径的 Task 分配，但使用复杂：

- 通常只能 await 一次。
- 不应随意缓存或多次组合。
- 若大多数情况仍异步，未必更省。

普通业务代码默认 `Task<T>`。只有测量证明分配值得优化时才用 ValueTask。

## 16. 异步流

`IAsyncEnumerable<T>` 允许边读取边处理，降低一次性物化大结果的峰值内存：

```csharp
await foreach (var row in QueryRowsAsync(ct).WithCancellation(ct))
{
    await WriteRowAsync(row, ct);
}
```

边界：数据库连接会保持更久；消费者太慢会占资源；跨网络输出要考虑断开和背压。

## 高频陷阱

1. async 自动新建线程。
2. await 后一定换线程。
3. `Task.WhenAll` 能安全并发同一个 DbContext。
4. CancellationToken 会强制杀死方法。
5. fire-and-forget 加 `_ =` 就安全。
6. Kafka 手动提交就等于恰好一次。
