# 03 · 委托、异常、可空与现代 C#

## 1. 委托：有类型的方法引用

委托把“以后要执行的行为”作为值传递。它包含目标方法签名，可能还包含目标对象。

```csharp
Func<decimal, decimal, decimal> price = (qty, unitPrice) => qty * unitPrice;
Action<string> log = message => Console.WriteLine(message);
Predicate<Stock> hasAvailable = stock => stock.AvailableQty > 0;
```

| 类型 | 返回 | 例子 |
|---|---|---|
| `Action<T...>` | void | 通知、日志 |
| `Func<T..., TResult>` | TResult | 计算、策略、工厂 |
| `Predicate<T>` | bool | 条件判断；很多 API 直接用 `Func<T,bool>` |

接口适合较大、具名、可演进的能力；委托适合单一行为和局部策略。不要为了“解耦”把复杂协议塞进一个超长 `Func`。

## 2. Lambda 与闭包

Lambda 可以捕获外层变量。编译器通常把被捕获变量提升到一个闭包对象，因此它的生命周期可能超过原方法。

```csharp
var actions = new List<Action>();
for (var i = 0; i < 3; i++)
{
    var copy = i;
    actions.Add(() => Console.WriteLine(copy));
}
```

现代 C# 的 `for` 变量捕获仍应显式理解共享变量问题。更重要的生产风险：

- 长生命周期回调捕获大对象，阻止 GC。
- 捕获 scoped 服务并把委托保存到 singleton。
- 多线程修改同一捕获变量，引入竞争。

## 3. 事件

`event` 限制外部只能订阅/退订，不能直接覆盖或触发发布者的委托。

订阅关系会形成引用。长生命周期发布者持有短生命周期订阅者时，忘记退订可能造成内存泄漏。弱事件或 `IDisposable` 订阅句柄是常见治理方式。

SignalR 是跨进程/网络的实时消息通道，不等同于 C# 进程内事件；二者都可表现发布订阅，但可靠性、序列化、连接和重试语义完全不同。

## 4. 异常的职责

异常适合表达当前调用无法正常完成的失败，不适合普通分支控制。

### 捕获原则

只在能做至少一件事时捕获：

- 恢复或降级。
- 增加有用上下文后重新抛出。
- 转换为边界协议，如 HTTP 错误。
- 记录一次且避免重复日志。

```csharp
try
{
    await service.ApplyAsync(request, ct);
}
catch (InsufficientStockException ex)
{
    return BadRequest(new { code = 400, message = ex.Message });
}
```

这里 Controller 能把领域失败翻译为 HTTP 400，因此捕获有意义。

### `throw` vs `throw ex`

在 catch 中 `throw;` 保留原始堆栈；`throw ex;` 会重置抛出点信息。若需要包一层：

```csharp
catch (SqlException ex)
{
    throw new InventoryPersistenceException("保存库存变动失败", ex);
}
```

保留 inner exception，但外部响应不能泄漏敏感数据库信息。

## 5. `finally` 与资源释放

`finally` 无论成功还是异常都会执行，但 `using`/`await using` 更适合资源生命周期：

```csharp
await using var tx = await db.Database.BeginTransactionAsync(ct);
```

不要在 `finally` 中抛出新异常覆盖原异常。释放失败若必须记录，需保留主异常上下文。

## 6. 业务异常、系统异常与取消

| 类型 | 例子 | 常见处理 |
|---|---|---|
| 业务拒绝 | 库存不足、期间已关账 | 4xx + 稳定错误码 |
| 输入错误 | 必填缺失、格式错误 | 模型验证/400 |
| 并发冲突 | RowVersion 变化 | 409，提示刷新/重试 |
| 系统故障 | DB 断开、磁盘满 | 5xx、告警、追踪 ID |
| 主动取消 | 客户端断开/超时 | 通常不当系统错误报警 |

不要捕获所有 `Exception` 然后返回 200 + `code=-1`，这会破坏 HTTP 语义和监控。

## 7. 可空引用类型的正确心智

可空注解是契约和静态分析，不是运行时护盾。

```csharp
public string ProductCd { get; set; } = string.Empty;
public string? OwnerCd { get; set; }
```

第一个表达“正常状态必须有值”，但 `string.Empty` 只是避免编译器警告，不代表业务验证已完成。仍要用 DataAnnotations、FluentValidation 或服务校验约束非空、长度和格式。

### 运算符

- `?.`：空条件访问。
- `??`：为空时使用后备值。
- `??=`：为空时赋值。
- `!`：只压制编译器警告，不做运行时检查。

`!` 是承诺，不是修复。每次使用都应能说明为什么这里运行时不可能为空。

## 8. 模式匹配

模式匹配把类型判断、解构和条件放在可读结构中：

```csharp
var label = stock switch
{
    { RecallFlag: true } => "禁止出库",
    { QcStatus: StockQcStatus.Failed or StockQcStatus.Hold } => "质检冻结",
    { AvailableQty: <= 0 } => "无可用库存",
    _ => "可分配"
};
```

优点是穷尽性和接近业务规则；条件过于复杂时仍应提取具名方法，避免“聪明的一行”。

## 9. record、init、required

```csharp
public sealed record StockKey(
    string WarehouseCd,
    string LocationCd,
    string ProductCd,
    string LotNo);
```

record 自动提供结构化相等和友好打印，适合组合业务键这样的值对象。

- `init` 只允许初始化阶段赋值。
- `required` 要求调用方在初始化时提供，但反射/反序列化仍需测试。
- record 属性若引用可变列表，record 本身不代表深层不可变。

## 10. `IDisposable`、`IAsyncDisposable`

`IDisposable` 释放同步资源；`IAsyncDisposable` 允许异步清理，例如需要异步 flush/close 的资源。

依赖注入容器创建的服务通常由容器负责释放，不要在业务代码中手动 Dispose 注入的 DbContext。

## 11. CP6 批判性案例：吞异常的 best effort

`StockMovementService` 在事务提交后调用财务桥和 SignalR 通知，并用空 catch 吞掉失败。这表达了“副作用不能让主库存交易失败”的业务选择，但空 catch 会损失可观测性。

更成熟的答法：

> 主交易提交后通知采用 best effort 是合理边界，但至少应记录结构化日志或写 outbox/重试表。否则失败既不回滚，也没有补偿证据。若财务过账必须最终一致，我会用 outbox 让库存提交和待发布事件同事务落库，再由后台可靠分发。

这是“理解现状 + 识别代价 + 给出改进”，比无条件夸项目更可信。

## 高频陷阱

1. Lambda 不分配对象。
2. event 会自动避免内存泄漏。
3. 所有异常都应该 catch 并记录。
4. `throw ex` 和 `throw` 一样。
5. `string!` 会在运行时检查非空。
6. record 一定是不可变和值类型。
