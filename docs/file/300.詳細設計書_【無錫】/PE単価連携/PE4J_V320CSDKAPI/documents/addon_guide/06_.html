6. POWER EGG3.0エンジンと開発のためのAPI¶

6.1. 共通処理エンジン¶

このパッケージでは、カレンダー、区分など各サブシステムで共通に扱うデータを管理しています。

6.1.1. カレンダーAPI¶

EJB： net.poweregg.common.CalendarService

カレンダーAPIでは、特定年月日の属性情報を管理する機能を提供します。 管理している属性は、以下の通りです。

  • 休日フラグ

  • イベント名称

6.1.2. 区分管理API¶

EJB: net.poweregg.common.ClassificationService

区分管理APIはアプリケーション毎の設定情報や区分項目を管理するために利用できます。

（例）商談レベル【Ａ、Ｂ、Ｃ...等】

区分情報は、会社番号、共通番号、区分番号のセットで識別されます。

会社毎に管理する必要のない区分情報は会社番号として全社共通（"0000000000"）を利用します。

共通番号は区分値をまとめるための単位として利用します。例えば、 商談レベルは共通番号"0608"として管理されています。

アドオンアプリケーションで区分管理EJBを利用する場合は、 共通番号として"9000"～"9999"番までの番号を利用してください。

※共通番号データ、区分データを登録する際は、SQL*Plusなどを利用してデータベースに登録してください。

区分管理APIで管理しているデータは、メソッド呼び出しの他にJSP内でTagLibを使うことでも利用することができます。

6.2. 連番管理API¶

EJB: net.poweregg.common.SlipNumberService

連番管理APIでは、アプリケーションで必要な各種の一意な連番を生成するための機能を提供します。

6.2.1. 連番管理レコードの追加¶

アプリケーションから連番管理エンジンを利用するには、ＺＴ伝票番号テーブル (ZT2_SLIPNO)にあらかじめ管理レコードを追加しておく必要があります。

データ型

説明

    番号は200103001から振られ、200103999までいくと200103001に戻ります。 2001年4月になると、連番部に関わらず200104001より付番します。

6.2.2. アプリケーションでの連番の採番¶

アプリケーションで連番を採番するには、連番管理EJBのfindConsecutivenessNo() メソッドを利用します。

例）全社共通で、プロセス番号(PROCNO)=9000の連番を取得する場合

import net.poweregg.common.SlipNumberService;
  ...
// SlipNumber EJBのインスタンスを取得
@EJB
SlipNumberService slipno;
// 連番を取得
Long number = slipno.findConConsecutivenessNo("0000000000", "9000");

注釈

データベースデータの主キーなどの番号を生成するために連番管理EJB を利用することは推奨しません。 連番管理EJBでは連番を生成するために、内部の管理情報に排他ロックを 掛けているので、多重度が増えた場合にボトルネックになる可能性があります。 データベースの主キーはデータベースのシーケンスを利用してください。

6.3. ワークフローエンジンAPI¶

EJB: net.poweregg.dataflow.DataFlowService

CDIアプリケーション用ヘルパーコンポーネント: DataFlowHelper

POWER EGG3.0では、情報を指定されたルートに従ってフローさせるための ワークフローエンジンを提供しています。

POWER EGG3.0でワークフローさせるデータはXML形式となっています。 アドオンアプリケーションがワークフローエンジンを利用するには、 アプリケーション内でXMLデータを作成し、そのデータを文書として 登録した後にワークフローさせます。

POWER EGGの決裁画面ではXMLデータをXSLTプロセッサを通して HTML化したものを表示するので、アドオン開発者はワークフローさせる XMLデータとHTML変換のためのXSLデータを設計する必要があります。

XSLデータは、PEWEBインストールディレクトリのappLib\XSLフォルダにファイルとして配置します。

スマートフォン用のXSLファイルを別途作成することで、 決裁画面をスマートフォンに表示することも 可能です。

スマートフォン用のXSLファイルはファイル名の末尾に 「_smartphone」と付与してください。

CDIアプリケーションからは、DataFlowHelperコンポーネントを利用する事 で比較的容易にワークフローアプリケーションを作成することができます。

DataFlowHelperを利用した申請アプリケーションのクラス図、 シーケンスについては、付録を参照してください。

6.3.1. 申請（applyメソッド）¶

アプリケーションが作成したXML形式の文書データをフローさせるためのメソッドです。 フローさせる文書データは、あらかじめ文書管理エンジンに登録されている必要 があります。

文書管理エンジンへの文書の登録については、文書管理エンジンの説明部分を参照してください。

6.3.2. 決裁状況の問い合わせ（findApplicationFormByRecepNoメソッド）¶

申請中の案件データの処理状況を確認するためのメソッドです。

6.3.3. 事後処理の組み込み¶

ワークフローアプリケーションによっては、承認されたとき、決裁されたときなど、 ワークフロー中にイベントが発生したタイミングでデータ更新処理などを行わなけ ればならない場合が有ります。データフローエンジンでは、このようなアプリケー ション固有の更新処理（事後処理）を組み込むためのインターフェースを提供して います。事後処理はJavaで開発し、POWER EGGに組込みタイプと、 Webアプリとして開発しPOWER EGGからCGIで呼び出されるものの2種類があります。

（１）Javaインターフェースによる事後処理（IProcAfterFlowインターフェース）

Javaインターフェースによる事後処理プログラムでは、net.poweregg.dataflow.IProcAfterFlow インターフェースをインプリメントし、doProcess(Long appRecepNo, Integer historyNo, String status) メソッド内で行いたい処理を記述します。

事後処理プログラムでアドオンのEJBを呼び出す場合、 Portable Global JNDI Nameを使ってEJBをlookupしてください。

注釈

POWEREGG V2.8cまでは、pe4j-engine.jar/META-INF/ejb-jar.xmlに ejb-local-refの定義の追加が必要でしたが、JavaEE6からPortable Global JNDI Nameの規約が制定されたため、ejb-local-refを定義 しなくてもEJBをLookupすることが可能になりました。

（２）URLインターフェースによる事後処理

URLインターフェースによる事後処理は、決裁時など指定したタイミングで POWER EGGサーバーから指定されたURLに対して”POST”で呼び出されます。 事後処理側の処理が正常終了した場合は、必ずHTTPステータス200を返却してください。 200以外のステータスの場合、POWER EGG側は事後処理が異常終了したものとみなし、 承認処理を失敗させます。

なお、POWER EGGサーバーからURL事後処理に渡すデータの文字コードは”UTF-8”です。

呼び出し時の引数は以下の通りです。

6.3.4. 補足情報URL¶

ワークフロー中の申請書を承認するときに、決裁の参考情報となる補足情報を表示 するためのWebアプリケーションを開発し、POWER EGGでの承認時に表示させることができます。

補足情報の表示は、承認画面の補足情報リンクをクリックすることで行います。

この補足情報URLは申請様式毎に指定することが出来ます。 POWER EGGでは、補足情報URLが設定されている申請様式の補足情報リンクをクリックしたときに、 起案番号などのパラメタを付加して設定されているURLを表示します。

補足情報URL起動時にPOWER EGGから付加されるパラメタは以下のとおりです。 （大文字、小文字の違いに注意してください）

6.3.5. 申請番号採番インターフェース¶

POWER EGG標準の採番ルールでは対応できない申請番号を付けたい場合、 申請番号を採番するJavaクラスを開発することができます。

申請番号採番アドオンモジュールは、net.poweregg.dataflow.AppNoGenerator インターフェースをインプリメントし、generateNoメソッドを実装してください。

開発した申請番号採番モジュールは、「採番ルールの登録」画面で登録します。

6.4. 添付ファイル操作API¶

EJB: net.poweregg.stock.FileAttachmentService

Word, Excel等のバイナリデータの添付ファイルのデータベースへの登録・削除を行う機能を提供します。

6.4.1. 添付ファイルを扱うプログラムの開発¶

添付ファイルの処理をアドオンアプリケーションに組み込むには、 添付ファイルJSFコンポーネント、添付ファイル操作APIを組み合わせて利用します。

利用するJSFコンポーネントは、inputAttachFile, outputAttachFileです。

（１）JSFでの設定

添付ファイルを扱うJSFでは、以下のタグ指定を使用します。

タグパラメタの詳細については、第８章のJSFコンポーネントの説明を参照してください。

①添付ファイルの登録、修正、削除を行う場合は、inputAttachFileコンポーネントを、 添付ファイルを組み込みたい箇所に指定します。

（記述例）

<p:inputAttachFile value="#{Bean.attachFiles}" />

このタグでは、添付ファイルの入力域を生成し、ユーザが指定した添付ファイルを、 net.poweregg.ui.param.AttachFile型のオブジェクトとして、 JSFマネージドビーンのプロパティにセットします。

②添付ファイルへのリンクを表示する場合は、outputAttachFileタグを該当の箇所に指定します。

（記述例）

<p:outputAttachFile value=”#{Bean.attachFile}”/>

（２）添付ファイル登録時のアプリケーションビーンでの処理

添付ファイルを扱うアプリケーションでは、前述のJSFコンポーネントによって マネージドビーンのプロパティにセットされたAttachFileオブジェクトを利用して、 データベースへの添付ファイルの登録を行います。

そのときの処理手順は、以下のようになります。

①添付ファイルオブジェクトの取得

inputAttachFileのvalue属性で指定した変数に添付ファイルを表現する AttachFileオブジェクトのリストがJSFによりセットされます。

（添付ファイルの取得）

// この変数に添付ファイルがセットされる.
AttachFile attachFile;
public void setAttachFile(List<AttachFile> attachFile {
   this.attachFile = attachFile;
}

②添付ファイル登録APIの呼び出し

AttachFileを引数として、FileAttachmentService#saveAttachFiles()を呼び出します。

このメソッドを呼び出すことにより、サーバー上に一時保存されている 添付ファイルがデータベースに登録され、データベースに登録済みのAttachFile オブジェクトが戻されます。

データベースに登録済みのAttachFileオブジェクトにはデータベース上の 文書ID(docid)がセットされます。

（添付ファイルの登録処理呼び出し例）

@EJB
FileAttachmentService fileAttachmentService;

// 添付ファイルの登録
attachFile = fileAttachmentService.saveAttachFiles(null,attachFiles);

アプリケーションで添付ファイルを扱う場合は、 ②で戻される添付オブジェクトの文書IDを保持しておく必要があります。

親文書と関連づけされている場合は、親文書の文書IDを保持しておけば、 後で親文書のIDから添付ファイルのIDを取得することができます。

6.5. アシストメッセージエンジンAPI¶

アシストメッセージエンジンでは、複数の方法によって個々のユーザのナビビュー に表示されるアシストメッセージを制御することができます。

6.5.1. アシストメッセージの書き込みと更新・削除¶

アシストメッセージをメッセージ単位で書き込んだり、削除したりするためのAPIです。 net.poweregg.assistmsg.ExternalMessageServiceとして提供されます。

このAPIでは

  1. アシストメッセージの書き込み、

  2. アシストメッセージの削除（メッセージ単位または識別名単位）、

  3. アシストメッセージの更新、

  4. メッセージ宛先の追加

を機能として提供しています。

6.5.2. ナビビュー表示のタイミングで動的に呼び出されるメッセージ生成プログラムの組み込み¶

このAPIを利用すると利用者がナビビューの表示を更新したタイミングで 動的に生成されるアシストメッセージを作成することができます。

アシストメッセージを生成するプログラムは、 net.poweregg.web.engine.navigation.portal.LocalizedAssistableまたは net.poweregg.nnv.view.workspace.LocalizedAssistableLocalインターフェースを 実装する形で作成し、POWER EGGシステムに組み込みます。

通常のJavaクラスとして作成する場合は、LocalizedAssistableを継承し EJBとして作成する場合はLocalizedAssistableLocalを継承してください。

POWER EGGに組み込まれたプログラムは、利用者がナビビューを表示した タイミングでPOWER EGGから動的に呼び出されます。

作成したプログラムのPOWER EGGへの登録は、ZT2_MESSENGER_LIBテーブルに レコードを追加することによって行います。

（メンテナンスアプリケーションは提供されていませんので、 データベースの対話型ユーティリティ等を利用して直接テーブルにレコードを挿入してください）

メッセージ生成プログラムでアドオンのEJBを呼び出す場合、 Potable Global JNDI Nameを使ってEJBをlookupしてください。

注釈

POWEREGG V2.8cまでは、pe4j-app.jar/META-INF/ejb-jar.xmlに ejb-local-refの定義の追加が必要でしたが、JavaEE6からPortable Global JNDI Nameの規約が制定されたため、ejb-local-refを定義 しなくてもEJBをLookupすることが可能になりました。

6.5.3. CSV形式ファイルからの一括でのアシストメッセージ生成¶

POWER EGGの持つメッセージ生成エンジンを利用して、規定されたCSV形式の データからアシストメッセージを生成するための連携方法です。

CSVデータからのアシストメッセージの生成は、POWER EGGが標準で持っている メッセージエンジンを通して行われます。

メッセージエンジンでは、メッセージが作成される条件やメッセージ出力先社員 （本人、上司など）をあらかじめ登録されているルール（アシストメッセージパターン） から読みとり、アシストメッセージを作成します。

※この方式を利用したアシストメッセージ作成の詳細については、POWER EGG3.0管理者マニュアルを参照してください。

6.7. 権限管理エンジンAPI¶

EJB: net.poweregg.security.AuthorityService

権限管理エンジンでは、POWER EGG内の各種の権限（メニュー、掲示板、文書等）に 関する操作とチェックを行うためのAPIを提供しています。

POWER EGG内では、権限は 1～9の権限レベルで管理されており、 9以外の権限レベルは、権限を利用するアプリケーションで 自由に設定・利用できるように設計されています。

アプリケーションでは、権限管理を行いたいデータに対して 権限管理エンジンにより取得した権限管理番号を保持しておき、 ユーザからのデータ要求時に権限エンジンにユーザが対象の権限を 保持しているかどうか問い合わせることによって権限有無の判定を行います。

6.7.3. デフォルト権限について¶

アプリケーションでは、ユーザが明示的に権限設定を行わなかった場合に 利用するデフォルトの権限を設定することができます。

デフォルト権限は処理単位で自由に設定することができます。

デフォルト権限では以下の４種類から選択し、権限レベルを指定します。

（１）登録者のみ

権限単位は「社員」・権限対象がログインユーザ社員の権限が作成されます。

（２）社外秘

対象会社がログインユーザ社員の所属会社で権限単位「基本」の権限が作成されます。

（３）部外秘

対象会社がログインユーザ社員の所属会社で権限単位が「部門」、権限対象がログインユーザの部門の権限が作成されます。

（４）全会社公開

対象会社が全会社で権限単位が「基本」の権限が作成されます。

デフォルト権限を登録する際は、手作業でデータベース(ZT2_DEFAULT_AUTHORITY)にレコードを登録してください。

アドオンアプリケーションで利用できる権限レコードの処理番号は、90001～99999です。 そのうち手作業で登録できるのは90001～95000で95001から99999までは自動採番される番号です。

また、手作業でデフォルト権限レコードを登録する場合は、権限名称を管理している ZT2_AUTHORITY_LEVELにもデータを登録する必要があります。

6.7.4. アプリケーションでの利用方法¶

アプリケーションで利用者の権限を判定する必要がある場合は、 権限を設定する対象となるデータに対して、権限ハンドルを設定する必要があります。

（１）権限設定部品の呼び出し

権限の設定には、権限設定部品を利用します。 アプリケーションから権限設定部品を利用するための規約は、以下の通りです。

①アプリケーションでは、設定済み権限の一覧を表示するために、 /ZSC/ZSC2001l.xhtmlをインクルードする。

②権限一覧を表示するまえに、AuthorityService#findAuthorityDtoを 呼び出して画面表示および権限設定画面用のDTOを生成する。

③②で取得したauthorityDtoを @Injectで権限設定画面とやり取りする。

（２）権限管理番号の取得

権限管理番号を取得する際は、権限管理エンジンのsaveAuthorityメソッドを呼び出します。 メソッドの引数として、（１）のauthorityDtoを渡すことで、 メモリ上で編集した権限情報がデータベースに格納され、権限オブジェクト(Auhority)が戻されます。

各アプリケーションでは、権限オブジェクトを自身のデータに関連させ、権限判定に利用します。

6.8. ナレッジポイントエンジン¶

EJB: net.poweregg.point.KnowledgePointService

ナレッジポイントエンジンでは、利用者のナレッジポイントを管理する機能を提供しています。 アドオンアプリケーションではナレッジポイントの登録や、蓄積されているポイント の参照を行うことができます。

6.8.1. ナレッジポイントを利用するための準備¶

アプリケーションでナレッジポイントを加算するためには、 まずナレッジポイントを発生させる対象となるアクションの管理情報を POWER EGGに登録する必要があります。

管理情報の登録は、POWER EGGのシステム管理メニューにある 「ポイント管理の設定」プログラムを利用して行います。

管理情報の分類コードは、第１分類と第２分類から構成されています。

アドオンシステムでナレッジポイント管理情報を登録する場合は、 第１分類として"U"で始まるコードを利用してください。 なお、第２分類は任意に指定することができます。

6.8.2. ナレッジポイントの加算¶

アプリケーションでナレッジポイントを加算するには、KnowledgePointService のaddPointメソッドを利用します。

例）ポイント管理分類コード "UAP01"-"0001"のポイントを加算する

import net.poweregg.point.KnowledgePointService;
..
// KnowledgePoint EJBのインスタンスを取得
@EJB
KnowledgePointService kp;

// ポイントを加算
kp.addPoints(
                login.getDeptID(),  //ポイント加算対象の部門ID
                login.getEmpID(),  //ポイント加算対象の社員ID
                "UAP01",   // 第１分類
                "0001",);   // 第２分類
