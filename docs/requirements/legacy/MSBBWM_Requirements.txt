第1章  WMS模块总体架构与业务定位
1.1  功能目的
WMSモジュール（MSBBWM系列）はCP6システムにおいて、ERP販売管理（PA系列）と MES製造執行（ME系列）の間に位置し、"物がどこに・いくつ・誰が動かしたか" を一元管理する。ERPは"売る/作る"を決め、MESは"作り方"を実行し、WMSは"在庫の現実"を保持する。本モジュールは独立WMS原型で、後続でmcframe7倉庫モジュール、又は外部WCSとAPI連携可。
1.2  业务流程定位

       ↓                      │

第3章  MSBBWM020 — 在庫照会
3.1  功能概述
全社の在庫状況を多次元で照会する画面。検索条件12項目・一覧18列。明細から StockTransaction（在庫トランザクション履歴）にドリルダウン可能。棚移動操作もここから起票する。
3.2  検索条件
拠点CD / 倉庫CD / ロケーションCD / 製品CD / 製品名(LIKE) / 製品区分 / ロットNO / 賞味期限(範囲) / 在庫数下限 / 在庫数上限 / 滞留日数下限 / 凍結中のみ
3.3  一覧列（18列）
拠点 / 倉庫 / ロケーション / 製品CD / 製品名 / 製品区分 / ロットNO / 入庫日 / 賞味期限 / 物理在庫 / 引当数量 / 利用可能在庫 / 単位 / 単価 / 在庫金額 / 滞留日数 / 直近入出庫日 / 状態
3.4  ドリルダウン
行クリック → 当該（製品×ロケーション×ロット）のトランザクション履歴ダイアログ
  - 列：日時 / 区分(IN/OUT/MOVE/ADJ) / 数量 / 関連伝票NO / 担当者 / 備考
3.5  棚移動機能
複数行選択 → 「棚移動」ボタン → 移動先ロケーション指定 → 移動数量入力
  - 種別 MOVE のトランザクション 2 件（源 OUT / 先 IN）を生成
  - 引当中（AllocatedQty > 0）の在庫は移動不可（要先解除）

第6章  MSBBWM050 — 出庫指示（生産材料）
6.1  功能概述
MES製造指図（WorkOrder）の確定時に、必要材料の出庫指示を自動生成する画面。手動起票も可能。引当（Reserve）→ ピッキング → 出庫確定の 3 段階処理。引当方式は FIFO（先入先出）を既定とし、製品マスタで LIFO/期限優先に切替可。
6.2  自動展開フロー
MES WM050
ME020 製造指図確定
   ↓ POST /api/mes/work-order/{no}/confirm
   ↓   サービス層で OutboundOrderService.CreateFromWorkOrder(wo) を呼ぶ
   ↓
T_OutboundOrder ヘッダ生成 + 明細展開（WorkOrderMaterial 単位）
   ↓
状態 0:下書き
6.3  画面字段（ヘッダ）
outboundNo（OUT-YYYYMMDD-NNNN、自動）
outboundType（1=生産材料 2=出荷 3=社内振替 9=その他）
workOrderNo（FK → MES）
warehouseCd
plannedDate
status（0~9）
6.4  明細
productCd / requiredQty / allocatedQty / pickedQty / unitCd / lotNo（引当時自動）/ locationCd（引当時自動）
6.5  引当アルゴリズム（FIFO 例）
1. 対象製品の Stock を AvailableQty>0 で抽出
2. ORDER BY ReceiveDate ASC, ExpiryDate ASC（FIFO + 期限優先）
3. ロット単位で順次引当 → StockTransaction (TXN_TYPE=RSV) 発行
4. AvailableQty 不足の場合：部分引当 or 全件失敗（製品マスタ設定）
5. 引当完了 → 指示ステータス=2（引当済）
6.6  操作ボタン
登録 / 確定（→1）/ 引当実行（→2）/ ピッキング開始（→3）/ 出庫確定（→4、Stock-/StockTxn OUT）/ 引当解除（→1）/ 取消

第7章  MSBBWM060 — 製品入庫（完成品上架）
7.1  功能概述
MES製造実績（ProductionResult）の指図完了時に、完成品の在庫計上を自動生成する。半製品入庫も同様。手動起票も可能。
7.2  自動展開
ME040 全工程完了 → 指図ステータス=4（完了） → WMS WM060 製品入庫レコード自動生成 → 担当者確認 → 確定で Stock+ / StockTxn IN
7.3  画面字段
inboundReceiptNo（RC-、自動）
sourceType（"PRODUCTION"）/ workOrderNo / productCd / lotNo（指図のロットNO引継）
goodQty（指図の累計良品数）/ locationCd（製品マスタ既定）
inspectionStatus（"検査済" or "未検査"）/ 検査NO（ME060 連携）
7.4  特殊規則
1. 品質検査未済（inspectionStatus=未検査）の場合：保留倉庫に入庫

第10章  MSBBWM090 — 棚卸（実地棚卸）
10.1  功能概述
定期 / 臨時棚卸を計画 → 実地カウント → 差異承認 → 在庫調整までを一貫管理。サイクル棚卸（一部範囲のみ）・全棚卸の両方をサポート。
10.2  棚卸ヘッダ
stockTakeNo（ST-YYYYMMDD-NNN）
stockTakeType（1=全棚卸 2=サイクル棚卸 3=臨時）
plannedDate / actualDate / status（0~9）
範囲：warehouseCd / locationCd（複数選択）/ productCategory
10.3  処理フロー
Phase 1: 計画
  - 範囲指定 → 帳簿在庫スナップショット作成 → T_StockTakeDetail 生成（BookQty 固定）
  - status=0 → 1（カウント中）
  - 対象 Stock は "棚卸中フラグ" ON（出庫禁止）

Phase 2: カウント
  - 担当者が現場でカウント → T_StockTakeDetail.CountedQty 入力
  - ハンディスキャン or 手入力（Element Plus テーブル直接編集）
  - 全明細入力完了 → status=2（差異確認中）

Phase 3: 差異承認
  - 差異 = CountedQty - BookQty
  - 差異 0 ：自動承認
  - 差異 ≠ 0 ：理由コード入力必須 + 上長承認（差異金額>閾値の場合）
  - status=3（承認待ち）→ 承認者が一覧画面で一括承認 → 4

Phase 4: 在庫調整
  - 承認済明細について TXN_TYPE=ADJ 発行
  - Stock.PhysicalQty = CountedQty （絶対値で上書き）
  - 棚卸中フラグ OFF

13.3  StockMovementService 中核メソッド
public async Task ApplyAsync(StockTransaction txn, CancellationToken ct)
  → using var tx = await _db.Database.BeginTransactionAsync(IsolationLevel.ReadCommitted, ct);
  → 1. 対象 Stock を SELECT FOR UPDATE 相当（RowVersion チェック）
  → 2. ALLOW_NEGATIVE=false かつ AvailableQty < 0 になる場合は throw InsufficientStockException
  → 3. Stock 更新 + StockTransaction INSERT
  → 4. SaveChanges → tx.Commit
  → 5. RabbitMQ "cp6.wms.stockchanged" 発行（後段 SignalR でダッシュボード更新）
13.4  既存基盤との接続
- 全 Controller は IService<T> パターン継承（ServiceBase override）
- 操作ログ：OperLogFilter 自動取得（既存）
- 認可：[Authorize(Roles="...")]（既存 JWT 基盤）
- キャッシュ：在庫照会・ダッシュボードは CacheService.GetOrSetAsync
- メッセージング：在庫変動イベントは RabbitMQService → cp6.wms.stockchanged キュー
- SignalR：NotifyHub に "StockChanged" / "InboundAlert" / "ShipmentReady" イベント追加

第20章  MSBBWM100 — 入荷検品（QC受入）
20.1  功能概述
仕入先からの到着品に対し、ASN（事前出荷通知）と現品照合 + 数量検査 + 品質サンプリング検査を行う画面。WM030/WM040の間に挟まる "受入精査" 工程。検品結果により：合格→正規入庫、保留→QC保留倉庫、不合格→返品起票。

第21章  MSBBWM110 — 自動棚配置・スロッティング
21.1  功能概述
入庫時に "どの棚に置くか" を AI/ルールで自動決定する機能。さらに定期的に "置き場所最適化（Slotting Optimization）" を実行し、棚を組み直す提案を出す。
21.2  自動棚配置アルゴリズム（入庫時リアルタイム）
判定優先順位：
  1. 製品マスタ DefaultLocationCd が指定 → そこへ（空き容量チェック）
  2. ABC分類（過去90日出荷頻度）：
     - A品（上位20%）→ ゴールデンゾーン（腰高さ、ピッキング動線短）
     - B品（中位30%）→ ミドルゾーン
     - C品（下位50%）→ 高所/奥棚
  3. 重量バランス：重い物 → 下段、軽い物 → 上段
  4. 製品区分制約：冷蔵→冷蔵庫、危険物→専用区画
  5. 同一製品の既存棚に空きあり → 集約優先
  6. 上記すべて失格 → 最寄りの空き棚（ロケーションツリー幅優先探索）
21.3  Slotting Optimization（定期最適化）
- 月次バッチで実行（手動起動も可）
- 過去N日の入出庫履歴を分析
- 移動コスト（移動本数×重量）vs 改善効果（ピッキング距離短縮）を計算
- 提案レポート出力 → 管理者承認 → 棚移動指示一括生成
21.4  ABC分析計算式
  出荷数 / 出荷金額 / 出荷件数 の 3 種選択可
  累計構成比 0~80% → A、80~95% → B、95~100% → C
21.5  画面
- ABC分析結果一覧（製品×現在ロケーション×推奨ロケーション×移動メリットスコア）
- ヒートマップ：ピッキング頻度の高い棚を赤、低い棚を青で表示
21.6  API
POST /api/wms/slotting/recommend         入庫1件の推奨ロケーション返却
POST /api/wms/slotting/abc-analyze       ABC分析実行
POST /api/wms/slotting/optimize          最適化提案生成
POST /api/wms/slotting/apply/{planId}    提案を棚移動指示に変換
第22章  MSBBWM120 — 補充指示（リプレニッシュ）
22.1  功能概述
ピッキング棚（前棚）の在庫が下限を割った場合、保管棚（後棚）から補充する指示を自動生成する。日次バッチ + リアルタイムトリガの2方式。
22.2  ロケーション 2 層モデル
区分
特徴
ピッキング棚（FORWARD）
作業者が拾う前棚。少量を在庫
保管棚（RESERVE）
バルク保管。大ロット
22.3  補充トリガ
- バッチ：日次 6:00 に全製品スキャン → ピッキング棚 < MinQty → 補充指示生成
- リアルタイム：ピッキング作業中 → スキャン後の在庫 < MinQty → SignalR push
- 出荷指示展開時：今日の出荷必要数 > ピッキング棚在庫 → 先回り補充
22.4  画面字段
replenishNo（RPL-YYYYMMDD-NNNN）/ priority（1=至急 2=通常）
明細：productCd / fromLocation（保管棚） / toLocation（ピッキング棚） / qty / status
22.5  API
POST /api/wms/replenish/scan                バッチ補充指示生成
POST /api/wms/replenish/{no}/execute        補充実行（StockTxn MOVE 2件）
GET  /api/wms/replenish/pending             未実行一覧
第23章  MSBBWM130 — クロスドッキング
23.1  功能概述
入庫品をいったん棚に置かず、そのまま出荷ドックへ転送する高効率モード。受注引当との連動が肝。
23.2  処理パターン
パターン
説明
事前計画型
受注 → 入庫予定とマッチング → 入庫時にクロスドック対象とマーク
機会型
入庫時に未引当受注を検索 → 該当あれば運用判断でクロスドック振替
23.3  画面字段
crossDockNo（XD-YYYYMMDD-NNNN）/ inboundNo / shippingNo（突合済出荷指示）
明細：productCd / qty / fromDock / toDock / 担当者
23.4  作業フロー
1. 入庫品が荷降ろし
2. システムが入庫予定をスキャン → クロスドック候補表示
3. 担当者が承認 → 在庫を一切経由せず StockTxn 1件（IN+OUT を結合する仮想科目）or 0件
4. 出荷ドックへ運搬・即出荷
23.5  会計処理
- 通常 IN→OUT で 2 件の StockTxn を発行（在庫滞留時間ほぼ 0）
- 監査要件で許可されれば "XDOCK" 種別を新設し 1 件で完結（オプション）
第24章  MSBBWM140 — キッティング・組立
24.1  功能概述
複数の単品在庫を組み合わせて「セット品」として新しい SKU を作成する機能。逆方向（バラシ／反組立）も対応。
24.2  典型ユースケース
- 段ボール本体 + 緩衝材 + 説明書 + 印刷ラベル → "出荷キット"
- 季節キャンペーン用詰合せ
- 修理交換部品セット
24.3  キット BOM（部品構成）
- T_KitMaster：キットSKU + 構成部品（製品CD×数量）×N
- 製品マスタ拡張：IsKitItem フラグ
24.4  組立処理
1. キット生産指示作成（kitOrderNo + 数量）
2. 構成部品が全部 在庫あり をチェック（不足部品リスト表示）
3. 部品 OUT トランザクション × N
4. キット品 IN トランザクション × 1
5. ロットNO は構成部品の最古ロットを継承（追溯性確保）
24.5  反組立（バラシ）
- 既存キット品 → バラシ → 部品 N 種類に戻す
- 中身を取出し再販売する場合に使用
- 厳密にはロット情報失われる → 「再加工ロット」採番
24.6  API
POST /api/wms/kit-order                  組立指示作成
POST /api/wms/kit-order/{no}/assemble    組立実行
POST /api/wms/kit-order/{no}/disassemble バラシ実行

第26章  MSBBWM160 — ロット追溯・回収管理
26.1  功能概述
ある製品ロットが「どの仕入ロット → どの製造指図 → どの顧客へ出荷されたか」を双方向追溯する画面。製品回収（リコール）発生時の影響範囲特定に必須。
26.2  追溯方向
方向
出発点
ゴール
順追溯（Forward）
仕入ロットNO
出荷した顧客一覧
逆追溯（Backward）
出荷した製品ロットNO
使用した仕入ロット一覧
両方向（Bi-directional）
任意ロットNO
上下流すべて
26.3  追溯ツリー
T_StockTransaction を再帰的に辿る：
  - IN（仕入入庫）→ OUT（材料出庫）→ ME040生産（指図ロット紐付）
  - → 製品 IN（完成品入庫）→ OUT（出荷）→ 顧客
26.4  リコール処理
1. リコール対象ロット指定
2. 順追溯で出荷顧客リスト取得
3. 在庫保有量計算（顧客先 + 自社在庫）
4. リコール書類自動生成（顧客別）
5. 返品RMA を自動起票（WM150 連携）
6. 該当ロットの全Stockに "REC" フラグ立て → 出荷禁止
26.5  画面
- 追溯ツリー（折りたたみ式、各ノードは StockTransaction）
- ガントチャート（時系列追溯）
- 影響顧客マップ（地理可視化）
26.6  API
GET /api/wms/trace/forward/{lotNo}      順追溯
GET /api/wms/trace/backward/{lotNo}     逆追溯
GET /api/wms/trace/full/{lotNo}         両方向
POST /api/wms/recall                    リコール起票
第27章  MSBBWM170 — 賞味期限・FEFO管理
27.1  功能概述
有効期限のある製品（インキ・接着剤・特殊紙等）の期限管理。FEFO（First Expired First Out）引当を実現。
27.2  期限管理対象
- 製品マスタ HasExpiryDate フラグで対象判定
- 入庫時に ExpiryDate 必須入力（製造日 + 賞味日数で自動計算可）
27.3  アラート設定（製品マスタ）
- 期限N日前で黄色警告
- 期限M日前で赤色警告
- 期限切れ → 自動凍結 + 廃棄起票
27.4  FEFO引当（WM050 引当アルゴリズム拡張）
ORDER BY ExpiryDate ASC, ReceiveDate ASC
（期限優先→ FIFO がタイブレーク）
27.5  廃棄処理
- 期限切れ Stock 自動検出（日次バッチ）
- "廃棄候補一覧" 画面で確認 → 担当者承認 → ADJ で在庫除去
- 廃棄理由・廃棄方法・金額損失を記録
27.6  API
GET  /api/wms/expiry/alert              期限切迫アラート一覧
POST /api/wms/expiry/dispose            廃棄一括実行

- ヒートマップで在庫過多・不足を可視化

31.2  T_PlateMold への拡張列

31.3  貸出・返却管理
- 製造指図発行 → 必要な印版/木型を倉庫から払出 → PlateMoldCheckout テーブル記録
- 使用後返却 → conditionLevel 再評価 → 次回点検日設定
- 5回使用毎に点検必須（製品マスタで頻度設定）
31.4  ロケーション特殊性
- 木型：寝かせ保管・温湿度管理
- 印版：垂直保管・遮光
- 棚マスタに保管条件タグ追加
31.5  API
GET  /api/wms/plate-mold/checkout-status  全数現在貸出状況
POST /api/wms/plate-mold/checkout         払出
POST /api/wms/plate-mold/return           返却 + 状態評価
第32章  MSBBWM230 — インキ・接着剤管理
32.1  功能概述
インキ・接着剤等の液体資材は ロット混合・賞味期限・色番号管理 が必要。一般在庫と分離管理。
32.2  特殊管理項目
- 色番号（色見本との対応）：DIC-XXX / Pantone-XXX
- 開封状態：未開封 / 開封済（開封後は別ロット扱い）
- 賞味期限：未開封180日 / 開封後30日 等
- 粘度・固形分等の物性データ
32.3  ロット混合
- 旧ロット残量 + 新ロットを混合使用する場合
- 新たに「混合ロット」を採番、原ロット2件は OUT、混合ロット1件は IN
- 賞味期限は「より早い方」を継承
32.4  色合わせ実績
- 色合わせ毎に消費量・配合比を記録
- 顧客名 + 色番号 で過去配合履歴検索可能（営業/技術部門が再利用）
32.5  API
POST /api/wms/ink/mix                混合ロット作成

第34章  MSBBWM250 — 客先預り在庫（VMI）
34.1  功能概述
顧客が所有する在庫を当社倉庫で預かる業態（VMI：Vendor Managed Inventory / 客先預り）。所有権は顧客にあり、出荷指示は顧客側システムからトリガされる。
34.2  特殊性
- T_Stock の OwnerType 列追加（"SELF" / "CUSTOMER"）
- 自社在庫と物理的に同じ棚でも論理的に分離
- 在庫評価額に算入しない（会計上は預り資産）
34.3  業務フロー
1. 顧客が当社で生産 → 完成品入庫時に "VMI" 区分マーク
2. 顧客側システムが在庫照会 API を叩く（権限制御）
3. 顧客が出荷要求 → 当社が出荷作業のみ実行
4. 月次：保管料 + 出荷作業料を顧客請求
34.4  保管料計算
- 日単位保管料 × 平均在庫日数 × 単価
- パレット数ベース or 容積ベース選択可
- 月次バッチで集計レポート生成
34.5  API
GET  /api/wms/vmi/stock/{customerCd}      顧客別VMI在庫
POST /api/wms/vmi/ship-request            顧客からの出荷要求受付
GET  /api/wms/vmi/billing/{yearMonth}     月次保管料計算
第35章  MSBBWM260 — 試作・サンプル在庫

- sampleType（試作/営業サンプル/展示会/苦情品再現）
- 関連プロジェクト
- 貸出先（営業担当・顧客）

35.3  画面
- サンプル一覧（小ロット高頻度・写真付き）
- 貸出ボード（カンバン形式：在庫中/貸出中/返却遅延）
35.4  API
