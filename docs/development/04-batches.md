# 依赖、批次与开工条件

先完成全部大任务的范围评估，再按各业务切片的真实依赖排期。下表是排期框架，当前只开展B0的评估和建档；后续批次的切片清单、开始时间和工期需依据WP01结论确定，没有在这里预先宣称CRM或其他包具备全部实现条件。

| 批次 | 建议范围 | 进入条件 | 可验收结果 |
|---|---|---|---|
| B0 全量评估 | WP01组织14包、125目标与现有三仓代码对照；盘点原始验收和247修订场景 | 当前准确设计组合、源码与包身份可定位 | 每目标有复用/修改/新增/待决定结论，输出首批切片、原验收清单、影响消费者和粗估范围 |
| B1 公共能力及专业基础 | WP02所需最小公共能力；按首批需求选择工程身份、物料/库位、财务基础和OA适配 | B0提供该切片准确差异和Owner；确定Provider与事务部署边界 | 精确类型、当前授权、幂等原结果、所需源对象和事务参与方通过对应定向验证 |
| B2 商业业务闭环 | 根据现有CRM/ERP成熟度选择询盘、线索、客户、报价、订单等可交付切片 | 相关公共能力和专业输入已可用；商业交接双方合同明确 | 每批交付从实际页面到数据/回执的一段完整业务流程；需求释放独立验收 |
| B3 供需与执行闭环 | 计划、采购、制造、质量、仓储按业务用例联动；所需工程许可随批接入 | 准确需求、技术基线、供给事实和库存事务能力齐备 | 一笔真实业务可经历采购/生产、检验、入库、供给更新、预留和领用，数量与原结果可追溯 |
| B4 结算、纠正与恢复 | 财务、退货/贷项、对账、取消、迟到执行及跨域恢复 | 相关原义务及物理事实Owner已经接入 | 不重复计价/过账/核销，未知结果可查，补偿与业务取消各有最终性 |
| B5 专项及交付完善 | 仓储专项、排程/绩效、预算/资产、空间运营、连接器等按业务需要安排 | 所需基础及具体场景的依赖验证通过 | 各专项独立验收，形成完整范围交付和后续环境准入清单 |

B1至B5是规划类别，不是必须完成整个上批所有模块才能开始下批。共用能力、财务原义务、工程发布、质量、审批及SPACE/WMS接缝要在实际消费者需要时提前接入；不能把它们一律拖到末期。单人开发默认保持一个主要实施任务，按依赖顺序交付，避免同时开启多个长期分支。

## 关键依赖及允许提前做的工作

| 能力 | 依赖和边界 | 开发安排 |
|---|---|---|
| CRM线索原子转化 | 当前租户/授权、准确ACC/CON/OPP图、同一事务和原结果槽 | 可先评估既有CRM实现；相关共同事务和合同完成后实施该切片，不等待全部公共平台功能 |
| 报价、订单与需求 | 客户/BP资格、估价/价格、适用工程输入、独立信用与需求释放合同 | 先核对物理接口和数据源，再按真实用例贯通；订单确认不能直接当作MRP需求 |
| 工单及技术采用 | ENG技术身份/基线、PLM用途许可/偏离、CFG发生映射和准确Owner | WP05必须为对应生产用例提供所需许可；候选WP0只作移植输入 |
| MRP和计划转单 | 需求、策略、SUP供给、WMS可用量、MES残量及供给约束 | 先做计算输入/数量映射与差异核对，再验证真实PR/WO转单；重算不双计新旧供给 |
| 采购或生产入库 | PUR/MES来源、QA判定、WMS物理移动及全部相关事务参与方 | 商业收货/报工/质检决定/库存生效分阶段登记，计划只消费准确供给事实 |
| 追加物料 | MES追加原因、需求身份、审批、MAT残量、PLAN接收及PR/领料后继 | 单独评估统一入口是否被现行合同完整覆盖，明确缺口后修订或实现；不把聊天设想直接算已接受功能 |
| 财务纠正与退货 | 原义务、MATCH/AP纠正close、WMS有效移动、数量/金额精度与原操作最终性 | 财务基础提前配合采购/销售/库存；不能以整个FIN包排在后面为由省略来源义务 |
| OA和SPACE接入 | 业务Owner应用回执、撤权、准确字段/版本/grant集合和当前资格 | 按被消费的能力接入，集成伙伴关系可双向；不作为整包串行依赖环 |

## 开始一个实施切片前

1. 固定该切片的目标、原合同组合及R1修订输出，确认所有Required来源与历史缺件处置。
2. 读取实际主线代码和相关测试，给出准确复用、改动、新增及旧路径退出范围；不根据服务类名宣布功能完成。
3. 写清页面、请求/响应/错误、Owner、事务、权限、幂等/原结果及恢复行为；既有接口按版本补充或适配。
4. 选取该切片的原始验收及修订正反场景；金额、数量、并发、取消/迟到、撤权与审批重放按实际风险安排。
5. 建立独立执行任务，记录工作量范围与估算依据，再从最新已确认main开分支。后续任务沿用已通过且输入未变的检查，按仓库规则集中审查。

一个大任务可以连续交付多个切片；单个切片通过不自动将整包或整个Target标成DONE。新增范围必须记录批准依据及分母变化，不能把可选提醒、人员交接、营销等功能静默塞入本轮125目标。

## 全链验证与发布边界

WP14从第一批集成开始协调，贯穿开发，并在收尾核对全部批准范围。每个来源事实、重复请求、取消/迟到与恢复场景都要绑定实际实现版本和执行证据。

本地开发通过、远端代码交付、正式生产候选、环境推广是不同结果。继续遵守[DevOps入口](../devops/README.md)与[R2规范](../client/r2/README.md)：不自动启动GitHub Actions，不改变发布权威、候选/签名/扫描/环境审批，也不因本台账排期而取得迁移现有数据或部署生产的授权。
