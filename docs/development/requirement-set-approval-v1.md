# 准确需求集原生评审与批准 v1

W196 原生批准、W298 可信撤回及 W308 来源范围/冲突裁决；对应 WP05-14，整项仍未完成。前置为 [需求专业评价](requirement-evaluation-v1.md)。

## Owner 与入口

`Main.Plm.RequirementSet.v1`；独立菜单/权限资源 `plm-requirement-set`，页面 `/plm/requirement-set`，API `/api/requirement-set/owner-v1`。当前对象、Scope/Members字段、原需求及其来源权限全部检查；部门归属由可信创建上下文或独立对象部门绑定配置，不从操作者推测。新增菜单动作不自动授予角色。

## 原集、成员与差异

不可变集合版本固定名称、范围、完整性依据、成员的准确需求/评价控制/批准引用和处置依据。必要性、定性/定量判据、单位和原始小数来自原需求版本，保存时不转换为浮点数。原来源条款、解释和判据可逐项审阅。后继版本保留完整历史、准确前后版本差异及其摘要。

未知或未批准成员可留在草稿，送审要求当前批准来源有效。旧成员和冲突义务沿整个祖先链保留，中间草稿不能消掉遗漏或挪用冲突标识。排除和未裁决冲突阻止送审、正向签署和批准采用；优先级、自由文本、ECM/DEV标签和范围分离提案不能代替有权来源裁决。

## 来源范围与冲突裁决（W308）

原来源准确条款可携带可选 `requirement-clause-terms/1`。客户/产品/配置各为 UNKNOWN、ALL 或带显式命名空间的 VALUES，维内 OR、维间 AND；同一需求所引条款的适用范围求并集。键按 Ordinal 比较，由内部来源有权人确认，不能以名称代键，也不宣称已核 CRM 客户或产品主数据。不同命名空间保持未知，不自动认定互斥。时间采用准确 UTC 半开区间，未知与无限显式区分，不经浏览器浮点日期改写。

每对引用条款计算交集；任一维明确不相交即可排除该条款对，任一条款对明确相交则需求范围相交，其余保留未知。读面返回总核对数和前20对示例，计算覆盖全部条款对。必须属性和可放宽性来自准确来源；没有 terms 的旧原件保持未知，不改旧摘要或历史签名。

新增/改变裁决通过原集合 CREATE/REVISE 和原键事务保存。`plm-requirement-set:conflict-decide` 加双方来源对象的 `plm-engineering-requirement:source-confirm`、当前字段/范围及最终权限共同核对；新动作不自动授予角色。裁决 `requirement-conflict-decision/1` 只允许显式保留双方原要求：

- SCOPE_SEPARATION 仅接受实际 DISJOINT。
- CLARIFY 是双方有权来源确认原要求可同时满足的解释，要求实际 OVERLAP、已知必须属性和可放宽性；不修改原判据、不豁免或排除任一成员，不替代集合专业批准。
- ECM 保存待工程变更评估去向，仍阻止集合批准；当前没有实际 ECM Owner 完成引用。
- DEV 要求范围/必须属性/可放宽性已知且没有禁止放宽的条款；仅保存待偏离评估去向，仍阻止集合批准。不存在默认许可或基础要求回写。

原件变化使新裁决失败，已保存裁决和批准事实留历史，当前采用仍检查成员来源可用性。后继集合可直接携带完全相同的裁决，不重复索取来源签署；读面追溯实际裁决所在的准确集合版本、当时操作者和时间，不能把后继编辑人冒充裁决人。修改两侧引用/提案会要求重新确认。原源需求 CONFLICT 关系也必须由准确两侧版本的已解决裁决覆盖。

来源确认、裁决、原回执和审计沿既有 Owner 同事务/CAS；当前读权控制历史和失写后的原结果查询。页面确认/取消与原键恢复使用既有环境/租户/操作者隔离机制。迁移 `20261104093000_RequirementConflictAuthorityV1` 只登记两个动作，不回填条款、不授角色、不修改原件或既有环境。

## 原生 FLOW 及 Owner 采用

专业政策采用当前租户启用角色、人数、依据和显式有效期，强制作者/最后修订者/送审者与签署人分离。不接受未接通的外部要求。固定评审包绑定集合版本、成员批准、前版及差异摘要。

送审原操作与 outbox 原子提交；复用实际 FLOW 绑定、接收、启动、任务及专业投票。专业人数按实际人员和被代理人分别去重；提交/正向签署/最终批准重新核对准确成员、政策与当前权限。成员撤回后可记录合格人员的驳回，不能继续批准。

FLOW 决定接收与业务批准分开：只有独立 Owner 采用动作写入准确版本批准、原操作、不可变回执和 outbox。新草稿不继承旧批准；旧版批准原件不因新草稿重写。成员批准撤回或来源改变后，集合当前使用资格不可用，历史仍可在当前读权限下查询。

C02服务身份、原生注册和准确Subject授权贯穿送审、决定投递、回执及缺口查询。丢失ACK先查询原键；撤销写权限后仍允许符合当前查询权限的原结果恢复，不自动重发业务写入。Owner身份和SQL schema来自封闭映射，工具、文档和需求集三种既有/新增身份并存。

## PostgreSQL 与使用边界

新增8项前向迁移，在隔离PG18实际执行。不可变原文、当前头CAS、当前授权根/Scope、写入读回、延迟原操作/原生来源证明保护原子性；不执行既有环境迁移。内部 `HoldApproved` 仅在消费方现有事务中持有当前批准及成员资格；HTTP Source是只读观察，不是最终采用令牌。

模式采用可信 `RequirementEvaluation:EvidenceMode` 与 Scope环境；原生绑定、接收/应用证据必须一致。后台配置 `RequirementSetReviewSubmissionDelivery`、`RequirementSetReviewDecisionDelivery`、`RequirementSetReviewReceiptDelivery`、`RequirementSetReviewReceiptRecovery` 默认关闭；本轮未启用正式环境服务。

浏览器三类原键按环境、模式、租户、操作者隔离，只保存公开操作引用，身份变化清理私有显示。固定目录复用且不修改生产配置。
