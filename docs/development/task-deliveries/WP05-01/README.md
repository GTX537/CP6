## 3. 新依据的组成与优先级

新版本由以下文件共同定义，任何一份单独存在均不能生效：

- [sources.json](sources.json)：原材料、当前仓库输入、准确接受/修订入口及SHA。
- [cases.json](cases.json)：221条可恢复场景逐条绑定目录JSON Pointer、原件行号/hash及完整原断言；另列8条目标适用R1场景、10条OA/ENG细化向量。三类来源保留独立身份，不把重叠向量算额外业务成绩。
- [normative-coverage.json](normative-coverage.json)：逐项登记ITER 30REQ、40BR、78FLD、20PROC、93逻辑字段及8待定参数，以及REL 18动作、8页字段目录，共295项定位；每项有适用对象、准确正文范围、可执行观察办法及适用的关联场景/剩余限制。该矩阵使正文义务不被“已有几条TC”替代。
- [coverage.md](coverage.md)：场景与正文索引，供人工审查；它不另定义义务。
- [adoption.json](adoption.json)：本版待采纳记录和缺口处置；当前不含批准人、批准时间或授权证据。

新ID以 `WP05-01/1/ITER|REL/RECOVERED|R1|DETAIL/...`、`WP05-01/1/BODY/...` 标识，属于本版验收定位。原AC/TC只保留为来源身份；AC/TC成对别名仍只算一条源断言。

适用规则按准确合同而非文件日期决定：

1. 当前已接受原正文、对应APR及其明确限制继续生效。REL PG01是明确后继编排，不追认为旧页；未知字段、物理Route和部署能力不从画布推断。
2. FB01/FB02、LR02/LR03、PG03/PG05按各自准确范围共同适用。PG05-CLAR-002附着于原场景，预约份额结清与业务记录关闭各自裁决，不增加历史AC数。
3. `CP6-DESIGN-REVISION-20261011/R1` 只覆盖具名差异：ITER采用 `ITER-OA-APPLICATION/1`；REL保持完整H命名空间、独立多输出RelationSet/Binding及CP22专业采用边界。未覆盖部分沿用原合同。
4. 本版只增加验收组织、观察点、缺口处置及采纳/完成门设计，不新增Owner协议、默认策略或存储表示。真实矛盾若上述规则未解决，登记准确来源并阻塞对应采用；不能“取最新”或静默取较宽松条款。

## 5. 如何执行与留证

每个运行记录至少固定：本版及制品hash、用例/正文义务ID、完整源身份、各仓源码SHA与合同/包版本、PostgreSQL版本/迁移标识、隔离环境、可信Tenant/Site/操作者及权限版本、原操作键/载荷摘要、输入、实际响应、持久前后状态/回执/审计、断言结果、证据路径和hash。敏感数据脱敏；不提交token、连接口令或生产资料。

场景Given/前置提供独占测试数据需求，When/动作规定触发，Then/预期规定可观察结果。执行者须同时读取准确源断言及正文观察项。合成数据只可支持注明范围的自动化测试；真实Owner/端到端/生产验收另列，不能因fixture通过关闭运行采用门。跨域共同场景可复用同一次运行，但必须显示每个Owner的独立责任和证据，不能把某仓结果复制给其余仓。

| 验证类别 | 必须观察的结果与反例 |
|---|---|
| ITER项目/输入/方案/任务 | 原身份和版本无损；草稿允许的空值保持；激活缺Owner拒绝；R2不改R1送审包；两个Occurrence保两项；权重分母0为null、Blocked不删分母；任务100%与FAIL分列。 |
| ITER评审/OA | 完整候选集合与RoundBinding匹配；Subject/Package/Policy/Technical分别固定。Submit写包/集合/绑定/轮次/Outbox/原回执/审计同事务；Inbox接收与业务应用分阶段。两运输事件同决定只应用一次；缺rejectDisposition阻塞；撤回/应用竞争只一方改变业务。不能向OA封闭对象加RETURN。 |
| ITER评价/关闭/恢复 | ADOPT依逐要求证据、有效评审和无Blocking；REJECT可Closed并保FAIL；CONTINUE有受理方和期限；外部未知不能结案。VER/ENG响应丢失查回原Plan/Baseline；终态迟到仅追加事实/处置。 |
| REL许可/准入 | 四Purpose无强弱继承；活动类别、范围、条件、profile明确。许可、预约、DEV Claim、MES真实建立分别留证；Unknown不执行、不盲退，不以顺序GET证明最终资格。 |
| REL计量/释放 | 同基准Q=C+R+P，真实超额X独立保留；6投入4良品仍按6消费；累计2→4不是6，根6/子2+4只计6。NOT_FOUND/根Cancelled/超时不足以释放；须覆盖原键、所有相关子执行及迟到请求封闭。C4→3未封闭转P；终态更正走后继，不覆盖旧结算。 |
| REL发布/采用/控制 | 同版补发只增Attempt；目标、ScopeVersion、AdoptionDefinition、许可绑定逐项相符。ACK、接受、就绪、真实采用、相符性、后果分轴；A成功不盖B未知；删B不抹旧义务；已采用与当前阻塞可并存。 |
| 租户/授权/精度 | A/B同键隔离；当前鉴权覆盖查询、回执、导出及下载；隐藏字段/对象存在不泄露；原量值/单位/Ref合法域无损。不以schema存在证明隔离，不自动选numeric精度或UUID替外域键。 |
| 并发/崩溃恢复 | 在原写入事务提交前失败：无部分业务效果；提交后丢响应：原键回同结果；异体重放拒绝；撤权/控制与新效果竞争使用已采用共同最终门；只读/拒绝路径不生成新许可、工单或消费。允许的失败审计与业务写集分开核对。 |

以上为后续必须实现的观察条件，本任务没有执行这些业务测试，也不声称已有服务能提供这些回执。ITER DP01–08中未定的角色/代理、保留期、容量、外部安全终结能力、多语言和代码适配不能由测试数据默认为已批准。PostgreSQL取代旧双库开发目标不豁免这些事项。

正文矩阵内字段的“类型建议”不自动成为最终存储上限。字段读写测试应对照已采纳的逻辑输入域，分别验证必填/可空/省略、合法边界、越界拒绝、只读字段注入和历史回读；未选定建议参数时记录 `BLOCKED_DECISION`，不得偷偷填默认值后宣称通过。

## 6. 采纳记录与生效

本稿交付、规范采纳、工具支持、实际实现、运行验证、远端交付是不同事件。设计提交或合并不等规范自动采纳。

采纳须形成追加式记录：`adoptionId`、准确版本及整个制品manifest hash、目标范围、明确接受新标准的原话/可核来源、决定人及时间、两条历史GAP的处置、覆盖矩阵审查结论/未决项、例外范围及失效条件。历史消息未取得准确时间/ID时如实为空，不补造。记录必须明确“以当前可知义务建立新标准，无法证明旧30/48逐项等价”。普通“继续”或领取WP05-01只授权做设计，不能替本版最终采纳。

需要逐项审查的五个问题：当前已接受正文是否遗漏；后继是否越权或丢失原义；R1是否只在明确范围叠加；所有已知断言是否有对象/操作/观察；历史不可比较和物理未定范围是否全部保留。**任何可知义务未映射、只有R1两例、仅改状态名、填造旧号、借用静态PASS或未授权扩大Owner均拒绝采纳。**

采纳后将当前proposed内容以具名决定绑定为生效版本；不得原地改写已采纳字节。同义勘误、义务新增/取消、场景或来源变更均形成后继版本、差异与重新采纳记录。发现原hash不符或未处理的真实冲突时，只冻结受影响新消费；历史结果按原版本保留并评估是否需要重验。

## 7. 对目标完成门的影响

当前 [manage_roadmap.py](../../tools/manage_roadmap.py) 的原门要求 `original_acceptance_inventory.state=COMPLETE` 且全部原用例PASS；本任务**不修改该工具/总台账/生成页/四份状态文件**。交付报告由协调对话在交付窗口统一同步这些状态。未完成该窗口与远端main核对，不宣称WP05-01交付完成。

采纳后的独立工具修订建议采用双路径，且替代路径仅对白名单ITER/REL生效：

```text
原路径 = 原清单COMPLETE + 全部原用例有真实PASS证据
替代路径 = 目标为ITER或REL
         + 本版准确制品及明确采纳记录有效
         + 两历史GAP永久保留，未填造原件/原AC恢复
         + 当前可知正文义务及全部可恢复场景映射闭合
         + 新依据每项必要业务断言有适用层级的实际执行证据
         + 未定参数/能力缺口已由准确后继决定解决
共同门 = 全部所需主体任务交付 + 所有目标R1运行场景PASS
       + 真实Owner/页面/worker/持久化和专项集成证据
       + 各所属仓远端main包含及包/合同采用证据
目标DONE = (原路径 或 经独立实现验证的替代路径) 且 共同门
```

不能将替代路径写成 `original_inventory=COMPLETE`。建议新增独立 `acceptance_basis`、`adoption_ref`、`historical_gaps`、`normative_coverage` 和按版本保存的执行结果，原清单字段保留原值；准确schema/迁移脚本需由协调对话另开工具任务，不能在多个分支各造定义。工具门未交付前，目标仍受现行门阻塞，即使某些业务已通过也不强行标DONE。

独立工具修订至少回归：未采纳拒绝；hash漂移拒绝；遗漏已恢复源/正文/R1拒绝；伪造历史COMPLETE拒绝；FAIL/BLOCKED/NOT_RUN拒绝；静态PASS不能作业务证据；非白名单目标不得绕原门；准确采纳且全部证据齐全才允许新路径；WP01汇总不把新依据有效计为“历史原件完整”。没有通过这些门的情况下，手工编辑JSON不能代替实现。

后续消费按现有任务分工：WP05-18～21实现ITER，WP05-32～36及42实现REL，WP05-61负责准确工程Progress，WP14-07提供相应跨域验证。这里是观察责任导航，不修改它们的依赖或声明已READY；领取时须重新核对当时主线与实际前置。

## 8. 本任务的设计验收

设计静态核对包括：原材料hash/位置、221条源清单无丢失/重复/断言改写、8条R1目标集合、10条细化向量、正文项目全集、引用和状态边界、原台账及业务文件未改。可复现命令和实际结果见 [delivery.md](delivery.md)；静态脚本只检查资料及映射，不执行数据库/服务，不写PASS到业务台账。

WP05-01可形成可审查设计交付；正式记DONE还需协调领取/交付窗口、任务级审查、项目状态同步及远端main包含性。新验收依据是否采纳记录在独立轴；即使本设计任务交付DONE，两个业务目标仍不能因此DONE。
