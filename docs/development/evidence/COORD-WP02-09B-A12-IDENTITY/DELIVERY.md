## 实施顺序与同卡验收

1. **Main.IAM、Main.C02 先固定提供方版本。** 在 Main 保留分支上继续使用原 C03 凭据。交付 A12 专用在线身份证明 `account-c03-service-identity/v1`，及匹配的 C02 账户来源 `cp6-account-c03-ingest-v1`，使用独立的 `com.gtx537.platform.service-principal.changed.v2` 和 schema `2.0.0`。这些是本卡待实现的版本。由真实服务认证和受信登记取得租户、客户端、稳定主体 UUID 和当前认证 epoch，签名绑定固定签发者、CRM 账户收件受众、A12 用途、本次请求的 nonce、签发时间和短时有效期。C02 发布可核对的来源版本、主体及 epoch，并处理停用、轮换和撤权。沿用现有询盘 v1 的含义与拒绝边界。冻结新 schema、来源、合同包内容摘要和提供方完整提交，再交 CRM 依确切版本联验。
2. **CRM.C02 验明调用者，CRM.Account 在当前账户上判权。** 在原 CRM 分支，以实际认证调用方、受信租户和本次请求核对签名、受众、用途、nonce 及有效期。预期主体和 epoch 从在线认证取得，与同一 PostgreSQL 事务的当前发布事实、账户归属及撤权锁核对。来源不可用、冲突、已过期或身份不匹配时拒绝。写入最终决定点核 `service:account.c03.ingest` 与账户范围，提交前重核。每次披露原回执时，另核当前读取者的 `account.command.read` 及原结果范围。C03 原请求凭据、询盘凭据、来信或旧允许均不能替代当前账户授权。
3. **已知请求入史，按真实链路验收。** 只处理原合同的伙伴成功和失败结果。结果到达前从独立来源核实既有请求及其与该租户账户的关联。未知请求仅隔离，禁止据结果补建。保留原键、原摘要、字符串 `BusinessPartnerKey` 及同一请求内的版本规则，用同一 PostgreSQL 连接和事务提交 Inbox、原请求结果历史、原命令回执、审计和 Outbox。
4. **两仓实际采用后核销。** 在正常签发、C02 生产与消费、CRM.Account 业务写入和原回执读取路径验证正例。覆盖询盘与账户凭据互相拒绝，错误签发者、受众、用途、nonce、租户、客户端、主体或 epoch 拒绝，过期、停用和轮换拒绝，及撤权与写入两种顺序。原 11 项 DEL01-A1/A3/A4/A7/A8、DEL07-A2/A3/A4/A5/A6/A9 和 `COM-S6-PRECHECKPOINT-FINALAUTH` 正反两例逐项运行并登记。须实证并发去重、摘要冲突隔离、整组回滚、提交结果未知按原键恢复、原回执当前读权，以及缺最终授权时零业务效果。保留明确标注的模拟业务输入和真实 PostgreSQL，身份及授权结论取自实际产品入口。[原验收逐项出口](https://github.com/GTX537/CP6.CRM/blob/64cf837fca119d0e238eed50593d4d6b43d4cc20/docs/development/evidence/WP02-09b/DELIVERY.md) · [原号交付与缺口](../WP02-09/DELIVERY.md)
