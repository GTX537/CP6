# BUG-921 — 操作日志降级保存隔离

W460-01；Issue [#921](https://github.com/GTX537/CP6/issues/921)；基线 `c0e56ee9b2bb9758e551d3cbcee0ff290d8cb77a`。本报告记录实际本地结果；最终远端采用、分支处置及DEV-2释放以对应PR、远端main和 `manage.ps1 finish` 为准。

## 改动

原 `OperLogFilter` 在Kafka不可用时，于业务动作结束后对同请求CP6Context添加日志并SaveChanges。业务拒绝/事务回滚没有自动清除待保存实体，后续日志保存可能意外提交它们。W459曾在原D7绑码看到同类写入；本窗用未修改的实际场景差量路径复现通用问题。

PostgreSQL仅在日志降级时从同一请求DI容器创建独立作用域，先将日志原已确认租户传给该作用域，再解析原类型CP6Context并保存日志。业务Context仅保留原租户读取，不保存、不清空或修改其跟踪数据。原Kafka成功优先和失败降级、构造、路径跳过、GET设置、请求体限制/脱敏、身份字段、异常状态映射及旁路失败诊断保持。历史非PostgreSQL路径保持。

## 实际验证

- 同一冻结源码在原产品执行3项：原场景拒绝问题1项复现，正常业务和原日志故障2项通过，零跳过。实际场景先暂存一个库区，再因已发布库位不能删除而拒绝。旧HTTP400后，日志同Context保存已落一条业务库区。另一租户、已发布原行及无关库存保持。
- 最终3项实际Main Kestrel/PostgreSQL18.6全部通过、零跳过。相同拒绝HTTP400，原几何写集逐项保持、暂存库区0条；实际日志保留一条，正确租户/操作/操作者，空间请求体仍不记录。原日志对动作异常记500，和最终业务HTTP400分列，本窗不改变该合同。
- 正常真实场景保存一条新库区和一条日志，业务200；实际PostgreSQL拒绝日志插入时仍业务200且库区提交，日志没有落库，保留 `SPACE_OPERLOG_DB_FALLBACK_FAILED` 安全诊断。该结果不作为日志必达或生产Kafka验收。
- 26项既有 `OperLogFilterTests` 实际通过、零跳过，覆盖原构造、传输、请求体、路径和状态行为，与3项原生分列。使用隔离模拟场景、身份与故障输入，真实宿主、业务、日志和数据库；未启动外部Kafka。

受影响WebApi/Tests正常SDK串行构建通过；Core、Entity、PostgreSql及锁定依赖使用W459已核对同源产品和SHA，没有重复构建。一次集中SPEC/QUALITY及数据原子性审查核对完整diff。私有证据 `D:/CP6-local-test/CP6-72H-20261109/W460-01/` 的red/green build/hosted、实际TRX/行集/诊断、compatibility、`actual.json` 和停止记录。自有测试宿主和隔离数据库均已停止。
