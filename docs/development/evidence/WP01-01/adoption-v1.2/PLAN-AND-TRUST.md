# Bounded implementation and trust boundary

This is the WP01-01 LEDGER_GATE_IMPLEMENTATION_ONLY / CONFIRMED slice. Full WP01-01 remains PLANNED / NOT_CHECKED. The implementation uses test-driven-development: record failing adapter and manager tests and exact pre-change sources, implement, then record the requested local regressions and one complete diff review.

The untrusted inputs are every package/manifest/roadmap field, path, receipt and claimed PASS. The trusted computing base is the reviewed adapter and manager, Python/git/gh/OpenSSH executables, the operator process environment, its protected external policy and allowed-signers files, GitHub authenticated TLS/API, and the separately governed signing authorities. An attacker able to replace these executables, environment or operator policy is outside this local ledger checker threat model. Ordinary repository authors cannot bootstrap authority from package fields, Git authorship, Handoff ACK or a receipt they place in their branch.

CP6_ACCEPTANCE_TRUST_POLICY is an operator-provisioned absolute path outside every Git worktree. It specifies independent authority/execution registry repositories, paths, principals, allowed-signers files and permitted product repositories. No policy is supplied or enabled in this task. Read-only gh API resolves current registry main and fetches raw signed bytes at that exact commit; ssh-keygen verifies the registry with a role-specific namespace and externally trusted signer. Current registry validity, per-record expiry/revocation, authorization action/target/version/manifest and append-only identity must all match. Registry administrators must retain immutable adoption identity history and publish revocations immediately; signed snapshots have at most a 24-hour validity window. A stale/missing/unverifiable source fails closed. Product source commits must be exactly on current remote main ancestry, independently queried, not a locally supplied remote SHA.

Authority registry attests the actual business authorization source and scope, not merely technical development authorization. Execution registry is separately signed and must attest the real execution origin and exact report plus original log bytes, identifying business runtime, environment, command, source and Owner/consumer. Its operator must observe those facts independently; accepting an unreviewed uploaded JSON/PASS is outside the registry contract and is not authorized by this implementation. Independent execution attestation remains required even when synthetic=false appears in a report.

Source verification uses contained paths under the checkout and operator-selected readonly archive roots (CP6_ACCEPTANCE_ARCHIVE_ROOTS, OS path separator). Historical Git blobs are read at exact recorded commits. No path may escape those roots, including symlinks. No source copy, test fixture, same-package authority or invented signature becomes trusted evidence. Registry URLs/principals are not inferred from candidate contents. Network and subprocess calls have bounded timeouts; no fetched code is executed.

The gate has three independent results: basis_adoption_valid, inventory_coverage_valid and target_runtime_valid. The new route is limited to PLM-ITER-01 and PLM-REL-01. WP01 inventory aggregation accepts 123 original inventories plus the two exact adopted bases; it never relabels missing originals. Runtime requires exact obligations, approved scenario-to-obligation/edge/profile binding and independent executions; 1256 planning edges are retained as planning obligations, not an unconditional runtime checklist. All existing TASK_DELIVERY and other manager gates remain in force.

Current business adoption and runtime are absent. Positive tests use isolated synthetic trust fixtures only; no live registry, keys, services, database or GitHub Actions are provisioned. Remaining real business inputs and implementation dependencies stay explicit in the candidate.
