# BUG-907 — 操作日志当前授权与清理父事务

W453-01；Issue [#907](https://github.com/GTX537/CP6/issues/907)；基线 `420a19467cab106e55757153de90abdb990eb11d`。本报告记录实际本地结果，最终远端采用、分支处置和DEV-2释放以对应PR、远端main及 `manage.ps1 finish` 为准。

## 改动及边界

`GET/DELETE api/OperLog` 原先在动作缓存检查后直接查询/清空DbContext。PostgreSQL 路径现在采用同 Context 的 `OperationLogOwnerV1`、既有 `operlog:query/delete` 和实际签名会话，认证共同根先于实际 `public."Sys_OperLogs"` 的 SHARE/SHARE ROW EXCLUSIVE。计数/分页读取和清理均在同一当前父事务内，最后检查同一会话和请求取消；回滚清理跟踪，数据库故障明确503，未知提交明确 `OPERLOG_OUTCOME_UNKNOWN`，不盲目重试。

原关键词 OR 规则、分页、时间排序、返回完整原实体/total、清空count及租户过滤保持，未增加输入上限或静默默认。历史非PostgreSQL完整控制器业务体和一参数构造使用保持；未新增双库验收。只有当前PostgreSQL入口采用新Owner与本地工厂，无模型、默认权限、包或工作流改动。

## 实际验证

- 同一冻结原生源码在原产品运行7项，6项失败/1项正常、零跳过。四类当前用户禁用/对应query或delete撤权后仍200，查询等待时撤权可抢先；第六项为故障响应口径：原DELETE原生故障500，但三条原行实际保持。原数据库已回滚，不能把它说成旧数据残留或丢失。
- 修复后7项实际Main Kestrel/PostgreSQL18.6通过、零跳过。用户禁用先完成时GET/DELETE均401，动作撤销均403，三条指定原模拟日志和无关库存写集保持；恢复用户/动作并重新登录后实际正常读取或清理。
- 查询先取得共同根时完成200，然后原生权限撤销继续，后续读取403；计数/分页与当前决定的顺序有实际锁等待证据。
- 实际一次性BEFORE DELETE故障触发，最终503且三条原行仍保持；移除故障后正常清理。原故障500/保留与最终503/保留分别记录，没有夸大原故障的写入效果。
- 正常关键词/分页/排序/完整原实体和清空count通过；原三条模拟记录清理，另一租户日志及无关库存保持。操作日志过滤器本来跳过日志接口自身以防递归，该规则未改。

原生控制通过持有已有认证根的实际SQL禁用用户或撤销动作；用户/角色表名来自实际模型，日志表名和整数identity主键已核对映射。日志表锁可能同时阻塞其他HTTP管理动作的日志/审计写入，因此本窗没有把这些控制伪称实际租户生命周期HTTP。它们是明确模拟身份/控制输入，实际宿主、签名认证、权限、业务服务及数据库执行。

首次fixture编译将 `Task<int>` 原生控制任务传入只接收HTTP任务的观察器而失败；新增专用原生控制锁观察器后重新编译，才执行上述原产品用例。未修改共享HTTP观察器或把该编译失败算成产品回归。修复只在原产品实际7项完成后实施。
