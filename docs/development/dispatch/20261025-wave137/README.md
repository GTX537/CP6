## 设计与验证

1. 先用真实 PostgreSQL 重现部门用户对已绑定库存成功调整后无法查询本次流水/恢复原操作的缺口。历史未绑定流水仍不可凭业务键推断部门。
2. 实际 StockMovementService 原语只在已授权父 Owner 的确切 DbContext/事务中继承。显式作用域关联根 OperationsAccess；各入口独立调整/移库、原操作调整/移库、盘点审批、收货（含品质委托与成品）、出库分配/发货/取消、MES反冲均实际采用。来源是本次真实修改的 Stock UUID，不是调用者声称的 UUID 或历史业务键反查。
3. 仅复制当前同租户健康、启用的 Stock 映射。无映射库存保留已有合法行为，新库存归属另立创建合同，不默认调用人部门。MOVE 两腿分别继承各自实际库存对象，不能把来源一侧部门强加到目标库存。
4. 流水 UUID 服务端分配，一次性能力绑定 DbContext/当前原事务/租户/真人/源 Stock UUID及映射revision/新流水UUID。保存流水后只为该新对象插入映射，记录结构化来源审计，同事务失败全部回滚。既有对象改归属仍走 IAM，禁止历史批量回填。
5. 映射版本受控转换：插入前所有参与者的组织版本均须与实际一致；单次参数化插入后证明非映射组织版本未变，仅接受本次预期映射变化。提交前复核精确来源/目标映射、真实对象及全部当前权限。源ABA、同事务撤权、额外映射变化、最终门故障均不得被版本转换掩盖。委托路径的验证注册在根 Owner。
6. 验证原结果查询/重放当前权限、同键一次效果、原输入冲突、未知提交恢复、仓区/租户/字段限制，MOVE两腿不同部门及第二腿失败整体回滚，各父路径实际继承；保留已有合法无绑定路径和历史不推断。
