# B / WP02-02：真实服务令牌自撤销接线

本窗口承接[任务卡](../../task-plans/WP02.md#wp02-02)的可信存储采用。完整任务仍 IN_PROGRESS；只批准这条入口与必要的隔离安装/验证，不据此开启 WP02-03、WP02-10 的全域权限改造。S02-00、WP02-01 已交付；Main 正式采用 Platform 0.10.3、租户池/目录、ERP/Identity RLS 与第十轮初始化能力均已在主线。

## 真实路径与原合同

核对[原 C02 设计](../../../superpowers/specs/2026-09-10-c02-identity-events-design.md)、[C01 说明](../../../crm/C01-SERVICE-IDENTITY.md)和以下当前源代码，而不是把模型总表数当 writer 清单：

- `CP6.WebApi/Controllers/Sys/CrmOidcController.cs` 的 `RevokeServiceToken`、`CrmOidcServiceTokens.Authenticate/RevokeAsync`。
- `CP6.Core/Services/CrmIdentity/CrmServiceTokenRecordStore.cs` 的 `RevokeAsync`，`IdentitySnapshotWriter.RevokeTokenAsync/WriteDataAsync/LoadLockedAsync`。
- PostgreSQL Core baseline 中 `crm_identity."ServiceToken"`、`crm_identity."Snapshot"`、`public."CrmIdentityTenantGenerations"`，`IdentityGenerationPostgreSqlV1` 的 generation trigger，以及 `crm_identity_priority` 真实 Outbox/RowVersion/函数依赖。
- `TenantConnectionManager`、`TenantConnectionLease`、`TenantEfCommandGuard`、`IdentityTenantTransaction`、`TenantLoginDirectoryV1` 与既有 `DatabaseSharedContext`。

请求保持严格 Basic 服务客户端认证、规范单值 jti、不枚举响应；只能撤销同 issuer、client_id 和绑定租户的实际签发记录。未知、其他客户端/租户及已撤销 jti 不能形成新效果，也不能披露存在性。服务 actor 不转换为自然人；浏览器令牌不由本入口撤销。现实现只在签发时检查 Enabled/scope/租户活跃，不能为了构造“当前授权”擅自让已停用客户端丧失合法自撤销能力。新模式的注册 IsActive 必须表达当前自撤销资格，而非简单复制签发开关。需要改变既有合同才提交具体冲突给 COORD。

## 必须交付的行为

1. **真实可信来源与准确绑定。** 用本宿主实际 Basic 校验结果及受控服务客户端/组织注册生成 `ctx-binding-v1`；实现本入口专用的 source verifier、binding authority，使用既有 executor/accessor。租户、主体、issuer、region、用途、存储路径和版本来自权威配置/记录，不能从 body/header/default tenant、自签布尔值、测试 verifier 或调用方提交的证据升格。实际凭据验证失败不打开业务连接；无效/缺失/漂移映射失败关闭。
2. **完整有限写集。** 自撤销会写 ServiceToken.RevokedAtUtc、Snapshot、trigger 派生的 generation、优先 Outbox 及其真实 RowVersion/序列依赖。核实此调用的 SaveChanges hooks/raw SQL，列出剩余附带对象；与普通用户/部门快照和普通 Outbox 分支区分，不能给所有 Core 表泛授权。保留 TenantId、原全局唯一键、字段容量/精度、事件 identity/version/摘要及同事务原子性。
3. **同一物理事务下执行和最终检查。** 用租户普通运行登录和受保护目录，让真实 store/writer 在已有 TenantStorageTransaction 同连接中完成所有效果。复用已有事务机制，不另造通用 UoW；不嵌套调用不支持重入的 adapter。现 `DatabaseSharedContext` 走 legacy public-only 配置，新租约固定 pg_catalog，且原 child context 不自动继承 guard；必须明确适配并保持同步/异步命令、raw SQL、child context 与最终提交的同一身份/事务检查。不得仅给外层加 wrapper 后在内部另开连接或提交。
4. **权限与重试不漏口。** 在最终写入/提交边界核验当前自撤销资格与绑定版本，保持目录锁到事务结束；区分 storage identity fence 与 Owner 授权 fence。若配置只支持进程启动时不可变快照，明确其版本/生命周期和实际支持的更新边界，不宣传跨实例即时撤权。重复/并发自撤销不重复发事件或增加快照版本；提交前取消/失败不留下部分效果；提交后响应丢失用既有持久事实恢复相同结果，不把异常当成回滚证明。
5. **真实入口可选择采用。** 通过专用宿主配置/注册启用这条路径，缺配置或布局错误明确拒绝，启用后不得悄悄回退到默认高权限 CP6Context。签发 `RecordAsync` 仍保持原合同；所选存储必须与实际签发记录属于同一个明确物理数据库，不能切到空库后把每次“找不到”称为撤销成功。仅控制测试使用空隔离库；不切换已有环境或改默认业务连接。整个实例的其他登录、ERP handler、dispatcher、普通 Owner 不在此窗口采用范围。
6. **可重现的显式安装。** 必要 DDL 使用独立、有明确版本的有限 profile/安装步骤，控制身份与运行身份分离，复用真实映射和 PostgreSQL 依赖。可以从原 baseline 派生精确对象，但不能写入“完整 Core baseline 已完成”的虚假历史，也不能悄悄改变 `erp-identity-messaging-v1` 的既有含义/恢复 seal。旧 profile 与已成功证据输入不变则复用；未知布局拒绝。全量 Core baseline 在自有夹具中安装只证明夹具准备，不表示所有表已租户化。控制操作保持静默窗口，应用不启动迁移，不创建生产凭据。
