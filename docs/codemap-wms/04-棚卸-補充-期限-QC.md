## 1. 棚卸 StockTake — 4 段流程（计划→盘点→差异确认→承认调整）

状态机（`StockTake.cs:12`）：`Planned(0) → Counting(1) → DiffReview(2) / AwaitingApproval(3) → Completed(4)`，旁路 `Cancelled(9)`。采番 `ST`。

### 1.1 计划/快照创建 — POST /api/wms/stock-take/plan
**前端**：`StockTakeListView.vue` 「スナップショット」按钮→弹窗→`onCreatePlan`（`:138-147`）→ 成功跳 `/wms/stock-take?no=`。api `stockTake.ts:13-15`。
**后端** `CreatePlanAsync`（`StockTakeService.cs:103-161`）：倉庫CD必填→**快照查询** `Stocks.Where(WarehouseCd && !IsDeleted)`(可选 LocationCd前缀/ProductCd)→0件抛错→`NextAsync("ST")`→头 `Status=Planned`→**逐行把 Stock 当前值定格** `BookQty=s.PhysicalQty`/`UnitPrice`/`StockId=s.Id`。实体 `StockTake`/`StockTakeDetail`(`BookQty decimal(21,8)`)。

### 1.2 盘点录入 + 差异确认 — PUT /counts、POST /submit
**前端**：`StockTakeView.vue`，`canStartCount`(status=0)先 start-count，`editable=status===1` 表格 `countedQty` 可编辑。`recalcDiff`（`:163-167`）前端即时算 `diffQty=countedQty-bookQty`。`onSaveCounts`（`:180-197`）/`onSubmit`（`:199-206`）。
**后端**：`UpdateCounts`（`:178-205`）仅 `Counting/DiffReview/AwaitingApproval` 可(否则 `WM-MSG-043`)，**服务端重算** `DiffQty=CountedQty-BookQty`/`DiffAmount`(不信前端)。`SubmitForReview`（`:207-250`）仅 `Counting` 可；未盘点 `CountedQty==null`→`WM-MSG-060`；差异≠0 无理由码→`WM-MSG-061`；**阈值判定** `needsApproval = ApprovalThresholdAmount.HasValue && maxAbsDiffAmount > threshold` → `Status = needsApproval ? AwaitingApproval(3) : DiffReview(2)`。

### 1.3 ⭐ 差异确定调整库存（经 ADJ）— POST /api/wms/stock-take/{no}/approve
**前端**：`canApprove=status===2||status===3`，`onApprove`（`StockTakeView.vue:208-215`）→ `stockTakeApi.approve`。
**后端** `ApproveAndApplyAsync`（`StockTakeService.cs:254-300`）：
```csharp
if (h.Status != DiffReview && h.Status != AwaitingApproval)
    throw new InvalidOperationException("WM-MSG-043: 差異確認 or 承認待ちでないため承認できません");
foreach (var d in details) {
    if (d.ApprovalStatus == Rejected) continue;
    var diff = d.DiffQty ?? 0m;
    if (diff != 0m) {
        var txnNo = await _stock.ApplyAsync(new StockMovementRequest {
            TxnType = WmsTxnType.ADJ, WarehouseCd = d.WarehouseCd, LocationCd = d.LocationCd,
            ProductCd = d.ProductCd, LotNo = d.LotNo, Qty = diff,   // ← 符号付き差分（正=IN效果/负=OUT效果）
            UnitPrice = d.UnitPrice, RelatedNo = stockTakeNo, RelatedType = "STOCKTAKE",
            Remark = $"棚卸差異調整 {stockTakeNo} 行 {d.LineNo} ({(diff>0?"+":"")}{diff})",
        });
        d.AdjustTxnNo = txnNo;   // 明细留痕
    }
    d.ApprovalStatus = Approved;
}
h.Status = StockTakeStatus.Completed; h.CompletedDate = DateTime.Today; h.ApproverCd = userName;
```
仅差异≠0 行发 ADJ，进 `ApplyDelta` ADJ 分支 `PhysicalQty += Qty`——**把账面 Stock 校正到实盘数**，`RelatedType="STOCKTAKE"` 成追溯钩子。错误码 `WM-MSG-043`(`:258`)。取消(`:302-312`)Completed 不可。

## 2. 補充 Replenish（拣货棚低于阈值→从保管棚 MOVE 补）

**前端**：`/wms/replenish` → `ReplenishView.vue`，「補充指示一括生成」批量建立来源单；每行「実行」不再直接改变库存，而是发布 v2 MOVE，并显示生成的任务号。状态 `2` 表示 MOVE 已发布，状态 `1` 只表示现场任务已真实完成。
**后端**：
- `GenerateBatchAsync`：取**ピッキング棚(`PIK-`前缀)** 且 `PhysicalQty<minQty` 自有库存 → 防重复（Pending 或 TaskIssued 都跳过）→ **找补充源** 同品**保管棚(`RES-`前缀)**`AvailableQty>0`，按 `ExpiryDate ASC→ReceiveDate ASC` 取一 → `actualQty=Min(needed, source.AvailableQty)` → 建 `ReplenishOrder(Status=Pending)`。
- `ExecuteAsync`：在同一事务调用 `MobileTaskV2Service.CreateAsync`，生成 `RelatedType=REPLENISH/RelatedNo=补充NO` 的 MOVE；只写 `RSV` 并预留目标容量，来源单进入 `TaskIssued(2)`，物理库存保持不变。
- `UpdateAsync`：关联任务仍为 `Pending` 时，重建源库存/目标容量预留并同步任务字段；任务一旦 `InProgress/Paused/Exception/Completed/PartiallyCompleted`，返回 `409 WM-V2-SOURCE-TASK-STARTED`。
- `CancelAsync`：原子取消全部 Pending 关联任务并释放预留；已开始或已有实绩时拒绝来源取消。
- `MobileTaskV2Service.CompleteAsync`：现场扫码完成时才在一个事务内写 MOVE OUT/IN；所有关联任务完成且累计实绩达到来源数量后，反写 `ReplenishOrder.Status=Executed(1)`、交易号和完成时间。
- 仓位优化同样遵循来源规则：`SlottingService.ApproveAsync` 为每条可迁移建议选择实际目标库位并生成 `SourceType=SLOTTING` 的 v2 MOVE；计划取消只允许联动取消尚未开始的任务。
- **数据范围**：补货单按目标库位所属区域过滤，创建、编辑、批量生成、执行和取消都使用相同范围；仓位优化会读取整仓库存与交易，因此仅允许拥有整仓授权的角色查询、分析、审批和取消，单一区域授权默认拒绝。
**稳定错误码**：`WM-V2-SOURCE-TASK-STARTED`、`WM-V2-SOURCE-LINK-MISMATCH`、`WM-SLOTTING-NO-MOVE-TASK`、`WM-V2-TARGET-CAPACITY`、`WM-CONFLICT-ROW-VERSION`。

## 3. 期限 Expiry — 近效期查询 + 一括廃棄

**前端**：`/wms/expiry` → `ExpiryView.vue`，`reload`（`:82-88`）按 days 查，`<7天`soon/`<0`overdue；多选「廃棄」`onDispose`（`:90-106`）。api `expiry.ts:5-10`。

## 4. ⭐ FEFO 引当逻辑（先过期先出）

> **FEFO 真正实现不在 ExpiryService**，而在 `OutboundService.AllocateAsync`（`IExpiryService.cs:11-12` 注释明示）。ExpiryService 只做查询+废弃。
核心 `FindCandidateStockAsync`（`OutboundService.cs:325-340`）三级排序 `ExpiryDate ASC → ReceiveDate ASC → LotNo ASC`（null→MaxValue 排末）+ 过滤 `!RecallFlag/AvailableQty>=needed/OwnerType==Self/QcStatus∉{Failed,Hold}`。详见 [03 出庫篇接缝①](03-出庫-出荷.md) 与 [README §2](README.md)。补充源选择用同向简化 FEFO(无 LotNo 三级键)。

## 5. ⭐ Lot追溯（纯查 T_StockTransaction，无专用表）

> `ILotTraceService.cs:12` 注释：「純クエリ：T_StockTransaction の再帰トラバース、専用テーブル不要」。
**前端**：`/wms/lot-trace` → `LotTraceView.vue`，productCd+lotNo+方向(FORWARD/BACKWARD)→`trace`（`:136-147`）+`loadSummary`+召回 `setRecall`。
**后端**：
- 公共节点 `GetNodesAsync`（`LotTraceService.cs:77-96`）：`StockTransactions.Where(ProductCd && LotNo && !IsDeleted).OrderBy(TxnDateTime)` 拉该 Lot 全时序流水→映射 `LotTraceNode`。
- **正向** `ResolveCustomersAsync`（`:98-142`）：筛出库流水 `RelatedType=="OUTBOUND" && (OUT || (MOVE&&Qty<0))`→`RelatedNo` 反查 `OutboundOrders`→客户。**该 Lot→OUTBOUND流水→出库单→客户**（货流到哪些客户）。
- **反向** `ResolveSuppliersAsync`（`:144-194`）：筛入库流水 `IN && "INBOUND"`→`InboundReceipts`→`InboundOrders`→`SupplierCd`。**该 Lot→INBOUND流水→入库实绩→入库预定→仕入先**（货从哪来）。
- **召回** `SetRecallFlagAsync`（`:42-55`）：该 `(ProductCd,LotNo)` 全 Stock 行 `RecallFlag=flag`→FEFO `FindCandidateStockAsync` 的 `!s.RecallFlag` 自动排除该 Lot。
**校验**：Controller `productCd/lotNo` 必填(裸文本)；summary 找不到→`404 WM-MSG-070`。Service 纯查询无 WM-MSG。

## 6. QC検品 — 录入 + 判定（PASS 自动入库）

**前端**：`/wms/qc-inspection` → `QcInspectionView.vue`，「入庫予定から作成」`onBridge`(createFromInbound)；详情录 受入/合格/不良/保留 数量；「判定」→`judgeDialog`。api `qcInspection.ts`。
**后端**：
- `CreateFromInboundAsync`（`QcInspectionService.cs:71-113`）：入库预定须 `Confirmed/PartialReceived`(否则 `WM-MSG-043`)→按明细建 `QcInspection`(`Status=Created`)+`QcInspectionItem`，采番 `QC`。
- `SaveItemsAsync`（`:145-178`）仅 `Created/Inspecting` 可(否则 `WM-MSG-043`)，`Created` 自动 0→1；逐行写 `ReceivedQty/AcceptedQty/RejectedQty/PendingQty`。
- `JudgeAsync`（`:180-240`）：`FinalJudgement` 空→`WM-MSG-102`；置 `Status=Judged`；**PASS 分支**取 `AcceptedQty>0` 明细→组 `InboundReceiptDto`(**LotNo 自动 `QC{yyyyMMdd}-{i:D3}`**，`ReceivedQty=AcceptedQty`，库位 `{wh}-RCV`)→**调 `_inbound.ConfirmReceiptAsync` 真实入库**(其内走 `IStockMovementService` IN)→回写 `GeneratedReceiptNo`；非 PASS 仅改状态不动库存。
**错误码**：`WM-MSG-043`(`:77,150,185,247`)、`WM-MSG-020`(`:82,117` 无明细)、`WM-MSG-070`、`WM-MSG-102`(`:188` 判定理由必填)。Controller `judge` catch `InsufficientStockException`。

## 关键发现（三专题速查）
1. **棚卸差异→库存**：`ApproveAndApplyAsync` 对差异≠0 行调 `ApplyAsync(ADJ, Qty=符号差分)`，`ApplyDelta` ADJ 分支 `PhysicalQty += Qty` 校正账面，`AdjustTxnNo` 回写。
2. **FEFO 引当**：在 `OutboundService.FindCandidateStockAsync`，三级 `ExpiryDate→ReceiveDate→LotNo`，配过滤 `!RecallFlag/Self/QcStatus∉{Failed,Hold}`。补充源同向简化 FEFO。
3. **LotTrace 纯查 T_StockTransaction**：正向筛 OUTBOUND→OutboundOrder→客户，反向筛 INBOUND→InboundReceipt→InboundOrder→仕入先，无专用追溯表。召回置 RecallFlag 即自动排除引当。
4. **QC PASS 经 ConfirmReceipt 自动入库**（合格量计入库存，LotNo 自动 `QC{date}-NNN`），非 PASS 不动库存。
