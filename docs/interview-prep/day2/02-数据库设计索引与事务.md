## 1. 数据库设计方法：从业务需求到表结构

### 1.1 概念（类比）

数据库设计不是"先想有哪些表"，而是**先想清楚业务里有哪些"东西"和"事情"**，再把它们落成表。

一个好用的类比：你在管理一个仓库。仓库里有两类信息：

- **"现在是什么样子"** —— 某个货位上现在放着多少某某产品。这是**状态（当前值）**，会被反复覆盖更新。
- **"发生过什么"** —— 昨天下午收了 100 件、今早出了 30 件。这是**事件（流水）**，一旦发生就永远不变，只会往后追加。

几乎所有制造业 / 仓储系统的核心，都是这一对"状态表 + 流水表"。CP6 里就是 `Stock`（在库实况）+ `StockTransaction`（在库流水）。把这一对设计好，你就理解了一半的 WMS。

### 1.2 从"出入库业务"推导出两张表：完整过程

我们不看代码，先纯用业务语言推导。假设产品经理给你一句话需求：

> "仓库要能收货入库、发货出库、库内移库、盘点调整；任何时刻都要能查到某个货位某个产品还有多少可用库存；月底要能对账，查清楚这个月每一笔进出。"

**第 1 步：找名词（实体）。** "货位""产品""库存""入库""出库""移库""盘点"。其中"库存"是个**状态**（当前有多少），"入库/出库/移库/盘点"都是**事件**（一次动作）。

**第 2 步：区分状态和事件。**
- 状态 → 一张 **Stock（库存实况）** 表。它回答"现在有多少"。
- 事件 → 一张 **StockTransaction（库存流水）** 表。它回答"发生过什么"。

**第 3 步：给状态表定"唯一定位一行"的键。** "某个货位某个产品的库存"——但同一个产品在同一个货位可能有不同批次（Lot），批次不同要分开算（先进先出、保质期）。所以唯一定位一行库存需要四个东西：**仓库 + 货位 + 产品 + 批次**。这就是 Stock 表的**业务唯一键（UK）**：`(WarehouseCd, LocationCd, ProductCd, LotNo)`。

**第 4 步：给状态表定"要存哪些量"。** 业务问"可用库存"。可用 = 物理在库 − 已被订单引当（锁定）的量。所以三个数量字段：`PhysicalQty`（物理在库）、`AllocatedQty`（引当中）、`AvailableQty`（可用）。

**第 5 步：给流水表定字段。** 每一笔事件都要记：什么类型（入/出/移/调）、什么时候、动了哪个货位哪个产品哪个批次、动了多少、关联的是哪张单据。并且流水**只增不改**——发生了就不许改，否则对账就没有可信的真相源了。

推导到这里，两张表的骨架就出来了。下面看 CP6 里真实的样子，你会发现和上面推导几乎一一对应。

### 1.3 CP6 真实标本：`Stock.cs`

`C:\CP6\CP6.Entity\DomainModels\Wms\Stock.cs`（节选，去掉了部分行业扩展字段）：

```csharp
[Table("T_Stock")]
public class Stock : BaseBizEntity
{
    /// <summary>倉庫CD（業務UK 構成 1/4）</summary>
    [Required, MaxLength(10)]
    public string WarehouseCd { get; set; } = string.Empty;

    /// <summary>ロケーションCD（業務UK 構成 2/4）</summary>
    [Required, MaxLength(30)]
    public string LocationCd { get; set; } = string.Empty;

    /// <summary>製品CD（業務UK 構成 3/4）</summary>
    [Required, MaxLength(20)]
    public string ProductCd { get; set; } = string.Empty;

    /// <summary>ロットNO（業務UK 構成 4/4、ロット管理しない場合は空文字）</summary>
    [Required, MaxLength(30)]
    public string LotNo { get; set; } = string.Empty;

    /// <summary>物理在庫数</summary>
    [Column(TypeName = "decimal(21,8)")]
    public decimal PhysicalQty { get; set; } = 0m;

    /// <summary>引当中数量</summary>
    [Column(TypeName = "decimal(21,8)")]
    public decimal AllocatedQty { get; set; } = 0m;

    /// <summary>利用可能在庫（= PhysicalQty - AllocatedQty）</summary>
    [Column(TypeName = "decimal(21,8)")]
    public decimal AvailableQty { get; set; } = 0m;

    // ... UnitCd / ReceiveDate / ExpiryDate / UnitPrice / RecallFlag / OwnerType / QcStatus 等
}
```

类头上的注释写得很明白（原文是日文，翻译过来）：

> 业务 UK：`(WarehouseCd, LocationCd, ProductCd, LotNo)`。
> 写入口只有 `StockMovementService`。**直接 UPDATE 禁止**。
> `PhysicalQty - AllocatedQty = AvailableQty`（DB 里物化存一份，Service 里每次也重算）。

### 1.4 CP6 真实标本：`StockTransaction.cs`

`C:\CP6\CP6.Entity\DomainModels\Wms\StockTransaction.cs`（节选）：

```csharp
[Table("T_StockTransaction")]
public class StockTransaction : BaseBizEntity
{
    /// <summary>トランザクションNO（業務 UK）</summary>
    [Required, MaxLength(25)]
    public string TxnNo { get; set; } = string.Empty;

    /// <summary>種別（IN/OUT/MOVE/ADJ/RSV/UNRSV）</summary>
    [Required, MaxLength(10)]
    public string TxnType { get; set; } = string.Empty;

    public DateTime TxnDateTime { get; set; } = DateTime.Now;

    [Required, MaxLength(10)] public string WarehouseCd { get; set; } = string.Empty;
    [Required, MaxLength(30)] public string LocationCd { get; set; } = string.Empty;
    [Required, MaxLength(20)] public string ProductCd { get; set; } = string.Empty;
    [Required, MaxLength(30)] public string LotNo { get; set; } = string.Empty;

    /// <summary>数量（IN/RSV は正、OUT/UNRSV は正、ADJ は差分の符号付き）</summary>
    [Column(TypeName = "decimal(21,8)")]
    public decimal Qty { get; set; }

    [MaxLength(25)] public string? RelatedNo { get; set; }   // 関連伝票NO
    [MaxLength(20)] public string? RelatedType { get; set; } // INBOUND/OUTBOUND/STOCKTAKE
    // ...
}
```

类头注释：

> 所有 Stock 变动，都以 **INSERT only** 记录在这里。**UPDATE / DELETE 禁止**。
> 集计报表以这张表为**唯一真实源**。

### 1.5 解析

对照 1.2 的推导，你会看到设计的每一步都落到了字段上：

| 推导结论 | Stock 表 | StockTransaction 表 |
| --- | --- | --- |
| 定位一行的业务键 | `(WarehouseCd, LocationCd, ProductCd, LotNo)` | `TxnNo`（一笔流水一个号） |
| 核心数量 | `PhysicalQty / AllocatedQty / AvailableQty` | `Qty`（带符号的增减量） |
| 只增不改 vs 可覆盖 | 可 UPDATE（但只准 Service 改） | **只 INSERT** |
| 谁负责写 | `StockMovementService`（单一写入口） | 同一个 Service，同一个事务里 |
| 对账真相源 | 状态（快照，会漂移就靠流水重算校验） | **真相源**（不可变日志） |

这里有个非常值钱的设计思想，面试时说出来很加分：

**"当前状态"可以由"全部事件"重算出来。** 理论上你只要有完整的 StockTransaction，就能把某个货位某产品从零开始把 Qty 一笔笔加起来，得到今天的 PhysicalQty。Stock 表只是这个累加结果的**物化缓存（materialized snapshot）**——为了不用每次查库存都扫全部历史。这就是"事件溯源（Event Sourcing）"思想的轻量应用。所以对账 = 拿 Stock 的快照值，和 StockTransaction 重算值比对，不一致就是有 bug。

### 1.6 坑与事故

- **事故一：多个入口直接写 Stock。** 如果不强制"只有 StockMovementService 能改 Stock"，某个新同事图省事在他的控制器里直接 `UPDATE T_Stock SET PhysicalQty = ...`，就绕过了同步写流水的逻辑。结果：库存变了，但流水里没有对应记录，月底对账对不上，谁也查不出这 30 件货去哪了。CP6 用注释 + 代码 review + Service 封装三重手段来守这条线。
- **事故二：把 AvailableQty 当独立可写字段。** AvailableQty 是派生值（= Physical − Allocated）。如果有人单独去改它而不改另外两个，三者就自相矛盾了。CP6 的做法是"DB 物化一份 + Service 每次重算覆盖"，物化是为了查询快，但真相永远以 Physical − Allocated 为准。
- **事故三：流水表允许 UPDATE。** 一旦允许改历史流水，审计和对账就失去了地基。制造业客户（尤其做食品、医药、纸业这些有追溯要求的）会因此过不了审计。CP6 明确"流水 INSERT only"。

### 1.7 面试问答

**Q：设计一个库存系统，你会怎么建表？**
A：核心是一对"状态表 + 流水表"。状态表（Stock）存当前每个"仓库+货位+产品+批次"的物理量、引当量、可用量，业务唯一键就是这四个字段的组合。流水表（StockTransaction）把每一笔进出移调以 INSERT only 记下来，作为对账的唯一真相源。状态可由流水累加重算，所以状态表本质是流水的物化快照。写入必须收口到单一 Service，在一个事务里同时更新状态、追加流水，保证两者永不脱节。

**Q：为什么库存流水要 INSERT only，不能 UPDATE？**
A：因为它是审计和对账的真相源。允许改历史就等于允许篡改账本，制造业（食品/医药/纸业）有法规追溯要求，改历史直接过不了审计。要"冲正"一笔错误流水，做法是再 INSERT 一笔反向流水（红冲），而不是改原记录。

## 2. 实体关系：一对一 / 一对多 / 多对多

### 2.1 概念（类比）

实体关系（ER）就是回答"两类东西之间是怎么对应的"。三种基本关系，用生活比方：

- **一对一（1:1）**：一个人对应一个身份证号。彼此唯一绑定。
- **一对多（1:N）**：一个订单对应多条订单明细行；但一条明细行只属于一个订单。"一头多脚"。
- **多对多（M:N）**：一个学生选多门课，一门课被多个学生选。两边都是"多"。关系型数据库**不能直接表达多对多**，必须引入一张**中间表（关联表 / 桥表）**，把 M:N 拆成两个 1:N。

**ER 图怎么画（面试白板常用记号）：**

```
一对一：  [用户] ──1───1── [用户扩展资料]
一对多：  [订单] ──1───<∞ [订单明细]        （叉号/无穷那头是"多"）
多对多：  [角色] ──1───<∞ [角色菜单] ∞>───1── [菜单]
                         └──── 中间表 ────┘
```

### 2.2 CP6 真实标本

**一对多（最常见）—— 订单主表 : 订单明细。**
CP6 里 WMS 入库单也是这个模式：`T_InboundOrder`（入库单主）: `T_InboundOrderDetail`（入库单明细）。明细行靠 `InboundNo` 挂回主表，一张入库单多条明细。迁移里能看到明细表的唯一键是 `(InboundNo, LineNo)`——单号 + 行号唯一定位一行明细，这是一对多在"多"那头的典型键设计。

**多对多—— 角色 : 菜单（本章的招牌案例）。**
一个角色能看多个菜单，一个菜单能被多个角色拥有。这是标准 M:N，CP6 用中间表 `Sys_RoleMenus` 解决：

```
[Sys_Roles] ──1──< [Sys_RoleMenus] >──1── [Sys_Menus]
   RoleId              RoleId               MenuId
                       MenuId
```

中间表 `Sys_RoleMenus` 的每一行 = "某角色拥有某菜单"这一个事实，核心就是两个外部键 `RoleId` + `MenuId`（CP6 里还加了 `TenantId` 做多租户隔离，见第 11 节）。

**一对一** 在 CP6 里相对少见（一对一常常是"能合成一张表却因为字段太多/访问频率不同而拆开"）。典型场景是把很少访问的大字段（比如某实体的一大段富文本/JSON 配置）拆到副表，主表 1 行对副表 0 或 1 行。

### 2.3 解析：多对多为什么必须要中间表

假设你不用中间表，硬要在 `Sys_Roles` 表里存"这个角色有哪些菜单"。你只有两条歪路：

1. **在角色表加一列 `MenuIds`，存 `"101,102,205,301"` 这种逗号拼接串。** 灾难。你没法用 SQL 高效查"哪些角色拥有菜单 205"（得对字符串做 `LIKE '%205%'`，还会误命中 1205），没法加外键约束，没法保证 205 真实存在。这叫**违反第一范式（1NF）**，见第 3 节。
2. **在角色表加 20 个列 Menu1、Menu2 … Menu20。** 更灾难。角色多一个菜单就要改表结构，且大部分列是 NULL。

正确解法只有一个：**中间表**。`Sys_RoleMenus` 每行只表达一个"角色×菜单"的配对。要查"哪些角色有菜单 205"，一句 `WHERE MenuId = 205` 就行；要给角色加菜单，就 INSERT 一行；要收回，就 DELETE 一行。干净、可索引、可约束。

### 2.4 坑与事故

- **中间表缺唯一约束 → 重复配对。** 中间表 `(RoleId, MenuId)` 必须唯一，否则"角色 A 拥有菜单 205"可能被存两遍。重复本身可能不报错，但会让"这个角色有几个菜单"这类计数翻倍，权限判断出诡异结果。CP6 正是踩过这个坑并修复的——见第 6 节的 `SysRoleMenuUniqueIndex` 迁移，它先删重复再建唯一索引。
- **一对多的"多"那头忘了带主表键。** 明细表如果不存 `InboundNo`，它就成了孤儿，不知道属于哪张单。
- **误把一对多做成多对多。** 如果两边关系其实是 1:N（一条明细只属于一张单），却建了中间表，纯属过度设计，多一次 JOIN。判断依据：问"这条明细行有没有可能同时属于两张入库单？"——不可能，那就是一对多，不要中间表。

### 2.5 面试问答

**Q：多对多在关系型数据库里怎么落地？**
A：关系型数据库不能直接表达多对多，必须引入中间表（桥表），把一个 M:N 拆成两个 1:N。中间表的每一行代表两边一次配对，核心是两张主表的键各存一列。比如 CP6 的角色-菜单是多对多，用中间表 `Sys_RoleMenus`，行里存 `RoleId` 和 `MenuId`，并在这两列（实际是加上 `TenantId` 的三列）上建唯一索引防重复配对。

**Q：一对一什么时候用？**
A：逻辑上能合成一张表，但出于两个理由拆开：一是某些字段很大或很少用（大文本、blob、扩展 JSON），拆到副表让主表更瘦、查询更快；二是访问权限/生命周期不同的字段分开管理。主表 1 行对副表 0/1 行，副表主键通常同时就是外键。

## 3. 范式与反范式

### 3.1 概念（类比）

**范式（Normal Form）** 是一套"把数据拆干净、不要重复存"的规则。核心动机：同一个事实只在一个地方存一份，改的时候只改一处，不会出现"这里改了那里没改"的自相矛盾。

三个最常用的范式，用一句话记：

- **1NF（第一范式）**：每个字段都是**不可再分的单值**。不能往一个格子里塞一个列表（`"101,102,205"`）、不能有重复列组（Menu1..Menu20）。
- **2NF（第二范式）**：在满足 1NF 基础上，**非键字段必须依赖整个主键，不能只依赖主键的一部分**。（只有复合主键才会违反 2NF。）
- **3NF（第三范式）**：在满足 2NF 基础上，**非键字段之间不能有依赖**（不能"字段 A 决定字段 B"，B 应该拆走）。俗称"非键字段只依赖键、依赖全部键、只依赖键本身"（the key, the whole key, nothing but the key）。

### 3.2 用制造业反例逐个讲

**违反 1NF 的反例：** 订单明细表里，一行的 `ProductCds` 字段存 `"P001,P002,P003"`。
问题：想查"卖了多少 P002"要做字符串匹配，无法索引、会误命中、无法约束。
正确：拆成三行明细，每行一个产品。

**违反 2NF 的反例：** 订单明细表主键是复合键 `(OrderNo, ProductCd)`，表里却有一列 `ProductName`。
分析：`ProductName` 只由 `ProductCd` 决定，跟 `OrderNo` 无关——它只依赖主键的**一部分**，这就违反 2NF。
后果：同一个产品出现在 100 张订单的明细里，产品名就存了 100 遍；改一次产品名要扫 100 行。
正确：`ProductName` 拆到产品主表，明细里只留 `ProductCd`，要名字时 JOIN。

**违反 3NF 的反例（本节招牌反例）：** 订单主表 `T_Order` 里，除了 `CustomerCd`（客户编号）之外，还冗余了一列 `CustomerName`（客户名）。
分析：主键是 `OrderNo`。`CustomerName` 不直接依赖 `OrderNo`，而是"`OrderNo` → `CustomerCd` → `CustomerName`"——非键字段 `CustomerName` 依赖了另一个非键字段 `CustomerCd`，这叫**传递依赖**，违反 3NF。
后果：客户改名（"XX 商事"改成"XX 株式会社"），你得去更新历史上所有订单里的 `CustomerName`；漏改一张，这张订单就显示旧名，数据自相矛盾。
正确（3NF）：订单表只存 `CustomerCd`，客户名放在客户主表 `T_BusinessPartner` 里，显示时 JOIN 取当前名。

### 3.3 反范式：什么时候故意"退化"

范式是默认追求，但有两类场景要**故意反范式**（有意冗余）。

#### 场景 A：性能类反范式（报表宽表）

订单列表页要显示客户名，如果每次都 JOIN 客户表，几十万行订单 + 高并发下 JOIN 成本高。做法是把 `CustomerName` 冗余进订单表或专门的**报表宽表**，用写入时同步/定时刷新来换查询时零 JOIN。**这是纯性能取舍**：代价是要维护冗余一致性，收益是查询快。能不做就不做，先靠索引和好查询解决，实在扛不住再上宽表。

#### 场景 B：业务正确性类反范式（快照字段）—— 最重要，必考

**订单明细为什么要冗余"下单时的单价"，而不是关联商品表取现价？**

这不是性能问题，是**业务正确性**问题。

想象场景：客户 6 月 1 日下单，产品 P001 当时单价 100 元，订单明细记下 `UnitPrice = 100`，总价按 100 算，客户也按 100 付了款。到了 6 月 20 日，公司调价，P001 现价变成 120 元。

现在你去看那张 6 月 1 日的订单：

- **如果订单明细不存单价、每次 JOIN 商品表取现价** → 这张历史订单会显示单价 120、总价按 120 重算，**和客户实际支付的金额对不上**。发票、对账、退货全乱套。这是**严重的业务错误**，不是慢一点的问题。
- **如果订单明细冗余了下单时的 `UnitPrice = 100`（快照）** → 这张订单永远显示成交时的真实价格，天塌下来也不变。

所以：**凡是"成交那一刻的事实"，都必须在单据行上做快照，绝不能事后靠关联主表取现值。** 单价、税率、汇率、客户名（成交时的名字，用于打印那张单）、规格描述……都属于快照范畴。

在 CP6 里，你能直接看到这个原则：`Stock` 和 `StockTransaction` 都带了 `UnitPrice`（`decimal(18,4)`）。库存流水记的是**那一笔进出发生时的单价**，用于库存评价和成本核算——如果不冗余、事后取产品主表现价，历史成本就全错了。

> 一句话记牢：**"快照冗余"违反的是范式，但维护的是业务真相。范式让你不自相矛盾，快照让你不背叛历史。两者冲突时，历史事实优先。**

### 3.4 坑与事故

- **该快照的没快照 → 改价穿越历史。** 上面的订单单价场景，是新手最容易犯、后果最严重的设计错误。面试官问"订单表要不要存单价"，答"关联商品表取就行"直接减分。
- **不该冗余的乱冗余 → 一致性地狱。** 反过来，把客户的电话、地址、信用额度这类"当前属性"冗余进每张订单（而它们不是成交快照的一部分），改一次客户信息要扫全部订单同步，漏一处就矛盾。冗余要有明确理由（性能 or 快照），不能随手加。
- **物化派生值不重算 → 漂移。** 前面 Stock 的 `AvailableQty` 就是物化派生值，CP6 用"Service 每次重算覆盖"来防漂移。冗余任何派生值都要配一个"如何保持同步"的机制。

### 3.5 面试问答

**Q：讲讲三大范式。**
A：1NF 要求字段原子、不可再分（不能一格塞列表）；2NF 在 1NF 基础上要求非键字段依赖完整主键、不能只依赖复合主键的一部分；3NF 在 2NF 基础上要求非键字段之间无传递依赖。一句话就是"依赖键、依赖全部键、只依赖键本身"。比如订单表里冗余客户名就违反 3NF，因为客户名传递依赖于客户编号而不是订单号。

**Q：订单明细里的单价，你是存一份还是关联商品表实时取？为什么？**
A：必须在明细行上冗余存一份下单时的单价快照，绝不能实时关联商品表取现价。因为单价是"成交那一刻的事实"，商品事后调价不能改变历史订单的成交金额，否则发票、对账、退货全和客户实付对不上。这是业务正确性问题，不是性能问题——这种"快照冗余"是故意违反范式来维护业务真相。CP6 的库存流水 StockTransaction 就冗余了 UnitPrice，记的是那一笔进出发生时的单价。

**Q：什么时候可以反范式？**
A：两类。一是性能反范式，比如报表宽表把常一起查的字段冗余进来避免 JOIN，代价是维护一致性；二是业务快照反范式，把成交时的单价/税率/汇率固化在单据行上。前者是优化手段、能不做就不做，后者是业务刚需、必须做。

## 4. 主键设计：自增 int vs GUID vs 业务主键

### 4.1 概念（类比）

主键就是每行的"身份证号"，唯一、不空、不变。选主键有三大流派：

| 流派 | 长什么样 | 生活类比 |
| --- | --- | --- |
| **自增整数（identity int/bigint）** | 1, 2, 3, 4 … | 排队叫号，来一个 +1 |
| **GUID（uniqueidentifier）** | `3F2504E0-4F89-41D3-9A0C-0305E82C3301` | 全球唯一的一串乱码，各自随机生成也几乎不撞 |
| **业务主键（自然键）** | `TXN20260715-00042`（单号） | 用业务本身有意义的编号当身份证 |

还有两个正交概念：

- **自然键（natural key）**：用业务里天然存在、有意义的东西当键（身份证号、单号、`(仓库+货位+产品+批次)`）。
- **代理键（surrogate key）**：额外造一个没有业务含义的键（自增 id 或 GUID）当主键，业务键退居"唯一约束"。

### 4.2 三种主键全对比

| 维度 | 自增 int/bigint | GUID | 业务主键（单号） |
| --- | --- | --- | --- |
| 存储大小 | 4/8 字节，小 | 16 字节，大 | 视长度，通常 20–30 字符更大 |
| 生成时机 | 必须**入库后**才知道值（DB 分配） | 入库**前**就能在代码里生成 | 入库前生成（需取号器保证唯一/连号） |
| 是否有序 | 严格递增，聚集索引友好，**几乎不碎片** | 随机 GUID **无序 → 聚集索引碎片严重** | 通常按时间前缀有序 |
| 跨库/分布式合并 | 会撞号（各库都从 1 开始） | **天生全球唯一，合并不撞** | 靠编号规则保证唯一 |
| 可读性/可猜测 | 可读、**可被猜/遍历**（安全风险，`/order/1`→`/order/2`） | 不可猜 | 可读且有业务含义 |
| 关联/外键体积 | 小，JOIN 快 | 大，索引和外键都胖 16 字节 | 更大 |
| 是否会变 | 不变 | 不变 | **有风险**（业务规则一改，单号格式/含义可能要变，见坑） |

### 4.3 CP6 真实标本：全 GUID 主键

CP6 所有实体的主键都是 GUID。看基类 `C:\CP6\CP6.Entity\BaseEntity.cs`：

```csharp
public abstract class BaseEntity
{
    /// <summary>主键，使用 Guid 自动生成</summary>
    [Key]
    [DatabaseGenerated(DatabaseGeneratedOption.Identity)]
    public Guid Id { get; set; }

    [MaxLength(100)] public string? Creator { get; set; }
    public DateTime CreateDate { get; set; } = DateTime.Now;
    [MaxLength(100)] public string? Modifier { get; set; }
    public DateTime? ModifyDate { get; set; }
}
```

所有业务实体（`Stock`、`StockTransaction`、订单、工单……）都继承自 `BaseEntity`（经由 `BaseTenantEntity` → `BaseBizEntity`），所以**全库统一 GUID 代理主键**。

注意一个精妙细节：`[DatabaseGenerated(DatabaseGeneratedOption.Identity)]` 加在 `Guid` 上，意味着这个 GUID 由**数据库端**生成（SQL Server 列默认用 `NEWSEQUENTIALID()`，生成的是**大致有序**的 GUID），而不是客户端 `Guid.NewGuid()` 生成的**完全随机** GUID。这正是为了缓解 4.5 要讲的"GUID 聚集索引碎片"问题——CP6 是知道这个坑并做了处理的。

### 4.4 CP6 为什么全 GUID？理由与代价

**理由（为什么值得）：**

1. **多租户 + 分布式友好。** CP6 是多租户 SaaS，数据可能要在不同环境间迁移、合并、灌种子数据（seed）。GUID 全局唯一，跨租户、跨库拷贝数据永不撞主键。用自增 int，两个环境各自从 1 开始，一合并全撞车。
2. **入库前就能拿到 id。** 代码里 `new Order()` 时 GUID 就已经定了，可以在同一个事务里先把 id 关联到子表、发消息、写日志，不用等 DB `SELECT SCOPE_IDENTITY()` 往返。做复杂对象图（订单 + 明细 + 引当）一次性保存时特别顺。
3. **不可猜测，安全。** URL 里 `/api/order/3F2504E0-...` 没法像 `/api/order/1` 那样被人顺手改成 2 去遍历别人的订单。
4. **统一基类，简化框架。** 全库一个 `BaseEntity` 定义 id，审计、软删、多租户过滤全在基类统一挂，代码极简。

**代价（付出了什么）：**

1. **16 字节，比 int 大 4 倍。** 每个主键、每个外键、每个索引条目都胖。几百万行时索引体积明显更大，内存里能缓存的页更少。
2. **随机 GUID 会让聚集索引碎片化**（见 4.5）——CP6 用数据库端 `NEWSEQUENTIALID()`（有序 GUID）来对冲。
3. **不可读。** 排查问题时 `3F2504E0-...` 不如 `订单 1024` 直观。CP6 靠业务单号（`TxnNo`、`InboundNo`）来补人类可读性——**GUID 做代理主键，业务单号做自然键/唯一索引**，两者分工。

### 4.5 为什么随机 GUID 做聚集索引会碎片（关键点）

这是索引章节的伏笔，先在这讲清楚。SQL Server 的聚集索引会**按主键顺序物理排列数据行**（详见第 7 节）。

- **自增 int**：新行的 key 永远比所有旧 key 大，永远**追加到最后一页**，像往本子最后一页续写，页填得满满的，几乎不碎片。
- **随机 GUID**（`Guid.NewGuid()`）：新行的 key 是随机的，可能要插到中间某一页。那一页如果满了，就得**页分裂（page split）**——一半数据搬到新页。频繁插入 = 频繁页分裂 = 数据物理上支离破碎（碎片），扫描变慢、页填充率低、索引变胖。
- **有序 GUID**（`NEWSEQUENTIALID()`）：SQL Server 生成的 GUID 带递增趋势，新行大致还是往后追加，碎片大幅减轻。**这就是 CP6 用 `DatabaseGenerated(Identity)` 让 DB 端生成 GUID 的原因。**

### 4.6 复合主键 vs 代理键 + 唯一约束

**复合主键**：主键由多列组成。比如中间表 `Sys_RoleMenus` 逻辑上"一个 (RoleId, MenuId) 配对唯一"，天然适合复合键。

但 CP6 的选择是：**统一用 GUID 单列 `Id` 当主键（代理键），把业务上的复合唯一性用"唯一索引"来兜底**。看 `Sys_RoleMenus`：主键是 `Id`（GUID），业务唯一性 `(TenantId, RoleId, MenuId)` 用一个唯一索引保证（第 6 节详讲）。

为什么这么选？

- 代理主键（GUID `Id`）体积固定、外键引用简单（子表只需引一列，不用引三列复合键）、框架统一。
- 业务唯一性交给唯一索引，一样能防重复，还能随业务演进灵活调整（改唯一键组合只是换个索引，不用动主键和所有外键）。

**自然键当主键的风险**：如果直接拿业务单号 `TxnNo` 当主键，一旦业务要求单号格式变更、或发现历史单号有重复要重编，你得改主键——而所有引用它的外键、索引全得跟着改，是场灾难。**代理键 + 自然键唯一约束**把这个风险隔离了：业务键怎么变，都只是换个唯一索引，主键岿然不动。

### 4.7 坑与事故

- **拿业务单号当主键，后来单号规则变了。** 经典事故。制造业单号格式经常随客户要求调整，主键一旦被这么绑死，重构成本极高。用代理键就没这问题。
- **自增 int 在多环境/多租户下合并撞号。** 测试库和生产库各自从 1 增，导出导入一合并主键冲突。CP6 的 GUID 免疫。
- **URL 直接暴露自增 id 被遍历。** `/invoice/1001` 改成 `/invoice/1002` 就看到别人发票，越权。GUID 天然防这一手（当然真正的授权还得靠后端校验，不能只靠 id 不可猜）。
- **完全随机 GUID 不做有序化，聚集索引碎片拖垮写入。** 大表高频插入时页分裂严重。要么用有序 GUID（`NEWSEQUENTIALID()` / 应用层 sequential guid），要么把聚集索引建在别的有序列上、GUID 只做非聚集主键。

### 4.8 面试问答

**Q：主键用自增 int 还是 GUID？**
A：看场景。单库、追求最小体积和最快 JOIN、id 不外露，用自增 int/bigint，聚集索引几乎不碎片。需要分布式/多租户/多环境数据合并、要在入库前拿到 id、不希望 id 可被遍历，用 GUID。GUID 代价是 16 字节偏大、随机 GUID 会让聚集索引碎片化——所以要么用数据库端 NEWSEQUENTIALID 生成有序 GUID，要么别把聚集索引建在随机 GUID 上。CP6 是多租户 SaaS，全库用 GUID，并用 `DatabaseGenerated(Identity)` 让 DB 生成有序 GUID 来对冲碎片。

**Q：自然键和代理键怎么选？**
A：优先代理键（自增或 GUID）当主键，把业务自然键做成唯一索引/约束。因为自然键有业务含义就有变更风险，一旦拿它当主键，业务规则一变就要改主键和所有外键，成本巨大。代理键无业务含义、永不变，把变化隔离在唯一索引上。CP6 就是 GUID 做主键、业务单号（TxnNo/InboundNo）做唯一索引这套组合。

**Q：为什么随机 GUID 做主键性能差？**
A：主键默认是聚集索引，SQL Server 按主键值物理排序存放数据行。随机 GUID 无序，新行经常要插到已满的中间页，触发页分裂，导致碎片、低填充率、索引膨胀、写入变慢。解决办法是用有序 GUID（NEWSEQUENTIALID）让新行趋于追加，或把聚集索引另建在有序列上。

## 5. 数据类型选择

### 5.1 概念（类比）

选数据类型 = 给每个字段配"刚好合身的容器"。容器太小装不下（溢出/截断），太大浪费空间还拖慢索引。选型三原则：**够用就好、语义准确、和索引/性能挂钩**。

### 5.2 SQL Server 常用类型全表

| 类型 | 用途 | 大小 | 关键注意 |
| --- | --- | --- | --- |
| `int` | 一般整数、计数 | 4 字节 | 范围约 ±21 亿 |
| `bigint` | 大计数、雪花 id | 8 字节 | 超过 21 亿用它（如流水自增号） |
| `decimal(p,s)` / `numeric` | **金额、数量**（精确小数） | 5–17 字节 | p=总位数，s=小数位。**绝不用 float 存钱** |
| `float` / `real` | 科学计算、近似值 | 8/4 字节 | 二进制浮点，`0.1+0.2≠0.3`，**禁止用于金额** |
| `nvarchar(N)` | 变长 Unicode 字符串 | 每字符 2 字节 + 2 | 存中日韩必须用 n 开头（Unicode） |
| `varchar(N)` | 变长非 Unicode | 每字符 1 字节 | 只存纯 ASCII（编码、英文）时省一半 |
| `nvarchar(max)` / `varchar(max)` | 超长文本（>4000/8000 字符） | 大对象（LOB） | 存到行外，**不能进索引键**，慢，见 5.5 |
| `char(N)` / `nchar(N)` | 定长字符串 | 固定 N | 长度恒定的编码（如国家码 2 位）才用 |
| `datetime2` | 日期时间 | 6–8 字节 | **首选**，范围大、精度高（到 100ns） |
| `datetime` | 旧日期时间 | 8 字节 | 精度只到 3.33ms、范围小，**新代码别用** |
| `date` / `time` | 只要日期 / 只要时间 | 3 / 5 字节 | 语义更准、更省 |
| `bit` | 布尔（0/1） | 1 位（多个 bit 合并成字节） | is 系列标志位 |
| `uniqueidentifier` | GUID | 16 字节 | CP6 主键类型 |
| `rowversion` / `timestamp` | 乐观锁版本 | 8 字节 | 每次行更新自动 +1，见第 9 节 |

### 5.3 CP6 真实标本

回看 `Stock.cs`，几个精心选型的例子：

```csharp
[Column(TypeName = "decimal(21,8)")]  public decimal PhysicalQty { get; set; }   // 数量：高精度
[Column(TypeName = "decimal(18,4)")]  public decimal? UnitPrice { get; set; }     // 单价：4 位小数
[Required, MaxLength(10)]             public string WarehouseCd { get; set; }      // 编码：短
[Required, MaxLength(30)]             public string LocationCd { get; set; }       // 货位码：稍长
public DateTime? ExpiryDate { get; set; }                                          // 保质期
public bool RecallFlag { get; set; } = false;                                      // 召回标志：bit
```

`BaseEntity` 里：

```csharp
public Guid Id { get; set; }                        // uniqueidentifier
public DateTime CreateDate { get; set; }             // EF 映射 datetime2
[MaxLength(100)] public string? Creator { get; set; }// nvarchar(100)
```

### 5.4 金额到底 `decimal(18,2)` 还是 `(18,4)`？

`decimal(p, s)`：`p` 是总有效数字位数，`s` 是小数位数。`(18,2)` = 最多 18 位数字，其中 2 位小数（能到千亿级、精确到分）。`(18,4)` = 4 位小数。

规则：

- **最终结算金额、发票金额**：通常 `decimal(18,2)`（到"分"/两位小数就够，符合大多数记账口径）。
- **单价、汇率、成本率、中间计算值**：常用 `decimal(18,4)` 甚至更多小数位。原因是**单价会参与乘法**（单价 × 数量），如果单价只留 2 位，`0.015 元/个 × 100000 个` 这种就会因为单价被四舍五入到 0.02 而算错一大截。多留小数位，把舍入误差推迟到最终金额那一步再收敛。

CP6 正是这么分的：`UnitPrice` 用 `decimal(18,4)`（单价要参与运算，多留位），数量 `PhysicalQty` 用 `decimal(21,8)`（纸业按面积/长度/重量算，8 位小数容纳很细的计量）。**这是"单价/数量高精度、最终金额两位"的教科书式选型。**

> 铁律：**钱和数量永远用 `decimal`，永远不用 `float`/`double`。** 浮点是二进制近似，`0.1 + 0.2` 存进去再取出来不等于 `0.3`，做金额累加会一分一分地漂，对账永远对不平。面试被问"金额用什么类型"答 float 直接出局。

### 5.5 `nvarchar(N)` vs `nvarchar(max)` 的性能差异

- **`nvarchar(N)`（N ≤ 4000）**：值存在数据行内（in-row），能作为索引键列、能高效比较排序。
- **`nvarchar(max)`**：当作**大对象（LOB）**，值可能存到行外的专门页里，行内只留一个指针。后果：
  - **不能作为索引键**（只能放进 INCLUDE 覆盖列，见第 7 节）；
  - 读取要额外跳到 LOB 页，慢；
  - 让每行变"重"，同样一页能放的行数变少，扫描更慢。

所以：**能估出上限就用 `nvarchar(N)`，只有确实可能超长（备注、富文本、JSON 配置）才用 `max`。** 别偷懒全上 `nvarchar(max)`。

### 5.6 CP6 `[MaxLength(100)]` 的意义

`Creator` 上的 `[MaxLength(100)]` 不只是个数字，它有三重作用：

1. **建表时映射成 `nvarchar(100)` 而非 `nvarchar(max)`**——让它 in-row、可索引、更快。这是最关键的性能意义。
2. **输入校验**：EF/校验层会拒绝超过 100 字符的值，把"脏数据"挡在入库前。
3. **契约文档**：告诉后来人"这个字段设计上不超过 100 字符"。

看 `Stock` 里 `WarehouseCd [MaxLength(10)]`、`LocationCd [MaxLength(30)]`、`Remark [MaxLength(500)]`——每个长度都是按业务实际估的。**如果全不写 MaxLength，EF 默认会把 string 映射成 `nvarchar(max)`，那这些编码字段就全成了 LOB，既进不了索引、又拖慢查询。** 所以 CP6 里几乎每个 string 字段都带 MaxLength，这是刻意的性能纪律。

### 5.7 坑与事故

- **金额用 float，对账对不平。** 最经典的类型事故。
- **中文字段用 varchar 而非 nvarchar，中文变问号。** varchar 是单字节编码，存中日韩会乱码/丢字。CP6 全用 nvarchar。
- **忘了 MaxLength，string 全成 nvarchar(max)。** 编码字段进不了索引，`WHERE ProductCd = 'P001'` 走不了高效索引，全表扫。
- **datetime 精度只有 3.33ms，高频时间戳撞值。** 用 datetime2。
- **decimal 精度不够被截断。** 单价只留 2 位小数，乘大数量后误差放大。

### 5.8 面试问答

**Q：金额字段用什么类型？decimal(18,2) 还是 (18,4)？**
A：一定用 decimal，绝不用 float（浮点是二进制近似，累加会漂，对账不平）。最终结算/发票金额通常 decimal(18,2) 精确到分；但单价、汇率、成本率这类要参与乘法的中间量用 decimal(18,4) 甚至更多小数位，因为单价先被舍入再乘大数量会放大误差，应该把舍入推迟到最终金额。CP6 的库存单价就是 decimal(18,4)、数量是 decimal(21,8)。

**Q：nvarchar(100) 和 nvarchar(max) 有什么区别？**
A：nvarchar(N)（N≤4000）值存在行内，能当索引键、比较排序快；nvarchar(max) 是大对象，可能存到行外，不能作索引键、读取要跳页、让行变重拖慢扫描。所以能估出长度上限就用定长度的 nvarchar(N)，只有备注、富文本这种确实可能超长的才用 max。CP6 几乎每个 string 都标 [MaxLength]，就是为了避免 EF 默认映射成 nvarchar(max)。

**Q：为什么中文字段要用 nvarchar 不用 varchar？**
A：varchar 单字节、非 Unicode，存中日韩会乱码或丢字；nvarchar 每字符 2 字节、Unicode，能正确存多语言。代价是占用翻倍，但对含中文的字段是必须的。纯 ASCII 编码字段才考虑 varchar 省空间。

## 6. 约束体系：NOT NULL / DEFAULT / UNIQUE / CHECK / FOREIGN KEY

### 6.1 概念（类比）

约束是数据库层面的"保安"，无论数据从哪个入口（应用、脚本、手工 SQL）进来，都要过这道岗。应用层校验会被绕过（有人直接连库跑 SQL），但数据库约束绕不过。五大约束：

| 约束 | 作用 | 类比 |
| --- | --- | --- |
| `NOT NULL` | 这列不许空 | 必填项 |
| `DEFAULT` | 不给值时用默认值 | 表单预填 |
| `UNIQUE` | 这列/组合不许重复 | 一个工位号只能一个人 |
| `CHECK` | 值必须满足条件 | 数量必须 ≥ 0 |
| `FOREIGN KEY` | 引用的值必须在父表存在 | 明细的订单号必须是真订单 |

### 6.2 CP6 真实标本

**NOT NULL + DEFAULT** 来自实体特性。`Stock` 里：

```csharp
[Required, MaxLength(10)] public string WarehouseCd { get; set; } = string.Empty;
//  ↑ Required → NOT NULL          ↑ 默认空串 → 相当于 DEFAULT ''
public decimal PhysicalQty { get; set; } = 0m;   // 默认 0
public bool RecallFlag { get; set; } = false;    // 默认 false
```

`[Required]` 映射成列的 `NOT NULL`；C# 属性初始值 + EF 配置映射成 `DEFAULT`。而 `string? UnitCd`（可空）映射成允许 NULL 的列。

**UNIQUE（业务唯一性兜底）—— 本节招牌案例。** 见 6.3。

### 6.3 唯一索引兜底业务唯一性：`SysRoleMenuUniqueIndex` 精读

先看背景：中间表 `Sys_RoleMenus` 逻辑上"同一租户下，一个角色对一个菜单只能有一条记录"。但早期它只建了个**非唯一**索引 `(TenantId, RoleId)`——只加速查询，不防重复。加上"兜底网/重复跑种子脚本"，库里已经积累了重复行。现在要升级成**唯一**索引来根治。

难点：**如果库里已有重复行，直接建唯一索引会失败**（"违反唯一约束"直接报错，迁移中断）。所以必须**先去重、再建唯一索引**。

真实迁移 `C:\CP6\CP6.Core\Migrations\20260710172302_SysRoleMenuUniqueIndex.cs`：

```csharp
public partial class SysRoleMenuUniqueIndex : Migration
{
    protected override void Up(MigrationBuilder migrationBuilder)
    {
        // ① 先删掉旧的非唯一索引
        migrationBuilder.DropIndex(
            name: "IX_Sys_RoleMenu_Tenant_Role",
            table: "Sys_RoleMenus");

        // ② P0 终审 #3：升唯一索引前先清存量重复 (TenantId,RoleId,MenuId) 行
        //    （原仅非唯一索引，兜底网/重跑种子可能已插重复）
        //    每组保留最小 Id，否则 CreateIndex(unique) 会失败。
        migrationBuilder.Sql(@"
DELETE rm FROM dbo.Sys_RoleMenus rm
WHERE rm.Id > (
    SELECT MIN(x.Id) FROM dbo.Sys_RoleMenus x
    WHERE x.TenantId = rm.TenantId AND x.RoleId = rm.RoleId AND x.MenuId = rm.MenuId
);");

        // ③ 现在数据干净了，建唯一索引
        migrationBuilder.CreateIndex(
            name: "IX_Sys_RoleMenu_Tenant_Role",
            table: "Sys_RoleMenus",
            columns: new[] { "TenantId", "RoleId", "MenuId" },
            unique: true);
    }

    protected override void Down(MigrationBuilder migrationBuilder)
    {
        // 回滚：删唯一索引，还原成旧的非唯一索引（防撞键：降回去不会因唯一性失败）
        migrationBuilder.DropIndex(
            name: "IX_Sys_RoleMenu_Tenant_Role",
            table: "Sys_RoleMenus");
        migrationBuilder.CreateIndex(
            name: "IX_Sys_RoleMenu_Tenant_Role",
            table: "Sys_RoleMenus",
            columns: new[] { "TenantId", "RoleId" });   // 注意：只有两列，非唯一
    }
}
```

**逐段解析：**

- **② 的去重 SQL 是精华。** 它用相关子查询：对每一行 `rm`，找出"同一 `(TenantId, RoleId, MenuId)` 组里最小的 Id"，凡是 Id 比这个最小值大的都删掉。效果 = **每个重复组只保留 Id 最小的那一行**。这是标准的"SQL 去重保留一条"写法，面试可能让你现场写。
- **①→②→③ 顺序不能乱。** 必须先删旧索引（否则名字冲突）、再去重（否则建唯一索引失败）、最后建唯一索引。这个顺序体现了"迁移要考虑存量脏数据"的工程素养。
- **Down() 的对称设计。** 回滚时把唯一索引降回非唯一 `(TenantId, RoleId)`。为什么降回去是安全的？因为**放宽约束（唯一→非唯一）永远不会撞键**，而收紧约束才可能失败。注释里"防撞键"就是这个意思。（同系列的另一个迁移 `SysRoleMenuTenantize` 的 Down 里还有 `DELETE FROM ... WHERE TenantId <> 'A1'` 来清理 Up 时复制出的多租户副本，是更彻底的对称回滚。）

这个迁移是"**唯一索引兜底业务唯一性**"的完整真实案例：应用层可能有 bug 插重复、种子脚本可能重跑，但只要数据库有唯一索引，重复行就**根本插不进来**——这是最后一道、也是最硬的一道防线。

### 6.4 外键的利弊之争 + CP6 实际怎么做的（如实呈现）

**争论双方：**

- **挺外键派**：外键 = 数据库自动保证"引用完整性"。明细的订单号必须指向真实存在的订单，删订单时能级联/阻止。数据永远不会出现"孤儿明细"。省心、可靠。
- **反外键派**：外键在高并发、大数据量、分库分表、频繁批量导入的场景下有成本——每次写入都要检查父表、加锁，影响性能和吞吐；分库后跨库外键根本没法建；灌种子/迁移数据时外键顺序约束很烦。很多互联网大厂规范"禁用物理外键，用应用层保证"。

**CP6 实际怎么做的（我用 Grep 在 `C:\CP6\CP6.Core\Migrations` 里如实查了）：**

CP6 是**混合实践，且明显偏向少用外键**：

- **核心高频表基本不用外键。** WMS 的 `T_Stock`、`T_StockTransaction`、入库单 `T_InboundOrder`/`T_InboundOrderDetail` 这些，迁移里**没有** `AddForeignKey`。它们靠**业务唯一键 + 应用层 Service 保证一致性**（还记得吗，Stock 只准 `StockMovementService` 写）。这符合"高频写、要吞吐、要多租户/可迁移"的诉求。
- **少数模块内部的主从表用了外键。** Grep 统计：真正的 `table.ForeignKey(...)` 调用只出现在约 15 个迁移里（MES、Fin、Pur 等模块的**同模块 header-detail 关系**）。例如 MES 的迁移 `AddMesModule`：

```csharp
// T_QualityInspectionItem 的明细挂回检验主表
table.ForeignKey(
    name: "FK_T_QualityInspectionItem_T_QualityInspection_InspectionNo",
    column: x => x.InspectionNo,
    principalTable: "T_QualityInspection",
    principalColumn: "InspectionNo",
    onDelete: ReferentialAction.Cascade);   // 删主表级联删明细

// 工单-物料、工单-工序也是同样模式，都 onDelete: Cascade
table.ForeignKey(
    name: "FK_T_WorkOrderMaterial_T_WorkOrder_WorkOrderNo",
    column: x => x.WorkOrderNo,
    principalTable: "T_WorkOrder",
    principalColumn: "WorkOrderNo",
    onDelete: ReferentialAction.Cascade);
```

**如实结论：** CP6 **不是"全用外键"也不是"全禁外键"**。它对**同模块内、生命周期强绑定的主从表**（工单→工序/物料、检验→检验项）用外键 + 级联删除，享受数据库自动保证的完整性；对**跨模块、高频、要吞吐和可迁移**的核心表（库存、流水、单据主表）则不建物理外键，靠业务唯一键和应用层 Service 兜底。这种"该硬约束的地方硬约束、该给性能和灵活性让路的地方让路"的取舍，正是成熟项目的样子——面试时能说出这种 nuance 比背"外键好/坏"强得多。

### 6.5 CHECK 约束

`CHECK` 让列值必须满足条件，比如 `PhysicalQty >= 0`（库存不能为负）、`Qty <> 0`（流水量不能为 0）。CP6 里更多把这类业务规则放在 Service 层校验（灵活、能给友好错误信息、能带业务上下文），数据库层则靠 NOT NULL + 唯一索引 + 类型精度守最硬的底线。CHECK 的取舍和外键类似：它是最后防线但不够灵活，团队按场景选择放在哪一层。

### 6.6 坑与事故

- **只靠应用层校验唯一性 → 并发下照样插重复。** 两个请求同时检查"不存在"然后同时插入，应用层的"先查再插"挡不住。**只有数据库唯一索引能真正防住**（第二个 INSERT 会被数据库拒绝）。CP6 的 `SysRoleMenuUniqueIndex` 就是这个道理。
- **建唯一索引前没去重 → 迁移直接失败。** 6.3 的核心教训：存量脏数据会让 `CREATE UNIQUE INDEX` 报错。必须先去重。
- **外键级联删除删过头。** `onDelete: Cascade` 很方便，但删一张工单会连带删掉它所有工序、物料记录——如果业务其实想"软删/保留历史"，级联硬删就把数据删没了。要想清楚级联策略（Cascade / Restrict / SetNull / NoAction）。
- **该有 NOT NULL 的列允许 NULL → 到处判空。** NULL 会污染聚合（`SUM` 忽略 NULL）、让 `= NULL` 永远不成立（要用 `IS NULL`）、逼得代码到处 `?.`。能非空就 NOT NULL + DEFAULT。

### 6.7 面试问答

**Q：业务上"一个角色对一个菜单只能有一条记录"，怎么保证？应用层判断够吗？**
A：应用层"先查不存在再插入"在并发下挡不住——两个请求同时查到不存在、同时插入就重复了。唯一可靠的办法是在数据库建唯一索引/约束，让重复行根本插不进来（第二个 INSERT 被数据库直接拒绝）。CP6 就是在 Sys_RoleMenus 的 (TenantId, RoleId, MenuId) 上建唯一索引。而且如果库里已有重复历史数据，建唯一索引前必须先去重（保留每组最小 Id 的那行），否则建索引会失败。

**Q：你们用外键吗？外键有什么利弊？**
A：外键的好处是数据库自动保证引用完整性，杜绝孤儿数据；坏处是高并发/大数据量/分库场景下有写入检查开销、跨库建不了、批量导入受约束顺序困扰。所以我们混合使用：同模块内生命周期强绑定的主从表（比如工单和它的工序、物料）用外键加级联，享受自动完整性；跨模块的高频核心表（库存、流水、单据）不建物理外键，靠业务唯一键加应用层单一写入口 Service 保证一致性，换取吞吐和可迁移性。

**Q：CHECK 约束和应用层校验放哪个？**
A：两者不冲突，是纵深防御。最硬的底线（非空、唯一、类型精度）放数据库，任何入口都绕不过；带业务上下文、要友好报错、经常变的规则（如状态机流转、复杂业务校验）放 Service 层。简单不变的值域约束（数量≥0）可以两边都放。

## 7. 索引彻底讲透（本章核心）

> 这是全章最重要的一节。制造业系统数据量大、查询密集，索引懂不懂直接决定你能不能把慢查询救活。

### 7.1 概念（类比）：索引是什么

索引就是书末尾的**目录/检索页**。没有索引，要在一本 800 页的书里找"聚集索引"这个词，你只能一页页翻（**全表扫描**）。有了目录，你直接查到"聚集索引……第 412 页"，翻过去（**索引查找**）。

代价：目录本身占纸（索引占存储）；书内容一改，目录也要跟着更新（**写入时要维护索引**）。所以索引加速读、拖慢写，且占空间——不是越多越好。

### 7.2 B+ 树结构（画图）

SQL Server 的索引是 **B+ 树**。它是一棵矮而宽的多层树：**根节点 → 中间节点 → 叶子节点**。数据不在根和中间，只在**叶子**层，叶子之间还用双向链表串起来（方便范围扫描）。

```
                        ┌─────────────────────┐
        根节点 (Root)    │   [ 1..1000 | 1001..2000 | 2001..3000 ]   │
                        └───┬──────────┬──────────┬───┘
              ┌─────────────┘          │          └─────────────┐
              ▼                        ▼                        ▼
     ┌────────────────┐      ┌────────────────┐       ┌────────────────┐
中间 │ [1..300|301..700| │    │ [1001..1300| ...] │     │ [2001..2400| ...] │   ← 中间节点(只存键+指针)
     │  701..1000]      │    └───────┬────────┘       └────────────────┘
     └──┬────┬─────┬────┘            │
        ▼    ▼     ▼                 ▼
   ┌──────┐┌──────┐┌──────┐   ┌──────────┐
叶 │1..300││301.. ││701.. │ ↔ │1001..1300│ ↔ ...   ← 叶子节点(存键 + 数据/行指针)，横向双向链表相连
   └──────┘└──────┘└──────┘   └──────────┘
```

**为什么用 B+ 树而不是二叉树？** 因为磁盘/内存以"页"（SQL Server 8KB）为单位读。B+ 树一个节点就是一页，能放几百个键，所以树非常"矮"——几百万行数据，树高常常只有 3~4 层。**找任何一行，最多读 3~4 个页**，这就是索引为什么快：把"翻几十万页"变成"翻 3~4 页"。

**查找过程**：从根开始，比较 key 落在哪个区间，顺着指针下到中间节点，再下到叶子，命中。像查字典先翻到"S"部再翻到"Sh"再找到"Shen"。

### 7.3 聚集索引 vs 非聚集索引

这是索引最核心的分野，必须彻底搞懂。

**聚集索引（Clustered Index）：**
- 一张表**只能有一个**。
- 它的**叶子节点就是数据行本身**。换句话说，**表的数据就是按聚集索引的键顺序物理排列存放的**。
- 默认情况下，**主键就是聚集索引**（CP6 里主键是 GUID `Id`，所以 GUID 就是聚集键——这就是第 4 节说 GUID 会碎片的原因）。
- 类比：聚集索引 = 字典正文本身，按拼音顺序编排。你按拼音找，找到就是内容，不用再跳。

**非聚集索引（Nonclustered Index）：**
- 一张表**可以有多个**（在不同列上）。
- 它的叶子节点**不是数据行**，而是**索引键 + 一个指回数据行的"书签"**（在有聚集索引的表里，这个书签就是聚集键值）。
- 类比：非聚集索引 = 书末尾的"术语索引页"，写着"聚集索引……见第 412 页"。你查到页码，还得**翻回正文那一页**才看到完整内容——这一步"翻回去"就是下面要讲的 **Key Lookup**。

**一句话记牢：聚集索引的叶子 = 数据；非聚集索引的叶子 = 键 + 指回数据的书签。**

### 7.4 为什么 GUID 主键做聚集索引会碎片（再讲一遍，这次带图）

聚集索引按键顺序物理排数据。

```
自增 int 主键（有序）：新行 key 永远最大 → 永远追加到最后一页
  页1[1..100] 页2[101..200] 页3[201..300] 页4[301...新行往这加] ← 满了就开新页，整整齐齐

随机 GUID 主键（无序）：新行 key 随机 → 可能要塞进中间已满的页
  页1[A3,F1,...满] 要插一个 key=C7 → 页1 已满 → 页分裂!
     页1[A3,C7,...一半]  新页1b[F1,...另一半]  ← 物理上被撕开，碎片产生
```

**页分裂（page split）** 的后果：数据物理顺序被打乱（逻辑相邻的行散落在不连续的页）、页填充率降到 50% 左右（浪费空间、缓存命中差）、写入变慢（每次分裂都是额外 IO）。这就是"随机 GUID 聚集索引碎片"的机制。CP6 用 `NEWSEQUENTIALID()`（有序 GUID）让新行趋于追加，把这个问题压下去。

### 7.5 覆盖索引与 INCLUDE

设想查询：

```sql
SELECT ProductCd, AvailableQty
FROM   T_Stock
WHERE  WarehouseCd = 'WH01' AND LocationCd = 'A-01-01';
```

假设有个非聚集索引在 `(WarehouseCd, LocationCd)` 上。执行时：
1. 用索引快速定位到符合条件的行（Seek）——但索引叶子里只有 `WarehouseCd, LocationCd` + 书签。
2. 查询还要 `ProductCd` 和 `AvailableQty`，索引里没有 → 每命中一行都要拿书签**翻回聚集索引取这两列**（Key Lookup）。命中 1000 行就翻回去 1000 次，很贵。

**覆盖索引（Covering Index）** = 让索引本身就包含查询需要的所有列，这样根本不用翻回数据表（"索引覆盖了整个查询"）。做法是把额外要 SELECT 的列用 **`INCLUDE`** 挂在索引叶子上：

```sql
CREATE NONCLUSTERED INDEX IX_Stock_WhLoc_Covering
ON T_Stock (WarehouseCd, LocationCd)         -- 键列：用于 Seek 和排序
INCLUDE (ProductCd, AvailableQty);           -- 包含列：只挂在叶子，供覆盖，不参与排序
```

现在同样的查询：Seek 定位后，`ProductCd`、`AvailableQty` 就在索引叶子里，**零 Key Lookup**。这就是覆盖索引。

**键列 vs INCLUDE 列的区别：** 键列参与排序、能用于 `WHERE`/`ORDER BY` 的定位，但占 B+ 树各层、有大小限制；INCLUDE 列只存在叶子层、不参与排序、可以放 `nvarchar(max)` 之外的较大列，纯粹为了"顺手带上省得回表"。经验：**放进 WHERE/JOIN/ORDER BY 的列当键列，只出现在 SELECT 里的列放 INCLUDE。**

### 7.6 复合索引最左前缀原则

复合索引 `(A, B, C)` 就像按"省、市、区"三级排序的通讯录。它能高效支持的查询是**从最左列开始、连续的前缀**：

| 查询条件 | 能用上这个索引吗？ | 说明 |
| --- | --- | --- |
| `WHERE A = ?` | ✅ 能 | 用了最左列 |
| `WHERE A = ? AND B = ?` | ✅ 能 | 用了左边两列 |
| `WHERE A = ? AND B = ? AND C = ?` | ✅ 全用上 | 完美 |
| `WHERE A = ? AND C = ?` | ⚠️ 部分 | 只能用 A 定位，C 用不上索引排序 |
| `WHERE B = ?` | ❌ 用不上 | 跳过了最左列 A，索引没法定位 |
| `WHERE C = ?` | ❌ 用不上 | 同上 |

**原理**：通讯录按省→市→区排序，你知道"省"就能翻到那一段；只知道"区"没法用（因为同名的区散落在各省各市，没有整体顺序）。所以**复合索引列的顺序至关重要**，把最常单独查、选择性最高的列放最左。

**CP6 印证**：`Sys_RoleMenus` 的唯一索引是 `(TenantId, RoleId, MenuId)`——`TenantId` 放最左，因为多租户系统里**每一个查询都带 TenantId**（全局过滤器自动加），把它放最左，所有查询都能吃到这个索引。同理 WMS 明细的 `(TenantId, InboundNo, LineNo)`、权限的 `(TenantId, RoleId, ResourceKey, FieldName)`——**清一色 TenantId 最左**，这不是巧合，是多租户索引设计的铁律（见第 11 节）。

### 7.7 索引失效场景全表（背下来）

即使建了索引，下面这些写法会让它**用不上**（退化成扫描）：

| 失效写法 | 例子 | 为什么失效 | 怎么救 |
| --- | --- | --- | --- |
| **列上用函数/运算** | `WHERE YEAR(TxnDateTime) = 2026` | 索引存的是原始值，不是 `YEAR(...)` 的结果 | 改成范围：`WHERE TxnDateTime >= '2026-01-01' AND < '2027-01-01'` |
| **隐式类型转换** | `WHERE ProductCd = 12345`（列是 nvarchar，传了数字） | 数据库把整列转类型再比，等于给列套了函数 | 传对类型：`WHERE ProductCd = N'12345'` |
| **前导通配符 LIKE** | `WHERE ProductCd LIKE '%001'` | 不知道开头，没法用有序索引定位（像查字典不知首字母） | 改成 `LIKE '001%'`（前缀匹配可用索引）；真要后缀搜用全文索引 |
| **OR 连接不同列** | `WHERE A = 1 OR B = 2` | 一条索引没法同时从 A 和 B 两头定位 | 拆成 `UNION`，或对 A、B 各建索引让优化器合并 |
| **`!=` / `NOT IN` / `<>`** | `WHERE Status <> 'DONE'` | 否定条件几乎要扫全部 | 改成正向枚举 `IN ('NEW','DOING')` |
| **对 NULL 的误用** | `WHERE Col = NULL` | `= NULL` 永远为未知，且优化器难用索引 | 用 `IS NULL` |

**最高频的两个（面试必问）：列上套函数、隐式转换。** 记住核心原理一句话：**只要你在 WHERE 里对索引列本身做了加工（函数、运算、类型转换），索引就废了——因为索引里存的是列的原始值，不是加工后的值。** 要让优化器能"直接拿列的原始值去索引里查"。

### 7.8 写放大：索引不是越多越好

每建一个索引，**每次 INSERT/UPDATE/DELETE 都要多维护一份索引**（B+ 树要插入/调整）。一张表建了 8 个索引，插一行就要写 1 份数据 + 8 份索引 = **写放大 9 倍**。所以：

- 索引加速读、**拖慢写**、占存储、增加锁竞争。
- 高频写、低频查的表（比如流水表）索引要克制。
- 定期检查"从没被用过的索引"（SQL Server 有 DMV `sys.dm_db_index_usage_stats` 可查），删掉纯占成本的。

### 7.9 如何决定给哪列建索引

判断口诀：**"高频出现在 WHERE / JOIN / ORDER BY 里，且选择性高"的列，值得建索引。**

- **WHERE 高频列**：经常拿来过滤的列（`WarehouseCd`、`Status`、`TxnDateTime`）。
- **JOIN 列**：两表关联的键（明细的 `InboundNo`）。
- **ORDER BY 列**：经常排序的列（按时间倒序列表），索引有序能省排序。
- **选择性（selectivity）高**：这列的值够"分散"。`性别`（只有男/女，选择性极低）建索引几乎没用——过滤完还剩一半数据，不如扫。`身份证号`（几乎每行不同，选择性极高）建索引极有效。**低选择性的列单独建索引通常没意义**，但可以放在复合索引里当靠后的列，或作为 INCLUDE。

**综合到 CP6**：`StockTransaction` 是高频写的流水表，查询模式主要是"按仓库/产品/时间段对账"，所以合理的索引是复合索引 `(TenantId, WarehouseCd, ProductCd, TxnDateTime)` 之类——TenantId 最左（每查必带）、然后是常用过滤列、时间列靠后支持范围。而 `TxnNo` 单独一个唯一索引（保证单号唯一 + 支持按单号精确查）。

### 7.10 坑与事故

- **给低选择性列（bit 标志、状态）单独建索引，白占成本还不被用。**
- **复合索引列顺序反了，最常用的查询吃不到索引。** 把选择性低/很少单独出现的列放最左，等于废了索引。
- **在 WHERE 里对时间列套 `CONVERT`/`YEAR` 导致索引失效，慢查询。** 改范围条件。
- **索引建太多拖垮写入。** 尤其流水、日志类高频插入表。
- **随机 GUID 聚集索引碎片（第 4/7 节）拖慢一切。**
- **只建了过滤列没覆盖 SELECT 列，海量 Key Lookup。** 用 INCLUDE 做覆盖索引。

### 7.11 面试问答

**Q：聚集索引和非聚集索引的区别？**
A：一张表只能有一个聚集索引，它的叶子节点就是数据行本身，表数据按聚集键物理排序存放（默认主键就是聚集索引）。非聚集索引可以有多个，叶子存的是索引键加一个指回数据行的书签，查到后可能还要拿书签回表取其他列（Key Lookup）。类比就是聚集索引是字典正文按拼音排，非聚集索引是书后的术语索引页要翻回正文。

**Q：什么是覆盖索引？**
A：让索引本身包含查询需要的所有列，这样查询在索引里就能取到全部数据，不用回表（无 Key Lookup），这个索引就"覆盖"了查询。做法是 WHERE/JOIN/ORDER BY 的列做键列，只在 SELECT 里出现的列用 INCLUDE 挂到叶子。它能把有大量回表的慢查询显著加速。

**Q：复合索引 (A,B,C) 的最左前缀原则是什么？WHERE B=? 能用上吗？**
A：复合索引按列顺序逐级排序，只能高效支持从最左列开始的连续前缀，比如 A、A+B、A+B+C 都能用。只查 B=? 用不上，因为跳过了最左列 A，索引整体没法定位。所以复合索引列顺序很关键，要把最常单独查、选择性高的列放最左。CP6 多租户表全把 TenantId 放最左，因为每个查询都带它。

**Q：索引失效有哪些常见场景？**
A：最常见是在索引列上套函数或运算（YEAR(日期)=2026）、隐式类型转换（列是字符串却传数字）——因为索引存的是原始值不是加工后的值。还有前导通配符 LIKE '%x'、OR 连接不同列、否定条件（!=、NOT IN）、= NULL。救法是把加工从列上挪走，比如日期函数改成范围条件、LIKE 改前缀匹配、OR 拆 UNION。

**Q：索引是不是越多越好？**
A：不是。索引加速读但每次写入都要维护所有索引，写放大严重，还占存储、增加锁竞争。高频写的表尤其要克制。应该只给高频出现在 WHERE/JOIN/ORDER BY 且选择性高的列建索引，并定期用 DMV 找出从不被用的索引删掉。

## 8. 执行计划入门

### 8.1 概念（类比）

执行计划 = 数据库拿到你的 SQL 后，"打算怎么执行"的作战地图。同一句 `SELECT`，可以走索引查找（快），也可以全表扫描（慢），优化器根据统计信息选一条它认为最省的路。**看执行计划 = 看优化器到底选了哪条路、哪一步最贵**，是诊断慢查询的头号工具。

### 8.2 在 SSMS 里怎么看

- **估计执行计划**：SSMS 里 `Ctrl+L`（或工具栏 "Display Estimated Execution Plan"）——不真跑，只看计划。
- **实际执行计划**：`Ctrl+M` 开启 "Include Actual Execution Plan"，再运行查询——真跑，能看到估计行数 vs 实际行数的偏差。
- **看逻辑读**：运行前执行 `SET STATISTICS IO ON;`，结果窗口的 "Messages" 标签会打印每张表的 **logical reads（逻辑读页数）**。逻辑读是最诚实的成本指标——它不受缓存/机器快慢影响，直接反映"这句查询摸了多少页"。**优化查询的目标常常就是把逻辑读从几万降到几十。**

### 8.3 关键算子：Seek vs Scan、Key Lookup

看执行计划先认三个最重要的图标/算子：

| 算子 | 含义 | 好还是坏 |
| --- | --- | --- |
| **Index Seek**（索引查找） | 顺着 B+ 树直接定位到目标行 | ✅ 好，说明索引用上了 |
| **Index Scan / Table Scan**（扫描） | 从头到尾扫整个索引/表 | ⚠️ 看情况：小表或要取大部分行时正常；大表精确查却 Scan = 索引没用上，坏 |
| **Key Lookup**（键查找/回表） | 非聚集索引查到后，拿书签翻回聚集索引取缺的列 | ⚠️ 少量可接受，大量出现 = 缺覆盖索引，是优化点 |
| **Nested Loops / Hash Match / Merge Join** | 三种 JOIN 算法 | 小结果集 Nested Loops 正常；大表 JOIN 出现 Hash 也正常 |
| **Sort** | 排序 | 若能靠索引有序省掉最好，大数据量 Sort 很贵 |

**Seek vs Scan 一句话**：Seek 是"翻目录直达"，Scan 是"从头翻到尾"。大表上本该精确命中几行的查询如果显示 Scan，基本就是索引失效或没建对索引。

### 8.4 估计行数偏差

执行计划里每个算子都有 "Estimated Number of Rows"（估计行数）和实际计划里的 "Actual Number of Rows"。**两者差距巨大（比如估计 10 行、实际 100 万行）是危险信号**——说明优化器基于过时的**统计信息**做了错误判断，可能选了糟糕的计划（比如以为结果小选了 Nested Loops，实际巨大导致慢）。救法：`UPDATE STATISTICS` 刷新统计信息，或检查是否有参数嗅探问题。

### 8.5 一条慢查询的完整诊断叙事（CP6 库存查询剧本）

> 场景：运维反馈"库存查询页越来越慢，某仓库查可用库存要转好几秒"。你来诊断。

**第 1 步：拿到那句 SQL。** 从日志/Profiler 抓到实际执行的语句，大致是：

```sql
SELECT ProductCd, LotNo, AvailableQty
FROM   T_Stock
WHERE  TenantId = @tid
  AND  WarehouseCd = 'WH01'
  AND  YEAR(ReceiveDate) = 2026     -- ← 可疑
ORDER BY ReceiveDate;
```

**第 2 步：开 `SET STATISTICS IO ON` + 实际执行计划，跑一遍。** 结果：`T_Stock` 逻辑读 48000 页，执行计划里赫然是 **Index Scan**（不是 Seek），还挂了个 **Sort**。48000 逻辑读 = 它几乎把整张 Stock 表都翻了一遍。

**第 3 步：读计划找病根。** 为什么 Scan 而不是 Seek？盯住 `WHERE` —— `YEAR(ReceiveDate) = 2026` **在索引列上套了 `YEAR()` 函数**（7.7 的头号失效场景）。即使 `ReceiveDate` 上有索引，套了函数就用不上，只能全扫再逐行算 `YEAR`。

**第 4 步：第一刀——去掉列上的函数。** 把 `YEAR(ReceiveDate) = 2026` 改写成范围条件：

```sql
  AND ReceiveDate >= '2026-01-01' AND ReceiveDate < '2027-01-01'
```

再跑：如果有 `(TenantId, WarehouseCd, ReceiveDate)` 的索引，现在能走 **Index Seek** 了，逻辑读掉到几百。

**第 5 步：第二刀——消灭 Key Lookup 做覆盖。** 看计划发现 Seek 之后还有大量 **Key Lookup**（因为索引里没有 `ProductCd`、`LotNo`、`AvailableQty`，每行都回表取）。补一个覆盖索引：

```sql
CREATE NONCLUSTERED INDEX IX_Stock_Tenant_Wh_Recv
ON T_Stock (TenantId, WarehouseCd, ReceiveDate)      -- 键列：过滤 + ORDER BY 有序
INCLUDE (ProductCd, LotNo, AvailableQty);            -- 覆盖 SELECT 列
```

再跑：Key Lookup 消失（索引覆盖了全部列）、`ORDER BY ReceiveDate` 也因索引本身有序省掉了 **Sort**。逻辑读从 48000 → 几十。查询从几秒 → 几毫秒。**诊断结束。**

这个叙事把本章的索引知识串成了实战：**看逻辑读定位成本 → 看 Scan/Seek 判断索引有没有用上 → 找到列上函数导致失效 → 改范围条件恢复 Seek → 加覆盖索引消灭 Key Lookup 和 Sort。** 面试让你"讲一次调优经历"，照这个结构讲就非常专业。

### 8.6 坑与事故

- **只看查询耗时不看逻辑读。** 耗时受缓存和机器负载干扰，第二次跑因为缓存变快会误判"已优化"。逻辑读是稳定的真相。
- **索引加了但查询没改（列上还套着函数），索引照样不被用。** 加索引和改写查询往往要一起做。
- **加覆盖索引 INCLUDE 了一堆大列，索引膨胀、写入变慢。** 覆盖也要节制，只 INCLUDE 真正需要的列。
- **统计信息过时，优化器选错计划。** 大批量数据变动后手动 `UPDATE STATISTICS`。

### 8.7 面试问答

**Q：怎么诊断一条慢查询？**
A：先抓到实际 SQL，开 SET STATISTICS IO ON 和实际执行计划跑一遍。看逻辑读判断成本、看算子是 Index Seek 还是 Scan——大表精确查却 Scan 说明索引没用上。常见病根是 WHERE 里对索引列套了函数或隐式转换导致失效，改成范围/正确类型恢复 Seek；如果 Seek 后有大量 Key Lookup，就加 INCLUDE 覆盖索引消灭回表；如果有昂贵 Sort，让索引有序来省掉。目标是把逻辑读从几万降到几十。

**Q：Key Lookup 是什么？为什么它是优化点？**
A：非聚集索引的叶子只有键和一个指回数据行的书签，如果查询要的列不在索引里，每命中一行就要拿书签回聚集索引取那些列，这一步就是 Key Lookup。命中几行没事，命中成千上万行就是大量随机回表，很贵。解决办法是把缺的列用 INCLUDE 加进索引做成覆盖索引，回表就消失了。

**Q：执行计划里估计行数和实际行数差很多说明什么？**
A：说明统计信息过时或有参数嗅探，优化器基于错误的行数估计选了不合适的计划（比如以为结果小选了 Nested Loops，实际很大就慢）。可以 UPDATE STATISTICS 刷新统计信息，或针对参数嗅探用 OPTION(RECOMPILE) 等手段。

## 9. 事务与隔离级别

### 9.1 概念（类比）：ACID

事务 = 一组要么全成功、要么全失败的操作，像 ATM 转账"扣我的 + 加他的"必须捆绑。四个特性 **ACID**：

| 字母 | 名称 | 含义 | 类比 |
| --- | --- | --- | --- |
| **A** | 原子性 Atomicity | 全做或全不做，中途失败全回滚 | 转账扣款和入账不可只做一半 |
| **C** | 一致性 Consistency | 事务前后数据满足所有约束规则 | 转账前后总额不变 |
| **I** | 隔离性 Isolation | 并发事务互不干扰（按隔离级别程度） | 你转账时别人看不到中间态 |
| **D** | 持久性 Durability | 提交后就算断电也不丢 | 转账成功写进硬盘/日志 |

CP6 里，"更新 Stock + 追加 StockTransaction"就必须在**一个事务**里（原子性）——不能库存改了流水没记，那对账就崩了。

### 9.2 并发三大异常

不加隔离，多个事务并发会读到脏东西。三个经典异常：

| 异常 | 现象 | 例子 |
| --- | --- | --- |
| **脏读 Dirty Read** | 读到别的事务**还没提交**的修改 | 事务 B 把库存改成 50 还没提交，事务 A 就读到 50，结果 B 回滚了，A 拿的是根本不存在的值 |
| **不可重复读 Non-repeatable Read** | 同一事务内两次读**同一行**，值变了 | A 第一次读库存 100，中间 B 提交把它改成 80，A 第二次读成了 80 |
| **幻读 Phantom Read** | 同一事务内两次读**同一范围**，行数变了 | A 统计"WH01 有几条库存"得 10 行，中间 B 插了一行并提交，A 再统计成 11 行，凭空多出一行"幻影" |

### 9.3 四大隔离级别对照表

隔离级别就是"你愿意容忍上面哪些异常，来换多少并发性能"。越严格越安全但并发越低。

| 隔离级别 | 脏读 | 不可重复读 | 幻读 | 说明 |
| --- | --- | --- | --- | --- |
| **Read Uncommitted**（读未提交） | ⚠️ 可能 | ⚠️ 可能 | ⚠️ 可能 | 最松，能读到未提交数据。`WITH (NOLOCK)` 就是这个级别 |
| **Read Committed**（读已提交） | ✅ 避免 | ⚠️ 可能 | ⚠️ 可能 | **SQL Server 默认**。只读已提交数据 |
| **Repeatable Read**（可重复读） | ✅ 避免 | ✅ 避免 | ⚠️ 可能 | 保证同行两次读一致（对读过的行加锁保持） |
| **Serializable**（串行化） | ✅ 避免 | ✅ 避免 | ✅ 避免 | 最严，仿佛事务一个个排队执行，并发最低 |

记忆：从上到下越来越严，每往下一格多挡一种异常。脏读→不可重复读→幻读，依次被 Read Committed、Repeatable Read、Serializable 挡住。

### 9.4 SQL Server 默认 Read Committed + RCSI

**SQL Server 默认隔离级别是 Read Committed。** 它靠**加锁**实现：读一行时如果那行正被别的事务改（持有排他锁），读操作就**等**，直到对方提交/回滚——所以读不到脏数据，但读会被写阻塞。

**RCSI（Read Committed Snapshot Isolation，读已提交快照隔离）** 是 Read Committed 的一个**行版本**变体。开启后（`ALTER DATABASE ... SET READ_COMMITTED_SNAPSHOT ON`），读操作**不再等锁**，而是去读这行**修改前的一个已提交版本快照**（版本存在 tempdb）。效果：

- **读不阻塞写、写不阻塞读**——并发大幅提升，这是它最大的好处。
- 读到的是"事务开始时已提交的版本"，仍然不脏。
- 代价：tempdb 要存行版本、有额外开销。

很多高并发系统（包括不少 .NET 业务系统）会开 RCSI 来消除"读被写堵住"的锁等待。面试能提到 RCSI 是加分项。

### 9.5 锁类型入门

**按"意图"分（兼容矩阵核心）：**

| 锁 | 谁申请 | 含义 |
| --- | --- | --- |
| **共享锁 S（Shared）** | 读操作 | "我在读，别人也能读，但别改" |
| **排他锁 X（Exclusive）** | 写操作（INSERT/UPDATE/DELETE） | "我在改，谁都别碰" |
| **更新锁 U（Update）** | 准备更新前的读 | "我打算改，先占个位防死锁"（S 和 X 之间的过渡，防两个都想升级成 X 而互等） |

**锁兼容矩阵**（✓=兼容可同时持有，✗=冲突要等）：

```
          已持有 S    已持有 U    已持有 X
申请 S      ✓          ✓          ✗
申请 U      ✓          ✗          ✗
申请 X      ✗          ✗          ✗
```

读记：**S 和 S 相容**（大家一起读没问题）；**X 和任何锁都冲突**（写是独占的）；**U 锁像"预约改"**，能和 S 共存（还在读阶段）但两个 U 互斥（不能俩人都预约改同一行）。**更新锁 U 的存在就是为了防死锁**——如果没有 U，两个事务都先加 S 读、再都想升级成 X 写，就会互相等对方的 S 释放 → 死锁。用 U 锁，第二个想改的先卡在 U 上，避免了这个死循环。

**按"粒度"分：** 行锁（Row）→ 页锁（Page，8KB 一页含多行）→ 表锁（Table）。粒度越细并发越好但管理开销越大。

**锁升级（Lock Escalation）：** 当一个事务在一张表上持有太多行锁（SQL Server 默认阈值约 5000 个），系统会把它们**升级成一个表锁**——省内存，但**代价是锁住了整张表**，并发骤降。所以一次性 `UPDATE` 几万行可能触发锁升级，把别人全堵在门外。避免办法：分批小事务处理。

### 9.6 死锁

**死锁 = 两个事务各持有对方想要的锁，互相无限等待。**

```
事务 A：锁了 行1(X)，想要 行2       ┐
事务 B：锁了 行2(X)，想要 行1       ┘  → 互等，谁也不放，死锁
```

**产生的四个条件**（经典操作系统理论，了解即可）：互斥、持有并等待、不可抢占、循环等待。实际记住**"循环等待"**这一条最关键——A 等 B、B 等 A 形成环。

**SQL Server 怎么处理：** 它有个死锁监视器定期检测。一旦发现死锁环，它会**选一个事务当"牺牲品"（deadlock victim）**——通常选回滚代价最小的那个——强制回滚它、报错 `1205`，让另一个事务得以继续。被选中的事务在应用层会收到死锁异常，**应用应该捕获后重试**。

**怎么避免死锁（面试高频，记住这条）：** **让所有事务按相同的顺序访问资源。** 上面的例子，如果规定"所有人都先锁行1、再锁行2"，就不会出现 A 锁 1 等 2、B 锁 2 等 1 的环了——B 也会先去锁行1，发现被 A 占了就乖乖等，A 拿完 1 和 2 提交后 B 再上，无死锁。其他手段：缩短事务、降低隔离级别、加合适索引减少锁范围、用 RCSI 让读不加锁。

### 9.7 CP6 真实标本：乐观锁 RowVersion

我用 Grep 在 `C:\CP6\CP6.Entity` 里查了"RowVersion / Timestamp"，CP6 **广泛使用乐观锁**。基类 `BaseBizEntity`：

```csharp
public abstract class BaseBizEntity : BaseTenantEntity
{
    public bool IsDeleted { get; set; } = false;

    /// <summary>
    /// 乐观锁版本号（SQL Server ROWVERSION / timestamp）
    /// EF Core 会自动在 UPDATE 的 WHERE 里附加此列，保证并发安全
    /// 发生冲突时抛 DbUpdateConcurrencyException -> API 层返回 409
    /// </summary>
    [Timestamp]
    public byte[]? RowVersion { get; set; }
}
```

因为所有业务实体都继承 `BaseBizEntity`，所以**全库业务表都自带 `RowVersion` 乐观锁列**（Fin 的各种单据、Wf 工作流实例、Space 站点等也都显式带了 `[Timestamp] RowVersion`）。下一节详讲它怎么防超卖。

### 9.8 坑与事故

- **长事务持锁不放，把别人全堵住。** 事务里夹了远程调用、发邮件、等用户输入 → 锁一直握着，并发雪崩。事务要短，只包住必须原子的 DB 操作。
- **不同代码路径以不同顺序访问同几张表 → 死锁。** 统一访问顺序能根治大量死锁。
- **一次性 UPDATE 几万行触发锁升级，锁了整表。** 分批。
- **滥用 `WITH (NOLOCK)` 想提速，读到脏数据/读到一半的行。** NOLOCK = Read Uncommitted，报表能容忍时可用，涉及金额/库存决策绝不能用。
- **应用层不捕获死锁重试，1205 直接抛给用户。** 死锁牺牲品要有重试逻辑。

### 9.9 面试问答

**Q：讲讲 ACID。**
A：原子性——事务内操作要么全做要么全不做，失败回滚；一致性——事务前后数据满足所有约束；隔离性——并发事务互不干扰，程度由隔离级别决定；持久性——提交后即便断电也不丢。比如库存更新和流水追加必须在一个事务里满足原子性，否则对账会崩。

**Q：脏读、不可重复读、幻读的区别？**
A：脏读是读到别人未提交的修改（对方可能回滚）；不可重复读是同一事务内两次读同一行值变了（别人改了并提交）；幻读是同一事务内两次读同一范围行数变了（别人插/删了行）。Read Committed 挡脏读，Repeatable Read 再挡不可重复读，Serializable 再挡幻读。

**Q：SQL Server 默认隔离级别？RCSI 是什么？**
A：默认 Read Committed，靠加锁实现，读会被未提交的写阻塞。RCSI 是它的行版本变体，开启后读操作去读这行修改前的已提交快照而不加锁，实现读不阻塞写、写不阻塞读，大幅提升并发，代价是 tempdb 存版本的开销。

**Q：什么是死锁？SQL Server 怎么处理？怎么避免？**
A：死锁是两个事务各持有对方想要的锁形成循环等待，谁都不放。SQL Server 有死锁监视器检测到后选一个回滚代价最小的事务当牺牲品强制回滚（报 1205），另一个继续，应用层应捕获后重试。避免的首要办法是让所有事务按相同顺序访问资源，打破循环等待；其次缩短事务、加索引减小锁范围、必要时用 RCSI。

**Q：更新锁 U 有什么用？**
A：它是共享锁和排他锁之间的过渡锁，用于"打算更新前先读"的场景。如果没有它，两个事务都先加共享锁读、再都想升级成排他锁写，就会互等对方的共享锁释放而死锁。更新锁互斥（两个 U 不能同时持有），第二个想改的先卡在 U 上，从而避免了这种死锁。

## 10. 并发实战：库存扣减防超卖三方案

> 这是制造业/电商面试**必问**的场景题。库存 100 件，同时来 3 个订单各扣 60 件，怎么保证不会都扣成功变成 -80？

### 10.1 问题本质

超卖的根源是"**先查后改**"之间有窗口：

```
事务A: 读库存=100 → 判断够扣60 → 扣成 40
事务B:      读库存=100(还没看到A的扣减) → 判断够扣60 → 扣成 40   ← 都以为够，都扣了，实际卖了120
```

两个事务都读到 100、都判断"够"、都扣。防超卖 = 消灭这个窗口。三种主流方案：

### 10.2 方案一：乐观锁（RowVersion / 版本号）

**思想**：不提前加锁，改的时候带上"我读到的版本号"，**提交时检查版本有没有被别人改过**。改过就说明有并发冲突，本次失败、重试。乐观 = 假设冲突很少，冲突了再处理。

**CP6 就是这套。** `BaseBizEntity` 的 `[Timestamp] RowVersion`，EF Core 自动在 UPDATE 时把它加进 WHERE：

```sql
-- EF Core 生成的 UPDATE（简化）：
UPDATE T_Stock
SET    AvailableQty = 40, RowVersion = <新值自动生成>
WHERE  Id = @id
  AND  RowVersion = @我读取时的RowVersion;   -- ← 关键：版本没变才更新

-- 如果受影响行数 = 0，说明 RowVersion 已被别人改过（并发冲突）
-- EF Core 抛 DbUpdateConcurrencyException → CP6 在 API 层转成 HTTP 409
```

流程：A 和 B 都读到库存（RowVersion = v1）。A 先提交，UPDATE 成功，RowVersion 变成 v2。B 再提交时 `WHERE RowVersion = v1` **匹配不到任何行**（现在是 v2 了），受影响 0 行 → 抛并发异常 → B 收到 409 → **应用捕获后重新读最新库存再试一次**。这样 B 第二次读到的是 A 扣完的 40，发现不够扣 60，正确地拒绝。

- **优点**：不加锁，读写并发高；适合**冲突较少**的场景（大部分时候没人跟你抢同一行）。
- **缺点**：冲突多时不停重试，浪费；需要应用层写重试逻辑。
- **适用**：CP6 这种业务系统的通用更新（改单据、改配置），冲突不频繁。

### 10.3 方案二：原子扣减（UPDATE ... WHERE qty >= n + 判断受影响行数）

**思想**：不先查后改，而是**把"检查够不够"和"扣减"合并成一条原子 UPDATE**，靠数据库行锁天然串行化，最后看**受影响行数**判断成没成。

```sql
UPDATE T_Stock
SET    AvailableQty = AvailableQty - @n
WHERE  Id = @id
  AND  AvailableQty >= @n;         -- ← 够扣才扣，条件和扣减在同一句里

-- @@ROWCOUNT = 1 → 扣成功
-- @@ROWCOUNT = 0 → 库存不足，扣失败（没有任何行被改，绝不会扣成负数）
```

这条 UPDATE 是原子的：数据库执行它时对这行加排他锁，A 和 B 的 UPDATE 被**串行化**——A 先执行把 100 扣成 40；B 执行时 `WHERE AvailableQty >= 60` 用当前值 40 判断，40 < 60 不满足，**0 行受影响**，B 得知库存不足。**永远不会超卖，也永远不会变负数**（条件保证了）。

- **优点**：一条 SQL 搞定，无需先查、无需版本号、无需显式事务包裹，性能好且绝对安全。**这是库存扣减最推荐、最干净的方案。**
- **缺点**：只适合"单行、条件明确"的扣减；复杂逻辑（要同时改多行、跨表联动）就不够用。
- **适用**：单点库存扣减的首选。

### 10.4 方案三：悲观锁（UPDLOCK / SELECT ... FOR UPDATE 语义）

**思想**：假设冲突很多，**读的时候就直接把行锁住**，别人想动这行得排队等我。悲观 = 假设一定会冲突，先下手锁。

SQL Server 里用锁提示：

```sql
BEGIN TRAN;

-- 读的时候就加更新锁(U) + 持有到事务结束(HOLDLOCK)，别的事务想改这行必须等
SELECT AvailableQty
FROM   T_Stock WITH (UPDLOCK, HOLDLOCK)
WHERE  Id = @id;

-- 应用层判断够不够（此时这行已被我锁定，别人改不了）
IF @avail >= @n
    UPDATE T_Stock SET AvailableQty = AvailableQty - @n WHERE Id = @id;

COMMIT;   -- 提交后才释放锁
```

A 先 `SELECT ... UPDLOCK` 锁住行，B 的 `SELECT ... UPDLOCK` 只能**等** A 提交释放锁。A 扣完 40 提交，B 才拿到锁，读到 40，判断不够，拒绝。串行执行，不会超卖。

- **优点**：逻辑直观（先锁再从容判断和改，中间可以有复杂业务逻辑）；冲突多时不用反复重试。
- **缺点**：**加锁阻塞并发**，锁的持有时间 = 整个事务时间，事务里别干慢活否则堵死一片；用不好会死锁（记得第 9 节：按相同顺序访问资源）。
- **适用**：冲突频繁、扣减逻辑复杂、且能接受一定串行化的场景。

### 10.5 三方案对比表

| 维度 | 乐观锁 RowVersion | 原子扣减 UPDATE WHERE | 悲观锁 UPDLOCK |
| --- | --- | --- | --- |
| 何时防冲突 | 提交时查版本 | 扣减语句自身条件 | 读取时就加锁 |
| 是否加锁 | 不预先加锁 | 靠单句行锁（极短） | 显式加锁持有到提交 |
| 并发性能 | 高（冲突少时） | 高 | 低（阻塞） |
| 冲突多时 | 频繁重试，浪费 | 直接返回失败，无浪费 | 排队等待 |
| 需要重试逻辑 | 是 | 否（一句成败立判） | 否 |
| 能否包裹复杂多步逻辑 | 能（整事务） | 不太适合（就一句） | 能（锁住后从容处理） |
| CP6 用哪个 | ✅ 通用更新用这个（RowVersion） | 推荐用于纯库存扣减 | 复杂/高冲突时备选 |
| 一句话 | 假设不冲突、冲突了重试 | 检查与扣减合一，最干净 | 假设会冲突、先锁为敬 |

### 10.6 面试怎么答（组合拳）

面试官问"库存扣减防超卖"，**最佳答案是分层给方案，并说明取舍**：

> "首选**原子扣减** `UPDATE ... SET qty = qty - n WHERE id = @id AND qty >= n`，靠数据库行锁串行化 + 检查受影响行数，一条 SQL 既判断又扣减，绝不超卖也不会为负，性能最好。如果扣减伴随复杂业务逻辑（要联动多表、走审批），单句不够，就用**乐观锁**：带 RowVersion 更新，冲突时抛并发异常、应用层重读重试——CP6 全库业务表基类就带 `[Timestamp] RowVersion`，EF Core 自动在 UPDATE 的 WHERE 里附加版本列，冲突转 HTTP 409。如果冲突极其频繁、重试代价太高，才上**悲观锁** UPDLOCK 提前锁行排队，但要接受它阻塞并发、且必须按统一顺序访问资源防死锁、事务里绝不能夹慢操作。"

这个回答展示了：知道三种方案、知道各自适用边界、知道 CP6 真实实现、知道死锁风险——一次性把深度打满。

### 10.7 坑与事故

- **只在应用层"先查库存够不够，再扣"，不加任何并发控制 → 必然超卖。** 这是最常见的错误答案。
- **乐观锁不写重试，冲突直接失败给用户。** 用户看到"操作失败"其实只是撞车了，该自动重试。
- **悲观锁事务里夹了 HTTP 调用/发消息，锁握着几秒，并发全堵。**
- **原子扣减写成 `SET qty = @查出来的值 - n`** 而不是 `SET qty = qty - n`——用查出来的旧值就又回到"先查后改"的窗口了，必须用 `qty = qty - n` 让数据库基于当前值算。

## 11. 多租户数据架构

### 11.1 概念（类比）

多租户（Multi-tenant）= 一套系统服务多个互相隔离的客户（租户）。像一栋公寓楼住很多户人家，关键是**户与户之间数据不能串门**。三种隔离方案，从"共享"到"独立"：

| 方案 | 类比 | 隔离强度 | 成本 |
| --- | --- | --- | --- |
| **单库行级（共享库共享表）** | 大通铺，每人东西贴 `TenantId` 标签区分 | 弱（靠代码保证） | 最低 |
| **Schema 隔离（共享库不同 Schema）** | 一栋楼每户一个独立房间（同一栋楼/同一个库，不同 schema/表前缀） | 中 | 中 |
| **分库（每租户一个库）** | 每户一栋独栋别墅（独立数据库） | 强（物理隔离） | 最高 |

### 11.2 三方案对比表

| 维度 | 单库行级（CP6） | Schema 隔离 | 分库 |
| --- | --- | --- | --- |
| 数据隔离 | 逻辑隔离（每行带 TenantId） | 中等（同库不同 schema） | 物理隔离（不同库） |
| 隔离可靠性 | **靠代码**（全局过滤器不能漏） | 较可靠 | 最可靠 |
| 成本/资源 | 最省（一套库一套表） | 中 | 最贵（N 个库要 N 份运维/备份） |
| 扩展到很多租户 | 轻松（加行而已） | schema 多了难管 | 租户多了库爆炸 |
| 跨租户统计/运营 | 容易（一句 SQL 带聚合） | 较难 | 很难（要跨库汇总） |
| 单租户定制/独立备份恢复 | 难（混在一起） | 中 | 容易（独立库单独搞） |
| 一个租户的大查询影响别人 | 会（共享资源） | 会 | 不会（物理隔离） |
| 迁移某租户到独立环境 | 要按 TenantId 抽数据 | 中 | 直接搬库 |

### 11.3 CP6 选型：单库行级隔离

CP6 用**单库行级**。证据在基类 `BaseTenantEntity`：

```csharp
public abstract class BaseTenantEntity : BaseEntity
{
    /// <summary>租户 Id（行级隔离硬墙；写入时由 SaveChanges 自动盖当前租户，查询时全局过滤）。</summary>
    public Guid TenantId { get; set; }
}
```

所有需要隔离的业务实体（`Stock`、`StockTransaction`、订单、`Sys_RoleMenus`……经由 `BaseBizEntity` 继承）都带 `TenantId`。CP6 的做法是：

- **写入时自动盖章**：`SaveChanges` 拦截，给新行自动填当前登录用户的 `TenantId`，开发者不用手写。
- **查询时全局过滤**：EF Core 全局查询过滤器（Global Query Filter）自动给每个查询加 `WHERE TenantId = @当前租户`，开发者写 `context.Stocks.Where(...)` 时**根本看不到 TenantId 条件，但它自动生效**——这是隔离的命门：**只要过滤器不漏，就不会串租户**。

**CP6 为什么选单库行级？**

1. **成本最低**：一套库、一套表、一份运维备份，服务成百上千租户。SaaS 起步阶段这是压倒性优势。
2. **跨租户运营容易**：平台方要统计"所有租户共用了多少库存记录""哪个租户最活跃"，一句带聚合的 SQL 就行，不用跨库汇总。
3. **升级/迁移一次搞定**：一次数据库迁移（migration）作用于所有租户，不用对 N 个库分别跑。
4. **代价可控**：隔离靠"全局过滤器 + 写入盖章"两道自动机制，只要框架层守住、加上唯一索引都带 TenantId，就能把风险压到很低。

代价是：隔离是"逻辑"的（同一张表里混着各租户的行），一旦全局过滤器有个查询漏了，就可能串租户——所以 CP6 把它做成**基类 + 框架自动机制**，不让业务代码有机会漏。

### 11.4 TenantId 要不要进索引？（关键设计题）

**要，而且通常放复合索引/唯一索引的最左列。** 回看第 6、7 节的真实证据，CP6 所有多租户唯一索引都是 **TenantId 打头**：

- `Sys_RoleMenus`：`(TenantId, RoleId, MenuId)`
- 用户角色：`(TenantId, UserId, RoleId)`
- 字段权限：`(TenantId, RoleId, ResourceKey, FieldName)`
- 入库明细：`(TenantId, InboundNo, LineNo)`

**为什么 TenantId 必须进索引、还得放最左？**

1. **每个查询都带 TenantId。** 全局过滤器给**所有**查询自动加了 `WHERE TenantId = @tid`。既然每次都过滤它，按最左前缀原则（7.6 节），把它放索引最左列，所有查询都能吃到这个索引先按租户"切一刀"，把搜索范围从"全部租户的行"缩到"当前租户的行"。
2. **保证业务唯一性是"租户内唯一"而非全局唯一。** `(RoleId, MenuId)` 在不同租户间可以重复（租户 A 和租户 B 各自有 RoleId=1 的角色），只有**加上 TenantId 才是正确的唯一范围**。所以 TenantId 不仅是为了查询快，更是**唯一约束正确性的一部分**——少了它，唯一索引会错误地跨租户禁止重复。
3. **防止租户间数据热点互相干扰**：按租户切分后，一个租户的数据在索引里是连续的一段，扫描更局部。

所以在多租户单库架构里，**TenantId 进索引最左列几乎是无脑正确的默认**。

### 11.5 坑与事故

- **全局查询过滤器被某个查询绕过（比如用了 `IgnoreQueryFilters()` 或原生 SQL 没带 TenantId）→ 串租户，看到别家数据。** 这是单库行级最致命的事故。必须靠基类统一 + code review + 测试守住。CP6 把过滤和盖章放框架层就是为这个。
- **唯一索引忘了带 TenantId → 跨租户误判重复。** 租户 B 想建 RoleId=1，结果因为租户 A 已有 RoleId=1 被唯一索引拦下，报"重复"——其实是索引漏了 TenantId。CP6 的迁移正是把索引升级成带 TenantId 的组合。
- **TenantId 没进索引 → 每个查询先全表再过滤租户，慢。**
- **删租户时数据清理不干净**（行级混在一起，要精确按 TenantId 删，漏删/误删风险）。

### 11.6 面试问答

**Q：多租户数据隔离有哪几种方案？怎么选？**
A：三种。单库行级（每行带 TenantId，共享库共享表，靠代码过滤隔离，成本最低、跨租户统计和升级最方便，但隔离是逻辑的、过滤器不能漏）；Schema 隔离（同库不同 schema，居中）；分库（每租户独立库，物理隔离最强、单租户备份定制容易，但成本和运维最重、跨租户统计难）。SaaS 起步和中小规模通常选单库行级性价比最高，超大客户或强合规要求可给独立库。CP6 用单库行级，基类 BaseTenantEntity 带 TenantId，靠 EF Core 全局查询过滤器自动加 WHERE TenantId 和写入自动盖章两道机制隔离。

**Q：TenantId 要不要建索引？放哪？**
A：要，通常放复合/唯一索引的最左列。因为多租户下每个查询都被全局过滤器自动加了 TenantId 条件，按最左前缀原则放最左所有查询都能用上、先按租户缩小范围；而且业务唯一性是"租户内唯一"，唯一索引必须带 TenantId 才正确，否则会跨租户误判重复。CP6 所有多租户唯一索引都是 TenantId 打头，比如 (TenantId, RoleId, MenuId)。

## 12. 大表治理入门

### 12.1 概念（类比）

有些表会无限膨胀——尤其**日志类、流水类、审计类**表，只进不出，几个月就上千万行、几个 GB。大表的麻烦：查询变慢、索引变胖、备份变久、DELETE 清理会长时间锁表。治理三板斧：**监控告警 → 归档 → 分区**。

### 12.2 CP6 真实标本：审计日志容量监控脚本

CP6 有张 `Sys_FieldAuditLogs`（字段级审计日志——记录谁在什么时候把哪个字段从什么值改成什么值），这种表天生疯长。CP6 上线前给它配了一个**容量监控告警**计划任务。真实脚本 `C:\CP6\scripts\audit-log-monitor.ps1`：

```powershell
# Sys_FieldAuditLog 容量监控(M-MES 终审 Important#1: 上线前至少容量告警)
# 计划任务 CP6-AuditLog-Monitor 每 4h 运行;日志 C:\CP6Backups\audit-log-monitor.log
# 阈值超限只告警不删数据——retention/归档策略本体待用户裁决
$ErrorActionPreference = "Stop"
$logFile = "C:\CP6Backups\audit-log-monitor.log"
$rowWarn = 1000000   # 100万行告警
$mbWarn  = 500       # 500MB 告警

try {
    $pw = (Get-Content "C:\CP6\.env" | Where-Object { $_ -match "^MSSQL_SA_PASSWORD=" }) -replace "^MSSQL_SA_PASSWORD=", ""
    # 关键 SQL：从系统表算出这张表的行数和物理大小(MB)
    $q = "SET NOCOUNT ON; SELECT p.rows, CAST(SUM(a.total_pages)*8/1024.0 AS DECIMAL(12,1)) AS mb
          FROM sys.tables t
          JOIN sys.partitions p ON t.object_id=p.object_id AND p.index_id IN (0,1)
          JOIN sys.allocation_units a ON p.partition_id=a.container_id
          WHERE t.name='Sys_FieldAuditLogs' GROUP BY p.rows;"
    $out = wsl -e docker exec cp6-db /opt/mssql-tools18/bin/sqlcmd -S localhost -U sa -P "$pw" -C -d CP6DB -h -1 -Q "$q" ...
    $rows = [long]$parts[0]; $mb = [decimal]$parts[1]

    $level = "OK"
    if ($rows -gt $rowWarn -or $mb -gt $mbWarn) { $level = "WARN" }   # 超任一阈值就告警

    $line = "{0} [{1}] Sys_FieldAuditLogs rows={2} size={3}MB ..." -f (Get-Date ...), $level, $rows, $mb ...
    Add-Content -Path $logFile -Value $line
    if ($level -eq "WARN") {
        Add-Content -Path $logFile -Value "  !! 超阈值: 需执行归档/purge 裁决..."
    }
} catch {
    Add-Content -Path $logFile -Value ("{0} [ERROR] {1}" -f (Get-Date ...), $_.Exception.Message)
}
```

**逐段解析：**

- **阈值**：100 万行 或 500 MB，任一超限就 `WARN`。这两个数字是"该考虑归档了"的预警线，不是硬上限。
- **怎么量表大小**：核心那句 SQL 查系统视图 `sys.tables` / `sys.partitions` / `sys.allocation_units`——`p.rows` 是行数，`SUM(a.total_pages) * 8 / 1024` 把"占用的 8KB 页数"换算成 MB。**这是标准的"查某张表占多大空间"SQL，值得记住。** `index_id IN (0,1)` 表示只算堆或聚集索引（数据本体），不重复算非聚集索引。
- **只告警不删数据**：注释写得很清楚——"阈值超限只告警不删数据，retention/归档策略本体待用户裁决"。这体现了一个重要工程原则：**自动删业务数据是高危操作，监控可以自动化，但"删/归档"的动作要人来拍板**，绝不让脚本自己偷偷删审计日志（审计日志尤其敏感，合规要求可能要保留数年）。
- **每 4 小时跑一次**（Windows 计划任务 `CP6-AuditLog-Monitor`），结果追加进日志文件。这是最朴素但有效的"大表健康巡检"。

### 12.3 归档策略

当监控告警"表太大了"，怎么处理？**归档（archiving）**：把老数据从热表搬到冷存储。

- **按时间归档**：审计/流水表通常只有近 3~6 个月的数据被高频查询，更老的可以搬走。做法：把 N 个月前的数据 `INSERT` 到归档表（`Sys_FieldAuditLogs_Archive`，甚至另一个库/廉价存储），再从主表 `DELETE`。
- **分批删除**：一次 `DELETE` 几百万行会长时间锁表 + 撑爆事务日志。要**分批**（每次删 5000~10000 行，循环，中间提交），避免锁升级（第 9 节）和日志暴涨。
- **保留期（retention）要业务/合规拍板**：审计日志可能法规要求保留 5~7 年，不能随便删——所以 CP6 脚本"只告警、归档动作待裁决"是对的。

### 12.4 分区表概念（了解即可）

**分区表（Partitioned Table）**：把一张逻辑大表，按某列（通常是日期）**物理切成多个分区**，比如按月一个分区。对外还是一张表，但底层数据分块存放。

好处：

- **查询裁剪（partition elimination）**：查"2026 年 7 月的流水"，优化器只扫 7 月那个分区，不碰其他月份——大幅减少扫描量。
- **按分区维护**：删除一整个月的老数据可以用"**分区切换/truncate 分区**"瞬间完成，不用逐行 DELETE（秒级 vs 小时级）。归档也可以整分区搬走。
- **索引维护更局部**。

代价：设计和维护更复杂（要建分区函数、分区方案，选对分区键），中小表不值得。**面试知道"大表可以按时间分区、查询能裁剪、按分区归档很快"这个概念即可**，具体实现是 DBA 深水区。

### 12.5 坑与事故

- **审计/日志表没人管，涨到几千万行才发现，查询和备份全被拖垮。** CP6 用监控告警提前预警就是防这个。
- **一次性 DELETE 几百万行清理，锁表 + 事务日志爆满 + 阻塞业务。** 必须分批。
- **脚本自动删审计日志，事后要查合规/追责时数据没了。** 删要人拍板，尤其审计类。
- **分区键选错**（比如选了个查询根本不带的列），享受不到分区裁剪，白搭复杂度。

### 12.6 面试问答

**Q：一张日志/审计表涨到上千万行、越来越慢，你怎么治理？**
A：三步。先监控告警——用查 sys.partitions/sys.allocation_units 的 SQL 定期统计行数和体积，超阈值（比如 100 万行/500MB）就预警，CP6 就有个每 4 小时跑的容量监控脚本。再归档——把超过保留期的老数据分批搬到归档表或冷库再从主表删，分批是为了避免一次删太多锁表和撑爆日志；保留期要按业务合规拍板，审计日志尤其不能乱删。数据量特别大时上分区表，按时间分区，查询能自动裁剪只扫相关分区，归档可以整分区快速切换。

**Q：为什么删大量数据要分批？**
A：一次 DELETE 几百万行会长时间持有大量锁并触发锁升级锁住整表、阻塞业务，还会让事务日志暴涨甚至撑满磁盘。分批每次删几千行、循环并中间提交，能把锁范围和日志增量控制在小范围，不影响在线业务。

## 章末：面试题 20 问（详细答案）

**1. 什么是关系型数据库？和非关系型的区别？**
关系型数据库把数据组织成二维表（行=记录、列=字段），表之间通过键关联，用 SQL 操作，强调结构化 schema、事务 ACID、强一致。NoSQL（文档/键值/列族/图）弱 schema、常最终一致、易水平扩展，适合海量非结构化、超高并发读写。制造业核心业务（库存、订单、财务）要强一致和事务，用关系型（CP6 用 SQL Server）；日志、缓存、搜索可能配 NoSQL。

**2. 从业务需求到表结构的设计流程？**
先从需求里找名词（实体）和动词（事件/行为），区分"状态"和"事件"：状态建可更新的状态表、事件建 INSERT only 的流水表；给每个实体定唯一定位一行的键（业务唯一键）；定字段和类型；理清实体间一对一/一对多/多对多关系，多对多建中间表；加约束（非空、唯一、外键取舍）；按查询模式设计索引。CP6 的出入库就是 Stock 状态表 + StockTransaction 流水表这一对。

**3. 三大范式分别是什么？**
1NF 字段原子不可分；2NF 非键字段依赖完整主键（不能只依赖复合主键的一部分）；3NF 非键字段间无传递依赖。一句话：依赖键、依赖全部键、只依赖键本身。订单表冗余客户名违反 3NF（客户名传递依赖客户编号）。

**4. 什么时候故意反范式？订单单价为例。**
两类：性能反范式（报表宽表冗余字段避免 JOIN，代价是维护一致性）和业务快照反范式（把成交时的单价/税率/汇率固化在单据行）。订单明细必须冗余下单时单价，绝不实时关联商品表取现价——否则商品调价会改变历史订单成交额，发票对账全错。这是业务正确性不是性能问题。CP6 库存流水就冗余了 UnitPrice。

**5. 主键用自增 int 还是 GUID？**
单库、要最小体积和最快 JOIN、id 不外露用自增 int；多租户/分布式/多环境数据合并、要入库前拿 id、要 id 不可遍历用 GUID。GUID 代价是 16 字节大、随机 GUID 让聚集索引碎片——用 NEWSEQUENTIALID 生成有序 GUID 对冲。CP6 多租户 SaaS 全用 GUID 且 DatabaseGenerated(Identity) 让 DB 端生成有序 GUID。

**6. 自然键和代理键怎么选？**
优先代理键（GUID/自增）做主键，自然键做唯一索引。因为自然键有业务含义就有变更风险，拿它做主键会在业务规则变化时被迫改主键和所有外键。CP6 用 GUID Id 做主键、业务单号 TxnNo/InboundNo 做唯一索引。

**7. 为什么随机 GUID 做聚集索引性能差？**
聚集索引按主键值物理排序存数据。随机 GUID 无序，新行常要插入已满的中间页触发页分裂，导致碎片、填充率低、索引膨胀、写入变慢。解决用有序 GUID 让新行趋于追加，或聚集索引另建在有序列上。

**8. 金额字段用什么类型？decimal(18,2) 还是 (18,4)？**
一定 decimal 不用 float（浮点近似累加会漂，对账不平）。最终结算金额常 decimal(18,2) 到分；单价/汇率/成本率这种参与乘法的中间量用 decimal(18,4) 多留位，避免先舍入再乘大数放大误差。CP6 库存单价 decimal(18,4)、数量 decimal(21,8)。

**9. nvarchar(N) 和 nvarchar(max) 区别？MaxLength 的意义？**
nvarchar(N)（N≤4000）值在行内、能当索引键、快；nvarchar(max) 是大对象可能存行外、不能作索引键、读取跳页、让行变重。能估上限就用定长。CP6 给几乎每个 string 标 [MaxLength]，避免 EF 默认映射成 nvarchar(max) 导致编码字段进不了索引。

**10. 聚集索引和非聚集索引的区别？**
表只能一个聚集索引，叶子就是数据行本身，数据按聚集键物理排序（默认主键即聚集索引）；非聚集索引可多个，叶子存键加指回数据行的书签，查后可能回表取列（Key Lookup）。

**11. 什么是覆盖索引和 INCLUDE？**
让索引包含查询所需全部列，查询在索引内就能取全数据、不回表，即覆盖。WHERE/JOIN/ORDER BY 列做键列，只在 SELECT 出现的列用 INCLUDE 挂叶子。能消灭大量 Key Lookup 显著提速。

**12. 复合索引最左前缀原则？WHERE 第二列能用上吗？**
复合索引按列顺序逐级排序，只支持从最左列起的连续前缀。只查第二列用不上（跳过了最左列无法定位）。所以列顺序关键，最常单独查、选择性高的放最左。CP6 多租户表 TenantId 全放最左因每查必带。

**13. 索引失效的常见场景？**
索引列上套函数/运算（YEAR(日期)）、隐式类型转换、前导通配符 LIKE '%x'、OR 连不同列、否定条件（!=/NOT IN）、= NULL。核心原理：对索引列本身做加工，索引存的是原始值就用不上。救法把加工从列挪走（日期改范围条件、LIKE 改前缀、OR 拆 UNION）。

**14. 索引越多越好吗？怎么决定给哪列建？**
不是。索引加速读但每次写都要维护全部索引（写放大）、占存储、增锁竞争。给高频出现在 WHERE/JOIN/ORDER BY 且选择性高的列建；低选择性列（性别/状态）单独建没用。定期用 DMV 删没被用过的索引。

**15. 怎么诊断一条慢查询？**
抓实际 SQL，开 SET STATISTICS IO ON + 实际执行计划跑。看逻辑读定成本、看 Seek/Scan 判断索引用没用上、看 Key Lookup 和 Sort 找回表和排序开销。常见病根是列上函数/隐式转换导致失效，改范围条件恢复 Seek，加覆盖索引消灭 Key Lookup，让索引有序省 Sort。目标逻辑读从几万降到几十。

**16. 讲讲 ACID 和三种并发异常。**
ACID：原子性（全做或全不做）、一致性（前后满足约束）、隔离性（并发互不干扰）、持久性（提交不丢）。三异常：脏读（读到未提交修改）、不可重复读（同行两次读值变了）、幻读（同范围两次读行数变了）。Read Committed 挡脏读、Repeatable Read 再挡不可重复读、Serializable 全挡。

**17. SQL Server 默认隔离级别？RCSI 是什么？**
默认 Read Committed，靠锁实现、读被未提交的写阻塞。RCSI 是其行版本变体，读去读修改前的已提交快照不加锁，读不阻塞写、写不阻塞读，提升并发，代价是 tempdb 存版本。

**18. 死锁怎么产生、怎么处理、怎么避免？**
两事务各持对方想要的锁形成循环等待。SQL Server 死锁监视器检测后选回滚代价最小的当牺牲品回滚（报 1205），应用应捕获重试。避免首选让所有事务按相同顺序访问资源打破循环，其次缩短事务、加索引减小锁范围、用 RCSI。

**19. 库存扣减怎么防超卖？**
首选原子扣减 UPDATE SET qty=qty-n WHERE id=@id AND qty>=n，靠行锁串行化 + 判断受影响行数，一句既检查又扣减，绝不超卖或为负。伴随复杂逻辑用乐观锁 RowVersion，冲突抛并发异常应用重试（CP6 基类带 [Timestamp] RowVersion，EF 自动加进 UPDATE 的 WHERE，冲突转 409）。冲突极频繁才用悲观锁 UPDLOCK 提前锁行，但阻塞并发且要防死锁。

**20. 多租户数据隔离方案？TenantId 要进索引吗？**
单库行级（每行带 TenantId，成本最低、跨租户统计易、隔离靠代码）、Schema 隔离（居中）、分库（物理隔离最强、成本最高）。CP6 用单库行级，BaseTenantEntity 带 TenantId，EF 全局过滤器自动加 WHERE、写入自动盖章。TenantId 要进索引且放最左列——每查必带它（最左前缀能用上），且业务唯一性是租户内唯一（唯一索引必须含 TenantId 才正确）。CP6 唯一索引全是 TenantId 打头。

## 动手练习 3 个

### 练习 1（设计题）：设计一张"生产工单"及其明细表

**要求**：制造业工单，一张工单包含表头（工单号、产品、计划数量、状态、计划开工/完工日）和多条工序明细（工序号、工序名、标准工时、状态）。请：
1. 画出 ER 图，标明关系类型；
2. 写出两张表的字段、类型（用 SQL Server 类型）、主键、业务唯一键；
3. 说明工单号是否该做主键（结合第 4 节）；
4. 决定要不要给明细表建外键指向工单（结合第 6 节 CP6 实践）。

**参考答案要点**：
- ER：工单 `T_WorkOrder` ──1──<∞ `T_WorkOrderProcess`（一对多）。
- 表头主键用 GUID `Id`（代理键），工单号 `WorkOrderNo nvarchar(30)` 做唯一索引；数量 `decimal(21,8)`；日期 `datetime2`；状态 `nvarchar(10)` + [MaxLength]。加 `TenantId`（多租户，放唯一索引最左）。
- 明细主键 GUID `Id`，业务唯一键 `(TenantId, WorkOrderNo, ProcessCd)`；标准工时 `decimal(18,4)`。
- 工单号**不做主键**：单号格式可能随业务变，用代理键 + 唯一索引隔离变更风险。
- 外键：这是同模块内主从、生命周期强绑定，参照 CP6 的 `FK_T_WorkOrderProcess_T_WorkOrder_WorkOrderNo`（onDelete: Cascade），可以建外键 + 级联；如果追求高吞吐/可迁移也可不建物理外键靠 Service 保证——两种都能自圆其说，关键是讲清取舍。

### 练习 2（并发题）：写出库存扣减防超卖的三种 SQL/伪代码

**要求**：库存表 `T_Stock(Id, AvailableQty, RowVersion)`，实现"扣减 @n 件，不足则失败"。分别用：
1. 原子扣减；2. 乐观锁 RowVersion；3. 悲观锁 UPDLOCK。并说明各自适用场景。

**参考答案要点**：
1. 原子扣减：
   ```sql
   UPDATE T_Stock SET AvailableQty = AvailableQty - @n
   WHERE Id = @id AND AvailableQty >= @n;
   -- @@ROWCOUNT=0 即库存不足
   ```
2. 乐观锁：读出 `AvailableQty` 和 `RowVersion`，应用层判断够扣后：
   ```sql
   UPDATE T_Stock SET AvailableQty = AvailableQty - @n, RowVersion = <new>
   WHERE Id = @id AND RowVersion = @readRowVersion;
   -- 0 行 → 并发冲突 → 重读重试
   ```
3. 悲观锁：
   ```sql
   BEGIN TRAN;
   SELECT AvailableQty FROM T_Stock WITH (UPDLOCK, HOLDLOCK) WHERE Id=@id;
   -- 判断够扣
   UPDATE T_Stock SET AvailableQty = AvailableQty - @n WHERE Id=@id;
   COMMIT;
   ```
   适用：1 纯库存扣减首选；2 扣减伴随复杂业务逻辑（CP6 RowVersion 路线）；3 高冲突且逻辑复杂。

### 练习 3（索引调优题）：给一条 CP6 慢查询设计索引

**场景**：库存查询页执行如下 SQL，运维反馈很慢（`T_Stock` 有几百万行）：

```sql
SELECT ProductCd, LotNo, AvailableQty, ExpiryDate
FROM   T_Stock
WHERE  TenantId = @tid
  AND  WarehouseCd = 'WH01'
  AND  YEAR(ExpiryDate) = 2026
ORDER BY ExpiryDate;
```

**要求**：
1. 指出这条 SQL 里导致索引失效的写法，并改写；
2. 设计一个能让它走 Index Seek、消灭 Key Lookup 和 Sort 的索引（写出 CREATE INDEX）；
3. 说明为什么 TenantId 放最左、ExpiryDate 放键列、其他列放 INCLUDE。

**参考答案要点**：
1. 失效点：`YEAR(ExpiryDate) = 2026` 在索引列上套函数，改成范围：
   ```sql
   AND ExpiryDate >= '2026-01-01' AND ExpiryDate < '2027-01-01'
   ```
2. 覆盖索引：
   ```sql
   CREATE NONCLUSTERED INDEX IX_Stock_Tenant_Wh_Expiry
   ON T_Stock (TenantId, WarehouseCd, ExpiryDate)
   INCLUDE (ProductCd, LotNo, AvailableQty);
   ```
3. 理由：`TenantId` 每查必带（全局过滤器）放最左，先按租户切一刀；`WarehouseCd` 等值过滤紧随；`ExpiryDate` 既是范围过滤又是 ORDER BY 列，放键列末尾让索引有序从而省掉 Sort；`ProductCd/LotNo/AvailableQty` 只出现在 SELECT，放 INCLUDE 做覆盖消灭 Key Lookup。改写 + 建索引后，逻辑读从几万降到几十。
