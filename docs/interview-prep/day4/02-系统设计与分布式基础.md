# 第 2 章：系统设计与分布式基础——从能运行到可依赖

> 系统设计不是背“Redis、Kafka、微服务”。真正的设计要从业务不变量、流量、数据规模和故障模型出发，说明每个组件解决了什么问题、引入了什么新问题。

## 1. 设计题的固定答题框架

收到题目后按顺序展开：

1. **澄清需求**：谁使用？核心动作？一致性要求？允许多大延迟？
2. **估算规模**：用户数、QPS、峰值倍率、数据量、保留周期。
3. **定义不变量**：例如库存不能为负、租户数据不能串、同一业务单不能重复过账。
4. **画主链路**：客户端、API、业务服务、数据库及外部依赖。
5. **设计数据模型与接口**：主键、唯一约束、状态机、幂等键。
6. **处理失败**：超时、重试、重复、乱序、部分成功、恢复。
7. **扩展与观测**：缓存、队列、水平扩展、指标、告警。
8. **说权衡**：一致性 vs 可用性、复杂度 vs 收益、成本 vs 容量。

跳过前四步直接说“上微服务和 Redis”，通常会被判断为只会堆名词。

---

## 2. 分层与模块化

典型 CP6 请求链：

```text
Controller：协议适配、参数校验、返回状态码
  ↓
Application/Service：用例编排、事务边界、权限与业务规则
  ↓
Domain：业务不变量与状态转换
  ↓
Repository/EF Core：持久化技术细节
  ↓
SQL Server：约束、事务、索引、最终数据事实
```

分层的目标不是文件夹整齐，而是控制变化方向。HTTP 细节不应渗入领域规则；数据库实体也不应未经约束直接成为外部 API 合同。

什么时候不要抽象：只有一个实现、变化概率低、抽象没有消除重复决策时，额外接口可能只是间接层。什么时候必须抽象：明确存在外部依赖、需要替换/测试边界、或多个模块共享稳定契约时。

---

## 3. 从单体到分布式：先理解代价

模块化单体通常具备：一次部署、进程内调用、单数据库事务、调试链路短。微服务带来独立部署和按模块扩缩容，但同时引入：网络失败、跨服务数据一致性、版本兼容、服务发现、追踪、重复消息和运维成本。

选择原则：

- 团队规模和业务边界尚不稳定时，优先模块化单体；
- 某模块确有独立扩容、隔离故障、不同发布节奏或团队自治需求时，再拆分；
- 拆分以业务能力和数据所有权为边界，不按 Controller/Service/Repository 技术层拆。

## 4. 缓存：先问一致性，再问速度

### 4.1 Cache Aside

```text
读：查缓存 → 命中直接返回
          → 未命中查数据库 → 写缓存 → 返回
写：更新数据库 → 删除缓存
```

通常选择“删除缓存”而非“更新缓存”，因为缓存可能是聚合结果，正确重算困难。删除也不保证绝对一致：并发读可能把旧值重新写回，因此要结合短 TTL、版本、延迟双删或事件驱动刷新，按业务容忍度选择。

### 4.2 三个高频故障

- **穿透**：查询根本不存在的数据，每次打 DB。用参数校验、空值短缓存、布隆过滤器。
- **击穿**：一个热点 key 过期，大量请求同时回源。用互斥重建、逻辑过期、预热。
- **雪崩**：大量 key 同时过期或缓存整体故障。TTL 加随机抖动、限流降级、多级缓存。

库存数量这类强一致数据不能把 Redis 当唯一真相，除非团队完整承担持久化、恢复和一致性协议的复杂度。更稳妥的常见方案是数据库约束/事务保证不变量，缓存只加速读。

## 5. 消息队列：异步不是“自动可靠”

MQ 常用于：解耦、削峰、异步处理和事件广播。它同时引入重复、乱序、延迟、积压和消息丢失风险。

### 5.1 投递语义

- 至多一次：可能丢，不重复。
- 至少一次：不轻易丢，但可能重复；工程中最常见。
- 恰好一次：通常只在限定系统边界和协议下成立，业务仍应设计幂等。

### 5.2 幂等消费者

为每个业务事件分配稳定 `MessageId` 或业务键。消费时在同一数据库事务内：

```text
检查 Inbox 是否已有 MessageId
  ├─ 有：直接确认，跳过业务动作
  └─ 无：执行业务动作 + 写 Inbox 记录 + 提交
```

数据库唯一约束是最后一道并发防线。仅“先查再插”仍会在并发下竞态。

### 5.3 Outbox 解决双写

错误流程：先提交数据库，再发 MQ。若数据库成功而发消息时进程崩溃，状态已改变但事件永久丢失。

Outbox 做法：业务数据与待发布事件在**同一个本地数据库事务**提交；后台发布器读取 Outbox 发 MQ，成功后标记完成。它把“不可原子的数据库+MQ双写”改成“数据库原子写 + 可重试发布”。消费者仍须幂等。

## 6. 一致性、事务与库存扣减

业务不变量：`AvailableQuantity >= 0`。

### 6.1 原子条件更新（推荐起点）

```sql
UPDATE Stocks
SET AvailableQuantity = AvailableQuantity - @qty
WHERE Id = @id
  AND TenantId = @tenantId
  AND AvailableQuantity >= @qty;
```

检查受影响行数：1 表示成功，0 表示库存不足或记录不存在。这比“先查余额，再 update”安全，因为判断和修改在数据库中原子完成。

### 6.2 乐观并发

读取时带版本号，更新时 `WHERE Version=@oldVersion`；影响 0 行表示冲突。适合冲突较少、希望避免长时间持锁的场景。失败后应重新读取并基于业务决定重试或提示用户。

### 6.3 悲观锁

在事务内锁定目标行，其他事务等待。逻辑直观但降低并发，锁顺序不一致还会死锁。适合冲突频繁、临界区短且数据库能承受等待的场景。

### 6.4 跨服务 Saga

跨服务不能依赖单个数据库事务时，把长事务拆成多个本地事务，并为已完成步骤设计补偿动作。补偿不是数据库回滚；例如“退款”是一个新的业务动作，必须可追踪、可重试、可能需要人工介入。

## 7. API 可靠性设计

### 7.1 幂等键

客户端对一次业务意图生成 `Idempotency-Key`。服务端以“租户 + 操作类型 + key”建立唯一约束，保存处理状态和结果。重复请求返回原结果，而不是再次执行。

注意：同一个 key 携带不同请求体应拒绝；记录应有合理保留期；正在处理中与已完成要区分。

### 7.2 超时、重试、熔断、限流

- 超时：防止资源无限占用。
- 重试：应对短暂故障，但必须受限且考虑幂等。
- 熔断：下游持续失败时快速失败，给它恢复时间。
- 限流：保护系统容量，可按租户、用户、接口或全局限制。
- 舱壁隔离：不同下游使用独立并发/连接预算，避免一个故障拖垮全部。

这些不是越多越好。错误组合会使延迟和流量成倍放大。必须定义总时间预算和降级结果。

## 8. 多租户设计

共享库共享表模式的每个租户数据表都应含 `TenantId`，但仅有字段远远不够：

1. 读侧全局查询过滤；
2. 写侧从可信身份上下文覆盖 TenantId，不能信任请求体；
3. 唯一索引通常包含 TenantId；
4. 原生 SQL、批量更新和后台任务显式带租户边界；
5. 缓存 key、消息、文件路径和日志查询都包含租户维度；
6. 用跨租户负向测试证明隔离有效。

面试最有价值的回答是指出：**过滤器主要保护读；写入覆盖、数据库约束和测试共同保护完整边界。**

## 9. 可扩展性与可用性

无状态 WebApi 可通过多实例水平扩展，但前提是会话、文件、任务锁等状态已外置或协调。负载均衡器只把请求分发出去，不会自动解决共享数据和重复任务。

容量设计关注：

- 平均 QPS 不够，必须看峰值与突发；
- 数据库连接池是有限资源，实例数翻倍会把总连接数也放大；
- P95/P99 比平均值更能反映尾部体验；
- 健康检查要区分 liveness（进程是否需重启）与 readiness（是否能接流量）。

## 10. 综合设计题：出库单提交

### 需求与不变量

- 同一出库单只能成功过账一次；
- 任一物料库存不能变负；
- 过账成功后异步通知审计、报表和外部系统；
- 外部系统失败不能回滚已合法完成的本地出库，但必须最终补偿/重试。

### 推荐主链路

```text
POST /outbounds/{id}/post + Idempotency-Key
  → 认证、租户与权限校验
  → 开启数据库事务
  → 检查单据状态/幂等记录
  → 按固定顺序对每个物料做原子条件扣减
  → 单据状态改 Posted
  → 写审计 + Outbox
  → 提交事务
  → 返回结果

后台 Outbox Publisher → MQ
消费者：Inbox 去重 → 更新报表/通知外部系统 → 失败重试/死信告警
```

必须说明的权衡：强一致范围只覆盖本地库存与单据；通知和外部集成采用最终一致；固定锁顺序降低死锁；幂等键和单据状态防重复；Outbox 防止事件丢失。

## 12. 先纠正一个习惯：设计不是画方框

很多候选人拿到“设计库存系统”就画 Vue、API、Redis、Kafka、SQL Server，然后说“高并发、高可用”。这张图没有说明正确性，也没有说明故障发生时数据会怎样。

一个可以评审的设计，必须先写四种事实：

### 12.1 业务不变量

不变量是任何时刻都不能被破坏的业务事实。例如：

- 已过账出库单不能再次过账；
- 可用库存不能小于零；
- 会计期间关闭后不能新增普通凭证；
- 同一租户内单号唯一；
- A 租户看不到 B 租户数据。

性能优化可以降级，业务不变量不能“尽量满足”。数据库约束、事务与幂等都是保护不变量的手段。

### 12.2 容量事实

至少做数量级估算。假设 300 家工厂，每家高峰 20 个并发用户，每用户平均 5 秒一个读请求：

```text
读 QPS ≈ 300 × 20 ÷ 5 = 1,200
若高峰系数 3，则设计峰值约 3,600 QPS
```

假设每次响应 20KB：

```text
出口流量 ≈ 3,600 × 20KB ≈ 72MB/s
```

数字不必一次精确，但必须把“几百用户”和“几万 QPS”分开。规模决定是否需要缓存、分片、异步和限流。

### 12.3 延迟与一致性目标

库存扣减可能要求提交后立即一致；报表可以延迟 30 秒；通知可延迟 1 分钟；审计可能要求不可静默丢失。不要用一套一致性策略处理所有数据。

### 12.4 故障模型

至少假设：进程崩溃、网络超时、消息重复、数据库死锁、下游不可用、部署新旧版本共存。没有失败模型，就无法判断重试、幂等和恢复设计是否足够。

## 13. CP6 持久化集成事件状态机

真实实体：`CP6.Entity/DomainModels/Integration/IntegrationEvent.cs`。状态包括：

```text
PENDING   已持久化，业务 hook 尚未完成
SUCCESS   成功终态
FAILED    失败，等待下一次重试
DEADLETTER 达到最大次数，转人工/告警处理
```

配套配置 `IntegrationEventOptions` 默认：

```csharp
public int MaxAttempts { get; set; } = 5;
public int[] BackoffSeconds { get; set; } = { 60, 120, 240, 480, 960 };
public int PollIntervalSeconds { get; set; } = 60;
public bool Enabled { get; set; } = true;
```

### 13.1 为什么事件必须持久化

如果只在内存里：

```csharp
await SaveOrderAsync();
_ = Task.Run(() => NotifyWmsAsync());
```

订单保存后进程可能立刻崩溃。内存任务消失，系统没有记录证明“还欠 WMS 一次通知”。持久化记录让未完成工作可被扫描、查询、告警和人工处理。

持久化的价值不是让错误消失，而是把错误从“不可见丢失”变成“可恢复状态”。

### 13.2 状态机比一个 `IsSuccess` 更强

布尔值只能表达成功/失败，无法区分“尚未处理”“可以重试”“已耗尽需人工”。显式状态机让每个状态的合法迁移清楚：

```text
PENDING ──成功──► SUCCESS
   │
   └─失败──► FAILED ──重试成功──► SUCCESS
                   │
                   ├─仍失败且未耗尽──► FAILED（更新 NextRetryAt）
                   └─耗尽──► DEADLETTER
```

设计状态机时要回答：每条边由谁触发？是否能重复触发？失败后停在哪？谁能把 DeadLetter 重新投放？

## 14. `IntegrationEventRetryWorker` 逐段解析

### 14.1 为什么 BackgroundService 注入 `IServiceScopeFactory`

Worker 注册为 HostedService，生命周期接近 Singleton；`CP6Context` 是 Scoped。长生命周期对象不能直接持有一个 DbContext 长期复用，否则会积累跟踪对象、跨工作混用状态并触发并发问题。

真实构造函数保存的是 scope factory：

```csharp
public IntegrationEventRetryWorker(
    IServiceScopeFactory scopeFactory,
    IOptions<IntegrationEventOptions> options,
    ILogger<IntegrationEventRetryWorker> logger)
```

每轮处理时创建/解析独立 scope，工作完成后释放 DbContext 与其他 scoped 服务。

### 14.2 循环为什么必须接受停止令牌

```csharp
while (!stoppingToken.IsCancellationRequested)
{
    if (_opts.Enabled)
        await ProcessOnceAsync(stoppingToken);

    await Task.Delay(
        TimeSpan.FromSeconds(_opts.PollIntervalSeconds),
        stoppingToken);
}
```

容器停止、滚动发布和应用关闭都会发出取消。若 `Task.Delay` 不接 token，关闭可能被迫等待整个轮询间隔；若 EF/dispatcher 不传 token，长 I/O 继续拖住关停。

捕获逻辑只吞“由关停 token 引起”的 `OperationCanceledException`：

```csharp
catch (OperationCanceledException)
    when (stoppingToken.IsCancellationRequested)
{
}
```

这比无条件 `catch (OperationCanceledException)` 更准确。其他来源的取消可能代表业务超时，不应全部伪装成正常关停。

### 14.3 为什么按租户循环

代码调用：

```csharp
await TenantScopeRunner.ForEachTenantAsync(
    _scopeFactory,
    (sp, _, c) => ProcessTenantOnceAsync(sp, c),
    _logger,
    ct);
```

CP6 的全局查询过滤和写入盖章依赖当前租户上下文。后台任务没有 HTTP 请求，也就没有 JWT 自动提供租户。若直接用默认上下文扫描，要么只处理默认租户，要么通过 `IgnoreQueryFilters` 读出所有租户后在错误上下文写入。

按租户创建 scope，使查询过滤、下游服务和保存逻辑都处于事件所属租户。**多租户隔离不仅是 Controller 的事，后台任务、缓存、消息和运维脚本都必须携带租户边界。**

### 14.4 到期查询为何这样写

```csharp
var due = await db.IntegrationEvents
    .Where(e => e.Status == IntegrationEventStatus.Failed
             && e.NextRetryAt != null
             && e.NextRetryAt <= now
             && e.Attempts < _opts.MaxAttempts)
    .OrderBy(e => e.NextRetryAt)
    .Take(50)
    .ToListAsync(ct);
```

逐项解释：

- 只扫 FAILED，避免重复处理 SUCCESS/DEADLETTER；
- `NextRetryAt <= now` 保证退避窗口；
- `Attempts < MaxAttempts` 保护上限；
- 先处理最早到期事件，降低老消息饥饿；
- `Take(50)` 给每轮设置工作预算，避免一次积压占满内存和数据库连接；
- `ToListAsync(ct)` 才是可取消异步 I/O。

对应索引至少应考虑租户过滤列、Status、NextRetryAt。是否把 Attempts 放索引要看选择性与执行计划，不能只因出现在 WHERE 就全部建索引。

### 14.5 退避为何递增

第一次失败后 60 秒，随后 120、240、480、960 秒。若下游宕机，固定每秒重试会制造流量风暴。退避让故障持续越久，尝试越稀疏。

生产更完善的策略会加入**随机抖动**，避免多个实例/事件在完全相同时间同时醒来：

```text
实际等待 = 基础退避 × 随机区间，例如 0.8～1.2
```

### 14.6 失败信息与死信

异常时保存 `LastError`、计算下一时间、保持 FAILED；达到上限后转 DeadLetter 并通知。这里要注意：错误字符串可能含敏感数据，生产应做脱敏和长度上限；死信通知本身也可能失败，需要可观察而不是假设永远成功。

## 15. 多实例 Worker 的并发缺口

当前查询是“先选出 50 条，再逐条修改”。当部署两个 WebApi 实例时，两个 Worker 可能在相近时刻读到同一 FAILED 事件并同时派发。

这不是说代码一定错，而是设计边界必须明确。可选方案：

### 方案 A：消费者业务幂等

允许重复派发，但下游用事件 ID/业务键去重。这通常是分布式系统的最终防线，即使上游抢占做得再好，网络重试仍可能重复。

### 方案 B：数据库租约/抢占

原子更新把待处理行改为 Processing，并写 `LeaseOwner`、`LeaseUntil`。只有成功影响行的实例拥有处理权；实例崩溃后租约过期，其他实例可接管。

### 方案 C：数据库锁提示

使用适合 SQL Server 的锁策略跳过已锁行。但与 ORM、事务时长和数据库耦合更深，需要真实并发测试。

### 方案 D：单独 Worker 部署

WebApi 多实例，重试 Worker 只运行一个实例。实现简单，但形成单处理者吞吐/可用性边界；仍要处理进程故障和重复。

面试加分点：主动指出“扫描批次 + 多实例”问题，并说明即使做抢占，消费者幂等仍不能省。

## 16. Kafka 标本：投递保证是业务选择

`KafkaProducerService` 配置：

```csharp
var producerConfig = new ProducerConfig
{
    BootstrapServers = bootstrap,
    MessageTimeoutMs = 5000,
    Acks = Acks.Leader,
    EnableIdempotence = false,
};
```

### 16.1 `Acks.Leader` 意味着什么

Leader 收到并确认就认为成功，不等待全部副本。这在吞吐与持久性之间做了选择。如果 leader 确认后、数据尚未复制就故障，存在丢失窗口。更严格场景可选 all 并配合副本/ISR，但延迟和可用性代价更高。

### 16.2 `EnableIdempotence = false`

生产者重试在某些情况下可能造成重复。该服务用于操作日志旁路，代码明确偏向吞吐与不阻断主业务。**同一个设置不能照搬到库存扣减事件。** 业务关键度不同，投递策略就不同。

### 16.3 Key 为 UserName

Kafka 同 key 通常进入同一分区，因此同一用户操作更容易保持分区内顺序。但这不保证全局顺序，也要考虑热点用户造成分区倾斜。

### 16.4 异常为什么被吞掉

真实代码捕获异常、记日志而不抛回业务请求。注释说明 Kafka 操作日志通道是旁路，消费者不可用时还有降级思路。

这体现故障隔离：审计通道短暂失败不应让所有业务接口不可用。但如果法规要求审计绝不能缺失，就不能只吞异常；应持久化待发记录、告警并明确系统是否需要 fail closed。设计必须从需求出发。

## 17. Cache Aside 的并发时间线

设数据库值 v1，缓存也为 v1。写请求把 DB 更新为 v2 后删除缓存，这是常见做法。但并发时可能发生：

```text
读请求 R：缓存未命中，开始查 DB，读到 v1
写请求 W：DB 更新到 v2，删除缓存
读请求 R：把刚才读到的 v1 写回缓存
结果：缓存短时间倒退为 v1
```

这说明“更新 DB 后删缓存”提供的是工程上常用的短暂最终一致，不是数学上的线性一致。

可选补强：

- 短 TTL，限制错误窗口；
- 缓存 value 带版本，只允许更高版本覆盖；
- 变更事件驱动失效；
- 延迟二次删除；
- 对强一致读取绕过缓存；
- 把操作串行化，但代价更高。

选哪种由业务容忍度决定。商品描述旧 10 秒通常可接受，库存承诺可能不行。

### 缓存 key 的多租户灾难

错误：

```text
stock:item:123
```

如果不同租户都有 item 123，A 缓存可能被 B 命中。正确 key 至少含租户：

```text
tenant:{tenantId}:stock:item:{itemId}:v{schemaVersion}
```

还要考虑语言、权限、仓库等决定响应的维度。漏一个维度，缓存就可能越权。

## 18. 库存并发：从错误实现一步步修正

### 18.1 错误一：只在内存判断

```csharp
var stock = await db.Stocks.FindAsync(id);
if (stock.Available >= qty)
{
    stock.Available -= qty;
    await db.SaveChangesAsync();
}
```

两个请求都读到 10，各扣 7，都通过判断，最后可能覆盖或得到负面业务结果。这是“检查—行动”竞态。

### 18.2 修正：数据库原子条件更新

```sql
UPDATE Stocks
SET Available = Available - @qty
WHERE TenantId = @tenantId
  AND Id = @id
  AND Available >= @qty;
```

受影响行数为 1 才成功。判断与写入由数据库作为一个语句完成。

### 18.3 多物料单据怎么办

一张出库单有 10 个物料，必须在一个短事务内逐项扣减，任一失败则回滚。为降低死锁，所有请求按稳定键（如 StockId）相同顺序更新。

事务里不要做远程 HTTP/MQ 调用，因为远程延迟会让数据库锁长期持有。提交后需要通知外部，用持久化事件/Outbox 把远程工作移出事务。

### 18.4 幂等与并发不是同一个问题

- 并发控制保护两个不同业务意图同时修改同一库存；
- 幂等保护同一个业务意图因重试被执行多次。

只做乐观锁不能自动识别“这是同一请求重发”；只做幂等也不能解决不同订单争抢同一库存。两者都需要。

## 19. Outbox 与 CP6 持久化事件的关系

标准 Outbox 要求“业务数据变化”和“待发布事件”在同一个本地事务写入。提交后独立发布器把事件发往消息系统。

判断一个实现是否真正解决双写，关键不在类名叫不叫 Outbox，而在：

1. 事件行是否与业务数据同事务提交；
2. 发布失败是否保留可重试状态；
3. 多实例是否安全抢占/允许重复；
4. 消费者是否幂等；
5. 是否有积压、死信与人工恢复。

CP6 的 `IntegrationEvent` + RetryWorker 提供了持久化、退避、死信和租户范围。学习时还应顺着具体业务 hook 验证第 1 点事务边界，而不是看到“IntegrationEvent”名字就自动宣布完全等同于 Outbox。

这是一条重要的工程阅读原则：**按代码行为判断模式，不按类名判断模式。**

## 20. CAP 不要背成口号

CAP 讨论的是发生网络分区时，分布式系统无法同时保证一致性和可用性。它不是说任何时候只能“三选二”，也不是数据库选型表。

用仓库场景理解：两个机房之间断网。如果两边都继续接受同一库存的扣减（可用），就可能各自承诺库存导致冲突；如果要求不超卖（强一致），至少一边需要拒绝/等待协调，牺牲分区期间可用性。

实际设计常把不同操作区别对待：库存承诺偏一致；商品查询可返回稍旧缓存；报表偏最终一致。不要给整个系统贴一个“CP/AP”标签就结束。

## 21. 设计题完整示范：生产报工

### 21.1 澄清

- 操作员对工单报良品、废品和工时；
- 可能在车间平板网络不稳定环境重复提交；
- 报工影响工单进度、库存入库、OEE 与成本；
- 工单进度和本次报工不能重复，报表可稍后更新。

### 21.2 不变量

- 数量不能为负；
- 同一设备/客户端生成的报工 ID 只能处理一次；
- 累计报工不能无规则超过工单数量；
- 工单与报工必须属于当前租户；
- 本地工单进度与报工明细同事务。

### 21.3 API

```http
POST /api/mes/work-orders/{id}/reports
Idempotency-Key: device-7-20260721-000381
Content-Type: application/json

{
  "goodQuantity": 98,
  "scrapQuantity": 2,
  "reportedAt": "2026-07-21T14:20:00Z",
  "machineId": "..."
}
```

成功返回 201；同 key 同 payload 返回原结果；同 key 不同 payload 返回 409；状态不允许或超量返回业务冲突；字段非法返回 400。

### 21.4 本地事务

插入幂等记录/报工明细，带并发版本更新工单累计量，写持久化事件。唯一约束和受影响行数是并发最后防线。

### 21.5 异步消费者

库存、OEE、成本按业务一致性要求选择同步同库或异步事件。异步消费者以 ReportId/EventId 去重；失败进入退避，耗尽进入死信告警。

### 21.6 离线边界

客户端本地保存待提交队列，恢复网络后用原幂等键重发。服务端时间与设备发生时间分别保存，防止设备时钟错误污染审计。

### 21.7 观测

指标包括报工成功率、冲突率、端到端事件延迟、死信数量；日志含 tenant、workOrderId、reportId、traceId，但不记录敏感 token。

这就是完整设计：从业务事实出发，覆盖正常路径、重试、重复、离线、状态与观测，而不是堆组件名。

## 22. 面试题 15 问（详细答案骨架）

### 1. 单体一定落后吗？

不是。模块化单体部署和事务简单、调试成本低。只有独立扩缩容、故障隔离、发布节奏或团队边界收益超过分布式成本时才拆服务。

### 2. Redis 能保证库存不超卖吗？

Redis 原子脚本可保护其内部计数，但还要解决持久化、数据库事实同步、故障恢复与双写。常见稳妥方案仍让数据库事务/约束保护最终不变量，缓存服务读性能。

### 3. 至少一次投递意味着什么？

系统倾向不丢，但在确认丢失、超时或消费者崩溃时会重复。因此消费者必须用稳定事件/业务键幂等。

### 4. “恰好一次”为什么要谨慎？

它通常只在特定 broker、事务和边界内成立。一旦消费者还写外部数据库/发 HTTP，端到端仍有双写与重试。业务幂等仍是必要保险。

### 5. 什么是消息顺序？

通常只能保证分区内顺序，不是全局顺序。把同一业务聚合的 key 放同分区，并用版本拒绝旧事件；全局顺序代价很高且常无必要。

### 6. 死信之后怎么办？

死信不是垃圾桶。要告警、展示原因与 payload 摘要、支持修复后重放、保留审计，并防止重放造成重复副作用。

### 7. 为什么事务里不调用远程服务？

网络延迟和失败不可控，会延长数据库锁、放大死锁和超时，还无法与本地事务原子提交。用持久化事件移出事务。

### 8. 幂等键存多久？

覆盖客户端可能重试的业务窗口，并考虑业务法规/审计。过短会让晚到重试重复执行；永久保存有容量成本。可按状态、业务类型和时间归档。

### 9. 同 key 不同请求体怎么办？

拒绝并返回冲突。可保存规范化请求 hash；否则错误复用 key 会静默拿到不相干旧结果。

### 10. 缓存穿透、击穿、雪崩区别？

穿透是不存在 key 每次回源；击穿是单热点过期并发回源；雪崩是大量 key 同时失效或缓存整体故障。对应空值/布隆、互斥重建、TTL 抖动/限流降级。

### 11. 水平扩展为什么要求无状态？

请求可能落到任一实例。若 session、文件或任务所有权只存在本机，切换实例会丢状态/重复工作。状态需外置或通过粘性会话（权宜）和协调机制管理。

### 12. 数据库为何常是瓶颈？

所有实例共享它，连接、锁、CPU、I/O 都有限。应用扩容只增加对数据库并发，需查询优化、缓存读、批处理、限流和容量规划共同处理。

### 13. Saga 补偿等于回滚吗？

不等于。退款、取消预留是新的业务动作，期间外部世界已经观察到原动作；补偿也可能失败，需要幂等和人工恢复。

### 14. 如何防缓存串租户？

key 包含租户和影响结果的权限/语言/仓库维度；封装统一 key builder；用跨租户负向测试；清理/失效也带相同租户边界。

### 15. 如何评审一个“用了 Kafka”的设计？

问消息为何需要异步、生产与消费保证、key/分区、重复与乱序、schema 演进、积压容量、死信重放、监控、权限与敏感数据，而不是只问能不能发送。

## 23. 动手实验与参考答案

### 实验 1：重试状态机测试

参考 CP6 `IntegrationEventRetryWorkerTests`，至少验证：到期成功转 SUCCESS、达到 5 次转 DEADLETTER、禁用时不派发、未到期跳过、第二次退避大于第一次。

为什么这些测试有价值：它们覆盖状态转换与时间边界，不只是“Worker 能启动”。

### 实验 2：双实例重复

用两个独立 scope 并发调用扫描逻辑，观察是否可能读取同一事件。然后提出租约或原子抢占方案，并保留消费者幂等。不要只在 InMemory provider 得出数据库锁结论，应使用 SQL Server 集成环境验证。

### 实验 3：库存并发

开两个独立数据库连接，同时对可用 10 的库存扣 7。错误“先查再改”可能双成功；条件 UPDATE 应只有一个受影响行为 1。最终断言库存为 3、成功数为 1。

### 实验 4：缓存租户隔离

给 A/B 租户创建相同 ItemId、不同名称。先让 A 填充缓存，再以 B 查询。若 B 得到 A 值，key 设计失败。修复后测试必须保留，防止以后回归。

完成标准：每个实验都保留“初始状态、并发/故障动作、预期不变量、实际证据”。
