## 2. 进程、线程、内存与上下文切换

### 2.1 进程与线程

- **进程**是资源隔离单位，拥有独立虚拟地址空间、句柄和运行时环境。
- **线程**是 CPU 调度单位，同一进程内线程共享堆、静态区和文件句柄，但每个线程有自己的栈与寄存器状态。
- `CP6.WebApi` 启动后通常是一个进程；它用线程池中的不同线程处理请求。
- 容器不是轻量虚拟机。容器里的应用仍是宿主机内核管理的进程，只是通过 namespace 和 cgroup 获得隔离与资源限制。

### 2.2 栈与堆

```text
进程地址空间
├─ 代码段：已编译指令
├─ 静态区：static 数据
├─ 托管堆：对象、数组、字符串，由 GC 管理
└─ 每线程栈：调用帧、局部变量、返回地址
```

不要用“值类型一定在栈，引用类型一定在堆”回答面试。更准确的说法是：**存储位置由上下文决定**。类对象的字段即使是 `int`，也随对象位于托管堆；被闭包捕获的局部变量会提升到堆上的闭包对象。

### 2.3 GC 为什么会影响延迟

.NET GC 通过代际回收优化“多数对象寿命很短”的现实：Gen 0、Gen 1、Gen 2。大量短命对象主要在 Gen 0 回收；存活久或很大的对象成本更高。

生产中关注：

- 高频创建大数组/大字符串会增加分配与 GC 压力；
- 大对象堆通常接收约 85KB 以上对象；
- GC 暂停会形成延迟尖峰；
- 不要因害怕 GC 到处对象池化，先用指标和 profiler 证明分配是瓶颈。

### 2.4 CPU 密集与 I/O 密集

- CPU 密集：压缩、加密、复杂计算。异步不会让计算凭空变快；可考虑并行，但受核心数约束。
- I/O 密集：数据库、HTTP、磁盘。`await` 让等待期间不占线程，从而提高吞吐量。

错误示例：在 Web 请求里用 `Task.Run` 包住 EF 查询。这只是额外占一个线程等待，并没有变成真正异步 I/O。正确做法是调用 `ToListAsync(ct)` 这类底层异步 API。

## 3. DNS：域名如何变成地址

解析通常经历浏览器缓存、操作系统缓存、本地 DNS/递归解析器，再到权威 DNS。DNS 记录常见类型：

| 类型 | 作用 |
|---|---|
| A / AAAA | 域名指向 IPv4 / IPv6 |
| CNAME | 一个名称别名到另一个名称 |
| TXT | 域名验证、安全策略等文本 |
| MX | 邮件服务器 |

DNS 成功只表示找到了地址，不表示端口开放、TLS 正常或应用健康。排障必须分层：

```powershell
Resolve-DnsName example.com
Test-NetConnection example.com -Port 443
curl.exe -vk https://example.com/health
```

分别验证名称解析、TCP 连通、TLS 与 HTTP。

## 4. TCP：可靠字节流如何工作

### 4.1 三次握手

```text
客户端 ── SYN(seq=x) ─────────► 服务端
客户端 ◄─ SYN+ACK(seq=y,ack=x+1) 服务端
客户端 ── ACK(ack=y+1) ───────► 服务端
```

三次握手让双方确认彼此的发送和接收能力，并同步初始序列号。TCP 通过序列号、确认、重传、滑动窗口、拥塞控制提供**有序、可靠的字节流**。

重点边界：

- TCP 不保留“消息边界”，应用协议必须自己定义长度或分隔方式；HTTP 就是应用层协议。
- TCP 成功不等于业务成功；服务端可能返回 500。
- TCP 可靠不等于绝不失败；断网、进程崩溃与超时仍会发生。

### 4.2 超时不是一个值

一次请求可能包含 DNS 超时、连接超时、TLS 握手超时、请求头超时、响应读取超时、数据库命令超时。只说“我们设置了 30 秒超时”是不完整的。

超时设计原则：

1. 上游总超时必须大于下游单次超时，但要留出处理和返回时间；
2. 重试只用于瞬时故障，且要指数退避并加入随机抖动；
3. 非幂等写操作不可盲目重试；
4. 把 `CancellationToken` 从 Controller 贯穿到 EF/HTTP 调用。

## 5. TLS 与 HTTPS

TLS 同时解决三件事：

- **机密性**：窃听者看不懂内容；
- **完整性**：内容被篡改能被发现；
- **身份认证**：证书链证明你连接的是目标服务。

简化握手过程：客户端给出支持的算法和随机数；服务端返回证书与协商结果；客户端验证域名、有效期、签发链；双方通过非对称机制协商会话密钥；之后用高效的对称加密传输。

常见误区：

- HTTPS 不阻止服务器自己记录敏感数据；日志仍需脱敏。
- HTTPS 不等于授权；拿到连接的人仍需 JWT/cookie 身份认证与权限检查。
- 忽略证书校验能“解决”测试环境错误，却会打开中间人攻击入口，不能进入生产。

## 6. HTTP 必须掌握的语义

### 6.1 方法与幂等性

| 方法 | 常见语义 | 幂等 |
|---|---|---|
| GET | 获取资源 | 是 |
| POST | 创建/执行命令 | 通常否 |
| PUT | 整体替换指定资源 | 是 |
| PATCH | 部分更新 | 取决于设计 |
| DELETE | 删除指定资源 | 语义上是 |

幂等指同一请求重复执行，最终资源状态与执行一次相同；不代表每次响应完全一样。库存出库命令若因网络超时重发，必须用业务请求号/幂等键避免重复扣减。

### 6.2 高频状态码

| 状态码 | 含义 | 排查方向 |
|---:|---|---|
| 400 | 请求格式或校验失败 | 参数、模型绑定 |
| 401 | 未认证/凭证无效 | token/cookie |
| 403 | 已认证但无权限 | 权限数据与策略 |
| 404 | 资源或路由不存在 | URL、路由、数据 |
| 409 | 状态冲突 | 并发、唯一约束 |
| 429 | 请求过多 | 限流策略 |
| 500 | 应用内部错误 | 异常与日志 |
| 502 | 网关收到无效上游响应 | 上游进程/端口 |
| 503 | 服务暂不可用 | 过载/维护/无实例 |
| 504 | 网关等待上游超时 | 慢查询/下游超时 |

### 6.3 Cookie、JWT、CORS 与 CSRF 不要混

- Cookie 是浏览器自动携带的小段数据；Session 是服务端状态模型。
- JWT 是自包含令牌格式，不意味着必须存 localStorage。
- CORS 是浏览器对跨源脚本读取响应的限制，不是服务端鉴权。
- CSRF 利用浏览器自动带凭证发起非本人意愿的请求；SameSite、CSRF token、检查来源可防护。
- XSS 是把恶意脚本注入页面；输出编码、避免不可信 HTML、CSP 是主要防线。

## 7. 浏览器事件循环与竞态

JavaScript 主线程执行调用栈。同步任务结束后，先清空微任务队列（Promise/`await` 延续），再进入后续任务和渲染机会。

典型搜索竞态：用户先搜 A，再搜 B；B 很快返回并显示，A 后返回却覆盖 B。解决方案不是“希望请求按顺序返回”，而是：

- 用 `AbortController` 取消旧请求；或
- 记录递增请求版本，只接受最新版本；或
- 对输入 debounce，减少无意义请求。

```ts
let version = 0
async function search(keyword: string) {
  const mine = ++version
  const data = await api.search(keyword)
  if (mine === version) rows.value = data
}
```

## 8. 一次请求的分层排障法

按从外到内顺序验证，每一步都要有证据：

1. 浏览器 Network：请求是否发出？URL、方法、状态码、耗时在哪一段？
2. DNS/TCP/TLS：能否解析和连接？证书是否有效？
3. 代理：请求是否到达 Nginx/网关？上游地址是否正确？
4. 应用：是否有同一 trace ID 的请求日志与异常？
5. 依赖：SQL、Redis、MQ 或下游 HTTP 的耗时与错误？
6. 资源：CPU、内存、线程池、连接池、磁盘是否饱和？

不要一上来重启。重启会破坏现场，只能作为止血手段，并必须在重启前保留关键日志、指标和转储信息。

## 9. 面试深水问答

### Q1：TCP 与 HTTP 的关系？

TCP 提供可靠有序字节流；HTTP 定义请求/响应的应用语义。HTTP/1.1 和 HTTP/2 通常运行在 TCP 上；HTTP/3 运行在基于 UDP 的 QUIC 上，但仍由 QUIC 提供可靠性与加密能力。

### Q2：为什么有了 HTTPS 还需要 JWT 权限？

HTTPS 保护传输通道并认证服务器；JWT/会话识别调用者；授权策略判断调用者能否执行动作。三者解决不同问题。

### Q3：502 与 504 怎么区分？

两者通常由代理产生。502 表示代理没拿到有效上游响应，例如连接被拒绝或协议错误；504 表示已等待上游但在规定时间内没有完成。实际仍需结合代理和应用日志确认。

### Q4：为什么不能无限重试？

故障时重试会放大流量，形成重试风暴；写操作还可能重复执行。应限制次数、退避抖动、只重试明确的瞬时错误，并结合幂等、熔断和总超时预算。

## 11. 教学标本：`http.ts` 不是“一个 axios 封装”那么简单

真实文件：`cp6.web/src/api/http.ts`。它承担了五项职责：

1. 把相对地址统一放到 `/api` 下；
2. 给请求设置 10 秒客户端等待上限；
3. 让浏览器携带 httpOnly Cookie；
4. 为非安全方法附加 CSRF token；
5. 对 401 做一次 refresh，并重放原请求。

先看创建实例的三行：

```ts
const http = axios.create({
  baseURL: '/api',
  timeout: 10000,
  withCredentials: true
})
```

### 11.1 `baseURL` 到底改变了什么

页面写：

```ts
await http.get('/wms/stocks')
```

axios 合成 `/api/wms/stocks`。开发环境通常由 Vite proxy 转发，生产环境通常由同源 Web 服务器或反向代理把 `/api` 转到 WebApi。浏览器不知道 Controller 在哪台机器，它只看到当前站点的 `/api`。

这层设计有两个实际价值：

- 前端代码不硬编码 `localhost:5000`、测试域名或生产域名；
- 页面与 API 保持同源，可显著简化 Cookie、CORS 与 CSRF 边界。

常见错误是把完整后端地址散落在几十个组件中。环境一换，所有组件都要改；浏览器还会立即进入跨源规则。

### 11.2 `timeout: 10000` 能取消服务端工作吗

不能直接保证。它表示客户端等待超过 10 秒后放弃这次请求。此时存在三种情况：

1. 请求尚未到达服务端；
2. 服务端正在执行；
3. 服务端已提交数据库，只是响应没能及时返回。

因此，“前端显示超时”不能推导出“业务没成功”。写操作必须有查询结果的办法，或使用幂等键安全重试。服务端还要把请求断开传播为 `CancellationToken`，并在适合取消的 EF/HTTP 操作中使用；数据库一旦提交，取消不能把现实倒回去。

### 11.3 `withCredentials`、httpOnly 与 CSRF 的关系

CP6 使用 Cookie 携带访问/刷新凭证。httpOnly 的意义是 JavaScript 不能读取 token，降低 XSS 直接窃取凭证的风险，但浏览器仍会自动发送 Cookie。

“自动发送”同时带来 CSRF 风险：恶意站点可能诱导浏览器向 CP6 发写请求。CP6 的请求拦截器因此读取一个**非 httpOnly** 的 `cp6_csrf` Cookie，并把同一个值放到请求头：

```ts
const method = (config.method || 'get').toLowerCase()
if (method !== 'get' && method !== 'head' && method !== 'options') {
  const csrf = getCookie('cp6_csrf')
  if (csrf) config.headers['X-CSRF-Token'] = csrf
}
```

服务端比较 Cookie 与请求头。第三方页面可以诱导浏览器带 Cookie，却通常无法跨源读取 Cookie 值并设置自定义头，这就是“双提交”防护的核心。

注意职责边界：

- httpOnly 防的是脚本读取敏感 Cookie，不自动防 CSRF；
- SameSite 能降低 CSRF 面，但不能替代所有场景的明确校验；
- CORS 决定浏览器是否允许跨源脚本读取/构造特定请求，不是用户权限系统；
- 服务端授权仍是最终安全边界。

### 11.4 为什么并发 401 只能发一次 refresh

假设页面同时加载菜单、用户资料、消息数和库存。访问凭证过期后，四个请求同时收到 401。如果每个请求都 refresh：

```text
请求 A 401 → refresh 1 → token 轮换成功
请求 B 401 → refresh 2 → 使用旧 refresh token，可能触发重用检测
请求 C 401 → refresh 3 → 再次失败
请求 D 401 → refresh 4 → 登录态混乱
```

CP6 使用模块级共享 Promise：

```ts
let refreshPromise: Promise<any> | null = null

function doRefresh() {
  if (!refreshPromise) {
    refreshPromise = http.post('/auth/refresh').finally(() => {
      refreshPromise = null
    })
  }
  return refreshPromise
}
```

第一个 401 创建 Promise，其他请求等待同一个 Promise。refresh 成功后，各自重放原请求。`config._retried` 防止同一请求无限刷新循环。

这里能看到事件循环知识的实际用途：多个异步回调共享同一个 Promise，并不需要阻塞线程；Promise 完成后，等待它的延续进入微任务队列。

## 12. 操作系统深入：一行 C# 代码如何落到 CPU

### 12.1 从源码到机器执行

C# 源码先由编译器生成 IL 和程序集元数据。程序运行时，CLR 加载程序集，JIT 在需要时把方法编译为目标机器码。CPU 只执行机器指令，不认识 C#、类或 `await`。

```text
C# 源码
  → Roslyn 编译
IL + 元数据（.dll）
  → CLR 加载 + JIT
机器码
  → OS 调度线程到 CPU 核心
执行
```

这解释了几个常见现象：

- 首次调用某段方法可能包含 JIT 成本；
- Debug 与 Release 的优化和可观察行为不同；
- 一个进程可以有很多线程，但某一时刻每个 CPU 逻辑核心只能执行一个线程的指令流；
- .NET 的内存安全与 GC 建立在 CLR 管理之上，不代表永远不会有内存泄漏——对象仍可能被错误引用而无法回收。

### 12.2 调用栈到底保存什么

调用：

```csharp
decimal Calculate(decimal price, int qty)
{
    var subtotal = price * qty;
    return AddTax(subtotal);
}
```

线程进入 `Calculate` 时建立一个栈帧，概念上记录参数、局部变量、返回地址和保存的寄存器。调用 `AddTax` 又压入新帧，返回时弹出。

递归没有终止条件会不断压栈，最终 `StackOverflowException`。这和托管堆“空间不足”不是一回事。栈强调调用生命周期，堆强调对象生命周期。

### 12.3 闭包为什么让局部变量活得更久

```csharp
Func<int> BuildCounter()
{
    var count = 0;
    return () => ++count;
}
```

`BuildCounter` 已返回，但 lambda 仍需访问 `count`。编译器会生成一个闭包对象，把 `count` 变成该对象字段。只要返回的委托还被引用，闭包对象就不能回收。

生产意义：在长生命周期事件、缓存或静态集合中注册捕获大对象的 lambda，可能让整棵对象图长期存活。内存泄漏在 GC 语言中常表现为“对象仍可达”，不是忘记 `free`。

### 12.4 GC 的暂停与分配率

不要只记 Gen 0/1/2。你还要理解三个量：

- **分配率**：每秒新分配多少内存；
- **存活率**：一次回收后还有多少对象存活；
- **暂停时间**：GC 为得到一致对象图而影响应用执行的时间。

例如一个接口把大结果先序列化成字符串，又转 UTF-8 byte[]，再复制进响应缓冲，单次请求可能产生多份大对象。高并发时即使没有永久泄漏，也会因高分配率频繁 GC。

正确顺序是先测量：`dotnet-counters` 看 allocation rate、GC heap size、Gen 2 collection count；确认热点后再用 profiler 找对象来源。不要凭感觉把所有对象改成池化，因为池会增加所有权、清理和并发复杂度。

## 13. TCP 不只是“三次握手”

### 13.1 为什么 TCP 叫字节流

发送方两次调用：

```text
send("ABC")
send("DEF")
```

接收方可能一次读到 `ABCDEF`，也可能先读 `AB`、再读 `CDEF`。TCP 只保证字节有序可靠，不保留两次 `send` 的边界。HTTP 使用报文结构与长度规则定义边界；自定义 TCP 协议则必须设计长度前缀、固定长度或可靠分隔符。

### 13.2 可靠性如何建立

- 序列号标识字节位置；
- ACK 告诉发送方已收到哪里；
- 超时或重复 ACK 触发重传；
- 接收窗口做流量控制，防止接收方被淹没；
- 拥塞窗口保护网络，避免发送方无限加速。

可靠性有成本。丢包发生时，后续数据即使已经到达，也可能因等待缺失字节而产生队头阻塞。HTTP/2 在单 TCP 连接多路复用，仍可能受 TCP 层丢包影响；HTTP/3/QUIC 把独立流放在 QUIC 层，减少跨流阻塞。

### 13.3 连接池为什么重要

每次请求都新建 TCP + TLS，增加握手往返、CPU 和临时端口压力。.NET 的 `HttpClient` 应通过 `IHttpClientFactory` 或合理长生命周期复用底层连接。

但“复用连接”不等于永不更新：DNS 地址会变化，连接会老化，下游可能主动关闭。现代 handler/工厂会管理连接生命周期。自己每次 `new HttpClient()` 再立刻 Dispose，是经典反模式。

### 13.4 数据库连接池与 HTTP 连接池的共同本质

两者都复用昂贵连接，但池容量有限：

```text
请求到达 200 个
数据库连接池上限 100
前 100 个持有连接执行
后 100 个等待“借连接”
慢 SQL 让归还变慢
等待请求继续堆积 → 超时 → 重试 → 更拥堵
```

因此扩容 WebApi 实例可能压垮数据库：每个实例有自己的池，总潜在连接数随实例数增长。容量规划必须把实例数、池上限和数据库承载一起计算。

## 14. TLS 深入：证书到底证明了什么

### 14.1 证书链

服务器证书包含公钥、域名、有效期、用途和签发者签名。客户端沿“服务器证书 → 中间 CA → 受信根 CA”验证签名，并检查访问域名是否匹配 SAN、证书是否过期。

所以以下错误含义不同：

- `name mismatch`：证书没有覆盖当前域名；
- `expired`：超过有效期；
- `unknown authority`：签发链无法到受信根；
- `handshake failure`：可能是协议/算法、客户端证书或代理问题。

### 14.2 为什么用非对称协商、对称传输

非对称密码适合身份和密钥协商，但计算昂贵；对称加密速度快，适合大量数据。TLS 握手安全地建立共享会话密钥，后续数据用对称算法加密并做完整性保护。

### 14.3 HTTPS 看不到什么、看得到什么

中间网络通常仍能看到目标 IP、连接时间、流量大小等元数据，但看不到 HTTP 路径、Header 和 Body 的明文（终止 TLS 的反向代理当然能看到）。因此敏感字段仍会在浏览器、代理、应用和数据库这些端点出现，日志与访问控制不可省略。

## 15. HTTP 缓存、并发控制与内容协商

### 15.1 缓存不只有 Redis

浏览器与代理可以使用：

- `Cache-Control: no-store`：不保存；
- `Cache-Control: private`：只允许用户私有缓存；
- `max-age`：新鲜时间；
- `ETag` + `If-None-Match`：内容版本未变化返回 304；
- `Last-Modified` + `If-Modified-Since`：按修改时间验证。

用户权限相关响应若被公共缓存错误共享，可能造成数据泄露。缓存键必须考虑租户、用户、语言和权限维度，或明确禁止共享缓存。

### 15.2 ETag 也能做乐观并发

服务端返回资源版本 `ETag: "v17"`。客户端更新时带 `If-Match: "v17"`。若当前已是 v18，服务端拒绝更新，避免静默覆盖。这和数据库 rowversion 思想相同，只是把并发版本带到了 HTTP 合同。

### 15.3 400、409 与 422 如何选择

- JSON 无法解析、类型错误：400；
- 请求语法正确，但和当前资源状态冲突：409；
- 422 常用于语法正确但语义校验失败，但团队要保持一致。

比状态码细枝末节更重要的是稳定错误合同，例如 `code`、`message`、`traceId`、字段错误列表。前端不应解析自然语言判断错误类型。

## 16. 浏览器事件循环：用时间线看懂竞态

执行：

```ts
console.log('A')
setTimeout(() => console.log('B'), 0)
Promise.resolve().then(() => console.log('C'))
console.log('D')
```

结果通常是：

```text
A
D
C
B
```

原因：当前调用栈先执行完，所以 A、D 先出；Promise 回调是微任务，在本轮栈清空后先执行；timer 回调进入后续任务。

`await` 可以理解为：当前 async 函数暂停，函数先返回 Promise；被等待 Promise 完成后，`await` 后的代码作为延续进入微任务。

### 搜索竞态完整解法

```ts
let controller: AbortController | null = null

async function search(keyword: string) {
  controller?.abort()
  controller = new AbortController()

  loading.value = true
  try {
    rows.value = await http.get('/stocks', {
      params: { keyword },
      signal: controller.signal
    })
  } catch (error: any) {
    if (error.code !== 'ERR_CANCELED') throw error
  } finally {
    // 更严谨的实现还需确保旧请求不能把新请求的 loading 改成 false。
    loading.value = false
  }
}
```

最后一句提示非常关键：即使取消了旧请求，它的 `finally` 仍可能运行。可结合版本号，只允许当前版本修改 `loading`。这就是“能运行”与“并发下正确”的差别。

## 17. 从浏览器到 CP6 `Program.cs`

CP6 请求末端的关键顺序是：

```csharp
app.UseHttpMetrics();
app.UseAuthentication();
app.UseMiddleware<TenantMiddleware>();
app.UseRequestLocalization(...);
app.UseMiddleware<BizExceptionMiddleware>();
app.UseMiddleware<CsrfMiddleware>();
app.UseMiddleware<MustChangePasswordMiddleware>();
app.UseAuthorization();
app.MapControllers();
```

逐层理解：

1. 指标包住后续请求，记录时长与状态；
2. Authentication 解析凭证并建立 `User`；
3. TenantMiddleware 才能从已认证 claim 得到当前租户；
4. 本地化确定后续错误消息语言；
5. 异常中间件包住下游，把业务异常转统一响应；
6. CSRF 在写请求进入业务前检查；
7. 强制改密策略阻止受限用户执行其他功能；
8. Authorization 根据已建立的身份与权限决定是否放行；
9. 最后匹配 Controller。

顺序不是审美。若租户中间件放在认证前，`User` 还没有 claim；若异常中间件放在会抛异常组件之后，它捕获不到异常；若授权在认证之前，系统没有身份可供判断。

## 19. 面试题 15 问（含答案骨架）

### 1. 进程和线程区别是什么？

进程是资源与地址空间隔离单位；线程是调度单位。同进程线程共享堆和句柄，各有栈和寄存器。项目中 WebApi 是进程，请求主要由线程池线程执行，异步 I/O 等待期间不占线程。

### 2. `await` 会创建线程吗？

不必然。真正异步 I/O 由 OS/驱动等待完成，`await` 保存状态并归还线程；结果就绪后由可用线程恢复延续。CPU 工作若主动 `Task.Run` 才会在线程池安排工作。

### 3. GC 语言为什么仍会内存泄漏？

GC 只回收不可达对象。静态集合、事件订阅、缓存和闭包如果错误持有引用，对象仍可达，就会持续占内存。

### 4. TCP 为什么三次握手而不是两次？

双方都要确认自己的发送与接收路径有效并同步初始序列号。第三次 ACK 让服务端知道客户端已收到服务端的 SYN/ACK，避免只完成单向确认。

### 5. TCP 可靠，HTTP 为什么仍超时？

可靠是连接存续时对字节传输的语义，不保证服务进程不崩、网络永不分区或业务在时限内完成。超时是资源预算与失败边界。

### 6. HTTPS 解决了什么？

通道机密性、完整性和服务器身份验证；不替代应用鉴权、输入校验、日志脱敏和端点安全。

### 7. 401 与 403？

401 表示缺少有效认证；403 表示身份已知但不允许该操作。出于防枚举策略，某些资源越权也可能统一返回 404，需团队明确。

### 8. 502 与 504？

502 是代理没得到有效上游响应，如连接拒绝或协议错误；504 是代理等待上游超过期限。结合代理与应用日志判断，不能只看页面文案。

### 9. CORS 能防 Postman 调接口吗？

不能。CORS 是浏览器执行的跨源读取规则，Postman/服务端客户端不受它约束。真正访问控制依赖认证授权。

### 10. Cookie 和 JWT 是对立选择吗？

不是。Cookie 是浏览器存储与自动携带机制，JWT 是 token 格式。JWT 可以存 Cookie；Cookie 也可以存不透明 session id。

### 11. 为什么不能无限重试？

持续故障时会放大流量，增加队列和资源占用；非幂等写可能重复副作用。重试应限定错误、次数、退避、抖动与总预算。

### 12. 为什么复用 HttpClient？

复用底层连接，避免反复 TCP/TLS 握手和端口耗尽。通过工厂管理 handler 生命周期，也能处理 DNS 变化与策略配置。

### 13. 页面旧数据覆盖新数据是什么问题？

异步响应乱序竞态。请求发出顺序不等于返回顺序；用取消、版本号或只接受最新请求解决。

### 14. 为什么中间件顺序重要？

中间件是嵌套管线，上游决定下游能看到的上下文，也只有包住下游才能处理其响应/异常。CP6 的租户解析必须在认证后，授权也必须在认证后。

### 15. 页面一直转圈怎么查？

先 Network 判断请求是否发出、状态与耗时，再分 DNS/TCP/TLS、代理、应用、数据库/依赖与资源层。每层用日志/指标/命令获取证据，不先重启破坏现场。

## 20. 章末练习参考答案

### 练习 1：画请求链路

合格图至少包含：Vue 事件 → axios 拦截器 → DNS → TCP → TLS → 反向代理 → Authentication → Tenant → CSRF → Authorization → Controller → EF → 连接池 → SQL Server → JSON → Promise 微任务 → Vue 渲染。每段标一个超时/错误。

### 练习 2：写操作超时如何安全重试

客户端为一次业务意图生成稳定幂等键；服务端用租户 + 操作 + key 建唯一约束，记录处理中/成功及结果摘要。客户端超时后先查询或携同 key 重试；服务端返回原结果，不能再次扣库存。

### 练习 3：解释 CP6 并发 refresh

共享 `refreshPromise` 是单航班（single-flight）思想：同一时刻只有首个调用实际执行 refresh，其他调用共享结果；成功后各自重放，失败统一清状态。`_retried` 是循环保险丝。
