# 第 3 章：测试体系与可测试代码——证明系统真的正确

> “我测过了”不是证据。高质量工程师能说明测了哪一层、隔离了什么、覆盖哪些风险、失败时如何定位。测试目标不是追求漂亮的覆盖率，而是用合理成本阻止重要回归。

## 1. 测试全景

| 层级 | 验证对象 | 特点 | CP6 场景 |
|---|---|---|---|
| 单元测试 | 一个纯业务单元 | 快、隔离、定位准 | 库存规则、金额计算 |
| 集成测试 | 多组件及真实基础设施边界 | 较慢、可信度高 | API + EF + SQL Server |
| 契约测试 | 系统间接口格式 | 阻止不兼容变更 | OpenAPI、消息事件 |
| 端到端测试 | 用户真实关键路径 | 最慢、最接近用户 | 登录→建单→审核 |

合理组合是大量单元测试、适量集成测试、少量关键 E2E。按风险分配，而不是每个方法机械复制三层测试。

## 2. Arrange–Act–Assert

```csharp
[Fact]
public void Deduct_WhenQuantityExceedsAvailable_ShouldReject()
{
    // Arrange
    var stock = new StockBalance(available: 5);

    // Act
    var act = () => stock.Deduct(6);

    // Assert
    act.Should().Throw<InsufficientStockException>();
}
```

好测试应当快速、独立、可重复、自验证。测试名表达“条件—行为—结果”，失败时不用先读实现就知道哪条规则坏了。

不要只断言“抛了异常”，还要验证异常类型、错误码以及状态没有被部分修改。不要让测试依赖当前日期、时区、执行顺序或另一测试留下的数据。

---

## 3. 什么应该 mock

Mock 用于隔离不稳定、昂贵或不可控的边界，例如外部支付、当前时间、消息发布端口。不要 mock 自己拥有的每个 class，否则测试只是在验证“mock 按设置返回”。

- 纯领域规则：不 mock，直接构造对象；
- 数据库查询翻译、事务和约束：用真实测试数据库；
- 外部 HTTP：用 fake server/受控 handler；
- 当前时间：注入 `TimeProvider`；
- 随机 ID：注入生成器，或只断言格式与唯一性。

EF Core InMemory provider 不是关系数据库：它不能完整模拟 SQL 翻译、外键、事务和 SQL Server 特性。验证数据库风险时，应使用隔离的真实 SQL Server 实例或测试容器。

## 4. 库存扣减测试矩阵

| 场景 | 输入 | 预期 |
|---|---|---|
| 正常 | 可用 10，扣 3 | 剩 7 |
| 边界 | 可用 10，扣 10 | 剩 0 |
| 超量 | 可用 10，扣 11 | 拒绝且不改变 |
| 非法数量 | 扣 0 或负数 | 参数错误 |
| 并发 | 两次同时扣 7 | 至多一次成功 |
| 重复请求 | 同一幂等键两次 | 只扣一次，结果一致 |
| 跨租户 | A 身份操作 B 库存 | 拒绝且数据不变 |
| 中途故障 | 扣多项时第 2 项失败 | 全部回滚 |

“正常路径通过”远远不够。最值钱的是边界、并发、权限和失败后的状态。

## 5. ASP.NET Core 集成测试

集成测试应启动真实应用管线，覆盖路由、模型绑定、中间件、认证授权、DI、序列化和数据库行为。典型工具是 `WebApplicationFactory<Program>`。

```csharp
public class StockApiTests : IClassFixture<WebApplicationFactory<Program>>
{
    private readonly HttpClient _client;

    public StockApiTests(WebApplicationFactory<Program> factory)
    {
        _client = factory.WithWebHostBuilder(builder =>
        {
            builder.UseEnvironment("Testing");
            // 在测试扩展中替换数据库、认证与外部服务。
        }).CreateClient();
    }

    [Fact]
    public async Task GetStock_WithoutAuthentication_Returns401()
    {
        var response = await _client.GetAsync("/api/stocks");
        response.StatusCode.Should().Be(HttpStatusCode.Unauthorized);
    }
}
```

必须覆盖的不只是 200：还包括 400、401、403、404、409、统一错误结构、租户隔离、事务失败无部分提交、取消和超时传播。

测试数据策略：每个测试使用唯一租户/业务键；运行前迁移测试库；运行后事务回滚或可靠清理；不共享会被并发修改的固定记录。

## 6. 数据库测试重点

以下行为需要真实数据库证明：

- LINQ 能否翻译成目标 SQL；
- 唯一索引、外键、CHECK 约束；
- 事务回滚与隔离级别；
- 并发 token/受影响行数；
- 迁移 Up 与 Down；
- 原生 SQL 和存储过程；
- 查询计划是否使用目标索引。

并发测试要用两个独立 DbContext/连接同时操作。不要在同一个 DbContext 上 `Task.WhenAll`，那只会证明 DbContext 不是线程安全的，并没有验证数据库并发策略。

## 7. Vue 单元与组件测试

前端测试优先验证用户可观察行为，不锁死内部实现。

```ts
it('非法数量时显示错误且不调用 API', async () => {
  const wrapper = mount(OutboundForm)
  await wrapper.get('[data-test=qty]').setValue('-1')
  await wrapper.get('[data-test=submit]').trigger('click')

  expect(wrapper.text()).toContain('数量必须大于 0')
  expect(api.postOutbound).not.toHaveBeenCalled()
})
```

优先通过可访问角色、标签或稳定的 `data-test` 查询，避免依赖 Element Plus 内部 class。组件重构布局后，业务行为未变，测试就不应全部破碎。

每个数据页面至少测试四态：加载、空数据、失败、成功。此外覆盖按钮权限、快速重复点击、旧请求晚返回、表单边界、路由参数变化和卸载后的异步清理。

## 8. E2E 测试

E2E 只保留关键路径：登录 → 选择租户/仓库 → 新建出库单 → 提交 → 验证库存和审计。

稳定性原则：

- 不使用固定 sleep，等待明确 UI 状态或网络响应；
- 数据通过 API/fixture 准备，不依赖前一测试；
- 失败保留截图、视频、trace 与服务端 trace ID；
- 第三方服务在非契约测试中用受控替身；
- flaky 失败不能靠“重跑到绿”结案。

---

## 9. 契约与版本兼容

前后端常见回归是字段改名、类型变化、可空性变化和错误格式变化。可从 OpenAPI 生成类型，在 CI 检查 schema diff，并为关键消费者建立契约测试。

安全演进采用 expand/contract：先新增兼容字段 → 消费者迁移 → 观察旧字段无调用 → 再删除。数据库列和消息事件也一样，避免一次部署要求所有组件瞬时切换。

---

## 10. 测试反模式

- 只看覆盖率，不看断言质量；
- 一个测试验证十个场景，失败难定位；
- 测私有方法而非公开行为；
- mock 整条调用链，重构即全碎；
- 依赖当前日期、时区、共享状态或执行顺序；
- E2E 用固定等待掩盖竞态；
- 捕获异常却不验证类型与最终状态；
- 让测试连接生产数据库。

覆盖率不是正确率。它只能告诉你哪些代码没跑到，不能证明跑到的代码被有效断言。高风险业务不变量、权限、资金/库存、并发与恢复路径优先级最高。

## 11. 实战任务与面试验收

选择 CP6 一个“创建/提交”用例，补齐：

1. 服务单元测试：正常、边界、非法、重复；
2. API 集成测试：200/400/401/403/409；
3. 数据库测试：唯一约束、并发和回滚；
4. 前端组件测试：加载、失败、重复点击；
5. 一条 E2E 核心路径。

面试问：“单元测试为什么不连数据库？”

答题骨架：单元测试要快速隔离地验证业务规则；真实数据库会引入网络、状态和速度，使失败原因不明确。但数据库语义必须由集成测试验证，二者分工而非替代。

最终验收：能为新功能先列测试矩阵；能解释 mock 边界；能演示一次测试先红后绿；能说明一次真实回归是被哪一层测试阻止的。

## 12. 测试不是代码数量，而是一条证据链

假设需求是“同一库位编码在同一租户内不可重复”。不同测试提供的证据不同：

1. 领域单元测试能证明校验函数会拒绝重复；
2. EF InMemory 测试能证明服务按预期调用；
3. SQL Server 集成测试才能证明真实唯一索引在并发绕过应用校验时仍会挡住；
4. API 测试证明数据库异常被翻译为稳定的 409/业务错误；
5. 页面测试证明用户看到可理解提示而不是无限 loading。

任何一层都不能独自证明完整行为。测试策略的核心问题不是“写不写测试”，而是“这个风险由哪一层最经济、最可信地证明”。

## 13. xUnit 的执行模型与生命周期

### 13.1 `[Fact]` 与 `[Theory]`

固定场景用 Fact：

```csharp
[Fact]
public void ZeroQuantity_ShouldBeRejected() { ... }
```

同一规则的多组输入用 Theory：

```csharp
[Theory]
[InlineData(0)]
[InlineData(-1)]
[InlineData(-999)]
public void NonPositiveQuantity_ShouldBeRejected(decimal qty)
{
    var act = () => Quantity.Create(qty);
    Assert.Throws<ArgumentOutOfRangeException>(act);
}
```

不要为了减少行数把不同业务原因硬塞到 Theory。若失败后的预期和解释不同，应拆成独立测试。

### 13.2 每个测试实例与共享 fixture

xUnit 通常为每个测试方法创建新的测试类实例，因此构造函数字段适合测试初始化，但不能假设一个测试修改的实例字段会留给下一个。

昂贵且可安全共享的环境可用 `IClassFixture<T>`；跨类共享可用 collection fixture。共享越多，测试间污染与并行冲突风险越高，必须明确数据隔离。

### 13.3 异步测试必须返回 Task

错误：

```csharp
[Fact]
public async void Save_ShouldWork() { ... }
```

正确：

```csharp
[Fact]
public async Task Save_ShouldWork() { ... }
```

`async void` 的异常不通过可等待 Task 返回给测试框架，完成时机和异常捕获都可能错误。只有事件处理器才通常需要 `async void`。

## 14. CP6 RetryWorker 测试逐段解析

真实文件：`CP6.Tests/IntegrationEventRetryWorkerTests.cs`。

### 14.1 为什么每个测试使用唯一数据库名

```csharp
private static DbContextOptions<CP6Context> NewOptions()
{
    return new DbContextOptionsBuilder<CP6Context>()
        .UseInMemoryDatabase(Guid.NewGuid().ToString())
        .Options;
}
```

InMemory provider 按名称共享数据。每次使用新 Guid，使测试之间不会看到对方事件。若写死 `"test"`，并行/顺序运行会积累数据，出现“单独运行通过、整套运行失败”。

### 14.2 Arrange 做了什么

测试创建一条已失败且到期的事件：

```csharp
NewFailedEvent(
    attempts: 1,
    nextRetryAt: DateTime.UtcNow.AddSeconds(-5))
```

dispatcher mock 返回 true，表达“这次派发成功”；notifier mock 用于确认不应触发死信通知。测试容器还注册 TenantContext/Enumerator，因为 Worker 会按租户创建 scope。

这是一种好 Arrange：它不是随便塞数据，而是精确构造状态机的起点。

### 14.3 Act 为什么短暂启动 Worker

```csharp
await worker.StartAsync(cts.Token);
await Task.Delay(200, CancellationToken.None);
await worker.StopAsync(CancellationToken.None);
```

它验证 `BackgroundService` 启动循环能实际触发处理。但固定 200ms 仍可能成为慢机器下的 flaky 风险。更可测试的结构是把单轮 `ProcessOnceAsync` 作为独立入口直接调用，循环/延迟只做少量生命周期测试。

这说明可测试性来自设计：把无限循环与“一轮业务逻辑”拆开，测试无需真的等 60 秒。

### 14.4 Assert 不只看状态

成功测试断言：

- Status 变 SUCCESS；
- Attempts 从 1 变 2；
- NextRetryAt 清空。

死信测试还验证 notifier 恰好调用一次：

```csharp
notifier.Verify(
    n => n.NotifyAsync(
        It.IsAny<IntegrationEvent>(),
        It.IsAny<CancellationToken>()),
    Times.Once);
```

状态断言证明数据，交互断言证明重要外部副作用。不要对所有内部调用都 Verify，那会把测试绑死在实现步骤上。

### 14.5 这个测试没有证明什么

InMemory 测试没有证明：

- LINQ 会被 SQL Server 正确翻译；
- 多实例能否重复领取同一事件；
- 数据库事务、锁和唯一索引行为；
- 真实时钟边界是否稳定；
- notifier 失败时 SaveChanges 的最终状态。

高质量面试回答会主动说明测试证据边界，而不是因测试绿色就宣称生产正确。

## 15. Mock 的行为验证与状态验证

### 15.1 状态验证优先

输入后检查返回值或最终状态，通常比验证内部调用稳定：

```csharp
var result = service.Calculate(...);
Assert.Equal(expectedTotal, result.Total);
```

### 15.2 何时验证交互

当外部交互本身就是契约时验证：支付只能扣一次、死信必须通知、权限失败绝不能调用仓储。

```csharp
repository.Verify(r => r.SaveAsync(It.IsAny<Order>(), ct), Times.Never);
```

### 15.3 严格 mock 还是宽松 mock

严格 mock 对未设置调用立即失败，适合窄而稳定的协议；但重构时脆弱。宽松 mock 默认返回空值，测试更易写，却可能让意外调用静默通过。

实用做法：对安全/资金/外部副作用显式 Verify，对普通查询以最终状态为主。

### 15.4 不要 mock `IQueryable`

手工 mock EF `DbSet`/`IQueryable` 很容易模拟错误的 LINQ 语义。查询逻辑更适合 SQLite/SQL Server 集成测试，业务规则则从查询中提取为纯函数单测。

## 16. CP6 真 SQL Server 测试为什么必要

`CP6.Tests/Infra/SqlServerFactAttribute.cs` 用环境变量门控真实 SQL Server 测试。注释明确列出 SQLite 无法覆盖：过滤唯一索引、NULL 中转换码、原生 rowversion。

### 16.1 环境门控

```csharp
if (string.IsNullOrEmpty(
    Environment.GetEnvironmentVariable("CP6_TEST_SQLSERVER")))
{
    Skip = "设 CP6_TEST_SQLSERVER=<连接串> 以运行真库集成测试";
}
```

优点：普通开发环境没有 SQL Server 时不误失败；提供环境后自动运行。风险：如果 CI 永远不配置，它们会永远 Skip，团队误以为绿色。CI 应至少有一个专门 job 强制运行真库套件，并对异常 skip 数告警。

### 16.2 每个测试类建唯一临时库

`SpaceSqlIntegrationTests` 从基础连接串派生 `CP6Test_{Guid}` 数据库。隔离真实 schema 与数据，结束删除。

这比所有测试共享一个 `CP6Test` 更可靠，但要处理：

- 测试崩溃后的孤儿数据库清理；
- 并行建库压力；
- 迁移耗时；
- 删除前强制断开连接的安全实现。

绝不能让测试连接串指向生产库。可额外验证数据库名必须匹配测试前缀，形成硬保护。

### 16.3 rowversion 测试证明了什么

真实测试使用两个 DbContext 读取同一行：

```text
ctxA 读取 RowVersion=V1
ctxB 读取 RowVersion=V1
ctxA 更新成功，DB 生成 V2
ctxB 更新：WHERE Id=@id AND RowVersion=V1
影响 0 行 → DbUpdateConcurrencyException
```

这才证明 SQL Server 的并发 token 生效。同一个 DbContext 修改两次不能模拟并发，因为它只有一个跟踪快照。

### 16.4 唯一索引测试比“先查重复”更重要

两个并发请求都可能在“先查”时看不到对方尚未提交的数据。唯一索引由数据库在最终写入点裁决，应用校验主要提供友好错误，约束才是最后防线。

## 17. 如何写一个真正的 API 集成测试

测试对象应包括：路由 → 模型绑定 → 中间件 → 认证授权 → Controller → Service → 数据库 → 错误响应。

### 17.1 测试启动

```csharp
public sealed class ApiFactory : WebApplicationFactory<Program>
{
    protected override void ConfigureWebHost(IWebHostBuilder builder)
    {
        builder.UseEnvironment("Testing");
        builder.ConfigureServices(services =>
        {
            // 移除生产 CP6Context 注册，加入测试数据库。
            // 替换 Kafka/RabbitMQ/外部 HTTP，不替换被测业务服务。
        });
    }
}
```

关键是替换**基础设施边界**，不要把 Controller 下所有服务都 mock 掉，否则只测试路由壳。

### 17.2 认证策略

两类测试都要有：

- 真登录/真 JWT 路径：少量，证明整个认证合同；
- 测试认证 handler：大量授权组合，快速构造 claims。

测试 handler 必须明确租户、用户、角色、权限 claims，避免默认“超级管理员”让越权测试失去意义。

### 17.3 错误合同断言

```csharp
var response = await client.PostAsJsonAsync(url, body);
Assert.Equal(HttpStatusCode.Conflict, response.StatusCode);

var problem = await response.Content
    .ReadFromJsonAsync<ProblemDetails>();
Assert.Equal("E-WMS-STOCK-CONFLICT", problem!.Extensions["code"]);
Assert.False(string.IsNullOrWhiteSpace(
    problem.Extensions["traceId"]?.ToString()));
```

不要只断言 `!response.IsSuccessStatusCode`。状态、稳定业务码和 traceId 都是前后端合同。

### 17.4 跨租户负向测试

```text
Arrange：租户 B 创建库存记录
Act：租户 A token 用 B 的 ID 查询/更新
Assert：404/403；B 数据完全不变；日志能审计但响应不泄露敏感详情
```

负向测试比“每个租户能读自己的数据”更能证明隔离。

## 18. 前端测试：从 CP6 `CpFilterBar.spec.ts` 学行为测试

真实测试验证的不只是“组件能 mount”：

### 18.1 事件合同

```ts
await findButton(w, '查询').trigger('click')
expect(w.emitted('search')).toEqual([[]])
```

它证明父组件可以依赖 `search` 事件。事件名或 payload 变化会立即暴露。

### 18.2 不修改 props

```ts
const model = { q: '' }
// ...输入 SHP-9
expect(payload).not.toBe(model)
expect(model.q).toBe('')
```

这条测试证明组件发出新对象，没有偷偷修改父传入对象。它保护的是 Vue 单向数据流，而非某个 DOM class。

### 18.3 边界行为

测试 fields ≤ 4 时没有展开按钮，>4 时先隐藏、多点一次再显示；日期 valueFormat 返回字符串而非 Date；number 返回数值而不是输入框字符串。

这类测试来自真实坑：UI 看起来一样，数据类型错会在 API 层才爆炸。好测试关注边界与合同。

### 18.4 哪些选择器比较脆弱

测试里 `.fld`、`.el-range-input` 依赖内部 class。对自有稳定 class 尚可；依赖第三方组件内部 DOM 时，Element Plus 升级可能让测试因结构变化失败。

优先级：可访问角色/label → 自有 `data-test` → 稳定自有 class → 第三方内部 class。不是绝对禁止，而是知道维护代价。

## 19. Playwright E2E：真实浏览器不等于完整业务

CP6 `golden-path.spec.ts` 有两个层次：

1. 按 ERP → MES → WMS 顺序打开页面，验证没有被踢回登录、Layout 和页面内容存在；
2. 通过 API 只读断言取引先、制造指图和库存数据存在。

它是一组很有价值的**跨模块 smoke/golden path**，能快速发现路由、登录态和页面崩溃。但要准确描述证据：打开页面并不等于真的完成一次新建/过账；API 有数据也不一定是本次测试创建的。

如果要证明出库事务，应补独立 E2E：创建唯一测试单 → 提交 → UI 显示 Posted → API/DB 确认库存变化 → 清理。测试名和文档应区分“页面烟测”与“业务交易 E2E”。

### 19.1 为什么禁止固定 sleep

```ts
await page.waitForTimeout(5000)
```

机器快时浪费 5 秒，机器慢时仍会失败。应等待有业务意义的条件：

```ts
await Promise.all([
  page.waitForResponse(r =>
    r.url().includes('/api/wms/outbounds') && r.status() === 201),
  page.getByRole('button', { name: '提交' }).click()
])
await expect(page.getByText('过账成功')).toBeVisible()
```

等待网络成功还不够，继续断言用户最终看到的状态。

## 20. 时间、随机与并发测试

### 20.1 不要把 `DateTime.UtcNow` 散落在业务规则

注入 `TimeProvider`：

```csharp
public sealed class RetryPolicy(TimeProvider clock)
{
    public bool IsDue(IntegrationEvent e) =>
        e.NextRetryAt <= clock.GetUtcNow().UtcDateTime;
}
```

测试使用可控时间，不必真的等待一分钟，也不会在断言前后跨过边界。

### 20.2 随机测试必须可复现

若用随机生成业务输入，失败时记录 seed。不能只说“跑一万次有一次失败”却无法重现。属性测试适合验证金额、数量、状态机等不变量，但仍需保留明确边界用例。

### 20.3 并发测试需要同步起跑

简单连续启动两个 Task 不保证真正重叠。可用 `Barrier`/`TaskCompletionSource` 让两个操作都完成读取后再同时提交。使用独立 DbContext 与连接，最后断言成功数和数据库最终不变量。

并发测试偶发通过不够。应循环多次、提高冲突概率，并在真实数据库执行。

## 21. 测试数据建设

推荐 fixture builder：

```csharp
var order = new OrderBuilder()
    .ForTenant(tenantA)
    .WithStatus(OrderStatus.Draft)
    .WithLine(product, quantity: 7)
    .Build();
```

Builder 给合理默认值，让每个测试只突出与场景有关的差异。不要用一个有 40 个参数的“大而全 Seed 方法”，也不要让默认值偷偷授予管理员权限。

数据库测试每次使用唯一业务键，例如测试名 + Guid；清理只删除本测试租户/前缀，避免误删他人数据。更安全的是每套测试独立数据库。

## 22. 覆盖率、变异测试与测试质量

### 22.1 分支覆盖比行覆盖更有信息

```csharp
if (stock >= qty) Approve(); else Reject();
```

执行一次 Approve 可能覆盖大多数行，却没验证 Reject。关注分支、异常和边界。

### 22.2 用“故意破坏”审查测试

把 `>=` 临时改成 `>`，把权限判断反转，把租户过滤移除。相关测试是否变红？如果不红，覆盖率再高也没保护该规则。

变异测试工具会自动进行类似改动并报告存活变异。即使不引入工具，人工对关键不变量做一次破坏实验也很有价值。

### 22.3 flaky 测试是生产信号

flaky 常暴露竞态、未等待异步、共享状态、时间边界或环境依赖。不要默认给它加重试。先保留失败 trace、找不确定性来源，再修测试或产品。

## 23. 从需求到测试的完整示范

需求：“出库过账成功后库存减少；重复请求不重复扣；库存不足返回冲突。”

### 单元层

- 数量 0/负数拒绝；
- 可用等于请求量时允许并变 0；
- 状态非 Draft 不允许过账；
- 相同幂等记录返回既有结果的领域决策。

### SQL Server 集成层

- 条件更新在两个并发请求中仅一个成功；
- 幂等唯一索引阻止两行；
- 第二物料失败时第一物料回滚；
- TenantId 参与 WHERE 与唯一键。

### API 层

- 未登录 401、无权限 403；
- 非法 body 400；
- 库存不足/版本冲突 409 + 业务码；
- 重发同 key 返回相同业务结果；
- 同 key 不同 body 返回 409；
- 响应包含 traceId。

### 前端组件层

- 提交期间按钮 disabled；
- 409 展示可操作提示并允许刷新；
- 401 refresh 成功后只重放一次；
- 组件卸载后不修改已销毁状态。

### E2E

- 创建唯一单据 → 提交 → 成功状态 → 库存减少一次；
- 浏览器层双击/网络重放仍只扣一次。

这就是“完整测试”，不是每层重复同一个断言，而是每层证明自己最擅长的风险。

## 24. 面试题 12 问（含答案）

### 1. 单元测试和集成测试区别？

前者隔离验证一个业务单元，快且定位准；后者验证组件与真实基础设施协作。不是按是否用了 mock 机械定义，关键是边界和证据。

### 2. InMemory 有什么坑？

不是真关系数据库，SQL 翻译、约束、事务、排序/比较和数据库特性可能不同。适合部分服务状态测试，不可替代目标数据库测试。

### 3. 为什么要两个 DbContext 测 rowversion？

并发本质是两个独立快照。两个上下文都读 V1，一方提交生成 V2，另一方携旧 V1 更新才会触发冲突。

### 4. 测试里是否应访问私有方法？

通常通过公开行为测试。私有方法难测往往说明职责太多，可提取独立业务对象，而非用反射绑定内部实现。

### 5. 何时 mock？

外部、慢、不稳定、不可控边界；不 mock 核心被测业务。数据库语义用集成测试，当前时间用可控抽象。

### 6. 覆盖率 100% 是否足够？

不够。可能没有有效断言、没覆盖组合/并发，或只运行每行一次。覆盖率是缺口线索，不是正确性证明。

### 7. 如何解决 flaky E2E？

保存 trace/视频，去掉固定 sleep，等待业务条件，隔离数据，控制时间和第三方依赖，调查产品竞态；不要只增加重试。

### 8. 如何测试后台 Worker？

把单轮处理与无限循环拆开，直接测试单轮状态转换；少量测试 Start/Stop 与取消；时间和 dispatcher 可控；真实数据库另测领取并发。

### 9. 如何测试多租户？

除正向外必须做跨租户负向：相同业务 ID/key、读写、缓存、后台任务、原生 SQL；断言不可见且目标数据不变。

### 10. 契约测试解决什么？

保证提供者与消费者对字段、类型、可空性和错误格式理解一致，阻止独立发布造成不兼容；不替代业务测试。

### 11. 测试数据库怎么清理？

优先每套独立临时库/容器；或事务回滚、唯一租户前缀精确清理。加硬保护，禁止生产数据库名/地址。

### 12. 测试慢怎么办？

先分类计时，缩短不必要 E2E，更多规则下沉单测，集成环境复用但数据隔离，并行安全后再并行；不能直接删除高价值测试。

## 25. 章末实操作业（带验收答案）

### 作业 A：给 RetryWorker 补异常测试

当 dispatcher 抛普通异常时，应断言 Status=FAILED、Attempts+1、LastError 有值、NextRetryAt 后移；未达到上限不通知。达到上限则 DEADLETTER、NextRetryAt=null、通知一次。

### 作业 B：证明 InMemory 的边界

写一条依赖 SQL Server filtered unique index/rowversion 的测试，先在 InMemory 运行，再在 SQL Server 运行，记录差异。答案不是“哪个 provider 更好”，而是不同 provider 能证明什么。

### 作业 C：前端 props 不变性

构造父组件传入 model，修改筛选字段后断言父原对象未被直接改、emit payload 是新对象。再删除复制逻辑让测试变红，证明测试有效。

### 作业 D：核心交易 E2E

测试创建自己唯一的数据，真正提交一次交易，验证 UI 与 API 最终状态，并清理。不能只打开页面或依赖预置数据。

只有当你能说明每条测试防住的具体回归，才算完成本章。
