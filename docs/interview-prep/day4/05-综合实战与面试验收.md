## 1. 综合项目：可靠的出库过账

### 需求

- Vue 页面录入仓库、物料和数量；
- API 校验身份、权限和租户；
- SQL Server 原子扣库存，不允许负数；
- 重复点击或网络重试不能重复过账；
- 成功后发送事件供审计/报表消费；
- 每次请求可追踪耗时与失败原因；
- 具备单元、集成和 E2E 测试。

### 先写不变量

1. 库存永不为负；
2. 单据只能从 Draft 合法转到 Posted；
3. 同一租户内业务单号唯一；
4. 同一幂等键只产生一次副作用；
5. A 租户不能读取或修改 B 租户数据；
6. 业务提交与 Outbox 事件同事务；
7. 重复消息不重复产生消费副作用。

如果不变量没有写清楚，就无法判断设计是否正确。

- 日志、指标、trace 和告警；
- 测试矩阵；
- 部署与回滚步骤。

参考主链路：

```text
Vue 防重复点击（体验层）
  → POST /api/outbounds/{id}/post
     Headers: Idempotency-Key, Authorization
  → trace、异常、认证、租户中间件
  → PostOutbound 授权
  → Service 开事务
     ├─ 幂等记录唯一约束
     ├─ 校验单据状态与租户
     ├─ 原子条件 UPDATE 扣库存
     ├─ 单据置 Posted
     ├─ 写审计
     └─ 写 Outbox
  → Commit → 200/409

Outbox Publisher → MQ → Consumer
                          ├─ Inbox 去重
                          ├─ 更新报表
                          └─ 失败重试/死信/告警
```

前端按钮置灰只能减少误操作；最终正确性由服务端幂等、状态机、条件更新和数据库唯一约束保证。

## 3. 失败注入清单

对每一点回答“用户看到什么、数据是什么状态、如何恢复”：

1. 请求到达服务端前网络断开；
2. 数据库提交成功但响应返回前断开；
3. 扣第二个物料时库存不足；
4. 两个请求同时过账同一单据；
5. 数据提交后进程立刻崩溃；
6. MQ 暂时不可用；
7. 消费成功但确认消息前崩溃；
8. 报表消费者持续失败；
9. A 租户伪造 B 的单据 ID；
10. 新版本部署时数据库仍是旧 schema。

若任一点可能造成重复扣减、永久丢事件、部分提交或跨租户读取，方案就还没闭环。

## 5. 面试口述

### 30 秒版本

“我做出库过账时先定义库存不为负、单据不可重复过账、租户严格隔离三个不变量。主事务用条件更新扣库存，同时更新单据并写 Outbox；请求用幂等键和唯一约束防网络重试。后台发布事件，消费者用 Inbox 去重。前端禁用按钮只是体验优化，正确性在服务端和数据库。链路有 trace、延迟与积压告警，并用并发和故障注入测试验证。”

### 2 分钟结构

1. 业务背景与规模；
2. 不变量；
3. 主链路；
4. 并发与幂等；
5. 事件与失败恢复；
6. 安全与租户；
7. 测试与观测；
8. 一个明确权衡。

### 追问：为什么不用分布式事务？

本地库存、单据和 Outbox 位于同一 SQL Server，用本地事务保证强一致。报表和通知允许秒级最终一致，用 Outbox 重试与消费幂等。分布式事务扩大协调和故障范围，外部系统也未必支持。若业务确实要求跨系统瞬时一致，应先重新确认不变量，再评估 Saga/补偿或把强一致数据收回同一边界。

## 9. 第一步：把模糊需求改成可验证规格

原始说法：“做一个出库过账，不能超卖，要可靠。”

这句话无法编码，因为“可靠”没有边界。先问：

1. 一张出库单能否分批过账？
2. 一行物料能否拆多个库位/批次？
3. 库存不足是整单失败还是部分成功？
4. 网络超时后客户端如何查询结果？
5. 过账成功后哪些下游必须同步，哪些可延迟？
6. 取消/冲销是修改原记录还是新增反向交易？
7. 同一单据是否允许两个人同时操作？

本教程采用以下明确决策：

- v1 整单一次过账，不做分批；
- 每行已明确库位与批次；
- 任一行失败整单回滚；
- 单据状态 Draft → Posted，Posted 不可再次直接修改；
- 库存、单据、库存流水、持久化事件同一 SQL Server 本地事务；
- 报表/通知最终一致；
- 冲销通过独立 Reversal 交易，不删除原审计事实。

现在才能写验收标准：

```gherkin
Given 单据为 Draft，库位 A 有 10 件
When 用户以幂等键 K 过账 7 件
Then 单据为 Posted，库存为 3，产生一条 -7 流水和一条待发布事件

When 相同请求以相同 K 重发
Then 返回第一次结果，库存仍为 3

When 另一个请求试图再过账同一单据
Then 返回 409，库存不变
```

## 10. 第二步：设计数据，而不是先写 Controller

### 10.1 单据头

```text
OutboundOrder
Id             uniqueidentifier PK
TenantId       uniqueidentifier NOT NULL
OutboundNo     nvarchar(...) NOT NULL
Status         tinyint NOT NULL     Draft/Posted/Reversed
PostedAtUtc    datetime2 NULL
PostedBy       nvarchar(...) NULL
RowVersion     rowversion
```

约束：同租户 `UNIQUE(TenantId, OutboundNo)`。RowVersion 用于防止两个操作者基于同一旧版本修改。

### 10.2 库存余额

```text
Stock
TenantId, WarehouseCd, LocationCd, ProductCd, LotNo
PhysicalQty
AllocatedQty
RowVersion
```

业务可用量可能是 `PhysicalQty - AllocatedQty - HoldQty`，必须由 CP6 实际领域定义决定。不能在不同页面各写一套公式。

### 10.3 库存流水

余额表示现在有多少，流水解释为何变成这样：

```text
StockTransaction
Id / TenantId / StockId
BusinessType = OutboundPost
BusinessId / BusinessNo
Quantity = -7
OccurredAtUtc / Operator / CorrelationId
```

不要通过覆盖余额丢掉历史。对账时应能从交易事实解释余额差异。

### 10.4 幂等记录

```text
IdempotencyRecord
TenantId
Operation        "outbound-post"
IdempotencyKey
RequestHash
Status           Processing/Completed/Failed
ResourceId
ResponseJson 或 ResultCode
CreatedAt/ExpiresAt
```

唯一约束：`(TenantId, Operation, IdempotencyKey)`。RequestHash 防止调用者错误地用同一 key 提交不同 body。

### 10.5 待发布事件

事件至少含稳定 EventId、TenantId、类型、聚合 ID、schemaVersion、payload、发生时间和发布状态。业务数据和事件行必须同事务写入，才能关闭 DB 成功/MQ 失败的窗口。

## 12. 第四步：服务端事务骨架

下面用伪真实 C# 表达边界，具体实体名按 CP6 调整：

```csharp
public async Task<PostOutboundResult> PostAsync(
    Guid outboundId,
    string idempotencyKey,
    byte[] expectedVersion,
    CancellationToken ct)
{
    ValidateIdempotencyKey(idempotencyKey);

    await using var tx = await _db.Database.BeginTransactionAsync(ct);

    var idem = await FindIdempotencyAsync(idempotencyKey, ct);
    if (idem?.Status == Completed)
        return DeserializeResult(idem.ResponseJson);

    if (idem is null)
    {
        _db.IdempotencyRecords.Add(NewProcessingRecord(...));
        // 唯一约束处理并发插入；不能只依赖前置查询。
        await _db.SaveChangesAsync(ct);
    }

    var order = await _db.OutboundOrders
        .Include(x => x.Lines)
        .SingleOrDefaultAsync(x => x.Id == outboundId, ct)
        ?? throw NotFound();

    EnsureDraftAndVersion(order, expectedVersion);

    foreach (var line in order.Lines.OrderBy(x => x.StockId))
    {
        var affected = await DeductAtomicallyAsync(line, ct);
        if (affected != 1)
            throw InsufficientStock(line);

        _db.StockTransactions.Add(ToTransaction(line));
    }

    order.Post(...);
    _db.IntegrationEvents.Add(ToPersistedEvent(order));

    var result = ToResult(order);
    CompleteIdempotency(result);

    await _db.SaveChangesAsync(ct);
    await tx.CommitAsync(ct);
    return result;
}
```

### 12.1 为什么按 StockId 排序

两张单据若同时扣相同的多行库存，但更新顺序不同：

```text
事务 A 锁库存 1，等库存 2
事务 B 锁库存 2，等库存 1
```

形成死锁。统一按稳定键排序不能消除所有死锁，但能显著减少锁环。应用仍需识别死锁并在幂等保护下有限重试。

### 12.2 为什么事件在事务内、发布在事务外

事务内只写事件行，不调用 Kafka/RabbitMQ。远程调用会延长锁并且无法与 SQL 原子提交。后台发布器提交后再发送，失败保留状态重试。

### 12.3 `SaveChanges` 为什么可能不止一次

为抢占幂等唯一键可能先保存 Processing 记录。但若它与业务事务在同一连接事务内，后续失败会一起回滚，下一次请求可重新尝试。若团队希望失败也保留幂等状态，需要另行设计事务边界；不能含糊。

### 12.4 CancellationToken 的边界

在提交前，取消可以停止不必要查询；提交开始后，不应让客户端断开造成“业务状态未知且无人记录”。数据库驱动的取消与事务结果必须被正确处理。无论客户端是否仍连接，最终状态要可查询、可幂等重放。

## 13. 第五步：原子扣减

概念 SQL：

```sql
UPDATE T_Stock
SET PhysicalQty = PhysicalQty - @qty,
    ModifyDate = SYSUTCDATETIME(),
    Modifier = @user
WHERE TenantId = @tenantId
  AND Id = @stockId
  AND PhysicalQty - AllocatedQty >= @qty;
```

必须检查受影响行数。0 行可能是不存在、跨租户、库存不足或并发变化；服务层可先用可信查询区分友好错误，但数据库条件是最终防线。

### 为什么不能先 SELECT 再 UPDATE

两个事务都可能在对方提交前读到可用 10，然后都通过扣 7。即使应用有 `if`，数据库写入点仍需原子裁决。

### 为什么还保留 RowVersion

条件扣减保护数量不为负；RowVersion 保护单据/其他字段不被旧编辑静默覆盖。它们保护不同不变量，不互相替代。

## 14. 第六步：Controller 保持薄

```csharp
[HttpPost("{id:guid}/post")]
[RequirePermission("wms-outbound", "post")]
public async Task<IActionResult> Post(
    Guid id,
    [FromHeader(Name = "Idempotency-Key")] string key,
    [FromBody] PostOutboundRequest request,
    CancellationToken ct)
{
    var result = await _service.PostAsync(id, key, request.RowVersion, ct);
    return Ok(new { code = 0, message = "OK", data = result });
}
```

Controller 负责 HTTP 适配；业务状态机、事务、扣减和幂等放 Service/领域层。统一异常中间件把业务异常映射为 HTTP 合同，避免每个 Controller 重复 try/catch 且格式漂移。

## 15. 第七步：Vue 页面不是只有一个按钮

页面至少有五种状态：初始、提交中、成功、业务冲突、未知结果。

```ts
const posting = ref(false)
const outcomeUnknown = ref(false)

async function postOrder() {
  if (posting.value) return
  posting.value = true
  outcomeUnknown.value = false

  const key = getOrCreateKeyForThisBusinessIntent()
  try {
    const result = await outboundApi.post(order.value.id, key, {
      rowVersion: order.value.rowVersion
    })
    applyPostedResult(result)
  } catch (error: any) {
    if (error.response?.status === 409) {
      await showConflictAndReload()
    } else if (!error.response) {
      // 网络/超时：不能直接说失败，因为服务端可能已提交。
      outcomeUnknown.value = true
      await queryResultByIdempotencyKey(key)
    } else {
      throw error
    }
  } finally {
    posting.value = false
  }
}
```

### 幂等键的生命周期

同一次用户意图的重试必须复用 key；用户修改内容、明确发起新意图才生成新 key。每点击一次都生成新 key，会让服务端无法识别重复。

### 按钮禁用的真实价值

减少正常用户双击与视觉混乱，但挡不住多标签页、脚本调用、代理重试和超时重发。它是 UX 防线，不是正确性防线。

---

## 16. 第八步：持久化事件发布器

发布器的最小职责：领取未发布事件 → 序列化/发送 → 标记完成；失败记录原因并安排退避。多实例时必须考虑重复领取。

```text
Pending
  → 原子领取 Processing(LeaseOwner, LeaseUntil)
  → PublishAsync
     ├─ 成功 → Published
     └─ 失败 → Failed + Attempts + NextRetryAt
                        └─ 达上限 → DeadLetter + 告警
```

即使有租约，也不能取消消费者幂等。可能发生：broker 已收到，但发布器没收到确认，租约到期后再次发送。

事件 payload 应包含完成消费所需的数据或稳定引用，但不要塞敏感凭证和无限增长对象图。事件 schema 有版本，消费者应容忍未知字段。

## 18. 第十步：可观测性设计

### 18.1 日志事件

```text
OutboundPostStarted
OutboundPostIdempotencyHit
OutboundPostSucceeded
OutboundPostConflict
OutboundPostFailed
IntegrationEventPublishFailed
IntegrationEventDeadLettered
```

字段：traceId、tenantId、outboundId、idempotencyKeyHash（不要原样敏感值）、userId、durationMs、resultCode、eventId。库存数量是否记录要考虑商业敏感与日志访问权限。

### 18.2 指标

- `outbound_post_requests_total{result}`；
- `outbound_post_duration_seconds`；
- `outbound_post_conflicts_total{reason}`；
- `integration_event_queue_depth{type}`；
- `integration_event_oldest_age_seconds{type}`；
- `integration_event_dead_letter_total{type}`。

不要把 outboundId/idempotencyKey 放 label。

### 18.3 trace spans

```text
POST outbound/post
├─ idempotency lookup
├─ load order
├─ deduct stock (每批或聚合，不要无限细)
├─ save transaction
└─ commit

后台另一个 trace：publish event → broker
消费者 trace：consume event → inbox dedupe → update report
```

消息头传播 correlation/trace context，但不要依赖 traceId 做业务幂等；两者职责不同。

若这是新功能，安全顺序：

1. 部署新增表/列/索引，不破坏旧代码；

## 20. 第十二步：故障注入逐题答案

### 20.1 请求到达前断网

服务端无幂等记录。客户端用同 key 重试，正常执行。

### 20.2 DB 提交后、响应前断网

服务端已 Completed。客户端看到未知结果，以同 key 查询/重试，得到原结果；不再次扣减。

### 20.3 扣第二物料失败

整个本地事务回滚：第一物料余额和流水也回滚，单据仍 Draft，事件不存在。返回库存不足明细。

### 20.4 两请求同时过账

幂等唯一键/单据状态/rowversion 共同裁决。相同 key 共享结果；不同 key 争同单据，最多一个完成，另一个 409。

### 20.5 提交后进程崩溃

事件行已随事务提交。重启后发布器扫描并发送；若业务和事件不是同事务，这里会永久丢通知。

### 20.6 broker 不可用

业务已合法提交，事件保持 Failed/Pending，按退避重试；队列年龄/深度告警。是否允许业务继续取决于通知一致性要求，本教程选择允许。

### 20.7 消费成功但 ACK 前崩溃

broker 重投。Inbox/业务唯一约束识别 EventId，第二次不重复更新报表，随后 ACK。

### 20.8 消费永久失败

有限重试后死信；告警与管理界面显示原因；修复数据/代码后授权人员重放。死信不可静默堆积。

### 20.9 跨租户伪造 ID

查询过滤使资源不可见，写 SQL 也含 TenantId；返回 404/团队统一错误。缓存、事件和审计均带租户。负向测试证明目标数据不变。

### 20.10 新旧 schema 共存

迁移只新增兼容结构；旧版忽略新表/可空字段，新版仍能处理旧数据。删除旧列留到所有实例与回滚窗口结束后。

## 21. 15 分钟现场排障剧本

场景：用户点击过账后转圈，最终 504，但稍后发现库存似乎减少。

### 0–2 分钟：确认影响

获取 traceId/单据号/租户/时间；问是单用户还是全站；暂停用户反复点击，保留现场。

### 2–5 分钟：判断结果

按幂等 key/单据 ID 查状态：单据是否 Posted、幂等记录状态、库存流水和事件是否存在。先回答“业务到底成功没”，再处理体验问题。

### 5–9 分钟：定位慢段

网关日志确认 504；trace 看 DB commit 前后时间；检查 SQL 阻塞、连接池、线程池和下游调用。若事务内误调用 broker，这是高概率根因。

### 9–12 分钟：止血

已提交则明确告知用户不要重做，并让页面通过状态查询恢复；未提交可安全同 key 重试。若新版本引入慢调用，关闭 feature flag 或回滚兼容版本。

### 12–15 分钟：验证与沟通

用唯一测试单验证一次；观察延迟/错误率；记录时间线、影响和后续根因动作。不能只说“服务已重启”。

## 23. 面试追问的深度回答

### “如果数据库提交成功，但幂等结果序列化失败呢？”

结果序列化应在提交前完成并作为同一事务记录，或只保存稳定业务标识、重建响应。不能业务已提交后才首次生成一个可能失败且无法恢复的结果。即使响应构建失败，重试也应从单据状态重建一致结果。

### “Processing 幂等记录卡死怎么办？”

记录 owner/开始时间/租约。超过合理窗口后不能盲目重新执行，先查询业务聚合是否已经 Posted：若已完成则修复为 Completed；若未完成且无活跃事务，可重新取得。恢复动作要原子并审计。

### “库存不足和并发冲突都是影响 0 行，怎么区分？”

原子 UPDATE 先保证正确；0 行后再在当前租户读取记录和状态，区分不存在、数量不足或版本变化，提供友好错误。即使诊断查询有新并发，最终结果仍是“本次未扣”，不会破坏正确性。

### “事件 payload 里放整张单据还是 ID？”

放 ID 耦合消费者到生产者数据库/查询 API，且以后读到的是新状态；放完整快照可重放但体积与隐私更高、schema 要演进。常见选择是事件所需的稳定事实快照 + 聚合 ID，不泄露无关字段，并按消费者需求设计。

### “为什么不直接同步更新所有下游？”

同步适合必须同一响应确认的强一致步骤；但会把下游延迟/故障带进主事务。报表/通知可最终一致，所以用持久化事件隔离。选择来自业务一致性要求，而非异步永远更先进。
