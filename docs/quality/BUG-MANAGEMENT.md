# CP6 BUG 管理

CP6 当前由一人开发，BUG 管理只保留能防止遗漏的最小流程。GitHub Issues 是活动 BUG 的唯一真相源；不建立额外看板，不维护多人指派，也不复制一套状态标签。

## 优先级

| 等级 | 何时使用 | 处理顺序 |
| --- | --- | --- |
| P0 | 登录、安全、数据正确性或发布被阻断 | 暂停普通开发，先处理 |
| P1 | 核心功能异常，但存在安全绕行 | 作为下一项任务 |
| P2 | 轻微体验、低频边界或文档问题 | 有空时处理 |

严重度和开发顺序暂不拆成两套字段。需要调整顺序时，直接编辑 Issue 内的优先级并留一条说明。

## 状态

只使用 GitHub 自带的两种状态：

- **Open**：尚未完成，包括待复现、修复中和待验证。
- **Closed**：修复已进入远端 `main`，且完成条件已有证据。

如果仍需 DEV/UAT/PROD 验证，Issue 保持 Open。无需为中间步骤增加标签；进展写在 Issue 评论中。

## 从报告到关闭

1. 使用仓库的 **BUG** Issue 表单登记问题，选择 P0/P1/P2，填写环境、复现步骤、预期/实际结果和完成条件。
2. 从最新 `main` 创建 `codex/bug-<issue编号>-<简短名称>` 分支。一个分支只修一个 Issue。
3. 先确认根因，再提交最小修复。新增回归测试必须在修复前能失败、修复后能通过。
4. PR 填写 Issue 编号、改动和验证结果：
   - 合并前已经完成全部验证，使用 `Closes #<编号>`。
   - 仍需合并后环境验证，使用 `Refs #<编号>`，验证后手工关闭。
5. 只有以下条件全部满足，Issue 才能关闭：
   - 根因已记录；
   - 修复和回归测试已提交，或写明无法自动化的理由；
   - 相关测试、构建或合同门禁通过；
   - 原复现步骤已重新验证；
   - 远端 `main` 已包含修复提交；
   - 需要目标环境验证时，证据已回写 Issue。

## 文档分工

- [GitHub Issues](https://github.com/GTX537/CP6/issues) 保存活动 BUG、根因和验收证据。
- [`07-KnownIssues.md`](../project-memory/07-KnownIssues.md) 只保存跨任务长期风险、技术债和无法立即关闭的环境限制。
- [`06-Todo.md`](../project-memory/06-Todo.md) 只保存路线和优先任务；可以链接 P0 Issue，但不复制 BUG 明细。
- [`CHANGELOG-AI.md`](../project-memory/CHANGELOG-AI.md) 在 BUG 关闭后记录对接手判断有影响的修复结果，不充当 BUG 列表。

## 日常查看

```powershell
gh issue list --label bug --state open
```

没有开放结果，就表示当前没有已登记但未关闭的 BUG；这不代表系统不存在未知缺陷。
