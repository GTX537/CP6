# WP1 database compatibility probe

This executable runs isolated, limited-table SQL Server/PostgreSQL experiments for [DB-COMPAT-01](../../docs/superpowers/specs/2026-10-02-database-compatibility-design.md). It does not install CP6 migrations or prove production acceptance.

Connections are read only from `CP6_TEST_SQLSERVER` / `CP6_TEST_POSTGRES` (or `--connection-env NAME`). The task owner first prepares a dedicated database named `CP6Compat_...` and supplies its 32-hex receipt identity through `CP6_TEST_DATABASE_OWNER`. Before creating a schema, SQL Server must have database extended properties `CP6CompatTask=DB-COMPAT-01-WP1` and `CP6CompatOwner=<receipt identity>`; PostgreSQL's database comment must equal `DB-COMPAT-01-WP1:<receipt identity>`. Missing/malformed owner is rejected before connection; a metadata mismatch is rejected after a read-only check and before DDL. Remote hosts, multiple PostgreSQL hosts and normal business database names are rejected before opening any connection. Each run installs a unique `CP6Compat_...` schema and an ownership marker atomically. Cleanup verifies database and schema identity, drops explicit objects and drops the schema without `CASCADE`. The executable never creates/drops a database, changes authentication, roles/services or calls remote workflows.

Compile only during the repository's shared local build slot:

```powershell
dotnet restore tools/CP6.DatabaseCompatibility.Probe/CP6.DatabaseCompatibility.Probe.csproj
dotnet build tools/CP6.DatabaseCompatibility.Probe/CP6.DatabaseCompatibility.Probe.csproj --no-restore
dotnet run --project tools/CP6.DatabaseCompatibility.Probe --no-build -- --self-test --output tmp/wp1-safety.json --source-sha <SHA>
```

For each database, first run the deliberate failing control. It omits the stale caller's token predicate and proves that the assertion detects a lost update. This is a controlled red fixture, not a claim that production code first failed TDD. Exit code `1`, exactly the named negative-control failure and successful cleanup are expected. Preserve the JSON and terminal output.

```powershell
dotnet run --project tools/CP6.DatabaseCompatibility.Probe --no-build -- --provider SqlServer --negative-control --output tmp/wp1-sql-negative.json --source-sha <SHA>
dotnet run --project tools/CP6.DatabaseCompatibility.Probe --no-build -- --provider SqlServer --output tmp/wp1-sql.json --source-sha <SHA>
dotnet run --project tools/CP6.DatabaseCompatibility.Probe --no-build -- --provider PostgreSql --negative-control --output tmp/wp1-pg-negative.json --source-sha <SHA>
dotnet run --project tools/CP6.DatabaseCompatibility.Probe --no-build -- --provider PostgreSql --output tmp/wp1-pg.json --source-sha <SHA>
```

Also run `--setup-negative-control` to deliberately fail after transactional `CREATE SCHEMA`: expected exit `1`, with cleanup querying the catalog to verify no schema remains. Missing `CP6_TEST_DATABASE_OWNER` and a valid-length mismatched receipt must each fail before any schema attempt. These controlled failures remain separate JSON artifacts.

The positive run must have no `Failed` or `Blocked` results. A demonstrated rejection of the SaveChanges-only application candidate is recorded as `Rejected`, alongside passing assertions that prove the gap. Exit codes: `0` all implemented assertions passed, `1` actual failure, `2` an explicitly blocked item. No connection strings or database exception messages are written to output; errors retain exception type and SQLSTATE/SQL Server error number. Reports preserve `SourceSha` as base HEAD, explicitly label uncommitted input, and record source-file hashes, loaded runtime-assembly hashes, direct NuGet lock versions and an aggregate input fingerprint. Runtime assembly informational version is reported truthfully even if it differs from its NuGet package version.

The probe covers database-generated opaque 8-byte `byte[]` and Base64 readback; EF updates/deletes; Dapper conditional writes and raw no-op/maintenance/trigger writes; ExecuteUpdate with explicit stale predicates; competing lease claims; replay audit and rollback; the application candidate's raw/bulk gaps; tenant/generation/position paging, rollback, tombstones, out-of-order events and actual process restart with exact returned count/order; two representative EF SaveChanges contexts plus Dapper; four actual CP6 Context DatabaseFacades plus Dapper; and actual fixed Platform 0.10.2 enqueue/claim/publish/retry/dead-letter/requeue/Inbox/checkpoint/retention paths. Outbox claim has a bounded interceptor barrier after both actual stores selected the same candidate and before either UPDATE. Checkpoint retry disposition, legitimate applied maximum and exact business effects are asserted. Retention checks before/equal/after cutoffs individually and preserves pending/active-lease/unfinished messages and checkpoints. Replay audit rejects a stale second context. SQL Server nonzero-offset datetimeoffset readback and PostgreSQL nonzero-offset rejection plus explicit UTC normalization are distinct provider contracts.

PostgreSQL tokens use a private noncycling bigint sequence encoded with `pg_catalog.int8send()` by a `BEFORE INSERT OR UPDATE` trigger. Its bytes are opaque; sequence allocation is not a directory commit-order cursor. Directory generation uses a transactional tenant row advanced by a directory trigger. Each page reads the generation and sorted active rows in one short repeatable-read transaction (PostgreSQL) or serializable transaction (SQL Server), and rejects a continuation whose committed generation changed. Tombstones retain aggregate event versions so older events cannot restore a revoked permission. The fixture's numeric `Position` is not the existing identity API: that API's string `Boundary`, opaque `NextCursor` and `LastAggregate` ordering remain intact in later integration. A version discriminator/new protector purpose must reject old rowversion-boundary cursors during generation adoption; a coincidentally equal numeric value must not resume one. Tombstone retention/purge, distributed event transport and complete identity API integration remain later work.

The four actual Context experiment uses the production provider options factory and exact connection/transaction objects. Each DatabaseFacade writes an explicitly named owned probe table; it does not replace the actual models, call full migrations or assert business entity SaveChanges compatibility. Actual package tables are created from its four-entity model and consumer PostgreSQL token override. Source is referenced through the fixed package, never copied from its audited repository.
