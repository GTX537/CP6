# C03 ERP SQL acceptance tests

This suite exercises actual SQL Server transactions and the ERP command handler using the frozen six-event contract bundle. It creates a fresh `CP6C03Test_<guid>` database, applies all `CP6Context` migrations, and drops only the database successfully created by that fixture. Each case uses separate enabled tenants. No InMemory, SQLite, `EnsureCreated`, skipped SQL cases, production database, or existing preview database is used.

Supply `CP6_C03_TEST_SQL` privately as a SQL Server connection string whose server is explicitly `localhost`, `127.0.0.1`, or IPv6 loopback. A named instance or port on that host is supported. The fixture always replaces the database name with `master` before creating its new database; attached database filenames are rejected. The login must have permission to create/drop this isolated database. Never place credentials in this repository, test arguments, logs, or evidence.

Run from the repository root:

```powershell
dotnet test eng/crm/erp-integration-tests/CP6.ErpIntegration.SqlTests.csproj --logger 'trx;LogFileName=c03-erp-sql.trx' --results-directory <private-evidence-directory>
Remove-Item Env:CP6_C03_TEST_SQL
```

Missing or unavailable SQL is a test failure. A successful run applies real migrations and verifies cleanup. Process termination can prevent teardown; any manual recovery must independently verify the exact database name created by that interrupted run. Never wildcard-drop fixture databases.

The suite performs real `BusinessPartnerService.CreateAsync(preRegister: true)`, explicit ERP account/currency profile changes, `QuotationService.CreateAsync`, quotation terms/acceptance operations with freshly read SQL rowversions, and actual `OrderService` creation. Product master inputs are approved ERP records tied to the same customer, quotation and branch `0001`. Only product/master prerequisites and deliberate invalid-master mutations are seeded. Integration results are always generated by `ErpRequestHandler` and read from the persisted Platform Outbox.

Coverage includes:

- BP promotion, master-data failures, frozen/cross-tenant rejection, same-message and business-key idempotency, stale SQL rowversions and immutable CRM account bindings.
- Accepted quotation order/line/provenance/Outbox/Inbox/post-commit bridge consistency, actual foreign currency rates, concurrent duplicate/version requests and stale-version replay.
- Actual production DI registration with an anonymous default-tenant request scope, verifying that foreign currency lookup still uses the event tenant and shared transaction context.
- Missing/nonpositive foreign currency master rates produce stable terminal failures before order numbering. Correcting ERP master data preserves the old request result and requires a new request version to create an order.
- Amount, currency, account/customer and quote-version mismatches; expired/revoked quotes; missing, ambiguous and unapproved product mappings.
- Exact, explicit quotation/product quantity/price units. These ERP fields are free text with no authoritative conversion map. A missing unit, alias/case difference, or mismatch returns terminal `C03_QUOTATION_UNIT_MISMATCH` before order numbering; the accepted amounts are never silently transferred between kg/g or PCS/BOX. Matching units and prices persist exactly on real order lines.
- The destination order-line decimal limit, concurrent Account binding collisions, per-registered-tenant retry fairness, and audited result/bridge delivery replay.
- A fault injected after actual order `SaveChanges` and before result Outbox creation, proving order/detail/document-sequence/bridge rollback followed by same-request retry.
- Conflicting business input, concurrent unrelated CRM and ordinary ERP order numbering, and actual SQL unique-index rejection.
- Exhausted retries, administrative deadletter replay preserving original message bytes/identity, immutable operation audit, duplicate-operation idempotency, and rejected cross-tenant/hash/rowversion/state/conflicting replay requests.

The mixed concurrency case permits at most five re-deliveries of the exact original CRM message after an observed SQL deadlock (`1205`; SQL `3903` can arise during the subsequent rollback). It advances the test clock beyond the configured backoff and still requires all six real orders, all three CRM creation events and bridge rows, and the full expected order-line amount. Ordinary ERP creates are never retried by the test. Unexpected SQL errors and failure to converge fail the case.

Forbidden external-call sentinels ensure the integration command never invokes PowerEgg/WMS/MES while staging its transaction. Ordinary ERP numbering tests explicitly disable their optional WMS/MES bridges. These tests establish local SQL integration evidence; they do not claim Kafka/Dapr transport, CRM UI, production acceptance, or deployment evidence.
