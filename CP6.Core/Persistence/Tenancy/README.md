# Internal tenant connection component

This is the bounded WP02-02 connection and ERP row-security component for `cp6-pg-tenancy-v1`, using the already adopted Platform 0.10.3 context boundary and Npgsql 8.0.8. It is not registered in Program and opens no business route. Existing connection factories, EF models, migrations and database environments are unchanged.

The host configuration Owner supplies an immutable `TenantStorageCatalog`, exact database/principal mappings and a private `ITenantCredentialResolver`. No request tenant, schema, connection string or serialized context evidence is accepted by `OpenCurrentAsync`. Binding queue references are copied; the directory copies all collections and rejects duplicate routes, duplicate configured endpoint tuples (case-normalized server, port, database), and assignments of the same login name to different tenants. DNS/IP aliases that resolve to the same cluster remain the configuration Owner's responsibility. Each tenant has one unambiguous database route in this host snapshot. Model versions must be explicitly registered, the layout must be supported and storage must be Ready.

The future host registration must provide one manager for the process's tenant connection budget, using its real `ITrustedContextAccessorV1`. Pool keys include the host/database/tenant/principal/credential and binding identity through their immutable binding plus catalog generation. Each live, initializing or draining DataSource reserves its full `MaxPoolSize`. Both the pool count and total reserved capacity are bounded. At capacity, the oldest idle pool is disposed first; borrowed pools cause a typed rejection. `ReplaceCatalog` atomically invalidates all old acquisitions and leases, including unchanged entries; configuration owners must include this conservative drain in rotation planning. It never kills an in-flight callback or pretends to revoke already committed effects. Release leases before awaiting manager disposal; disposal waits for their real connections to be returned.

The lease exposes only explicit local transaction callbacks. Both business reads and writes require `InTransactionAsync`; `TenantStorageTransaction.ExecuteAsync` rechecks the current trusted object, binding generation, database, `session_user`, `current_user` and fixed `pg_catalog` search path before invoking host code. `CommitAsync` repeats those checks; commit is explicit, never automatic or retried. Uncommitted transactions roll back on disposal. Nested B scopes cannot use A leases, and a captured object after its scope ends cannot reopen or operate a lease. Context evidence has no expiry field; this component invents no TTL and does not turn earlier evidence into current authorization.

Callbacks are trusted in-process host code, not an arbitrary SQL service. Use explicitly qualified, controlled identifiers. Do not retain or return the raw connection, transaction, commands, readers or session; do not dispatch detached work, switch session identity, or commit the raw transaction. The wrapper cannot sandbox code that deliberately bypasses this contract. Dispose readers before returning. A cancellation or exception around commit can still require Owner reconciliation; never infer that an exception proves rollback or retry the operation automatically.

Connection settings fix pooling/reset, bounded timeouts, `Enlist=false`, multiplexing disabled, no error detail or parameter logging, UTF8/UTC and `pg_catalog`. There is no connection-string or Options input. A harmless explicit whitespace Options value prevents the Npgsql 8 null fallback to ambient PGOPTIONS; the actual search path is independently checked. See [Npgsql 8.0.8 startup source](https://github.com/npgsql/npgsql/blob/v8.0.8/src/Npgsql/Internal/NpgsqlConnector.cs) and [connection settings](https://www.npgsql.org/doc/connection-string-parameters.html). The runtime guard rejects superuser/BYPASSRLS/role-management/replication/database-owner/CREATE/TEMP identities. This is a minimal guard, not a complete role-membership, object ACL or RLS audit. TLS defaults to VerifyFull; a different mode is a private host configuration choice (the owned local fixture uses Disable).

`ErpTenantRowSecurityV1.InstallAsync` is a control-only, explicit first-install overlay after the actual PostgreSQL ERP baseline, inside the caller's transaction. It creates a protected `cp6_tenancy_v1.login_tenant` directory binding login OID **and** name to a nonempty tenant. Its no-argument `current_tenant_id()` helper uses `session_user`, a fixed search path and a minimal NOLOGIN function owner with SELECT only on the directory. Runtime roles receive no mapping access or helper-owner membership. All eight existing ERP tables stay in `erp_integration`, retain every original key/index/column and gain ENABLE/FORCE RLS with explicit SELECT, INSERT, UPDATE and DELETE policies; UPDATE independently guards old and new rows. Six mutable tables receive SELECT/INSERT/UPDATE; two replay audit tables receive SELECT/INSERT only. No table grants runtime DELETE until an Owner retention policy is separately approved. Compatibility functions and the existing token sequence receive named grants only. The installer rejects pre-existing security objects, policies, unexpected grants/ownership and elevated runtime rights, rather than adopting them. It hardens PUBLIC database/schema/function defaults for this isolated layout. It does not install on application startup, commit for its caller, migrate existing data, retry provisioning or claim restart/recovery idempotence. Installation reruns require a separately designed upgrade path.

`TenantStorageTransaction.ExecuteErpAsync` accepts only the supported `erp-integration-v1` model, `erp-integration-tenant-rls-v1` migration marker and registered `erp_integration` queue domain under the existing supported layout. These are trusted host configuration assertions, not evidence of business authorization. It constructs the real `ErpIntegrationContext` on the lease's actual connection and transaction; the context is disposed at the end of the awaited callback and must never be retained or returned. It reuses the three PostgreSQL provider services from `DatabaseContextOptions.ConfigurePostgreSql` without invoking that factory's legacy public-only connection validator. The lease remains at `pg_catalog`, and the provider's known business collation is explicitly qualified to `public`. Every synchronous/asynchronous EF reader/scalar/nonquery command rechecks current scope/catalog binding, connection identity, the same transaction, and the protected helper result against the lease tenant. Runtime contexts have no retry strategy, pooling or dynamic tenant model: this particular model has a single fixed schema. The Owner calls the transaction wrapper's `CommitAsync` after the ERP callback, so tenant-schema writes and ERP writes share the same commit or rollback.

The mapping directory has a database-local advisory transaction lock: the two-int key `(1129330260, 1)` (ASCII `CP6T`, directory version 1), reserved here for this component. The helper acquires its shared form before reading; INSERT/UPDATE/DELETE statement triggers acquire its exclusive form before changing mappings. Thus a checked mapping remains pinned through the runtime transaction, closing the gap between an EF guard query and a later RLS statement under ReadCommitted. The helper is VOLATILE so a lookup that waits for a control writer reads the post-wait snapshot; see PostgreSQL [function snapshots](https://www.postgresql.org/docs/18/xfunc-volatility.html) and [transaction advisory locks](https://www.postgresql.org/docs/18/explicit-locking.html#ADVISORY-LOCKS). Directory TRUNCATE is rejected outright to avoid a table-lock/advisory-lock ordering conflict. The lock covers the whole directory in this bounded version: control mapping changes wait for active ERP transactions; capacity and long-transaction behavior need host adoption work. This fence protects storage identity only. It is not the Owner's current-authorization/revocation fence, and trusted control must not bypass the triggers or reuse this key for unrelated locks.

Exceptions expose a fixed typed failure and, for PostgreSQL rejection, SQLSTATE only. Credential resolver exception text and PostgreSQL DETAIL are not propagated, including PostgreSQL failures wrapped by EF `DbUpdateException`. Local tests are selected with `FullyQualifiedName~CP6.Tests.Persistence.Tenancy`. The real PostgreSQL facts opt in when `CP6_TENANCY_PG_ROOT` or `CP6_TENANCY_PG_BIN` is set; a requested run requires both, a new absolute root named `tenant-connections-*`, installed binaries and unused loopback port 55436. Select the connection or ERP test class separately because each fixture owns that port and requires a new root. The ERP fixture executes the real baseline migration and compatibility prerequisites/triggers, then seeds synthetic A/B model entities; the per-tenant schema table is only an atomicity probe. It checks ownership before stopping its cluster and preserves data/logs. Missing requested resources fail; unrequested integration facts report skipped. No existing instance or database is touched.

The eight-table [ERP inventory](../../../docs/development/evidence/WP02-02/erp-tenant-isolation/OBJECTS.md) bounds this implementation. Still required before business adoption: other contexts' complete object/unique-key inventory, layout/RLS and any dynamic EF model/cache adoption, actual host source verification and current authorization, Owner same-transaction final fence and real atomic business write set, full provisioning/migration/restore, and the 17 full PGT scenarios. These component tests do not mark WP02-02 or business adoption complete.
